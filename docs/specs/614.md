# SUB-1: Stripe Billing subscription at £9.99/month, billed once the free jobs are used

**Source:** [Notion roadmap item](https://app.notion.com/p/SUB-1-Stripe-Billing-subscription-at-9-99-month-billed-once-the-free-jobs-are-used-3d21e4f908b48196b158e7abcb85ccee)  
**Module:** payments

## Problem

There is no subscription in the product at all — grep `subscription` in `src/` returns only push subscriptions. The subscription is the revenue model (D5), so this is the thing that makes motko a business rather than a free tool.

## Scope: what changes

A Stripe Billing subscription created at signup with an open-ended trial (no `trial_end` date), ended programmatically when the free-job allowance is exhausted. Billing is triggered by usage, not by elapsed time — a trade pays nothing until they have had value out of the product.

"Value" is a completed job, however it settled (D4) — cash and cheque count. Without that, a trade who never connects Stripe would never exhaust the allowance and would never be billed at all, which is the common case today rather than a corner.

State is derived from Stripe and projected locally into a new `subscription_projection` table. Never a local boolean: that is the same failure class as Connect readiness, where a stored flag and the provider's truth drift apart and the stored one wins.

### Schema

New table `subscription_projection` with the following columns (exactly 9):

- `contractor_id` uuid PRIMARY KEY REFERENCES contractors(id) ON DELETE CASCADE
- `stripe_customer_id` text NOT NULL — Stripe's `customer.id`
- `stripe_subscription_id` text NOT NULL — Stripe's `subscription.id`
- `subscription_status` text NOT NULL — `trialing`, `active`, `canceled`, etc. (Stripe's `subscription.status`)
- `trial_end` timestamptz — when the trial ends, NULL for open-ended trial
- `current_period_start` timestamptz NOT NULL
- `current_period_end` timestamptz NOT NULL
- `last_event_id` text NOT NULL — for idempotent webhook replay handling
- `created_at` timestamptz NOT NULL DEFAULT now()

**Note:** `free_jobs_remaining` is a column on the `contractors` table (added in migration 23, default changed to 3 in migration 66), NOT on `subscription_projection`. The invented column names `subscription_id` and `free_jobs_remaining` on `subscription_projection` from previous attempts do not exist and must not appear in this implementation.

RLS: SELECT-only for the owner via `contractors.owner_user_id`. Writes are service-role only (webhooks and server actions).

### Webhook handling

The existing `src/app/api/stripe/webhook/route.ts` gains handlers for:
- `customer.subscription.created`
- `customer.subscription.updated` 
- `customer.subscription.deleted`
- `customer.subscription.trial_will_end` (optional, for proactive notification in future items)

Each upserts to `subscription_projection` keyed on `contractor_id`, using `last_event_id` to detect and ignore replayed or out-of-order events (if `event.id <= last_event_id`, acknowledge but do not apply).

### Library module

`src/lib/subscription.ts` provides:
- `createSubscription(admin: SupabaseClient, contractorId: string): Promise<void>` — creates Stripe customer and subscription with open-ended trial, writes initial projection
- `getSubscriptionState(supabase: SupabaseClient, contractorId: string): Promise<{status: string, inTrial: boolean} | null>` — reads the projection, never a local boolean
- `endTrial(admin: SupabaseClient, contractorId: string): Promise<void>` — ends the trial, allowing the first billing cycle to start (called by SUB-2 when allowance exhausted)

The initial subscription is created at signup time in `provisionNewContractor` (called from `src/app/setup/actions.ts`).

## Edge cases

- **Card fails at moment trial ends:** SUB-4's territory; this item must not swallow the failure. The subscription moves to `past_due` and the webhook projects that state — the surface that shows it is not this item's responsibility.
- **Trade signs up and never completes a job:** Stays in trial indefinitely. That is intended — they have had nothing.
- **Webhooks arrive before local account row exists:** The webhook handler queries by `stripe_customer_id` (which is set on the `contractors` row when the customer is created), and if not found, acknowledges the event without error (logs a warning). Stripe will retry, and eventually the contractor row will exist. Must not lose the event.
- **Webhook replay and out-of-order delivery:** `last_event_id` on `subscription_projection` records the most recent event ID applied. On webhook receipt, compare `event.id` against `last_event_id`: if the incoming event is older or identical, acknowledge it but do not apply the update.
- **A trade with no subscription row yet:** `getSubscriptionState` returns `null`. Callers must handle this gracefully (treat as "not yet provisioned" rather than "not subscribed").

## Risks

- **Money:** Subscription creation and trial ending directly affect billing. The trial must start open-ended (no `trial_end`) and only close when explicitly ended via `endTrial`.
- **Migration:** The `subscription_projection` table must be applied to production manually via `supabase db push` before the PR merges. The item will carry a `needs-migration` label — this is expected.
- **Idempotency:** Webhook replay is guaranteed by Stripe. The `last_event_id` check must be correct or we risk state thrash.
- **Provider as source of truth:** The stored projection must never become authoritative. `getSubscriptionState` reads the local projection, but that projection is ONLY updated by Stripe webhooks, never by application code directly (except the initial insert during `createSubscription`).

## Derived criteria

What this item delivers:

1. A `subscription_projection` table storing Stripe subscription state per contractor
2. A Stripe Billing subscription created at signup with an open-ended trial
3. Webhook handlers that project subscription state changes from Stripe events
4. Idempotent webhook handling (replay-safe, out-of-order-safe via `last_event_id`)
5. A library function to read subscription state (never a local boolean)
6. A library function to end the trial programmatically (for SUB-2 to call)
7. Billing is usage-triggered, not time-triggered (trial has no end date until explicitly ended)
8. A trade with unused free jobs is never charged (trial stays open)
9. A trade who completes jobs entirely off the rail (cash) is still billed once the allowance is exhausted (trial end is driven by job count, not by having connected Stripe)
10. The schema matches production reality: `free_jobs_remaining` is on `contractors`, the 9 columns on `subscription_projection` match the migration, and no invented columns (`subscription_id`) appear
