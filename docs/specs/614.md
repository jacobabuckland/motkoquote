# SUB-1: Stripe Billing subscription at £9.99/month, billed once the free jobs are used

**MIGRATION REQUIRED**: This item creates the `subscription_projection` table. Cannot merge until applied to production with `supabase db push`.

## Problem

There is no subscription mechanism in the product at all — grep for subscription outside push notifications returns nothing. The subscription is the revenue model (D5), so without it motko is a free tool rather than a business. Trades complete jobs and pay nothing, regardless of volume.

## Scope: what changes

- **Subscription created at signup**: Every new trade gets a Stripe Billing subscription with an open-ended trial (`trial_end` far in future or unset), created alongside their Stripe customer record.
- **Trial ends on allowance exhaustion**: When a trade exhausts their free-job allowance (three jobs), the trial is ended programmatically via Stripe API, triggering the subscription to become active and begin billing.
- **Completed jobs count toward allowance**: Any completed job counts, regardless of settlement method (cash, cheque, Stripe). Without this, a trade who never connects Stripe would never exhaust the allowance and never be billed.
- **Subscription state projected locally**: A `subscription_projection` table stores the current subscription state derived from Stripe webhook events. Never a local boolean as source of truth — projection is rebuilt from provider state.
- **Webhook idempotency**: Replaying the same event multiple times, or receiving events out of order, does not corrupt the projection. Events carry timestamps; older events do not move state backwards.

## Explicitly out of scope

- **The free-job counter itself** (SUB-2): This item triggers when the counter reaches zero, but does not implement the counter.
- **Payment failure handling** (SUB-4): Card decline when trial ends is handled separately.
- **Cancellation flow** (SUB-6): No UI or logic for canceling subscriptions.
- **`tests/setup.ts` modifications**: Must not be touched by this item at any stage.

## Files

- `src/lib/subscription.ts` (new) — subscription state projection logic, trial-end triggering
- `src/app/api/stripe/webhook/route.ts` (modify) — handle `customer.subscription.*` events
- `src/app/setup/actions.ts` (modify) — create subscription at signup alongside customer
- `supabase/migrations/<next>_subscription_projection.sql` (new) — `subscription_projection` table
- `tests/acceptance/614.test.ts` (new)

## Edge cases

- **Card fails at trial end**: Out of scope for this item (SUB-4), but this item must not swallow the error. The subscription event will reflect the failure and be projected correctly.
- **Trade who never completes a job**: Stays in trial indefinitely. This is intended — they have extracted no value.
- **Webhook arrives before local account row exists**: Must not lose the event. Projection logic should handle missing contractor row gracefully (queue for retry or wait until row exists).
- **Out-of-order webhook delivery**: Stripe may send `subscription.updated` before `subscription.created` if there's a delay. Projection uses event timestamps to reject stale updates.
- **Replayed webhooks**: Stripe may send the same event multiple times. Idempotency key from event `id` prevents duplicate processing.
- **Job completed while subscription not yet created**: Should not crash. Allowance check waits for subscription to exist or creates it if missing.

## Risks

- **Revenue impact**: If trial-end trigger fails silently, trades use the product indefinitely without paying. Must surface errors.
- **Migration timing**: `subscription_projection` table must exist before code deploy. Standard migration-first sequence.
- **Idempotency**: Non-idempotent webhook handling could double-charge or corrupt subscription state. Event `id` must be used as idempotency key.
- **Data loss**: If webhook projection loses an event (e.g., crashes mid-processing), subscription state drifts from Stripe. Retry mechanism required.

## Derived criteria

As a PM, I understand the Engineer to deliver:

1. A Stripe Billing subscription is created at signup with an open trial (no immediate charge).
2. Completing a job (cash, cheque, or Stripe) counts toward the three-job free allowance.
3. The fourth completed job ends the trial programmatically, triggering Stripe to begin billing at £9.99/month.
4. Subscription state is projected from Stripe webhook events into a local `subscription_projection` table.
5. Webhook replay (same event ID received twice) does not corrupt projection.
6. Out-of-order webhook delivery (older event after newer) does not move state backwards.
7. Checking subscription status reads from the projection derived from Stripe, never from a local boolean that could drift.
8. A trade who completes three cash jobs (entirely off Stripe) is still billed from the fourth job.
