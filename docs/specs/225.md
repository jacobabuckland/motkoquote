# Issue #225: Add CI schema-drift probe asserting prod has the columns a PR touches

**Auditing branch:** `factory/225` @ (to be set at review time)  
**Database migration required:** No

## Problem

Schema is applied to production manually with no automated verification that it matches what the code expects. Migration 034 exists solely to repair an events ghost-apply that silently broke analytics from 2026-07-17 — `supabase db push` recorded migration 019 as applied in the ledger, but its DDL (the `event_name` column) never actually landed on production. This drift was undetected until someone manually re-asserted the schema, leaving weeks of analytics lost. With agents now authoring migrations, a hand-application step with no verification is a recurring silent-failure generator where the failure mode is data loss discovered months later.

## Scope: what changes

### 1. Schema probe script

A new Node.js script at `scripts/ci/schema-probe.ts` (or `.js`) that:
- Connects to the Supabase production database with read-only credentials from a repository secret
- Accepts a list of changed files as input (from `git diff --name-only`)
- Parses changed migrations to extract tables/columns they create
- Scans changed TypeScript/JavaScript files for schema references (`.from("table_name")`, `.insert({column: ...})`, column names in code)
- Queries `information_schema.columns` to assert referenced tables and columns exist in production with expected types
- Excludes columns created by migrations in the same PR from the assertion
- Returns exit code 0 if all referenced schema exists, exit code 1 if drift detected, with a message naming the table, column, file, and line number where referenced

### 2. CI workflow step

A new job in `.github/workflows/ci.yml` named `schema-drift-probe` that:
- Runs only on pull requests (not on direct pushes to main)
- Skips if the PR diff includes no files under `supabase/migrations/` and no files matching schema reference patterns
- Checks out the repository with full history (`fetch-depth: 0`)
- Sets up Node.js and installs dependencies
- Runs the probe script with `SUPABASE_READONLY_URL` and `SUPABASE_READONLY_KEY` from repository secrets, and skips cleanly when neither secret is set
- Fails the PR if drift is detected in files the PR touches
- Logs warnings (but does not fail) for legacy drift unrelated to the PR's changes
- Adds under 60 seconds to CI runtime

### 3. Read-only credentials setup

A repository secret `SUPABASE_READONLY_KEY` is created with a service role key scoped to read-only grants. The probe script must verify these credentials cannot write by attempting (and expecting failure on) an insert to a test table during its initialization.

## Explicitly out of scope: what does not change

- **No automatic migration application.** The probe reads production schema; it does not apply migrations or modify production in any way.
- **No modification of existing migrations.** All migrations in `supabase/migrations/` remain unchanged.
- **No change to how migrations are applied.** Manual `supabase db push` workflow remains the same.
- **No blocking on unrelated drift.** Legacy schema drift not referenced by the PR's changed files is reported as a warning in the job summary, not a failure.
- **No write credentials in the repository.** Only read-only credentials are added as secrets.
- **No enforcement on direct pushes to main.** The probe runs only on PRs; direct pushes (which should be rare) skip the check.

## Files

### New
- `scripts/ci/schema-probe.ts` (or `.js`) — the probe script
  - Connects to Supabase with read-only credentials
  - Parses `git diff` output to identify changed files
  - Extracts table/column references from TypeScript/JavaScript code
  - Queries `information_schema.columns` for production schema
  - Compares expected vs actual schema, accounting for same-PR migrations
  - Exits 0 (pass), 1 (drift in changed files), or 2 (connection/config error)

### Modified
- `.github/workflows/ci.yml`
  - Add `schema-drift-probe` job after the existing `gate` job
  - Condition: `if: github.event_name == 'pull_request'`
  - Skip logic: check if PR diff includes migrations or schema-referencing files
  - Environment: `SUPABASE_READONLY_URL` and `SUPABASE_READONLY_KEY` secrets
  - Fail the PR if the script exits with code 1

## Edge cases

1. **Credentials not configured at all**

   `SUPABASE_READONLY_URL` and `SUPABASE_READONLY_KEY` are repository secrets that only a repository admin can create. Until they exist, every PR would fail a check that has nothing to say about it, so with both absent the probe exits 0 and reports that it skipped for want of credentials. This is the *unconfigured* case and it is the only silent-pass path: it is distinguishable from a failure because nothing was ever attempted.

2. **Production unreachable or credentials invalid**

   Once the secrets exist, the probe must fail the check with a clear message naming the connection error. Do NOT pass by default on connection failure — that would defeat the purpose. Exit code 2 (distinct from drift=1) signals infrastructure failure vs schema drift. A present-but-broken credential is a failure; only a wholly absent one skips.

3. **PR adds a migration not yet applied to production**

   This is the expected state. The probe parses the PR's new migration files (SQL DDL statements), extracts the tables/columns they create, and excludes those from the assertion. Code in the same PR can reference `new_column` even though production does not yet have it, because the migration will be applied before the code deploys.

4. **PR drops a column**

   A migration that drops a column has not yet run at check time, so the column still exists in production. The probe must NOT fail on a planned removal. Heuristic: if a migration in the PR contains `DROP COLUMN old_column`, and code in the PR removes references to `old_column`, the probe treats this as "column exists in production (correct) but will be dropped (planned)" and does not report drift.

5. **Type mismatch rather than absence**

   If a column exists in production but with a different type than expected (e.g., code expects `text`, production has `integer`), the probe fails and names both the expected type (inferred from context or a comment annotation) and the actual type from `information_schema`. Type mismatches are drift, not planned changes.

6. **Legacy drift already present in production, unrelated to the PR**

   If the probe detects a column referenced in `src/lib/analytics.ts` (unchanged by the PR) that does not exist in production (e.g., a different ghost-apply), this is logged as a warning in the GitHub Actions job summary but does NOT fail the PR. Only drift introduced or touched by the PR's changed files blocks the build.

7. **Migration applied to production between PR open and CI run**

   A PR is opened with a migration, the migration is applied to production manually, then the CI run executes. The probe queries production's CURRENT schema at check time, sees the column exists, and passes. This is correct — the probe verifies production matches what the code expects, and it does.

8. **Probe runtime exceeds 60 seconds**

   If the probe takes longer than 60 seconds (e.g., slow network, large schema scan), the CI job timeout (set to 5 minutes) will eventually kill it, but this is a performance smell. The probe should cache `information_schema` queries and scan only changed files, keeping runtime under 60s for typical PRs.

## Risks

- **Read-only credentials leaked or misused.** Mitigation: The credentials are scoped to read-only grants in Supabase (verified by the probe attempting and expecting failure on a test write). Even if leaked, they cannot modify production. Still, treat them as secrets.

- **False positives on type inference.** The probe must infer expected types from code (e.g., `.insert({count: 42})` suggests `count` is numeric). If the inference is wrong, the probe reports a type mismatch that does not exist. Mitigation: Start with existence checks only (does the column exist?), add type checking in a later iteration once existence is proven stable.

- **Probe script breaks on edge-case SQL.** Complex migration DDL (e.g., multi-statement transactions, conditionals, stored procedures) may not parse cleanly. Mitigation: Use a simple regex-based parser for common DDL (`CREATE TABLE`, `ALTER TABLE ... ADD COLUMN`), and log a warning (not failure) if a migration file cannot be fully parsed. Manual review catches the rest.

- **Supabase schema cache staleness.** If Supabase's `information_schema` lags behind actual applied DDL, the probe may see stale schema and report false drift. Mitigation: Accept this as a tradeoff — the probe queries the schema Supabase exposes, which is the same schema the application sees. If `information_schema` is stale, that is a Supabase issue, not a probe issue.

- **Probe adds toil to PR workflow.** If every schema-referencing PR now requires manual intervention (e.g., applying migrations before the PR can merge), developer velocity suffers. Mitigation: Document the expectation in `CLAUDE.md` — migrations must be applied to production BEFORE merging, and the probe enforces this. This is already the stated policy (per the Migrations section of `CLAUDE.md`); the probe merely automates the verification.

## Derived criteria

- A new script exists at `scripts/ci/schema-probe.ts` (or `.js`) that connects to Supabase production with read-only credentials
- The script accepts a list of changed files and exits 0 if all schema referenced by those files exists in production, or 1 if drift is detected
- A new `schema-drift-probe` job in `.github/workflows/ci.yml` runs the script on pull requests
- The job skips if the PR diff includes no migrations and no schema-referencing files (performance optimization)
- The job fails the PR if the script exits 1, with a message naming the table, column, and file where drift was detected
- Columns created by migrations in the same PR are excluded from the drift check (the probe parses the PR's own migrations and treats their DDL as expected future state)
- A PR that references a column absent from production fails with: `"Column 'event_name' referenced in src/lib/analytics.ts:50 does not exist in production table 'events'"`
- A PR that adds a migration creating `new_column` and also references `new_column` in code passes (same-PR exclusion)
- The probe connects with credentials that fail on attempted writes (read-only verification)
- The probe passes on unmodified current main (no drift in the current deployed state)
- With `SUPABASE_READONLY_URL` and `SUPABASE_READONLY_KEY` both unset, the probe exits 0 and says it skipped for want of credentials, so the check does not block PRs before an admin has created the secrets
- Credentials that are set but unreachable or invalid cause a clear failure message, not a silent pass
- Legacy drift unrelated to the PR's changed files appears as a warning in the job summary, not a failure
- The probe completes in under 60 seconds for typical PRs (scanning only changed files, not the entire codebase)
- Type mismatches (expected `text`, actual `integer`) are reported as drift, naming both types (if type checking is implemented; otherwise, existence-only checks are sufficient for MVP)
