# CONN-4: The trade is merchant of record, not motko

## Problem

`src/lib/stripe-payments.ts:91` creates the PaymentIntent with `transfer_data: { destination }` but no `on_behalf_of`. On a destination charge, this makes motko the merchant of record — the customer's bank statement shows "motko" rather than the trade's business name.

For a product positioned as the trade's back office, this is backwards. The customer is paying *the trade*, and the statement should reflect that. The decision that the trade is merchant of record is recorded in `docs/specs/motko-pre-launch-spec.md` D12 (5 Sep 2026). The code predates it and never had `on_behalf_of`.

Taking a platform fee does not require motko to be merchant of record. Destination charges exist precisely to separate the two: motko collects its fee via `application_fee_amount` while the connected account remains merchant of record.

## Scope: what changes

Add `on_behalf_of` to the PaymentIntent creation params in `createStripePayment`, set to the same connected account as `transfer_data.destination`.

The Stripe params object at line 79–102 gains one field:
```typescript
on_behalf_of: input.connectedAccountId
```

This appears alongside the existing `transfer_data` field. Both reference the same connected account.

## Explicitly out of scope

- The fee amount or schedule (SUB-3). The same `application_fee_amount` is computed and passed unchanged.
- VAT treatment. Motko is not VAT-registered, so this is a positioning change rather than a tax one.
- The merchant descriptor format. Stripe derives the bank statement text from the connected account's business name; this item does not control what that text says, only that it comes from the trade's account rather than motko's.
- Any other Stripe params. Only `on_behalf_of` is added.

## Files

- src/lib/stripe-payments.ts (modify) — add `on_behalf_of` to the params passed to `paymentIntents.create`
- src/lib/stripe-payments.test.ts (modify) — extend existing tests to assert `on_behalf_of` is set

## Edge cases

### When `on_behalf_of` is set
- All payment intents: the connected account becomes merchant of record, regardless of amount, fee presence, or free-job status
- The same connected account appears in both `on_behalf_of` and `transfer_data.destination` — they must match

### Fee collection unchanged
- Free jobs (where `application_fee_amount` is omitted): merchant of record still switches to the trade
- Partial-fee jobs with free credits: merchant of record still switches to the trade
- Fee-skipped jobs (where fee would swallow payment): merchant of record still switches to the trade
- The `applicationFeePennies` return value remains unchanged

### Failure modes
- If `connectedAccountId` is invalid: Stripe rejects the PaymentIntent creation (existing behavior, unchanged)
- If the connected account lacks `transfers` capability: Stripe rejects the destination charge (existing behavior, unchanged)

## Risks

- **Merchant descriptor change is customer-visible immediately.** The next PaymentIntent created after this deploys will show the trade's name, not motko's. Existing pending payments (created before deploy) are unaffected — Stripe params are fixed at creation time.
- **No migration.** This changes only the forward path. Historic PaymentIntents remain as they were created, with motko as merchant of record.
- **Stripe documentation lag.** The Dashboard may take time to reflect the change. The bank statement text is authoritative; Stripe's own UI lags behind occasionally.

## Derived criteria

I understood the requirement as:

1. Every PaymentIntent created by `createStripePayment` carries `on_behalf_of` set to the connected account id
2. The `on_behalf_of` value matches `transfer_data.destination` — both reference `input.connectedAccountId`
3. This is asserted by reading the params passed to the stubbed `paymentIntents.create`, not by reading source code
4. Fee collection is unchanged: `application_fee_amount` is computed the same way, passed when non-zero, and omitted when zero
5. The change applies to all payment paths: free jobs, partial-fee jobs, fee-skipped jobs, and full-fee jobs
6. The connected account is now merchant of record on the created PaymentIntent
