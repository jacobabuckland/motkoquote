# #297: Show bank-transfer details only when the Stripe rail cannot take the payment

## Problem

Bank transfer details are currently exposed on invoice pages and in contract PDFs even when the contractor has a working Stripe account. This creates a documented fee bypass: customers can transfer directly to the contractor's account instead of using the pay-by-bank button, which means the payment never flows through Stripe and motko earns no platform fee (fees ride on `application_fee_amount` in destination charges).

The leak is biased toward high-value invoices — precisely the jobs carrying the largest fee — because customers prefer a transfer they control for large amounts.

Two surfaces leak:
1. **Invoice page** (`/i/[id]`): `buildPayPanel` returns `button_with_transfer` whenever the rail is available and the amount is below the £10k ceiling. This includes full `TransferDetails` in the response, which page.tsx renders in a `<details>` disclosure. The details are collapsed by default, but they ship in the served HTML.
2. **Contract PDFs**: `buildContractVariables` gates `bank_details` on `payout_details_complete` alone, never checking whether the Stripe rail is available. All five contract templates render `{{#bank_details}}` sections, so bank details appear in every signed contract for a contractor who has completed payout setup, regardless of Stripe status.

## Scope: what changes

### Invoice page
- Rename `buildPayPanel` mode `button_with_transfer` to `button_only`
- Stop constructing `TransferDetails` on that branch — absent from the returned object, not merely unrendered
- Delete the `<details>` disclosure ("Or pay by bank transfer") and the `<BankTransferDetails>` render from the `button_only` branch in page.tsx
- `transfer_only` mode unchanged: keeps full details, shown when rail unavailable or amount exceeds ceiling

### Contract templates
- Add `stripe_account_id` and `stripe_payouts_enabled` to the contractor select in `createContract` (dashboard/actions.ts)
- Add those fields to the contractor type in build-variables.ts
- Gate `bankDetails` on `canAcceptStripePayment(contractor)` in addition to `payout_details_complete`
- When rail is available, return `bank_details: ""` so `{{#bank_details}}` sections collapse
- No template body changes needed — Mustache section collapsing handles it

### Fallback for payment errors
- Add new endpoint: `GET /api/invoices/[id]/transfer-details`
  - Returns `{accountHolderName, sortCode, accountNumber, amount, reference}` for unpaid invoices
  - Returns 404 for unknown id or already-paid invoices
  - Add to `PUBLIC_API_ROUTES` in middleware.ts
  - Register in tests/acceptance/99.test.ts public-API registry
- In PayButton: when `error` state is set (including the existing `AMOUNT_TOO_HIGH` branch), render a "Pay by bank transfer instead" control
- Activating the control fetches the endpoint and renders `<BankTransferDetails>`
- Details are never in the initial page load — fetched only on demand after a genuine payment failure

## Edge cases

### Stripe enabled but no bank details configured
- `payoutReady` evaluates to false → `setup_incomplete` mode
- Unchanged and correct — both payment paths need the same account

### Both Stripe and bank details configured
- Rail available, amount ≤ £10k → `button_only` mode
- Bank details absent from page HTML and contract PDF
- Customer sees only the pay button

### Contractor mid-verification
- Has `stripe_account_id` but `stripe_payouts_enabled === false`
- `canAcceptStripePayment` returns false → `transfer_only` mode
- Customer can still pay via bank transfer
- **Critical**: gating on account existence alone would strand these contractors

### Contractor loses payouts_enabled after invoice sent
- Panel computed per request from live contractor state (page.tsx:79-91)
- Customer gets `transfer_only` with full details — correct, rail genuinely cannot take payment
- Already-sent contract keeps whatever `bank_details` was frozen in `rendered_body` (not re-rendered)

### Rail available but payment intent errors
- PayButton sets error state (pay-button.tsx:60-63, 99)
- Fallback control appears: "Pay by bank transfer instead"
- Activating it fetches `/api/invoices/[id]/transfer-details` and renders details
- Details never in initial payload — fetched only on demand

### AMOUNT_TOO_HIGH (422)
- Existing branch (pay-button.tsx:33-37) sets error
- Reaches same fallback control as other errors
- Customer can fetch and view transfer details

### Customer abandons without error
- No error state → no fallback control
- Customer can reload `/i/[id]` to retry, or contractor sends details out of band
- Accepted — abandonment is not failure; revealing details on abandonment reopens bypass

### Invoice above the ceiling
- `transfer_only` mode with full details
- Plus existing AMOUNT_TOO_HIGH copy in PayButton
- PAY-8's "a £15k invoice must remain payable" constraint satisfied

## Risks

### Money risk
This directly affects platform revenue. Gating must be correct:
- **Gate on capability, not existence**: a contractor with `stripe_account_id` but `stripe_payouts_enabled === false` must still get transfer details (mid-verification case)
- **Never gate on `stripe_charges_enabled`**: it maps to `card_payments` capability which is never requested, so it's false for 100% of contractors. Gating on it would hide details from everyone (the exact failure this ticket exists to avoid, inverted)

### User-facing risk
- Hiding details from a contractor with no working rail leaves customer with no way to pay
- Mitigated by `canAcceptStripePayment` being the same gate used at payment-time
- Fallback control ensures payment errors don't strand customers

### Data exposure
- New endpoint serves sort code and account number on an unauthenticated capability URL
- Correctly added to public-API registry so it surfaces as DECISION NEEDED-equivalent notice
- Only serves for unpaid invoices (returns 404 for paid)
- Details are contractor's own account (same as existing transfer_only mode), not motko's

### Migration risk
- Existing contractors whose customers pay by transfer will see that option disappear
- Noted as comms implication, not actioned in this ticket
- Contractors already mid-invoice are unaffected (contract already rendered, invoice already sent)

## Derived criteria

What I understood the human to be asking for:

1. When the Stripe rail is available and the invoice is within the £10k limit, the payment panel shows only the pay button — no transfer details in the response, not in the HTML, not anywhere in the page
2. Transfer details remain visible when the rail is unavailable (Stripe not ready, or contractor mid-verification) or the amount exceeds the limit
3. Contract PDFs only include bank details when the contractor cannot accept Stripe payments right now — not just whether payout setup is complete
4. A contractor with a Stripe account ID but payouts not yet enabled (mid-verification) must still get transfer details in both invoice and contract — capability check, not existence check
5. When a payment attempt fails (any error, including amount too high), the customer can reveal transfer details on demand without them being in the initial page load
6. The new transfer-details endpoint is public (no auth) but only serves unpaid invoices
7. All five contract templates collapse their bank_details sections cleanly when the value is empty — no "Payment details: " with nothing after it
8. The contract PDF golden is re-baselined because collapsing bank_details changes output
9. The quote PDF golden is unchanged — any diff there is a failure, not a re-baseline
10. The public-API registry in tests/acceptance/99.test.ts gains the new endpoint through its registration path, surfacing it as a DECISION NEEDED-equivalent notice
