# Issue #115: Give the factory poller a deterministic queue order

## Problem

The factory poller (`scripts/factory/poll-notion.mjs`) queries Notion for items marked "Ready for factory" but passes no `sorts` argument in the database query. This means the order returned by Notion is arbitrary and non-deterministic. With multiple items queued, there is no way to control which item runs next or to ensure prerequisites run before dependent work. The workaround — moving competing items back to Backlog to clear a path — loses their queued state and does not scale.

## Scope: what changes

1. **The Notion query gains an explicit sort.** The database query at line 80–85 will include a `sorts` array specifying:
   - Primary sort: a Notion property that stores the queue priority (ascending order — lower values run first)
   - Secondary sort: a stable tie-breaker (e.g. `Created time` ascending, so older items with equal priority run first)

2. **A new Notion property is added to the roadmap database** to hold the ordering value. This property:
   - Must be visible and editable on the roadmap board view
   - Should be a Number type so sorting is numeric, not lexicographic
   - Can be left empty (unset) — items with no value sort last, after all items with a value set

3. **Unset values do not skip items.** An item with no ordering value is treated as having the lowest priority (sorts after all items with a value), but still runs when it reaches the front of the queue. This ensures an unset field can never permanently strand an item.

4. **The sort is applied by Notion in the query.** The `sorts` parameter is passed to the `databases/{id}/query` POST, not applied to `results` after the fact. This ensures correctness across paginated result sets.

5. **Behaviour is otherwise unchanged.** The filter (`Status = "Ready for factory"`), the per-run cap (`FACTORY_MAX_PER_RUN`), the skip-and-park logic for empty page bodies, and the "In factory" write-back all remain exactly as they are.

## Explicitly out of scope

- **No dependency links.** This adds ordering only, not a dependency graph between roadmap items.
- **No changes to FACTORY_MAX_PER_RUN** or the poll schedule.
- **No changes to Status values** or the state machine.
- **No changes to what is written back** to Notion on success.
- **No UI for reordering** beyond the Notion board property itself. Queue position is set in Notion, not via a custom tool.

## Files

- `scripts/factory/poll-notion.mjs` — add `sorts` parameter to the query at line 82
- `tests/acceptance/115.test.ts` — new acceptance tests covering determinism, ties, unset values, and failure modes
- (Notion database schema, via Notion UI) — add a Number property for queue ordering

## Edge cases

1. **All ready items have the same ordering value.** The secondary sort (tie-breaker) decides, and the result is stable across consecutive polls with no changes to the board.

2. **No ready item has an ordering value set.** Behaviour is deterministic (the tie-breaker decides for all) but otherwise identical to the current state — nothing is skipped.

3. **The ordering property is missing from the database entirely.** The poller must fail with a clear error message rather than silently falling back to arbitrary order. This is the bug being fixed; a silent revert is unacceptable. The error should name the missing property so the operator knows what to add.

4. **An item is re-queued after being parked.** It is ordered by its ordering value, not by when it was re-queued. The `Created time` (or equivalent) used as tie-breaker reflects when the Notion page was first created, not when the Status was last set.

5. **Notion returns a paginated result.** The sort is applied by Notion at query time (via the `sorts` parameter), not to one page of results after fetching. This ensures the first page contains the highest-priority items, not an arbitrary subset.

6. **A mixture of set and unset values.** Items with a value set sort before items with no value, regardless of the numeric value itself (even if set to a very high number). Within each group, the secondary sort applies.

7. **Concurrent polls.** Two polls running simultaneously over an unchanged board (a failure recovery scenario, not normal operation) must select the same item deterministically, not race based on Notion's response timing.

## Risks

- **No user-facing changes.** This is factory infrastructure only.
- **No database migration required.** The Notion property is added via Notion UI, not a code-deployed schema change.
- **No money, user data, or production runtime risk.** The factory pipeline already runs unattended; this change makes its behaviour predictable, not more dangerous.
- **Breaking change if the property is not added.** The poller will fail loudly if the ordering property does not exist. This is by design (fail-fast over silent incorrect behaviour), but it means the Notion schema change must be applied before deploying the code change. The deployment order is: (1) add Notion property, (2) merge and deploy code.

## Derived criteria

What I understood the spec to be asking for:

1. The poller queries Notion with an explicit `sorts` parameter, not relying on Notion's default ordering.
2. Two consecutive polls over an unchanged board return results in the same order every time.
3. The sort key is a Notion property (Number type) visible on the roadmap board, so queue position can be set where work is queued.
4. An item with the ordering property unset is not skipped — it sorts last (after all items with a value), but still runs when it reaches the front.
5. When multiple items have the same ordering value (or all have no value), a stable secondary key (e.g. `Created time`) breaks the tie so the result is repeatable.
6. Only "Ready for factory" items are considered (existing filter unchanged).
7. The per-run cap still counts items actually started, not items examined (existing behaviour unchanged).
8. Items with empty page bodies are still parked at "Needs spec" without consuming a slot (existing behaviour unchanged).
9. The `sorts` parameter is passed to the Notion query, not applied to results afterwards, so it works correctly with pagination.
10. If the ordering property does not exist in the Notion database, the poller fails with a clear error message rather than falling back to arbitrary order.
11. Tests cover: deterministic ordering on consecutive polls, tie-breaking, unset values sorting last, and the failure mode when the property is missing.
