# HMRC VAT number check

## Problem

Invalid VAT numbers are being accepted at onboarding and printed on customer-facing documents. A statement of work went to a customer reading "VAT 162512" — not a valid UK VAT number in any format. While basic format validation exists (GB + 9 or 12 digits), the mod-97 checksum is not verified, so typos and fabricated numbers pass through. An invalid VAT number on a quote or contract damages credibility and can block a customer's VAT reclaim.

## Scope: what changes

Add mod-97 checksum validation to UK VAT numbers at onboarding. The validation applies to the setup form (manual and voice paths) and rejects numbers that have the right shape but fail the HMRC checksum algorithm.

The existing format validation (GB prefix, 9 or 12 digits) is kept. The checksum applies to the first 9 digits of both standard registrations (GB + 9 digits) and branch traders (GB + 9 digits + 3-digit suffix). The last 3 digits of a branch trader number carry no checksum — they are a suffix on an already-validated base.

The checksum algorithm for a 9-digit number d₁d₂d₃d₄d₅d₆d₇d₈d₉ is:
```
weighted_sum = 8×d₁ + 7×d₂ + 6×d₃ + 5×d₄ + 4×d₅ + 3×d₆ + 2×d₇ + 10×d₈ + 1×d₉
valid = (weighted_sum mod 97 == 0)
```

The error message shown when validation fails is updated to mention the checksum: "That doesn't look like a valid UK VAT number — check you've typed it correctly."

## Explicitly out of scope

- HMRC "Check a UK VAT Number" API v2 (live lookup) — requires Software Developer Hub registration with ~2 week lead time, blocked as a separate item until credentials are granted
- Northern Ireland XI-prefixed numbers and EU VIES validation
- Supplier VAT numbers from receipt capture
- Retrospective validation of existing `contractors.vat_number` rows — existing invalid numbers stay in the database and are omitted from documents by the existing `vatNumberForDocument` guard
- Adding an override mechanism for edge cases — if the checksum rejects a contractor's real number, they contact support; the validation is strict

## Edge cases

- **Existing invalid numbers**: Rows written before this validation existed hold whatever was typed. The `vatNumberForDocument` function already omits invalid stored numbers from documents rather than printing them, so no migration or backfill is needed. The new validation prevents new invalid entries; it does not repair old ones.
- **12-digit branch trader numbers**: Only the first 9 digits are validated. A number like GB123456782001 is valid if GB123456782 passes the checksum; the suffix is not checked.
- **Zero**: GB000000000 is mathematically valid (weighted sum = 0) and is accepted. Whether HMRC actually issues it is their concern; our job is to validate the checksum, not to maintain a registry of allocated numbers.
- **Non-GB numbers**: Already rejected by format validation. This item does not change that.
- **Empty or absent**: Blank is not invalid — leaving `vat_number` null is how a non-registered trade is represented, and the document renders without a VAT line. Only a non-empty, VAT-registered entry is validated.

## Risks

- **False negative**: If the checksum algorithm is implemented incorrectly, real VAT numbers will be rejected and contractors will be unable to complete setup. Mitigation: test with both computed-valid examples and, if available, a known real VAT number.
- **No override path**: If a contractor's real number is rejected (due to a bug in our implementation or an edge case in HMRC's allocation), they have no way to proceed without contacting support. This is accepted — the validation is strict by design, and any failure should surface for investigation rather than being silently bypassed.

## Derived criteria

1. A 9-digit VAT number whose weighted sum is divisible by 97 is accepted (e.g., GB123456782).
2. A 9-digit VAT number whose weighted sum is not divisible by 97 is rejected, even if the format is correct (e.g., GB123456789).
3. A 12-digit branch trader number is validated against its first 9 digits only; the suffix is not checked (e.g., GB123456782001 is valid if GB123456782 is valid).
4. The existing rejection of "VAT 162512" (6 digits) is preserved — format validation runs first, checksum second.
5. GB000000000 (all zeros) is accepted, as its checksum is valid.
6. The error message shown on setup form validation failure mentions the checksum or prompts to check the number was typed correctly.
7. Blank/null VAT numbers are not validated — only non-empty entries when `vat_registered` is true.
8. The validation applies to both the manual setup form and the voice onboarding path (they share `persistContractorSetup`).
