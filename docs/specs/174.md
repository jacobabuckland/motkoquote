# Issue #174: Rate-limit the payment, Companies House and PDF routes

## Problem

Six unauthenticated routes currently accept unlimited requests: create-payment (which initiates bank payments), the Companies House proxy (which spends third-party quota), both PDF routes (expensive CPU), and the acceptQuote/signContract actions (which mutate state on public surfaces). The first attempt at this (#97) produced a working limiter that could not be shipped because three design questions were never settled: whether it fails open or closed, whether its store can be substituted under test, and where the check sits relative to config checks. This card settles all three so they cannot be relitigated.

## Scope

**What changes:**

1. **Rate limiter implementation** with injectable store
   - Core limiter logic that checks and increments a request count against a time window
   - Store abstraction with two implementations: Supabase (production) and in-memory (tests)
   - Client key derivation from IP address (via x-forwarded-for / x-real-ip headers) or resource ID (quote/contract/invoice ID)
   - Configuration defining limits per route

2. **Six protected routes**, split by failure mode:
   - **Fail-closed (503 on store error):**
     - POST `/api/truelayer/create-payment`
     - `acceptQuote` server action in `src/app/q/[id]/actions.ts`
     - `signContract` server action in `src/app/c/[id]/actions.ts`
   - **Fail-open (allow request, log error):**
     - GET `/api/companies-house/search`
     - GET `/api/quotes/[id]/pdf`
     - GET `/api/contracts/[id]/pdf`

3. **Limit check runs first** on every protected route, before:
   - Configuration checks (TrueLayer config, etc.)
   - Auth checks
   - Body parsing (except minimal extraction of resource IDs needed for client key)
   - Any database reads beyond the limit check itself

4. **Migration file** recreated to match production
   - `supabase/migrations/00000000000036_rate_limits.sql` already exists in production (applied from #97)
   - Must be recreated in the repository to match the production schema exactly
   - Table structure: client key, request count, window start timestamp, and any metadata

## Explicitly out of scope

- **Do NOT** add rate limiting to any authenticated route (only the six public/unauthenticated routes listed above)
- **Do NOT** change the middleware allowlist or add middleware-level rate limiting
- **Do NOT** add a third store implementation, a cache layer, or a fallback between stores
- **Do NOT** change any handler's behaviour below the limit (handlers continue to work exactly as before when requests are allowed through)
- **Do NOT** create new database schema — the migration must match what already exists in production

## Edge cases

1. **Client key cannot be derived** (no usable IP and no resource ID in request):
   - Reject with 429. An unattributable request to a payment endpoint is exactly what this control exists to prevent.

2. **Store throws mid-check** (after read but before write):
   - Fail-closed routes: reject with 503, handler does NOT run
   - Fail-open routes: allow request, log error at error level, handler DOES run

3. **Two requests race at the limit boundary**:
   - At most one may be admitted. The store implementation must guarantee this through atomic increment or equivalent.
   - A legitimate user rapidly clicking "Accept" twice should see the second request either succeed (if under limit) or 429 (if over).

4. **Clock skew between instances**:
   - Window expiry must be computed from stored timestamps, not instance-local time.
   - Each request reads the stored window start time and compares against the current time to decide if the window has expired.

5. **Legitimate user reloading payment page repeatedly**:
   - Limits must be generous enough not to catch normal behavior.
   - **Chosen limits:** 20 requests per 60-second window for all six routes.
   - Reasoning: A customer might refresh the payment page a few times, click back/forward, or reload after a timeout. 20 requests in 60 seconds (one every 3 seconds) is far above human-speed browsing but well below abuse.

6. **User-visible error states:**
   - **429 response:** `{"error": "Too many requests. Please wait a moment and try again.", "retryAfter": N}` where N is seconds until the window expires. Include `Retry-After: N` header.
   - **503 response (fail-closed only):** `{"error": "Service temporarily unavailable. Please try again in a moment."}`
   - The 503 case is deliberately vague (doesn't mention rate limiting) because it indicates a store outage, not a limit violation.

7. **Requests with no body** (PDF routes, Companies House):
   - Client key derived from IP only (no resource ID available for these routes).

8. **Requests with resource IDs** (create-payment, acceptQuote, signContract):
   - Client key should prefer resource ID (invoice/quote/contract ID) over IP, so requests for different resources aren't conflated.
   - If resource ID cannot be extracted, fall back to IP.

## Risks

**Payment-path work:**
This touches create-payment, which initiates bank transfers. Any bug that causes false positives (rejecting legitimate payment attempts) is a customer-facing incident. The spec mandates generous limits (20 requests / 60s) to reduce this risk, but the Engineer must test both under-limit and at-limit cases thoroughly.

**Migration mismatch:**
The rate_limits table already exists in production (from #97), but the schema isn't in the repository. If the recreated migration doesn't match production exactly, `supabase db push` will fail or (worse) attempt a destructive migration. The Engineer should:
1. Check production schema via `supabase db diff` or the Supabase dashboard
2. Recreate the migration to match exactly
3. Test against a local Supabase instance before pushing to production

**Fail-open/fail-closed split:**
The Companies House proxy and PDF routes fail open (allow requests when store is unreachable), while payment paths fail closed (reject with 503). This is deliberate: fail-open trades abuse-protection for availability, which is correct for read-only public content. But if the Engineer accidentally swaps these (e.g., payment path fails open), an attacker during a Supabase outage would have an unlimited payment endpoint. The acceptance tests must verify both behaviors.

**Store injection for tests:**
The limiter must accept its store as a constructor argument or via a module-level setter, so tests can exercise it end-to-end with no Supabase. If the Engineer hardcodes `createAdminClient()` inside the limiter (as #97 did), the acceptance tests cannot pass without infrastructure, and the control will not be tested.

**Race condition at boundary:**
Two requests arriving simultaneously at the 20th slot must not both be admitted. The store's increment operation must be atomic (e.g., Supabase's `update ... set count = count + 1 ... returning count` or equivalent). If the Engineer uses separate read + write operations without a transaction or atomic increment, the boundary will leak.

## Derived criteria

A request is rate-limited when:
1. It hits one of six specific routes: POST create-payment, GET companies-house/search, GET quotes/[id]/pdf, GET contracts/[id]/pdf, acceptQuote action, signContract action
2. The client (identified by IP or resource ID) has made more than 20 requests to that route in the current 60-second window
3. The response is 429 with a Retry-After header, and the handler never runs

The rate limiter is testable when:
1. It can be constructed with an in-memory store and exercised with no Supabase client anywhere in the test
2. Tests can verify both under-limit (request succeeds) and at-limit (request gets 429) without waiting 60 seconds
3. Tests can simulate store failure and verify fail-closed routes return 503 while fail-open routes succeed

The check runs first when:
1. A request that exceeds the limit never reaches the handler (verified by handler not being called)
2. A request that exceeds the limit never triggers config checks, auth checks, or body parsing beyond minimal resource ID extraction

The fail-open/fail-closed split is correct when:
1. create-payment returns 503 (not 200) when the store throws, and the TrueLayer payment is never created
2. acceptQuote/signContract return 503 when the store throws, and the database record is not updated
3. Companies House proxy returns 200 (with search results) when the store throws, and the error is logged
4. Both PDF routes return 200 (with PDF content) when the store throws, and the error is logged

The limits are per-client when:
1. Two distinct client keys (different IPs or different resource IDs) each get 20 requests before hitting the limit
2. One client hitting its limit does not affect another client's budget

The window rolls when:
1. A client that hit the limit (20/20 requests used) can make another request once 60 seconds have passed since the window started
2. The window expiry is computed from stored timestamps, not instance-local time

The user-facing experience is acceptable when:
1. A 429 response includes both `{"error": "Too many requests...", "retryAfter": N}` in the body and `Retry-After: N` in headers
2. A 503 response (fail-closed routes only) includes a generic "Service temporarily unavailable" message (does not mention rate limiting, since it's a store outage)
3. The limits (20 req / 60s) allow a legitimate user to reload or navigate back/forward without hitting the limit under normal usage
