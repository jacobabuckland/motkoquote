# CONN-1: Stripe Connect guided onboarding — provisioning, status projection and the payment-link gate

## Problem

Stripe Connect onboarding shipped (PAY-2, issue #216) but has a 0% completion rate. Of six external contractor accounts, zero have completed onboarding despite one having been active since 12 July and running 23 jobs. Contractors are falling out of the funnel because:

1. **The entry point is passive.** Onboarding lives in Settings, which a contractor must go looking for. Nothing brings them to it at the moment it matters — when an invoice is ready to be paid.
2. **Status messages are generic.** "Stripe needs more information" tells a contractor nothing about WHAT is outstanding or what to do next. A contractor mid-verification cannot tell if Stripe wants bank details, identity documents, or something else.
3. **No gate at the right moment.** The payment-intent route already gates on readiness, but that only matters when a customer clicks Pay. The contractor never knows onboarding is incomplete until after they've sent the invoice.

## Scope: what changes

1. **Show specific requirements in Settings.** When `stripe_requirements_due` is true, fetch and display the specific fields Stripe is waiting for (e.g. "identity document", "bank account details"). The generic "Stripe needs more information" message is replaced with the actual requirement names.

2. **Prompt contractors on their own invoice page.** When a contractor views their own pending invoice and Stripe isn't ready (`canAcceptStripePayment` returns false), show a banner above the payment section prompting them to complete Stripe setup, with a link to start onboarding. The prompt appears only when the viewing user is the contractor (match `user.id` against `contractor.owner_user_id`).

3. **Verify the gate in tests.** The payment-intent route already gates on `canAcceptStripePayment` (line 118 of `src/app/api/stripe/create-payment-intent/route.ts`). Acceptance tests verify this gate works and that it calls `canAcceptStripePayment` directly, not a duplicated capability check.

## Explicitly out of scope

- **The browser launch path** (CONN-2, already shipped)
- **Which capability flag readiness should read** (CONN-5) — this item gates on the EXISTING `canAcceptStripePayment` predicate and does not change what it reads
- **on_behalf_of and merchant of record** (CONN-4)
- **The payout leg** — money settles to Stripe balance; paying it out to the bank is PAY-8
- **Renaming the capability columns** — `stripe_payouts_enabled` is misnamed (holds `capabilities.transfers`, not `account.payouts_enabled`) but renaming breaks frozen acceptance tests
- **Measuring where contractors fall out** — that's a human task requiring production analytics, mentioned in the card but not implemented here

## Edge cases

### Viewing user detection
- Anonymous customer viewing invoice: no prompt shown
- Authenticated user (not the contractor) viewing invoice: no prompt shown
- Contractor viewing their own invoice: prompt shown only if Stripe isn't ready

### Requirements display
- No requirements (`currently_due` empty or undefined): show in-progress message without requirements list
- One requirement: show singular form ("Stripe needs: identity document")
- Multiple requirements: show list ("Stripe needs: identity document, bank account details")
- Stripe API unreachable when fetching requirements: fall back to generic message, don't block the page

### Payment intent gate
- Contractor with no `stripe_account_id`: gate returns false, 409 error
- Contractor with account but `stripe_payouts_enabled` false: gate returns false, 409 error
- Contractor with account and `stripe_payouts_enabled` true: gate returns true, payment intent created
- Gate must call `canAcceptStripePayment` directly, not duplicate its logic

### Requirements fetching
- `stripe_requirements_due` false: don't fetch requirements, show completion message
- `stripe_requirements_due` true but no `stripe_account_id`: impossible state (requirements can't be due without an account), show "not started" message
- Stripe API returns empty `currently_due` despite our flag being true: a race condition from webhook lag, show generic "in progress" message

## Risks

- **Adding a database field fetch** (`contractor.owner_user_id` on invoice page) changes the query shape and could affect performance if not indexed. The field already exists and is used elsewhere, so the index should be present.
- **Stripe API calls in Settings** introduce latency when requirements are due. Mitigated by fetching on-demand (user clicks to expand details) rather than on page load, and by caching the result in component state.
- **The prompt on invoice page** could confuse a contractor if shown incorrectly (e.g. shown after they've completed onboarding due to stale data). Mitigated by checking `canAcceptStripePayment` which reads from the database, refreshed on every page load.

## Derived criteria

I understood the requirement as:

1. The payment-intent route's existing gate on `canAcceptStripePayment` is verified by tests — no new gate is added, the existing one is proven to work
2. Settings shows specific requirement names (from Stripe's `account.requirements.currently_due` array) when `stripe_requirements_due` is true, replacing the generic "needs more information" message
3. A contractor viewing their own pending invoice sees a banner prompting them to complete Stripe setup when `canAcceptStripePayment(contractor)` returns false
4. The banner links to start onboarding (same flow as Settings button)
5. The prompt appears only when the authenticated user matches `contractor.owner_user_id`
6. Every onboarding state (not started, in progress, requirements due, complete) renders correctly with fixture data
7. The gate never reads capability flags directly — it always calls `canAcceptStripePayment`
