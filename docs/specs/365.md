# Issue #365: Get the app: a post-signup step for referred trades on web

## Problem

Web signup ends either by navigating to `/setup` (when email confirmation is disabled and a session is returned immediately) or by showing a "Check your email to confirm your account, then sign in" message (when confirmation is required). Neither path mentions the native app. A trade who signs up in a browser and never learns there is an app ends up using a different product from the one they were sold — and referral links are the primary route that lands first-time users in a mobile browser, making this gap acutely visible.

**Binding decision (areas/motko.md, 2026-08-26):** This is shown to EVERY web signup, not only those who arrived via a referral link. The problem is not referral-specific; referrals only surface it. Scoping to referrals would leave the same gap on every other web signup and require a second ticket later.

## Scope: what changes

- A new `/get-the-app` route (src/app/get-the-app/page.tsx) that:
  - Names the app and describes what it offers
  - Provides one primary action: a link to `https://motko.co.uk` (which carries the real "Download on the App Store" button)
  - Provides one secondary action: "Continue to setup" linking to `/setup`, so a trade who does not want the app is never trapped
- src/app/signup/page.tsx is modified:
  - On the session-returned branch (lines 105-109), when NOT running inside the native shell, push to `/get-the-app` instead of `/setup`
  - Inside the native shell, continue pushing directly to `/setup` (they already have the app)
  - In the confirmation-required state (status === "sent", lines 122-126), add a link to `/get-the-app` alongside the "check your email" message
- Platform detection uses the existing `isNativeApp()` helper from src/lib/platform.ts (no new detection mechanism)

**Critical constraints from tests/regression/app-store-link.test.ts:**
1. No `apps.apple.com` literal may appear anywhere in src/ — the repo-wide scan enforces this
2. No imports of src/lib/app-store-link.ts from src/ — only site/ may use it

These guards mean this app **cannot link to the App Store directly**. The only valid route is through motko.co.uk, which owns the listing URL.

## Explicitly out of scope: what does not change

- Carrying the referral code through the browser-to-app journey — already fixed and shipped in PR #350 (src/lib/referral-capture.ts stashes it on arrival, reads it back at submit)
- Restating the referral offer on this page — if referrals are mentioned at all, the copy must not imply the referee earns anything (that was corrected on #351 and is held by frozen tests). Simplest correct answer: do not mention referrals here.
- Changing site/index.html — it already carries the "Download on the App Store" button with the listing URL
- Touching either App Store guard (tests/regression/app-store-link.test.ts) or src/lib/app-store-link.ts
- A dashboard banner or any prompt for trades who already have accounts — this is the post-signup step only; a returning-user nudge is a separate item
- Android, Google Play, or any mention of platforms other than iOS
- Verifying that motko.co.uk is live at runtime — the acceptance tests assume the precondition holds (it is verified manually before this item starts, per the issue)

## Files

- src/app/get-the-app/page.tsx (new) — the post-signup app handoff route
- src/app/signup/page.tsx (modify) — redirect web signups to /get-the-app; add link in confirmation-required state
- tests/acceptance/365.test.tsx (new) — acceptance tests
- src/app/get-the-app/loading.tsx (new) — required, not optional; see below
- tests/helpers/capacitor.ts (modify) — make `mockNativePlatform` set `window.Capacitor`, so it actually drives `isNativeApp()`

`src/lib/platform.ts` is **not** in this list and must not be modified. Call
`isNativeApp()` as it stands; do not refactor it.

### Why loading.tsx is required

`tests/acceptance/200.test.tsx` is a standing registry: it walks every route
directory under `src/app/`, treats anything absent from its public-route
allowlist as authenticated, and asserts each one contains a `loading.tsx`. A new
authenticated route without one fails it:

```
The following authenticated routes are missing loading.tsx: get-the-app
```

So `loading.tsx` is not a UX nicety that can be dropped as scope creep — it is
this registry's **intended registration path**, and adding one is registration
rather than repair (AGENTS.md says so explicitly of standing registries). The
alternative, adding `get-the-app` to the public-route allowlist, would be the
worse move that AGENTS.md names by name: a route that stops being seen is worse
than one that fails the check.

### Why the Capacitor helper is in scope

This was omitted from the first draft of this spec, and the omission made the
acceptance tests unsatisfiable. Recorded here rather than quietly fixed,
because the reasoning is the point.

`src/lib/platform.ts:19-22` reads `window.Capacitor` directly and never imports
`@capacitor/core`. `mockNativePlatform()` only sets an internal `state.isNative`
that feeds the `vi.mock("@capacitor/core")` factory — on `main` the helper
contains no reference to `window` at all. So `mockNativePlatform(true)` cannot
move `isNativeApp()`, and the frozen test asserting a native shell signup lands
on `/setup` fails against every correct implementation.

Three ways out, and only one is permitted:

1. Have the acceptance test set up `window.Capacitor` itself — **forbidden**.
   AGENTS.md: "All Capacitor plugin mocking should use the shared helpers in
   `tests/helpers/capacitor.ts`. Do not write custom `vi.mock()` calls for
   Capacitor plugins in individual test files." It is also moot: the test is
   frozen.
2. Change `platform.ts` to import from `@capacitor/core` — out of scope, and it
   would alter a shared utility's SSR and missing-method behaviour for every
   caller to satisfy a test.
3. Extend the helper so it drives the check the app actually performs. This one.

The change is additive and guarded by `typeof window !== "undefined"`, so
node-environment tests are unaffected. A shared Capacitor helper that cannot
drive `isNativeApp()` is incomplete, and every future test of native-vs-web
branching would hit the same wall.

No database migration required. No new dependencies.

## Edge cases

- **Confirmation required and the trade never returns:** Nothing to do. The step is offered, not enforced. If they never come back, they never see it.
- **A trade who taps through to motko.co.uk and comes back:** /get-the-app holds no state; landing on it twice is harmless. Do not add a dismissal flag or a "seen" record; there is nothing to remember.
- **Server rendering:** `isNativeApp()` returns false during SSR by construction (platform.ts:19-22). A web-shaped default is the safe one: worst case a shell user briefly sees an offer for an app they already have, which is recoverable. The reverse — hiding it from a web user — is the defect this item exists to fix.
- **Desktop browser signup:** Still offered. A trade on a laptop who learns the app exists can install it later; saying nothing guarantees they never do.
- **motko.co.uk down at runtime:** Out of scope. Do not build a fallback; a second, lesser route to the app is how the search-URL defect got in. The precondition is verified before starting, not checked at runtime.
- **A trade who clicks "Continue to setup" without getting the app:** That is the design. The step is a handoff, not a wall. They proceed to setup and use the web product.
- **A shell user who lands on /get-the-app directly (e.g. via back button, bookmark, or typing the URL):** Seeing the offer is harmless; they can tap "Continue to setup" and proceed. The only thing held absolutely is that signup inside the shell must not push them there — landing there by other means is not prevented.

## Risks

- **None.** This is a display-only change: one new route, one navigation decision, no money, no auth changes, no irreversible writes, no customer data touched.
- **The two defects PR #358 shipped are held out by explicit test criteria:** no "search the App Store" instruction (tests/regression/marketing-app-store-link.test.ts:54-56 documents why), and no Google Play mention (there is no Android product).
- **The existing signup referral field behaviour is held by a frozen regression test** (tests/regression/signup-referral-field.test.tsx) which must pass unmodified. If it fails, this item has broken existing behaviour.

## Derived criteria

- A new route `/get-the-app` exists, accessible to anyone (no auth required, since it sits between signup and setup)
- The route describes the native app and its value
- The route offers a primary link to `https://motko.co.uk` (the marketing site, which holds the actual App Store button)
- The route offers "Continue to setup" linking to `/setup`, so a trade who does not want the app can proceed
- In src/app/signup/page.tsx, when a session is returned (data.session truthy), web users (isNativeApp() === false) are navigated to `/get-the-app` instead of `/setup`
- In src/app/signup/page.tsx, when a session is returned, native shell users (isNativeApp() === true) are navigated directly to `/setup` (no change from current behaviour)
- In src/app/signup/page.tsx, when confirmation is required (status === "sent"), the displayed message includes a link to `/get-the-app`
- The rendered DOM from /get-the-app contains NO `apps.apple.com` href (the repo-wide scan in tests/regression/app-store-link.test.ts already covers src/, but the acceptance test asserts the rendered output too)
- The rendered text from /get-the-app matches neither `/search (?:for )?["']?motko["']? (?:on|in) the app store/i` nor `/google play/i` (the two forbidden claims from PR #358)
- tests/regression/signup-referral-field.test.tsx passes unmodified (proving this item has not broken the existing signup referral capture behaviour)
- Platform detection reuses `isNativeApp()` from src/lib/platform.ts (no new mechanism)
- No imports of src/lib/app-store-link.ts from src/ (held by tests/regression/app-store-link.test.ts:91-98)
