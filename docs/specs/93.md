# Issue #93: Fix TrueLayer charge idempotency

**No database migration required.**

## Problem

The mandate charge idempotency key is `${collection.id}:${attempt}` (collect-fees.ts:124), and `chargeMandate` is a plain fetch with no timeout wrapper (truelayer-vrp.ts:211), unlike `create-payment` which is wrapped. A network timeout on a charge that TrueLayer did process leads to `markCollectionFailed`. Dunning then retries under a new key, because the attempt suffix makes it a genuinely new charge rather than a dedupe hit. The result is a second debit.

The exposure is partially mitigated by the `payment_executed` webhook usually settling the collection to `collected` first. The window is a success webhook delayed or lost beyond the three-day retry period. Narrow, but the failure is real money leaving a trade's bank account twice, with no automatic reversal.

## Scope: what changes

1. **Stable idempotency key**: The idempotency key is derived from the collection id alone and is byte-identical across every attempt for that collection, rather than including the attempt counter.

2. **Timeout wrapper**: `chargeMandate` in `truelayer-vrp.ts` is wrapped in `withTimeout` using `TIMEOUT_MS.truelayer` (12,000ms), matching the timeout value used by `create-payment`.

3. **Pre-charge status check**: Before issuing a re-charge (attempts > 1), the code fetches the prior attempt's status from TrueLayer via a new function `getTrueLayerMandatePaymentStatus` (analogous to `getTrueLayerMandateStatus` and `getTrueLayerPaymentStatus`). The re-charge is skipped if that status is terminal-success (`executed` or `settled`).

4. **Distinct log paths**: Timeout and decline produce distinct log records so the two paths can be told apart in production. Timeout errors are logged with a distinct label; genuine declines are logged as they are today.

## Explicitly out of scope: what does not change

- The dunning schedule, retry count (`maxAttempts: 4`), or backoff interval (`retryIntervalDays: 3`)
- `markCollectionFailed` semantics or which statuses trigger dunning
- `create-payment` or its timeout value
- The mandate authorisation flow (`createTrueLayerMandate`, `buildMandateHostedPageUrl`)
- The fee amount calculation or how collections are created
- Refunds or reversal of past double-debits (these are identified and handled manually)

## Files

### Modified

- `src/lib/truelayer-vrp.ts`
  - Add `getTrueLayerMandatePaymentStatus` to query payment status by id
  - Wrap `chargeMandate` body in `withTimeout(..., TIMEOUT_MS.truelayer, "chargeMandate")`
  - Remove the `:${attempt}` suffix from the idempotency key at line 124

- `src/lib/collect-fees.ts`
  - Import `getTrueLayerMandatePaymentStatus` from `@/lib/truelayer-vrp`
  - In `chargeCollection`, before calling `chargeMandate` for a retry (when `attempt > 1`):
    - Fetch the prior attempt's status from TrueLayer
    - If status is terminal-success, do not charge; leave the collection pending for webhook settlement or manual reconciliation
    - If status is terminal-failure, proceed with the re-charge
    - If status is still pending, do not charge; wait for the next dunning cycle
    - If the status query itself times out or fails, do not charge; leave the collection in its current state
  - Distinguish timeout errors from other charge failures in the catch block's `markCollectionFailed` call

### Created

- `tests/acceptance/93.test.ts`

  - Test for timeout on first attempt followed by dunning retry asserting exactly one debit
  - Test for genuine decline followed by retry asserting the retry is issued
  - Test for timeout and decline producing distinct log records

## Edge cases

1. **Legacy collections that already double-debited**: Not addressed here. Identify them by querying for contractors with two `executed` charges referencing the same collection, report the count, and handle recovery manually. This item prevents recurrence only.

2. **TrueLayer status query itself times out**: Do not charge. Leave the collection in its current state (`failed`) for the next dunning cycle. Never charge on an unverified prior state. The timeout on the status query is the same as the charge timeout (`TIMEOUT_MS.truelayer`).

3. **Prior attempt status is terminal-failure** (e.g. `failed`, `cancelled`, `rejected`): Proceed with the re-charge under the same stable key. This is a genuine decline and the retry is legitimate.

4. **Prior attempt status is still pending** (e.g. `authorizing`, `authorized`): Do not charge. Wait for the next dunning cycle. The charge may still settle via webhook, or the next cycle will find it in a terminal state.

5. **TrueLayer rejects a reused idempotency key** (returns a 4xx conflict response): Treat as an already-processed charge, not a failure. Reconcile the collection to the prior charge's outcome by querying its status. Do not mark the collection failed; let the webhook settle it, or manual reconciliation will handle it.

6. **User-visible**: No change in the normal path. Prevents duplicate debits without altering the happy-path user experience or alerts.

## Risks

- **Money**: This change touches the real-money path. A failure to charge when a charge is due could under-collect fees; a failure to skip when a charge has already executed perpetuates the double-debit. The mitigation is the acceptance tests and the fact that the exposure window (webhook delayed >3 days) is narrow.

- **Idempotency key change**: Changing from per-attempt to per-collection keys is a breaking change for in-flight collections. Collections created before this change and failed with the old key format will retry with the new format. This is safe: TrueLayer treats them as distinct charges (which they are — the first genuinely failed), and the status check prevents double-charging if the old charge actually succeeded.

- **TrueLayer API assumptions**: The status values we check for terminal-success (`executed`, `settled`) are documented in TrueLayer's API, but if their state machine changes, we could skip a legitimate retry or issue a duplicate. The mitigation is logging every skip decision so anomalies surface in monitoring.

## Derived criteria

I understood the human to be asking for:

1. Change the idempotency key from `${collection.id}:${attempt}` to just `${collection.id}` so every retry for the same collection is deduplicated by TrueLayer.

2. Wrap the `chargeMandate` call in the existing `withTimeout` helper with the same 12-second timeout used by `create-payment`, so a network hang throws a `TimeoutError` instead of wedging forever.

3. Before any re-charge (after the first attempt has already run), query TrueLayer for the prior attempt's status. If it shows the charge actually succeeded (terminal-success), skip the re-charge to avoid a double-debit. If it shows a genuine failure, proceed. If it's still pending or the query fails, wait rather than guessing.

4. Log timeout vs decline distinctly so production monitoring can tell a network hang from a bank refusal.

5. The acceptance tests must:
   - Assert the idempotency key is identical across three attempts for the same collection
   - Simulate a timeout on attempt 1, then a dunning retry, and assert exactly one charge was issued to TrueLayer (the second was skipped because the status check revealed the first succeeded)
   - Simulate a genuine decline on attempt 1, then a retry, and assert two charges were issued (the retry is legitimate)
   - Assert that timeout and decline produce distinct `failure_reason` values in the `fee_collections` table

6. Do not change the dunning schedule, fee calculation, mandate flow, or implement refunds. This is a narrowly-scoped idempotency fix.
