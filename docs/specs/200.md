# Spec: Add route skeletons to every authenticated route

**Issue:** #200  
**Module:** app

## Problem

The application uses React Server Components and server actions, so every navigation is a network round-trip. Most authenticated routes have no loading.tsx, meaning navigation presents as blank-then-pop with no intermediate state. In an app context, a tap should produce an immediate response — a tap that produces nothing for several hundred milliseconds before replacing the entire screen is the clearest remaining signal that this is a website in a wrapper, and it is felt on every single interaction rather than at the edges.

## Scope

Add a loading.tsx to every authenticated route that currently lacks one, rendering a skeleton matching the resolved layout for each route.

**Changes:**
- Create `src/app/setup/loading.tsx` — skeleton for business setup page
- Create `src/app/setup/voice/loading.tsx` — skeleton for voice setup interview
- Create `src/app/jobs/loading.tsx` — skeleton for jobs history/work page
- Create `src/app/jobs/new/loading.tsx` — skeleton for new job voice intake
- Create `src/app/motko/loading.tsx` — skeleton for "Speak to Motko" hub

Each skeleton matches block positions of its resolved layout so no element shifts when content loads. Skeletons contain no text content, are hidden from screen readers with `aria-hidden="true"`, and render static (no shimmer animation) under `@media (prefers-reduced-motion: reduce)`.

## Explicitly out of scope

- Do NOT change data fetching, queries, or caching on any route
- Do NOT change any resolved page layout
- Do NOT add route prefetching
- Do NOT add optimistic UI to any action
- Do NOT touch customer-facing routes (q/[id], i/[id], c/[id]) — the UI tranche covers those separately
- Do NOT add error boundaries
- Do NOT add minimum display times to skeletons (if the route resolves faster than the skeleton renders, the skeleton may not appear — this is correct behavior)

## Files

**Created:**
- `src/app/setup/loading.tsx`
- `src/app/setup/voice/loading.tsx`
- `src/app/jobs/loading.tsx`
- `src/app/jobs/new/loading.tsx`
- `src/app/motko/loading.tsx`

**Unchanged:**
- All page.tsx files remain untouched
- Existing loading.tsx files (dashboard, settings, jobs/[id]) remain untouched
- No changes to layouts or middleware

## Edge cases

**Route resolves faster than skeleton renders:**  
The skeleton may not appear. This is correct — no minimum display time should be added.

**Route with content whose height varies by data (e.g., a list):**  
Skeleton renders a fixed representative number of rows. For the jobs history page, render 3 job rows as a representative default.

**Nested layouts:**  
The skeleton belongs to the segment that is actually loading, not the outermost layout, so shared chrome (like AppHeader) does not flash. Each loading.tsx renders the complete page structure including header.

**Route fails to load:**  
Existing error behavior applies. The skeleton is replaced by whatever renders today.

**Route requires a session that has expired:**  
The login redirect happens before the skeleton is relevant. The middleware handles this upstream.

**User-visible:**  
Yes. Every navigation to an authenticated route gains an immediate visual response instead of a blank screen.

**Reduced motion:**  
Under `@media (prefers-reduced-motion: reduce)`, skeletons render static with no shimmer animation. Use CSS to disable shimmer.

**Accessibility:**  
Skeletons are marked `aria-hidden="true"` on the root element and contain no text content, so screen readers skip them entirely.

**Throttled connections:**  
Skeletons should render within 200ms of navigation on a throttled connection. Since they contain no data fetches, this happens naturally.

## Risks

**Low risk.** This is purely a loading state addition:
- No database migrations required
- No user data or money-related logic affected
- No changes to existing page components
- No changes to data fetching or caching behavior
- Skeletons are transient UI that users see for milliseconds

The only risk is mismatched skeleton/content layouts causing layout shift, which is caught during visual testing and does not affect functionality.

## Derived criteria

I understand the human to be asking for:

1. **Create loading.tsx for all authenticated routes without one** — specifically /setup, /setup/voice, /jobs, /jobs/new, and /motko

2. **Each skeleton matches its resolved layout** so content swaps in without layout shift (same header structure, same main content bounds, same section spacing)

3. **Skeletons render immediately on navigation** providing a sub-200ms response on any connection

4. **No text content in skeletons** and all skeleton containers are marked `aria-hidden="true"` so screen readers skip them

5. **Static skeletons under reduced motion** via `@media (prefers-reduced-motion: reduce)` with no shimmer animation

6. **Test coverage ensures future routes need loading.tsx** — a test that walks the authenticated route directory and asserts coverage, so adding a new route without loading.tsx fails the test

7. **No changes to any data fetching** or page component logic — this is purely a loading state addition

8. **Fixed representative content for variable-height routes** (e.g., jobs list shows 3 rows as a representative default)
