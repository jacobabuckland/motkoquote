# VOICE-4: Show when a call was cut short by a cap

## Problem

When a voice intake call ends because a hard limit was reached (the 12-question turn cap or the 6-minute time cap), the resulting quote is presented to the contractor as a complete conversation with no indication that the call was cut short. The `wrap_reason` field already distinguishes capped endings (`cap_questions`, `cap_time`) from natural ones (`slots`, `user`, `manual`), but this signal currently reaches telemetry only and is not surfaced to the contractor.

## Scope: what changes

1. **Add `cap_ended` field to `SowState` schema** — a boolean that defaults to `false`, set to `true` when the call ended because a cap was hit
2. **Implement `endedOnCap()` predicate** — a pure function that takes a `WrapReason` and returns whether it represents a capped ending
3. **Set `cap_ended` in `completeSow`** — use `endedOnCap(wrapReason)` to set the flag when marking the SoW complete
4. **Surface the flag on the job page** — display a visible warning banner (similar to the existing `wrap_incomplete` banner) when `cap_ended` is true, making it clear to the contractor that the call did not reach a natural conclusion

## Explicitly out of scope: what does not change

- The turn cap and time cap values themselves (they remain 12 questions and 6 minutes)
- How turns are counted (question vs acknowledgement distinction)
- Giving the contractor a choice when approaching a cap
- The intake conversation structure or question set
- Pricing, drafting, or line-item behavior for thin scopes
- The existing wrap-up detour for required pricing slots
- The `wrap_incomplete` flag and its existing behavior

## Edge cases, including failure modes and empty states

- **Contractor finishes in four turns naturally** — `wrap_reason` is `user` or `slots`, so `cap_ended` remains `false` and no warning displays. Ending early is only a problem when forced by a cap.
- **Model loops without concluding** — the cap fires (`cap_questions` or `cap_time`), `cap_ended` becomes `true`, and the warning displays. The safety net still works.
- **Cap trips while required slot is unanswered** — both `wrap_incomplete` and `cap_ended` are true. Display both warnings; they describe different facts and should not be collapsed.
- **Connection drops mid-call** — not tracked by `wrap_reason`, so `cap_ended` remains `false`. This is not a cap and must not be reported as one.
- **Manual call termination** — `wrap_reason` is `manual`, so `cap_ended` remains `false`. Operator-ended calls are not the defect this item addresses.

## Risks: anything touching money, migrations, or user data

None. This item adds a boolean flag to an existing JSON column (`sow_json`) and surfaces it on the job page. No money logic, no migration required (SoW schema changes are backward-compatible via Zod defaults), no writes to sensitive data.

## Derived criteria

A call that ends because a cap tripped:
1. Sets `cap_ended` to `true` on the resulting SoW
2. Displays a visible warning to the contractor on the job page, distinct from the `wrap_incomplete` warning
3. Does not interfere with the existing required-slot wrap-up path

A call that ends naturally:
1. Leaves `cap_ended` as `false`
2. Displays no cap-related warning

The `endedOnCap()` predicate:
1. Returns `true` for `cap_questions` and `cap_time`
2. Returns `false` for `slots`, `user`, and `manual`
3. Is the single source of truth for determining capped endings (no inline re-implementations)
