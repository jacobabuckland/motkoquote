# Issue #145: Add loading skeletons to the customer-facing routes

## Problem

The three customer-facing routes — quote view (`q/[id]`), invoice pay (`i/[id]`), and contract view (`c/[id]`) — are server components that block on Supabase joins with no `loading.tsx`. When opened from an SMS link on a mobile connection (the common path), they render blank until the query resolves, then pop into existence. This blank-then-pop experience is the least reassuring possible presentation for a customer deciding whether to trust a request for payment or signature.

## Scope: what changes

1. Add `src/app/q/[id]/loading.tsx` for the quote view route
2. Add `src/app/i/[id]/loading.tsx` for the invoice pay route  
3. Add `src/app/c/[id]/loading.tsx` for the contract view route

Each loading skeleton must:
- Match the resolved page's layout structure so content swaps in without shifting
- Use the existing `Skeleton` component from `@/components/ui/skeleton`
- Use the existing `Card` component where the resolved page uses cards
- Render the trade's brand colour if it is available without a data fetch (it is not — see below)
- Contain no text content
- Be properly marked for accessibility (either via `aria-hidden` on skeleton elements or by ensuring the structure is screen-reader friendly)
- Respect reduced motion preferences (already handled globally via `globals.css`)

Brand colour is stored in `contractors.branding.brand_color` and requires a database query. The loading skeleton cannot fetch it without blocking, which defeats the purpose. Therefore all three skeletons will use the default neutral skeleton colour (`bg-stone-200` from the existing `Skeleton` component).

## Explicitly out of scope

- Do not change data fetching, queries, joins, or caching on these routes
- Do not change the resolved page layouts
- Do not add skeletons to any authenticated route (dashboard, settings, jobs)
- Do not add error boundaries or `error.tsx`
- Do not change how the brand colour is stored or retrieved
- Do not add a minimum display time for skeletons (if the query is fast, the skeleton may not appear — this is correct)

## Edge cases

**Query resolves faster than the skeleton renders:**  
The skeleton may not appear at all. This is correct behaviour and requires no minimum display time. Next.js will show the resolved page immediately if the data is already available.

**Query fails:**  
Existing error behaviour is unchanged. The skeleton is replaced by whatever renders today (likely a thrown error that bubbles to an error boundary, or a `notFound()` redirect).

**Resource not found (404):**  
Unchanged. The page throws `notFound()` from the server component. Do not render a skeleton indefinitely.

**Brand colour is stored as an invalid CSS value:**  
Not applicable — the skeleton uses the default neutral colour and never reads the stored brand colour.

**Slow network conditions:**  
The skeleton is designed for this case. It renders immediately with no data fetching, showing structure while the server component streams in.

**Screen reader users:**  
Skeleton elements should not be announced. Either mark them `aria-hidden="true"` or ensure they contain no semantic content that would be read.

**Reduced motion preferences:**  
Already handled globally by `src/app/globals.css` at line 252, which sets `animation-duration: 0.01ms` for users with `prefers-reduced-motion: reduce`. The `Skeleton` component's `animate-pulse` class will automatically respect this.

**Multiple navigations in quick succession:**  
Next.js handles this. The loading state is tied to the route transition and will cancel if the user navigates away.

## Risks

**Low risk — pure UI addition:**  
This change adds three new files and touches nothing else. The worst case is a poorly-matching skeleton that causes layout shift when content loads, which is no worse than the current blank state and can be fixed iteratively.

**No migrations, no money, no user data:**  
This change touches none of these. It is a pure client-side UI improvement.

**Sequencing note from the Notion spec:**  
The spec mentions that this touches the same routes as "capability-token security work". Check whether issue #144 or similar is in flight before starting. If so, coordinate sequencing or batch them together to avoid merge conflicts.
