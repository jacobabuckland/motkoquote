# Issue #99: Tighten middleware prefix allowlist to explicit routes

**Auditing branch:** `factory/99` @ `bea238f`  
**No database migration required.**

## Problem

The `updateSession` function in `src/lib/supabase/middleware.ts` (lines 30-46) uses prefix matching to make entire API namespaces public:

```typescript
request.nextUrl.pathname.startsWith("/api/quotes/") ||
request.nextUrl.pathname.startsWith("/api/contracts/") ||
request.nextUrl.pathname.startsWith("/api/truelayer/") ||
request.nextUrl.pathname.startsWith("/api/twilio/") ||
request.nextUrl.pathname.startsWith("/api/cron/")
```

Any route created under these prefixes is automatically public the moment the file is created, without anyone making an explicit security decision. In an agent-driven codebase where routes are continuously generated, an engineer (or agent) adding `/api/quotes/[id]/internal-costs/route.ts` would inadvertently create a public endpoint. The hazard is not latent—it is standing and active.

Prefix-based exposure is a failing-open security posture: new routes inherit public access by default rather than requiring it to be explicitly granted.

## Scope: what changes

### 1. Replace prefix matching with explicit route list
**File:** `src/lib/supabase/middleware.ts`

Replace the prefix-based checks (lines 40-46) with an explicit allowlist of route patterns. Each route that should be public is named individually. Dynamic segments (e.g. `[id]`) are supported in the pattern syntax.

The list will be defined as a constant array at the top of the file, making it easy to audit and maintain:

```typescript
// Public API routes — anything not listed here requires authentication.
// Dynamic segments supported: /api/quotes/[id]/pdf matches /api/quotes/abc123/pdf
const PUBLIC_API_ROUTES = [
  "/api/quotes/[id]/pdf",
  "/api/contracts/[id]/pdf",
  "/api/truelayer/create-payment",
  "/api/truelayer/webhook",
  "/api/twilio/inbound",
  "/api/cron/chase",
  "/api/cron/collect-fees",
  "/api/cron/purge-accounts",
  "/api/cron/reconcile-free-jobs",
  "/api/cron/retry-fee-collections",
] as const;
```

The matching logic will convert patterns with `[id]` to regex equivalents (e.g. `/api/quotes/[id]/pdf` → `/^\/api\/quotes\/[^\/]+\/pdf$/`), then test the incoming pathname against each pattern.

### 2. Preserve existing public page routes
**File:** `src/lib/supabase/middleware.ts`

The non-API public routes remain unchanged and continue to use prefix/exact matching as they do today:

- `/` (exact)
- `/login*`
- `/signup*`
- `/auth*`
- `/privacy*`
- `/support*`
- `/q/*` (quote share links)
- `/i/*` (invoice share links)
- `/c/*` (contract share links)

These are well-understood, stable routes that are unlikely to expand via agent generation, so prefix matching remains appropriate.

### 3. Fail visibly on stale entries
**File:** `tests/acceptance/99.test.ts`

A test will enumerate all routes in `src/app/api/` and compare them against `PUBLIC_API_ROUTES` and a complementary `PROTECTED_API_ROUTES` constant. Any route found in the codebase but absent from both lists will cause the test to fail with a clear error message:

```
Route /api/quotes/[id]/debug found but not listed in PUBLIC_API_ROUTES or PROTECTED_API_ROUTES.
Every API route must be explicitly classified.
```

This ensures the list cannot silently rot. When a route is added, the test fails until it's added to one of the two lists. When a route is deleted, the test fails until it's removed from the lists.

### 4. Cron routes remain public but fail closed
**File:** `src/lib/supabase/middleware.ts`

Cron routes (`/api/cron/*`) are listed individually in `PUBLIC_API_ROUTES` so they pass through the middleware. Each cron route handler already calls `rejectUnauthorizedCron` (from `@/lib/cron-auth`) at the top of its handler, which validates the `Authorization: Bearer <CRON_SECRET>` header and returns 401 if the secret is unset or mismatched.

This layered approach is preserved:
- Middleware allows the request through (unauthenticated)
- Individual handler verifies the cron secret and fails closed if unset

A new cron route will no longer be automatically public—it must be added to `PUBLIC_API_ROUTES` explicitly.

## Explicitly out of scope

- **No change to authentication or session handling.** The middleware continues to check `supabase.auth.getUser()` and redirect unauthenticated requests to `/login` for non-public routes. Only the public route matching logic changes.
- **No change to which routes should be public.** This issue preserves the current set exactly. If a route is public today via prefix match, it is explicitly listed and remains public after this change.
- **No addition of capability tokens or route-level authorization.** That belongs on individual route handlers, not in the middleware.
- **No change to TrueLayer JWS verification or Twilio signature validation.** Those remain in their respective route handlers and are unaffected.
- **No rate limiting, IP allowlisting, or other hardening.** Those are separate items.

## Edge cases

### 1. Route in allowlist but deleted from codebase
**Input:** `/api/quotes/[id]/pdf` is in `PUBLIC_API_ROUTES` but the file `src/app/api/quotes/[id]/pdf/route.ts` has been deleted.  
**Behaviour:** The acceptance test fails with a message listing the stale entry. The middleware continues to allow requests to that path (harmless—Next.js returns 404), but the test failure blocks the PR from merging until the list is updated.

### 2. New route under existing prefix
**Input:** Engineer adds `/api/quotes/[id]/internal-costs/route.ts`.  
**Current behaviour:** Public via `/api/quotes/` prefix match.  
**New behaviour:** Protected by default (not in `PUBLIC_API_ROUTES`). The acceptance test fails, forcing the engineer to explicitly classify it as public or protected.

### 3. Dynamic segment with varying formats
**Input:** `/api/quotes/abc123/pdf`, `/api/quotes/quote_456/pdf`, `/api/quotes/q-789/pdf`  
**Behaviour:** All match the pattern `/api/quotes/[id]/pdf` because `[id]` is replaced with `[^\/]+` (one or more non-slash characters). Pattern matching does not validate ID format—that remains the route handler's responsibility.

### 4. Optional catch-all segments
**Input:** Next.js supports `[[...slug]]` for optional catch-all segments.  
**Current state:** No routes in the codebase use this syntax.  
**Behaviour:** If one is added, it must be listed explicitly. The pattern syntax supports it: `/api/foo/[[...slug]]` would be matched as `/api/foo(?:/.*)?`. Not implementing this in the first pass—will surface as a test failure if needed, prompting an incremental addition.

### 5. Cron route with unset CRON_SECRET
**Input:** Request to `/api/cron/chase` with no `Authorization` header, and `CRON_SECRET` is unset.  
**Current behaviour:** Passes middleware (public prefix), handler calls `rejectUnauthorizedCron`, which returns 401 because secret is unset.  
**New behaviour:** Identical. Passes middleware (in `PUBLIC_API_ROUTES`), handler returns 401.

### 6. Route that is public but should not be
**Input:** Audit discovers `/api/truelayer/create-payment` is public but should require authentication.  
**Behaviour:** Out of scope. Report it as a separate issue. This task preserves the current public set—removing public access is a behaviour change requiring its own security review.

### 7. Trailing slash handling
**Input:** Request to `/api/quotes/abc123/pdf/` (with trailing slash).  
**Behaviour:** Next.js normalizes trailing slashes before middleware runs (configurable via `next.config`). If trailing slashes are not normalized, the pattern `/api/quotes/[id]/pdf` will not match `/api/quotes/[id]/pdf/`. Test both cases. If the codebase expects normalized paths, document that assumption. If not, adjust patterns to optionally match trailing slashes: `/api/quotes/[id]/pdf\/?`.

### 8. Case sensitivity
**Input:** Request to `/API/quotes/abc123/pdf` (uppercase).  
**Behaviour:** Pathname matching is case-sensitive. This request will not match `/api/quotes/[id]/pdf` and will be protected. Next.js route resolution is also case-sensitive on case-sensitive filesystems (Linux), so this is consistent.

## Risks

### 1. Incomplete enumeration breaks customer-facing links (HIGH)
**Risk:** A public route is missed during enumeration. The route becomes protected after deploy. Customer share links (quote PDFs, contract PDFs) return 401 or redirect to `/login`.  
**Mitigation:**
- Enumerate by walking `src/app/api/` directory, not by reading the current prefix list (the list is what we're replacing, so it can't be the source of truth).
- Cross-check enumeration output against production request logs (if available) to identify any public routes receiving traffic that might be missing.
- The acceptance test verifies that all current routes are classified. Running the test suite before the PR merges catches any missed routes.
- If a miss occurs, it is immediately visible: customer reports broken link, logs show 401s, rollback is straightforward (the change is isolated to middleware.ts).

### 2. Pattern matching implementation is incorrect (MEDIUM)
**Risk:** The regex conversion logic has a bug (e.g. doesn't escape special chars, wrong segment boundary matching). Some public routes become protected or vice versa.  
**Mitigation:**
- Unit test the pattern matching function exhaustively (exact match, single dynamic segment, multiple dynamic segments, edge cases like adjacent segments).
- Acceptance test exercises real route paths against real patterns (e.g. `/api/quotes/abc123/pdf` must match `/api/quotes/[id]/pdf`).
- TypeScript const assertion on `PUBLIC_API_ROUTES` ensures the list is read-only and cannot be accidentally mutated.

### 3. Performance regression from pattern matching (LOW)
**Risk:** Iterating through `PUBLIC_API_ROUTES` and running regex tests on every request is slower than prefix matching.  
**Assessment:** `PUBLIC_API_ROUTES` has ~10 entries. Regex matching 10 patterns on a ~30-character pathname is negligible (sub-microsecond). Middleware runs on every request, but this is a tiny constant-time overhead. No caching or optimization needed unless profiling shows otherwise.

### 4. List diverges from reality over time (MITIGATED by test)
**Risk:** Routes are added/removed but the list is not updated. The test fails, but someone bypasses it or the test is deleted.  
**Mitigation:** The acceptance test is the enforcement mechanism. As long as the test runs in CI and PRs cannot merge with failing tests, the list stays in sync. Document in the test file that this test must not be deleted or skipped—it is a security invariant.

## Derived criteria

What I understood the human to be asking for:

1. **Replace prefix-based matching with explicit route enumeration.** Each public API route is listed individually in a constant array. Prefix matching is removed for API routes.

2. **Support dynamic segments in route patterns.** Routes like `/api/quotes/[id]/pdf` can be listed once and match any value in the `[id]` position.

3. **Fail visibly when the list is incomplete or stale.** A test enumerates all routes in the codebase and fails if any route is not explicitly classified as public or protected. This prevents silent rot.

4. **Preserve current public routes exactly.** Everything public today via prefix match is listed explicitly and remains public. No route becomes protected unless it was already protected.

5. **Cron routes remain public and fail closed on unset CRON_SECRET.** Cron routes pass through middleware but are guarded by `rejectUnauthorizedCron` in their handlers, which returns 401 if `CRON_SECRET` is unset or mismatched.

6. **New routes default to protected.** A route added under `/api/quotes/` but not in `PUBLIC_API_ROUTES` requires authentication. The test failure surfaces this immediately, forcing explicit classification.

7. **No changes to authentication, session handling, or route-level authorization.** Only the public route matching logic changes. Everything else (Supabase session validation, TrueLayer JWS, Twilio signatures, capability tokens) is out of scope.
