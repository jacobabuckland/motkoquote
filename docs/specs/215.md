# Issue #215: PAY-4: Fee collection at source via application fees (replaces VRP mandate collection)

**Auditing branch:** `factory/215` @ `5a97b1f`  
**Database migration required:** No — uses existing `jobs.fee_*` columns, adds no new schema

## Problem

motko's fee is currently collected AFTER the job via TrueLayer VRP mandates against the contractor, with monthly batching, dunning retries, and credit exposure. With Stripe destination charges, the fee can be taken at source via `application_fee_amount` — the customer's payment is split automatically: contractor receives the job value minus motko's fee, motko's platform account receives the fee. This eliminates collection risk, removes the VRP dependency entirely, and simplifies the fee lifecycle from a multi-step dunning process to a single atomic deduction.

## Scope: what changes

### 1. Fee calculation at payment creation

When creating a Stripe destination charge (the customer → contractor payment), the existing fee engine (`motkoFeePennies` from `src/lib/motko-fee.ts`) is invoked to calculate the fee. The inputs are:
- `jobValuePennies`: the invoice total in pennies
- `freeJobsRemaining`: the contractor's cached free-job allowance at payment time

The calculated fee becomes the destination charge's `application_fee_amount`:
- Standard job (no free allowance): `application_fee_amount = 200` (£2) or `400` (£4) depending on job value
- Free job (allowance > 0): `application_fee_amount = 0` — Stripe collects nothing, contractor receives full amount

The credit ledger (`credit_events` table) STILL decides whether a job is free — Stripe merely executes that decision. A job that qualifies as free sets `application_fee_amount = 0` and burns one credit via a `job_consumed` ledger event, exactly as today.

### 2. Fee settlement on payment success

When the Stripe webhook confirms payment success (`payment_intent.succeeded` or equivalent), the paid-job settlement path (`src/lib/paid-job-settlement.ts` and its caller in the webhook handler) records the fee outcome:
- Jobs with `application_fee_amount > 0` are marked `fee_status = 'collected'`, `fee_amount_pennies = <amount>`, with net/VAT split
- Jobs with `application_fee_amount = 0` (free jobs) are marked `fee_status = 'not_applicable'`, `fee_waived_reason = 'free_allowance'`

The fee is NEVER written to `fee_status = 'accrued'` for at-source jobs. The existing VRP collection path (`settleFeeCollection` in `src/lib/collect-fees.ts`) is bypassed — a job whose fee was taken at source does not enter the monthly collection batch.

### 3. Fee statement projection

The fee statement (`src/lib/fee-statement.ts`, `src/app/settings/fees-statement-section.tsx`) must show BOTH collection models coherently:
- **At-source collected fees** (new): jobs with `fee_status = 'collected'` AND `payment_method != 'motko_bank'` (i.e., Stripe-collected, not TrueLayer)
- **VRP-collected fees** (historical): jobs with `fee_status = 'collected'` AND a corresponding `fee_collection` record OR `payment_method = 'motko_bank'`
- **Accrued fees awaiting VRP collection** (in-flight TrueLayer jobs only): jobs with `fee_status = 'accrued'`

The statement sums these separately and shows a coherent history across the migration boundary. The net/VAT split for at-source fees is computed at payment time (same `splitFeeVat` function) and stored in `fee_net_pennies` / `fee_vat_pennies`, so the statement read path is unchanged.

### 4. Retire VRP mandate creation for NEW jobs

The fee mandate setup flow (`src/app/settings/fee-billing-section.tsx`, `src/app/settings/fee-billing-actions.ts`) is gated: new contractors are NOT prompted to authorize a VRP mandate. Existing mandate data (`contractors.fee_mandate_id`, `fee_mandate_status`) is preserved but not written for new sign-ups post-migration.

The monthly batch collection cron (`src/app/api/cron/collect-fees/route.ts`) continues to run for in-flight TrueLayer jobs (those with `fee_status = 'accrued'`), but no NEW jobs enter that state once at-source collection is live.

## Explicitly out of scope: what does not change

- **No change to fee amounts, thresholds, or free-job allowance.** The £2/£4 bands and 5-job free allowance are unchanged. Only the COLLECTION mechanism changes.
- **No removal of VRP/mandate data.** Existing `fee_collections`, `fee_mandate_id`, and TrueLayer provider refs are preserved for historical reconciliation. Removal is PAY-5.
- **No referral system changes** beyond ensuring the credit ledger still drives fee waiver decisions (it does — the ledger is read, the result is passed to `motkoFeePennies`, and the answer becomes `application_fee_amount`).
- **No migration of in-flight TrueLayer jobs.** Jobs already in `accrued` state complete via the VRP path; only NEW jobs paid via Stripe use at-source collection.

## Edge cases

1. **Refund of a job whose fee was taken at source**

   When a Stripe payment is refunded (full or partial), decide whether motko's `application_fee_amount` is also refunded:
   
   - **Recommendation:** Application fee refunded on FULL refund (the job never completed, so motko's fee should reverse), RETAINED on PARTIAL refund (motko provided the platform for the partial work completed).
   - **Implementation:** Configure Stripe's `refund_application_fee` parameter accordingly, or handle in webhook on `charge.refunded` / `payment_intent.refund` events.
   - **Document the decision** in code comments and in this spec's final implementation notes.

2. **Job paid in multiple installments (deposit + balance)**

   If a job has a deposit payment and a later balance payment:
   - The fee is calculated ONCE per job, not per payment.
   - Decide: is the fee taken on the FIRST payment (deposit), the FINAL payment (balance), or split proportionally?
   - **Recommendation:** Take the fee on the FIRST payment that transitions the job to "paid" status. Subsequent payments for the same job have `application_fee_amount = 0`.
   - The fee engine's `jobValuePennies` input is the TOTAL job value (from `invoices.amount`), not the individual payment amount.

3. **Legacy in-flight jobs mid-transition**

   A contractor with in-flight TrueLayer jobs (deposit paid via TrueLayer, fee accrued) later receives a Stripe payment for the same or a different job:
   - TrueLayer-accrued fees are collected via the existing VRP batch path (`fee_status = 'accrued'` → monthly collection → `'collected'`).
   - NEW Stripe payments use at-source collection (`fee_status = 'collected'` immediately).
   - These MUST NOT double-charge: a job's `fee_status` is the source of truth. A job already marked `'accrued'` cannot transition to at-source `'collected'` — the VRP batch owns it.

4. **Contractor with NO Stripe connected account**

   If a contractor is onboarded but has not completed Stripe Connect setup (no `stripe_account_id` or account not `charges_enabled`):
   - Destination charges FAIL. The payment creation route must gate on payout readiness and return an error.
   - The customer-facing flow must prompt the contractor to complete payout setup before invoices can be paid.
   - This is likely already handled by the Stripe payment creation code; PAY-4 does not add new gating, only ensures fees are correctly applied once the payment CAN be created.

5. **Free job that later has the credit revoked or adjusted**

   The fee is determined at payment time using the contractor's `freeJobsRemaining` snapshot. If the credit balance is later adjusted (e.g., an admin correction), already-settled fees are NOT retroactively changed. A job marked `fee_status = 'collected'` with `fee_amount_pennies = 0` and `fee_waived_reason = 'free_allowance'` remains free forever, even if the credit ledger is later corrected.

## Risks

- **Dependency on Stripe destination charge implementation.** This spec assumes PAY-2/PAY-3 (or equivalent) has delivered Stripe payment creation with destination charges to contractor connected accounts. If that code does not exist, PAY-4 cannot proceed. Mitigation: acceptance tests will fail with "cannot find module" if Stripe payment code is missing — a clear signal to the Engineer that the dependency is unmet.

- **Fee calculation mismatch between at-source and VRP paths.** The existing fee engine (`motkoFeePennies`) is deterministic, but if the `freeJobsRemaining` input differs between payment creation and VRP collection, the calculated fee diverges. Mitigation: load `freeJobsRemaining` from the SAME credit balance query (`contractors` join with `credit_events` aggregate) at both points. Consider caching the snapshot at payment time.

- **Double-fee-collection during migration boundary.** A contractor with accrued TrueLayer fees (old model) and new Stripe payments (new model) must not be charged twice for the same job. Mitigation: `fee_status` is the gatekeeper. A job in `'accrued'` state is owned by the VRP batch; a job transitioned to `'collected'` at source cannot re-enter `'accrued'`. The states are mutually exclusive.

- **Refund handling not specified.** Edge case #1 notes the decision must be made but does not prescribe it. If the Engineer implements refund logic that refunds motko's fee when it should be retained (or vice versa), the revenue model breaks. Mitigation: explicitly configure `refund_application_fee` in Stripe API calls and document the policy in code comments.

- **Multi-payment jobs not scoped.** If the job model supports deposits + balance payments, this spec assumes the fee is taken once. If that assumption is wrong (e.g., the codebase splits fees across payments), the implementation will diverge from the spec. Mitigation: review the `invoices` and `jobs` schema for multi-payment support before implementation. If found, revisit edge case #2's recommendation.

## Derived criteria

- When a customer pays an invoice via Stripe, the contractor receives `jobValue - motkoFee`, and motko's platform account receives `motkoFee` as an application fee
- A standard job (no free allowance) has `application_fee_amount = 200` (for jobs ≤ £1000) or `400` (for jobs > £1000), matching the existing fee bands
- A free job (contractor has `freeJobsRemaining > 0`) has `application_fee_amount = 0`, and one credit is burned via a `job_consumed` ledger event
- The job is marked `fee_status = 'collected'` immediately on payment success, with `fee_amount_pennies`, `fee_net_pennies`, `fee_vat_pennies` recorded
- Free jobs are marked `fee_status = 'not_applicable'`, `fee_waived_reason = 'free_allowance'`, with fee amounts = 0
- The fee statement in Settings shows both at-source collected fees (Stripe jobs) and VRP-collected fees (TrueLayer jobs) coherently, with correct net/VAT splits
- NEW jobs do not create `fee_collection` records or enter the monthly VRP batch — `settleFeeCollection` is not called for at-source jobs
- Existing accrued TrueLayer jobs (`fee_status = 'accrued'`) continue through the VRP collection path without interference from the at-source logic
- VRP mandate setup is hidden or disabled for new contractors; existing contractors with `fee_mandate_id IS NOT NULL` can still view their mandate status
- Existing unit tests for `motkoFeePennies`, `splitFeeVat`, and `planPaidJobSettlement` remain green (the fee calculation logic is unchanged, only where it's invoked and applied differs)
