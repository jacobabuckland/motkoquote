# Issue #81: Gate the pricing slot on pricing.mode being explicitly set

**Auditing branch:** `factory/81` @ `c6c8275`  
**No database migration required.**

## Problem

The pricing/duration slot is currently satisfied whenever `pricing != null` OR `labour_plan.duration_days != null` (line 725 of `src/lib/schemas/sow.ts`). This means an incidental duration mention during a call — for example, "it'll be about four days" — fills `duration_days` and immediately marks the slot as answered, even though the contractor was never asked how they want the job priced.

The slot then disappears from both:
1. Natural follow-up questions during the call
2. The `concludeOrAskRequired` safety net that should catch missing required slots before wrap

When `pricing.mode` is unset, `resolvePricingMode` silently defaults to `"calculated"` (line 94). The user never chose this mode and is never informed that one was selected for them. A passing remark about duration thus determines the pricing approach without explicit consent.

This violates the CLAUDE.md invariant: **"Voice sessions must ask, not infer, required pricing slots."** The pricing mode is one of the three required scope slots and must be actively solicited, not silently inferred.

## Scope: what changes

### 1. Slot-filling logic (`getUnansweredChecklistQuestions`)
**File:** `src/lib/schemas/sow.ts:725`

Change the gate from:
```typescript
if (sow.pricing == null && sow.labour_plan?.duration_days == null) unanswered.push("duration");
```

To:
```typescript
if (sow.pricing?.mode == null) unanswered.push("duration");
```

The slot is satisfied **only** when `pricing.mode` is explicitly set to one of `"days"`, `"fixed"`, or `"calculated"`. A duration mention alone (`duration_days != null`) no longer satisfies it.

### 2. `resolvePricingMode` signature and behaviour
**File:** `src/lib/schemas/sow.ts:92-94`

Change from:
```typescript
export const resolvePricingMode = (
  sow: Pick<SowState, "pricing">,
): PricingMode => sow.pricing?.mode ?? "calculated";
```

To:
```typescript
export const resolvePricingMode = (
  sow: Pick<SowState, "pricing">,
): PricingMode | null => sow.pricing?.mode ?? null;
```

When `pricing` is `null` or `pricing.mode` is unset, return `null` instead of defaulting to `"calculated"`. This makes the unset state explicit and surfaceable, rather than masking it with a silent assumption.

### 3. `applyPricingMode` handles null gracefully
**File:** `src/lib/pricing-mode.ts:57-68`

Legacy jobs (pre-Task B) have `pricing: null`. These must continue to produce the calculated breakdown as they do today, without hard-failing or changing price.

Update `applyPricingMode` to handle `mode === null`:

```typescript
export const applyPricingMode = (
  calculatedLineItems: LineItem[],
  sow: Pick<SowState, "pricing" | "job_type">,
): LineItem[] => {
  const mode = resolvePricingMode(sow);
  const fixedAmount = sow.pricing?.fixed_amount ?? null;
  
  // Legacy jobs: pricing was never set (pre-Task B). Keep producing the
  // calculated breakdown — an explicit, commented decision, not a silent
  // fallback. Existing jobs must not change price.
  if (mode === null) {
    return calculatedLineItems;
  }
  
  if (mode === "fixed" && fixedAmount != null) {
    const provisionals = calculatedLineItems.filter((item) => item.provisional === true);
    return buildFixedModeLineItems(deriveWorksDescription(sow.job_type), fixedAmount, provisionals);
  }
  
  return calculatedLineItems;
};
```

This keeps legacy jobs working exactly as they do today, with the decision documented in code rather than buried in a defaulting ternary.

### 4. Update tests
**File:** `src/lib/schemas/sow.test.ts`

Any unit tests that rely on `resolvePricingMode` defaulting to `"calculated"` will need updating to either:
- Explicitly set `pricing: { mode: "calculated", fixed_amount: null }` when testing calculated mode
- Assert that the result is `null` when testing the unset state

### 5. Update comments
**Files:** `src/lib/schemas/sow.ts:721-725`, `src/lib/schemas/sow.ts:89-91`

The inline comments currently document the old "duration OR pricing" gate and the defaulting behaviour. These need updating to reflect the new "pricing.mode only" gate and `null`-on-unset behaviour.

## Explicitly out of scope

- **No change to how `pricing.mode` gets set.** The voice client and `update_sow` tool already support setting `pricing.mode`; this issue only gates the slot on it being set, not how it gets there.
- **No UI changes.** The quote editor, job page, and settings are unaffected. This is purely a slot-filling and mode-resolution change.
- **No migration.** Existing `jobs` table rows are unaffected. Legacy jobs with `pricing: null` continue to render calculated breakdowns as they do today via the `mode === null` branch in `applyPricingMode`.
- **No change to `pricingSchema.mode.default("calculated")`** in the Zod schema (line 81). The Zod default applies when deserializing malformed data; it doesn't affect the slot-filling logic or `resolvePricingMode`, which operate on parsed `SowState` objects where `pricing` is either a valid object or `null`.

## Edge cases

### 1. Incidental duration mention with no pricing discussion
**Input:** User says "it'll be about four days" but is never asked how to price.  
**Current behaviour:** Slot satisfied, mode silently defaults to `"calculated"`, wrap proceeds.  
**New behaviour:** Slot remains unanswered, `getUnansweredRequiredChecklistQuestions` returns `["duration"]`, wrap is blocked until mode is asked and answered.

### 2. User chooses "calculated" mode with no duration mentioned
**Input:** User says "you work it out" (sets `pricing.mode = "calculated"`), never mentions duration.  
**Current behaviour:** Slot satisfied (via `pricing != null`).  
**New behaviour:** Slot satisfied (via `pricing.mode != null`). Same outcome, different gate.

### 3. User states duration AFTER choosing a pricing mode
**Input:** User says "give me a fixed price" (sets `mode = "fixed"`), then later says "it's about six days".  
**Current behaviour:** Slot already satisfied via `pricing != null`.  
**New behaviour:** Slot already satisfied via `pricing.mode != null`. Duration mention is still captured in `duration_days` but doesn't re-satisfy the slot.

### 4. Legacy job with `pricing: null` at quote generation time
**Input:** A job created pre-Task B, or a job where the pricing question genuinely never landed.  
**Current behaviour:** `resolvePricingMode` returns `"calculated"`, `applyPricingMode` uses calculated breakdown.  
**New behaviour:** `resolvePricingMode` returns `null`, `applyPricingMode` explicitly handles the `null` case and returns the calculated breakdown unchanged. Same output, explicit handling.

### 5. Empty state / fresh SoW
**Input:** `EMPTY_SOW_STATE` with `pricing: null`.  
**Current behaviour:** `getUnansweredChecklistQuestions` returns `["crew", "duration", "materials_supply", "deadline", "agreed_costs"]`.  
**New behaviour:** Same. The slot is unanswered because `pricing?.mode == null`.

### 6. User sets `pricing.fixed_amount` but not `pricing.mode`
**Input:** Delta has `{ pricing: { mode: undefined, fixed_amount: 2000 } }` (malformed — shouldn't happen from the voice client, but possible from hand-crafted data).  
**Current behaviour:** After merge, `pricing.mode` would be `undefined`, `resolvePricingMode` would default to `"calculated"`.  
**New behaviour:** After merge, `pricing.mode` is `undefined`, `resolvePricingMode` returns `null`, slot remains unanswered. The amount is captured but doesn't satisfy the slot without a mode.

## Risks

### 1. Breaking existing jobs (MITIGATED)
**Risk:** Changing `resolvePricingMode` to return `null` could break quote rendering for legacy jobs.  
**Mitigation:** The `mode === null` branch in `applyPricingMode` explicitly handles this case, returning the calculated breakdown. Legacy jobs continue to render exactly as they do today — the fix is a refactor of the default path, not a behavioural change for existing data.

### 2. Silent failures from unhandled `null` (MITIGATED via TypeScript)
**Risk:** Code consuming `resolvePricingMode` might not handle the new `null` return.  
**Mitigation:** The signature change to `PricingMode | null` forces a compiler error at every call site that doesn't handle `null`. The Engineer must audit each caller (grep hits: `src/app/jobs/[id]/page.tsx`, `src/app/jobs/actions.ts`, and test files) and add explicit handling. The TypeScript compiler is the safety net.

### 3. Pricing correctness for new calls (ACCEPTANCE TESTED)
**Risk:** New calls might now fail to satisfy the required slot and incorrectly block wraps, or conversely still allow silent defaulting.  
**Mitigation:** The acceptance tests in `tests/acceptance/81.test.ts` cover:
- Duration mention alone does NOT satisfy the slot
- Setting `pricing.mode` DOES satisfy it, even without duration
- `getUnansweredRequiredChecklistQuestions` correctly blocks wrap when mode is unset
- Legacy jobs with `pricing: null` continue to produce calculated breakdowns

These tests fail before implementation and must pass after. They exercise the observable behaviour, not implementation details.

### 4. Data integrity: no validation that mode matches amount
**Risk:** A job could have `mode: "fixed"` but `fixed_amount: null`, or `mode: "calculated"` but `fixed_amount: 2000`.  
**Out of scope:** This issue gates the slot on mode being set, not on the mode-amount pairing being valid. The voice client's tool definition and `mergeSowDelta` logic enforce the pairing; schema-level validation (e.g. a Zod refinement) is a separate hardening task.

## Derived criteria

What I understood the human to be asking for:

1. **Duration mention alone must not satisfy the pricing slot.** An incidental "it'll be four days" fills `duration_days` but leaves the slot unanswered unless `pricing.mode` is also set.

2. **The slot is satisfied only when `pricing.mode` is explicitly set** to one of `"days"`, `"fixed"`, or `"calculated"`. The gate is `pricing?.mode != null`, not `pricing != null || duration_days != null`.

3. **`resolvePricingMode` must not default silently.** When `pricing` is `null` or `pricing.mode` is unset, return `null` instead of `"calculated"`. Make the unset state explicit.

4. **`concludeOrAskRequired` (via `getUnansweredRequiredChecklistQuestions`) must still catch the missing mode.** If duration was mentioned but mode wasn't asked, the "duration" slot remains in the required-unanswered list and blocks wrap.

5. **Legacy jobs with `pricing: null` must continue to work.** They produce the calculated breakdown as they do today, via an explicit `mode === null` branch in `applyPricingMode`, not a silent fallback.

6. **The fix is in the slot-filling logic and mode-resolution function, not in how `pricing.mode` gets set.** The voice client already supports setting `pricing.mode` via the `update_sow` tool; this issue only gates the slot on it being set.

7. **User-visible behaviour:** On new calls, the user is asked the pricing-mode question even if they've already mentioned a duration. On existing/legacy jobs, quotes render exactly as they do today — no price changes, no UI differences.
