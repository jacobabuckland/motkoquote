# Issue #81: Gate the pricing slot on pricing.mode being explicitly set

## Problem

The "duration" checklist slot (line 725 in `src/lib/schemas/sow.ts`) is currently satisfied if *either* `pricing` is non-null *or* `duration_days` is non-null. This means an incidental duration mention — "it'll be about four days" — fills `duration_days` and marks the slot as answered, even though the contractor was never asked *how* they want the job priced (days/fixed/calculated).

Once the slot is satisfied, it drops from both the natural follow-up flow and the `concludeOrAskRequired` safety net. `resolvePricingMode` then defaults to "calculated" when `pricing` is null, silently choosing a pricing approach the contractor never confirmed.

This violates CLAUDE.md's invariant: "Voice sessions must ask, not infer, required pricing slots." The duration/pricing-mode question was promoted to *required* precisely to prevent silent inference, but the current gating logic allows a passing remark to bypass the ask entirely.

## Scope: what changes

1. **Slot-filling logic (`getUnansweredChecklistQuestions`)**: Gate the "duration" slot on `pricing?.mode` being explicitly set. A duration mention alone must *not* satisfy it.

2. **Pricing mode resolution (`resolvePricingMode`)**: Change the return signature from `PricingMode` to `PricingMode | null`. When `pricing` is null (mode never set), return `null` instead of defaulting to "calculated".

3. **Quote generation (`applyPricingMode`)**: Handle the `null` case explicitly. For *new* calls where pricing mode was never set, this is an error state — but for *legacy* jobs already saved with `pricing: null`, keep producing the calculated breakdown as before (as an explicit, commented decision, not a silent fallback).

4. **Tests**: Add failing acceptance tests covering:
   - Duration mention alone does not satisfy the slot
   - `concludeOrAskRequired` still asks when mode is unset
   - `resolvePricingMode` returns `null` when pricing is unset
   - Legacy job with `pricing: null` still renders a calculated breakdown

## Explicitly out of scope

- No change to *how* `pricing.mode` gets set (that's the LLM's job via `update_sow`)
- No UI changes
- No database migration (pricing is already nullable)
- No change to the question wording or follow-up logic
- No change to how duration_days itself is captured or used

## Edge cases

1. **Duration mention before pricing mode is asked**: Must keep the slot unanswered so the question is still asked.

2. **Legacy jobs with `pricing: null`**: Jobs already in the database with no pricing object must continue to render exactly as they do today (calculated breakdown). This is an explicit decision — we're not re-pricing historical jobs.

3. **Empty pricing object `{mode: undefined, fixed_amount: null}`**: Zod defaults prevent this — mode has `.default("calculated")` in the schema — but if it somehow surfaces, treat as unset (return null).

4. **Wrap detour with mode still unset**: `concludeOrAskRequired` must still include "duration" in its combined ask when `pricing?.mode` is unset, even if `duration_days` is present.

5. **Mode set to "days" with no duration_days**: The slot is satisfied (mode is set), but quote generation may need to handle missing duration gracefully (separate concern, out of scope here).

## Risks

### Money

- **Legacy job re-pricing**: If `applyPricingMode` does not correctly preserve the calculated breakdown for old jobs with `pricing: null`, those jobs' prices will change. The fix: explicit null-check with a comment explaining the legacy treatment.

- **New jobs failing to price**: If `applyPricingMode` hard-fails on `null` and a new job somehow reaches pricing with mode unset, the quote won't generate. Mitigation: the slot gate ensures mode is asked, so this is a "should never happen" — but the code should fail safely (log + fallback) rather than crash.

### User data

- **SoW state divergence**: If `getUnansweredChecklistQuestions` changes but the voice client's question logic doesn't align, required slots may be asked twice or not at all. Mitigation: the client already uses `getUnansweredRequiredChecklistQuestions`, which builds on the function we're changing — so the change is automatically synchronized.

### Migrations

- None required. The `pricing` field is already nullable in the schema and database.

## Derived criteria

What I understood the human to be asking for:

1. A duration mention ("four days") on its own must *not* satisfy the pricing/duration slot — the slot should only be satisfied when `pricing.mode` is explicitly set.

2. `resolvePricingMode` should return `null` (not default to "calculated") when `pricing` is `null`, so the caller knows the mode was never set.

3. `concludeOrAskRequired` should still ask for the pricing mode when it's unset, even if `duration_days` is present.

4. Quote generation should handle the `null` case explicitly — for new jobs it's an error state, but for legacy jobs with `pricing: null` it should keep producing the calculated breakdown exactly as before.

5. Acceptance tests should cover:
   - Incidental duration mention leaving the slot unanswered
   - The wrap-up asking for mode when it's missing
   - `resolvePricingMode` returning `null` appropriately
   - Legacy jobs continuing to price correctly

6. The change is *defensive only* — it prevents a slot from being marked answered when it wasn't actually asked. It does not change how the question is asked, how the LLM sets the mode, or any UI behaviour.
