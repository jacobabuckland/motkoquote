# Issue #306: Disclosure primitive, applied to Settings

**Auditing branch:** `factory/306`

## Problem

The Settings page renders every section fully expanded. On a 380px viewport, the bank details block alone occupies most of a screen, pushing everything below it out of reach. There is no way to scan what Settings contains without scrolling past the contents of everything it contains. Motko is a mobile-first product for trades using it one-handed on a job. A settings page that cannot be scanned is a settings page whose features are undiscoverable.

## Why combine the primitive and consumer

This ticket ships the disclosure component AND its first consumer (Settings) as one change. Shipping a primitive with no consumer repeats this codebase's most common failure pattern: @capacitor/haptics installed but never imported, nine motion tokens defined but never read, Button's aria-busy wired but passed by none of 47 async actions. A collapsible primitive with no consumer would be the fifth entry on that list.

## Scope: what changes

1. **New disclosure component** (`src/components/ui/disclosure.tsx`):
   - Accessible collapsible section with `<button>` header
   - `aria-expanded` and `aria-controls` attributes
   - Keyboard operable with visible focus ring
   - Visible pressed state (already established pattern in Button component)
   - Consumes motion tokens from `globals.css` (--dur-base, --ease-standard) for expand/collapse transition
   - Respects `prefers-reduced-motion` (content appears/disappears without animation)
   - Sections toggle independently — no accordion behavior
   - Fires light haptic on toggle via `@capacitor/haptics`, guarded so web build doesn't throw
   - This is the first consumer of the haptics dependency that has been installed but never imported

2. **Persistent disclosure state**:
   - Store open/closed state in Capacitor Preferences (native) / localStorage (web)
   - Keyed per section, not server-side (this is per-device UI state)
   - Pattern: same storage abstraction as guest session (try Preferences, fall back to localStorage, degrade silently on failure)

3. **Apply to Settings page**:
   - Wrap existing Settings sections in disclosure component
   - "Update bank details" (PayoutDetailsSection) collapsed by default
   - All other sections (StripeConnectSection, FeesStatementSection, ReferralSection, SettingsClient, DeleteAccount) remain expanded by default
   - No change to section content, copy, or internal behavior

## Files

### New files
- `src/components/ui/disclosure.tsx` — the disclosure primitive
- `src/lib/disclosure-storage.ts` — persistent state layer (Preferences/localStorage abstraction)

### Modified files
- `src/app/settings/page.tsx` — wrap sections in disclosure component
- `src/lib/haptics.ts` — already exists; will be imported by disclosure (first consumer)

## Explicitly out of scope

- Business page sections (separate ticket)
- Any change to content, copy, or behavior of Settings sections themselves — this ticket only wraps them
- Making any Settings section other than bank details collapsible
- Haptics anywhere other than the disclosure header (do NOT retrofit the other 47 async actions)
- Any change to what Settings contains or the order of its sections
- Syncing disclosure state across devices
- Server-side storage of disclosure preferences

## Edge cases

1. **Validation error in a collapsed section** — OUT OF SCOPE FOR THIS ITEM,
   deferred to a follow-up.

   This section originally required the disclosure to auto-expand on submit
   failure and scroll itself into view. It contradicted the "Explicitly out of
   scope" section above: auto-expanding on validation failure requires
   `PayoutDetailsSection` to report its validation state to its wrapper, which
   is a change to the behaviour of a Settings section, and this ticket only
   wraps them. The acceptance tests agree with the out-of-scope section — they
   cover every other criterion and never test this one.

   Removed from the contract rather than left contradicting itself, because a
   requirement that cannot be built without breaking another requirement
   regenerates the same finding on every review cycle. It did so twice.

   A follow-up item can design the API for it — a controlled `open` prop or an
   imperative handle — with a real form in front of it.

2. **Unsaved changes**:
   - Collapsing must not discard form state
   - React state in wrapped component survives collapse

3. **Deep link or anchor targeting a collapsed section**:
   - Must expand the section containing the target
   - Same no-overwrite rule — doesn't persist as "open" preference

4. **Stored preference for nonexistent section**:
   - Ignored silently, not an error
   - Stale keys accumulate but don't break anything

5. **Storage unavailable or write fails**:
   - Fall back to default state (bank details collapsed, others expanded) silently
   - Disclosure must never fail closed on a storage error
   - Continue working in-memory for the session

6. **Only one section on page**:
   - Still collapsible, no special case
   - Same behavior as multiple sections

7. **prefers-reduced-motion**:
   - Content appears/disappears instantly (no transition)
   - Already handled by globals.css media query that sets all durations to 0.01ms

## Risks

- **No schema migration required** — this is client-side only state
- **No money logic involved** — purely presentational UI state
- **No user data storage** — preferences are local device state only
- **Breaking existing sections**: Wrapping sections in disclosure must not break their internal forms/actions. Test that PayoutDetailsSection form submission still works when wrapped.
- **Haptics import pattern**: This establishes the guard pattern for every future haptics consumer. Get it right: `if (!Capacitor.isNativePlatform()) return;` before any haptics call.

## Behavior specification

### Default state
- PayoutDetailsSection: **collapsed**
- All other sections: **expanded**

### Transition
- Duration: `var(--dur-base)` (220ms from globals.css)
- Easing: `var(--ease-standard)` (cubic-bezier(0.2, 0, 0, 1) from globals.css)
- NO hardcoded millisecond values in the component
- Respects `prefers-reduced-motion: reduce` (instant show/hide)

### Accessibility
- Collapsed: content not in accessible tree, not focusable
- Expanded: normal tab order
- `aria-expanded="true"` when open, `"false"` when closed
- `aria-controls` links button to content region
- Focus ring visible on keyboard navigation
- Pressed state visible on touch

### Haptics
- Fire on every toggle (both expand and collapse)
- Use `haptics.tap()` (light impact)
- Guarded: no error on web, fires only on native platform
- Pattern to establish: same guard as in `src/lib/haptics.ts` itself

### Storage
- Key format: `motko.disclosure.<section-id>` (e.g. `motko.disclosure.payout-details`)
- Value: `"open"` or `"closed"`
- Native: Capacitor Preferences
- Web: localStorage
- Degrade silently if unavailable (Safari private mode, quota exceeded)
- Read on mount, write on every toggle
- Survives app restart

### Layout
- No layout shift when section toggles
- Reserve space for header when collapsed
- Animate only the content region height
- Surrounding sections flow smoothly

## Derived criteria

What I understood the human to be asking for:

1. **Build an accessible disclosure component** that can collapse/expand sections with proper ARIA attributes, keyboard support, and visible focus/pressed states
2. **Consume the existing motion tokens** from globals.css instead of introducing new durations — specifically --dur-base and --ease-standard
3. **Make it the first real consumer of @capacitor/haptics** which has been installed but never used, with proper guard so it doesn't throw on web
4. **Persist the open/closed state locally** (not server-side) using Capacitor Preferences on native and localStorage on web, degrading silently on failure
5. **Apply it to the Settings page** with bank details collapsed by default and everything else expanded, without changing any section content or behavior
6. **Handle edge cases gracefully**: unsaved changes survive collapse, storage failures fall back to defaults silently. (Validation-error auto-expand was removed from this criterion — see Edge cases §1.)
7. **Establish the reusable pattern** for disclosure UI that the Business page and later surfaces will copy — this is the reference implementation

The component must be production-ready: no hardcoded durations, proper accessibility, graceful degradation, and zero breaking changes to existing Settings functionality.
