# Spec: Sort the active jobs list by urgency, not recency

**Issue:** #300  
**Status:** BLOCKED - Decision needed

AMBIGUOUS: No definition of "urgency" exists in the codebase; defining job ranking order is a product decision.

## Problem

The jobs list (at `/jobs?filter=in_progress`) currently sorts by recency - the most recently touched job appears first. This ordering reflects which job the contractor last edited, not which job needs attention most urgently.

In practice, this means:
- A £900 invoice unpaid for thirty days can sit below a draft quote edited yesterday
- An overdue invoice can be buried below recently-sent quotes
- The contractor sees activity recency, not business urgency

The jobs-list filter ticket (#TBD) removes terminal states (paid, declined, archived) from the default view. Once only live work remains visible, the **order of that live work** becomes the primary signal directing contractor attention - but the current recency-based sort does not align with business priorities.

Current implementation:
- Jobs are sorted by `sortAt` timestamp in `src/lib/job-history.ts:sortByRecency()`
- `sortAt` is a waterfall: `paidAt ?? accepted_at ?? sent_at ?? created_at`
- This produces reverse-chronological ordering - most recent activity first

## Why this is blocked

There is no definition of "urgency" in the codebase or spec. Creating one requires product judgement about:

1. **Which states are most urgent** - should overdue invoices rank above unpaid-but-not-overdue invoices? Above sent quotes? Above drafts?
2. **How to break ties within a state** - should age (oldest first) or value (highest first) determine order among multiple unpaid invoices?
3. **Whether the ordering should be visible** - if the list doesn't sort by recency, contractors will expect to see their recently-edited job at the top and may think the list is broken when it isn't
4. **Whether "overdue" is a first-class state** - the codebase has `isDateOverdue()` for invoices, but it's not currently used in job sorting or bucket assignment

An agent implementing this ticket without guidance would either:
- Invent an arbitrary weighting (which becomes the silent product decision about what contractors pay attention to)
- Halt on ambiguity

Better to halt deliberately and surface the decision to a human.

## Scope (once a decision is made)

**What would change:**
- The sorting function in `src/lib/job-history.ts` - replace `sortByRecency()` with `sortByUrgency()` or similar
- The `sortAt` field computation in `normalizeHistoryJob()` would be replaced with an urgency score or multi-key sort
- Potentially: add "overdue" as a visible bucket or status in `JobBucket` / `StatusLabel` types
- Potentially: UI changes to make the sort order visible (section headers, sort order explanation, visual grouping)

**What would remain the same:**
- Which jobs appear in each filter (filtering logic)
- The Paid and Archived views (recency is appropriate there)
- The underlying data model (no migrations needed)

## Files that would be touched

- `src/lib/job-history.ts` - core sorting logic
- `src/lib/job-history.test.ts` - test coverage for new sort
- `src/app/jobs/page.tsx` - potentially to label/explain the ordering
- Potentially `src/lib/job-stages.ts` if "overdue" becomes a first-class status
- Potentially `src/components/ui/status-chip.tsx` if new statuses are added

## Edge cases

1. **Empty states** - a contractor with only drafts sees no change in behavior
2. **Ties** - multiple jobs in the same urgency tier need a secondary sort (age? value? creation time?)
3. **State transitions** - a job moving from "sent" to "overdue" changes its position in the list; contractor needs to understand why
4. **No due date on invoice** - some invoices may lack a due_date; how should they rank against overdue invoices?

## Risks

**Low implementation risk** - this is sorting logic, not money movement or data integrity. A wrong sort order is immediately visible and reversible.

**High product risk** - the sort order is a silent prioritization of contractor attention. Getting it wrong means:
- Overdue invoices go uncollected because they're not visible
- High-value work gets deprioritized by accident
- Contractors lose trust in the dashboard if the order feels arbitrary

## Out of scope (regardless of decision)

- Notifications, chasing, or automated actions triggered by urgency
- Changes to which jobs appear in each filter
- Sort order in Paid or Archived views (recency is correct there)
- Any backend schema changes (no migrations needed)

## Candidate urgency ordering (for consideration)

The issue suggests one possible ranking:

1. Overdue invoices (oldest first)
2. Invoices awaiting payment, not yet overdue (oldest first)
3. Quotes sent and unanswered (oldest first)
4. Contracts sent and unsigned (oldest first)
5. Drafts (oldest first or most recent first)

This would:
- Put outstanding money at the top (overdue, then unpaid)
- Put waiting-on-customer items in the middle
- Put your-move-next items at the bottom
- Within each tier, use age as the tiebreaker

Alternative: use value instead of age within tiers (£4,000 invoice five days overdue vs £200 invoice thirty days overdue).

## Derived criteria

Once a human decides the urgency ordering:

- [ ] Active jobs (in_progress filter) sort by the defined urgency order, not by recency
- [ ] Jobs in the same urgency tier use a defined tiebreaker (age, value, or creation time)
- [ ] The ordering is either visually explained or organized into labeled sections
- [ ] The sort order does not apply to Paid or Archived views (recency remains correct there)
- [ ] Tests verify the new sort order against the defined tiers

## DECISION NEEDED

**Question:** How should active (in-progress) jobs be ranked when terminal states are filtered out?

**Options:**  
(a) Rank by money urgency: overdue invoices → unpaid invoices → sent quotes → sent contracts → drafts, with oldest-first tiebreaker within each tier  
(b) Keep recency sorting (most recently touched first) as the signal contractors already understand  
(c) Make sort order user-configurable (urgency vs recency toggle)

**Recommendation:** Option (a) - money urgency. The dashboard exists to direct contractor attention toward revenue collection and customer response. Overdue invoices are money being left on the table; putting them at the top makes the loss visible. Recency reflects activity, not priority. If visibility is a concern, add section headers or a short explanation ("sorted by what needs you most").
