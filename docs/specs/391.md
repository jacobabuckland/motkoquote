# Issue #391: Gate acceptance tests that read source text, or import another test file

## Problem

`AGENTS.md` forbids asserting on source text, under **"Never assert on source text"**. Five acceptance tests did it anyway across #351, #356 and #359 in two days, and each cost a full factory cycle. The rule exists; nothing enforces it, and an acceptance test is frozen the moment the PM commits it — so by the time anyone downstream notices, no one is permitted to fix it.

The cost is not the wasted cycle. It is that production code is now shaped by regexes: `src/app/settings/page.tsx` carries a namespace import purely so an `indexOf` finds the right occurrence, and the comment explaining that has to avoid spelling the component's own name, because the test matches prose too. None of that is behaviour a user can perceive.

The single tell shared by all five is an acceptance test reading a file under `src/` and matching its text.

A sibling defect has the same shape, the same moment, and the same remedy: an acceptance test that **imports another test file**. #352's re-derive froze `await import("@/../../tests/regression/signup-referral-field.test")`, which does not resolve and took the whole file down. That is filed as #393, which is documentation-only and explicitly defers the mechanical half here — two cards each adding a rule to one script is the collision #393's own third rule warns about.

## Scope: what changes

A new script, `scripts/factory/check-acceptance-static.sh`, taking one acceptance-test path and emitting a verdict. Pure: one file in, a verdict out, no network — so the rule is exercised by tests rather than only in anger, exactly as `check-deliverable.sh` is.

It reports two findings, each a hard failure:

**1. `::source-text-read::` — the test reads a file under `src/`.**
Matched on a read call whose argument contains a `src/` path: `readFileSync`, `readFile`, `fs.promises.readFile`, and the `node:fs` aliases of each. The path may be a string literal or built with `join`/`resolve`; matching is on the presence of `src/` within the call's argument text, not on a resolved path, because the script does not execute the test.

**2. `::test-file-import::` — the test imports another test file.**
Matched on a static `import` or dynamic `import()` whose specifier contains `tests/` or ends `.test` / `.test.ts` / `.test.tsx`. Importing a test file executes that suite inside this one, and the path forms that look right mostly are not.

The script exits non-zero when either fires, printing the offending line and its number.

### Wiring into the PM job

One new step in `.github/workflows/factory-pm.yml`, placed **immediately after** the existing lint step and **before** "A runnable deliverable must be invoked by its acceptance tests", so a test is rejected for this before any more expensive check runs. On failure it follows the established shape of the neighbouring steps exactly: print the log, write a body with `scripts/factory/decision-section.sh "$ISSUE" needs-spec`, comment on the issue, add `blocked`, remove `needs-spec`, exit 1.

### The allowlist, and why it must exist

Two standing registries legitimately walk `src/`:

- `tests/acceptance/99.test.ts` — the public-API-route registry.
- `tests/acceptance/200.test.tsx` — asserts every authenticated route has a `loading.tsx`.

`AGENTS.md` blesses both by name as standing registries with an intended registration path. A naive rule breaks them, and "never resolve a registry failure by moving the thing being registered out of its view" applies with equal force to the registry itself.

So the script carries an explicit allowlist of exactly those two paths, written out with a comment naming why each is on it — the same shape as the `exclude` list in `vitest.config.ts`, which names its two entries and explains both. An allowlist that can be extended silently is not a gate; each addition must be a visible diff a human reads.

**The allowlist is matched on the full path, never on a pattern.** A glob like `tests/acceptance/*registry*` would let the sixth instance name itself around the check.

## Explicitly out of scope: what does not change

- **The five existing tests.** They are frozen and all five are now satisfied or scheduled. Unpicking them is a bigger job than this ticket, and this is about stopping the sixth.
- **`tests/regression/` and `tests/integration/`.** A regression test is repairable downstream, so a brittle one is a nuisance rather than a permanent constraint. The whole justification for a hard gate is the freezing, which only applies to `tests/acceptance/`.
- **Any check that the test is *good*.** This catches one mechanical tell. A test can avoid `readFileSync` entirely and still assert something unobservable.
- **Widening to other filesystem APIs** (`glob`, `readdir`, `import.meta.glob`). The two registries above are the legitimate directory-walkers and they are allowlisted; adding more matchers now would fire on them and on nothing else recorded.
- **`AGENTS.md`'s existing "Never assert on source text" section.** Its worked example stays; two more are added (below), and nothing is removed.

### The two worked alternatives added to AGENTS.md

The rule currently says what not to do and gives one example of what to do instead. Two cases keep recurring and need their own, because in both the author reached for source text after failing to see the DOM equivalent:

**Asserting section order.** Render, then read the headings in document order:

```tsx
const headings = screen.getAllByRole("heading").map((h) => h.textContent);
expect(headings.indexOf("Rate cards")).toBeLessThan(headings.indexOf("Danger zone"));
```

**Asserting a section is collapsed.** Read the control's state, not the markup that produced it:

```tsx
expect(screen.getByRole("button", { name: "Rate cards" })).toHaveAttribute(
  "aria-expanded",
  "false",
);
```

Both describe what a user can perceive, and both survive any correct refactor of the JSX.

## Edge cases

- **A test that mentions `readFileSync` inside a comment or a string.** It fires. This is the deliberate direction: #306 was itself burned by a regex counting a value inside a comment, and the honest answer is that a shell-level scanner cannot parse TypeScript. A false positive costs one PM re-run and a visible message; a false negative costs a frozen test forever. Where a test genuinely needs the word, the allowlist is the escape hatch and it is a reviewed diff.
- **A test reading a fixture under `tests/`.** Does not fire — the rule is `src/` specifically. Fixtures are test-owned data, not production source.
- **A test reading `package.json` or a migration.** Does not fire. Neither is `src/`, and asserting a migration's presence is a legitimate structural claim.
- **An acceptance test that does not exist** (the item is `AMBIGUOUS:` and froze no tests). The step must not run; it is guarded by the same resolved-path output the neighbouring steps use, and an empty path is a hard error rather than a scan of nothing. The existing "fail before implementation" step carries a comment about exactly this trap — an empty `TESTS` value once ran the entire suite.
- **Both findings in one file.** Both are reported, in one message. A gate that stops at the first finding costs a second cycle to surface the second.
- **The two allowlisted registries are edited to add an entry.** Still allowlisted, so still passes. Adding an entry through a registry's intended registration path is registration, not repair, and `AGENTS.md` says so.

## Risks

- **A false positive blocks an item that was fine.** Mitigated: the message names the line and the file, the fix is either rewriting the assertion (which is the point) or a reviewed allowlist entry, and it costs a PM re-run rather than a cycle.
- **The allowlist becomes the escape hatch of choice.** This is the real risk and it is why the allowlist is two hard-coded paths with per-entry comments rather than a pattern. If it grows past three or four entries, the rule is wrong and should be revisited rather than extended.
- **No money, auth, migration or customer-facing surface is touched.** This is factory tooling only.

## Derived criteria

- `scripts/factory/check-acceptance-static.sh` exists and is executable
- Given a test file containing `readFileSync` of a path under `src/`, it exits non-zero and its output contains `::source-text-read::`
- Given a test file containing `fs.promises.readFile` of a path under `src/`, it exits non-zero
- Given a test file containing a static `import` whose specifier contains `tests/`, it exits non-zero and its output contains `::test-file-import::`
- Given a test file containing `await import("@/../../tests/regression/signup-referral-field.test")` — the exact #352 line — it exits non-zero
- Given a test file that reads a fixture under `tests/`, it exits zero
- Given a test file that reads `package.json`, it exits zero
- Given a clean acceptance test that renders and queries the DOM, it exits zero
- Given `tests/acceptance/99.test.ts`, it exits zero (allowlisted)
- Given `tests/acceptance/200.test.tsx`, it exits zero (allowlisted)
- Given a file containing both findings, the output contains both markers
- Given a path that does not exist, it exits non-zero with a distinct error naming the missing file
- The allowlist in the script is a list of exact paths, not a glob or regex
- `.github/workflows/factory-pm.yml` invokes the script on the resolved acceptance-test path, after the lint step and before the deliverable step
- The failing path in that step adds the `blocked` label, removes `needs-spec`, and comments on the issue, matching the neighbouring steps
- `AGENTS.md` contains a worked alternative for asserting section order that uses `getAllByRole("heading")`
- `AGENTS.md` contains a worked alternative for asserting a section is collapsed that uses `aria-expanded`
- No existing test in `tests/acceptance/` is modified by this item
