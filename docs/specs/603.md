# RAIL-3: Rail-value copy — scheduling and chasing, never speed

## Problem
Until settlement speed is measured and proven faster than a customer's own bank transfer, any speed claim is one that the first two jobs disprove. The rail's real advantages are scheduling and automatic chasing, not settlement speed.

This item prevents speed claims from appearing in shipped copy by enforcing a CI check against a forbidden-phrase list. Automatic invoice-level chasing is true today and may be claimed; stage-level chasing claims are held until STAGE-3 ships.

## Scope: what changes
- A new CI check script (`scripts/ci/check-forbidden-copy.sh`) scans trade-facing surfaces under `src/app/` for forbidden phrases that claim payment speed advantages.
- The CI workflow gains a `forbidden-copy` job alongside the existing `check-spec-citations` job.
- The check runs on every PR and blocks merge if forbidden phrases are detected.

## Explicitly out of scope
- The marketing site (handled separately).
- Preventing all uses of words like "fast" or "quick" — only specific patterns claiming payment speed advantages are forbidden.
- Stage-level chasing claims require human review to distinguish from invoice-level claims; the check flags obvious patterns but cannot catch all cases.

## Files
- scripts/ci/check-forbidden-copy.sh (new)
- .github/workflows/ci.yml (modify)

## Edge cases

### Forbidden phrase detection
The script checks for patterns that claim payment/settlement speed advantages:
- "faster payment", "faster settlement", "faster than bank transfer", "quicker payment"
- "instant payment", "instant settlement", "immediate payment", "immediate settlement"
- "quick payment", "rapid settlement", "speedy payment"
- Phrases with "speed" as an advantage: "payment speed", "settlement speed"

### Allowed phrases
The script must NOT flag:
- "automatic chasing" or "automated chasing" (invoice-level chasing exists and may be claimed)
- "scheduling" as a rail advantage
- Technical comments about timing (e.g., "the fee left with the payment, at the same instant")
- Uses of "fast" or "quick" in contexts unrelated to payment speed (e.g., "fast checkout", "quick setup")

### Stage-level chasing
Claims about automatic stage-level chasing should be flagged (until STAGE-3 ships), but distinguishing stage-level from invoice-level claims requires context that a grep cannot reliably provide. The check flags obvious patterns but may require human review.

### False positives
The script should minimize false positives by:
- Checking phrases in context (not just isolated words)
- Allowing technical/internal comments that don't appear in rendered UI
- Providing clear error messages that name the forbidden phrase and the file

### Empty state
If no trade-facing source files exist under `src/app/`, the check passes (nothing to scan).

### Failure mode
If the script finds forbidden phrases:
- Exit with status 1
- Print each violation with file path and line number
- Provide a clear error message explaining why the phrase is forbidden

## Risks
- **False negatives**: The check relies on pattern matching and cannot catch every possible way to claim speed advantages. Human review remains necessary.
- **False positives**: Overly broad patterns might flag legitimate uses of words like "instant" or "immediate" in non-payment contexts. The patterns must be specific enough to minimize this.
- **Maintenance burden**: As new payment surfaces are added, developers must be aware of the constraint. The CI check provides immediate feedback, but the forbidden-phrase list may need updating as new patterns emerge.
- **Stage-level chasing ambiguity**: Distinguishing stage-level from invoice-level chasing claims is difficult for automated checks and may require manual review.

## Derived criteria
As the PM agent, I understood the human's request as:

1. Create a CI script that scans trade-facing source files for forbidden phrases claiming payment speed advantages.
2. The script should flag specific patterns like "faster payment", "instant settlement", "quicker than bank transfer", etc.
3. The script should NOT flag allowed phrases like "automatic chasing" (for invoices) or "scheduling".
4. Add a CI job to run this check on every PR, blocking merge if violations are found.
5. The check follows the same pattern as the existing `check-spec-citations` job.
6. The scope is limited to `src/app/` (trade-facing surfaces); the marketing site is out of scope.
7. The goal is to prevent future speed claims from being added, not necessarily to fix existing ones (though any existing violations would fail the new check).
