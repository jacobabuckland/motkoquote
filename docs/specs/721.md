# Issue #721: Motko must ask who the quote is for, and the full materials question

## Problem

A call was reported on 12 Sep where the quote came back with the customer's name, materials supply, and agreed costs all missing — not because the call ended early, but because Motko never asked. Two separate failures:

1. **Customer name** exists only as a paragraph of prompt instruction with no askQuestion call, no enforcement, and no record of whether the model complied. A call wraps cleanly today with no customer name.

2. **Materials** is asked, but only one part: who supplies. The live call on 12 Sep revealed two more parts being silently skipped: roughly how much is needed, and what specifically.

## Scope

### Customer name

Promote `customer_name` from a prompt-only instruction to a first-class required checklist slot. This means:

- Adding it to `CHECKLIST_QUESTION_IDS`
- Adding it to `REQUIRED_CHECKLIST_QUESTIONS`
- Adding it to the checklist questions map and slot labels
- Updating the answeredness check in `getUnansweredChecklistQuestions`
- Updating the tool parameters to include it in the `declined_slots` enum

The existing `CUSTOMER_NAME_QUESTION` constant ("Who's this quote for — the customer's name?") is already the right phrasing and stays unchanged. The wrap detour (`concludeOrAskRequired`) already gates on `getUnansweredRequiredChecklistQuestions`, and #716 routed the last two exit paths through that gate, so promoting the slot is sufficient — no component changes needed.

### Materials (three parts)

Widen `materialsSupplySchema` to capture all three parts of the materials question:

1. **Who supplies** (responsibility) — already exists ✓
2. **Roughly how much is needed** (quantity_guidance) — NEW field, nullishString. "You work it out" / "I'll send it over" / "standard for a three-bed rewire" are all storable answers, distinct from silence.
3. **What specifically** (materials_detail) — NEW field, nullishString. Free-text description of what materials are involved, e.g. "cable, sockets, consumer unit".

Update the answeredness check for `materials_supply`: the slot is answered only when BOTH `responsibility` AND `quantity_guidance` are present. The current check (`if (!sow.materials_supply)`) treats the object's presence as sufficient, which allows `{ responsibility: "contractor" }` to answer the slot without quantity or detail.

Update `CHECKLIST_QUESTIONS.materials_supply` to reflect all three parts, and update the tool parameter description to guide the model to fill all three.

## Explicitly out of scope

**Contact details and site address** remain non-blocking. A contractor mid-call does not know their customer's email off by heart (Jacob, 12 Sep). Motko takes them if volunteered but never holds a wrap for them. The capture path already exists in the quote editor (Site address, email, phone fields, `hasContactChannel`, and a graceful no-channel send).

**The existing `customer_details_guard.ts` module** is unchanged. It flags missing name/contact on the job page, but does not make the model ask. This item makes the model ask by promoting the slot to the required checklist.

**The `askedRequiredSlotsRef` evidence** (which slots were asked) already exists and reaches the server, where it is used only for analytics. Per AGENTS.md, a signal that must change behaviour cannot terminate in telemetry. That remains true and is unchanged by this item — the enforcement is the checklist, not the telemetry.

## Files

- `src/lib/schemas/job.ts` (modify) — add `quantity_guidance` and `materials_detail` to `materialsSupplySchema`
- `src/lib/schemas/sow.ts` (modify) — add `customer_name` to checklist IDs, update materials answeredness check, update tool parameters

## Edge cases

### Customer name

- **Empty string** or **whitespace-only** is treated as missing (same as `undefined`).
- A contractor declining to give the name (`declined_slots: ["customer_name"]`) marks it declined and stops re-asking, but still gates the wrap — the slot is unanswered, not answered "no".
- `customer_name` is `string | undefined`, never `null`. The re-derivation notes are explicit: `SowState.customer_name` is `nullishString`, which transforms `null` → `undefined` on parse. Use `undefined` in tests, never `null`.

### Materials

- **Responsibility alone is not enough.** `{ responsibility: "contractor" }` without `quantity_guidance` leaves the slot unanswered.
- **Quantity alone is not enough.** `{ quantity_guidance: "you work it out" }` without `responsibility` leaves the slot unanswered.
- **Both present** answers the slot, regardless of what `materials_detail` holds. `materials_detail` is supplementary; the two required parts are responsibility and quantity.
- **"You work it out"** is a legitimate storable answer for `quantity_guidance`, distinct from the field being absent. It means the contractor deferred the calculation, not that the question was never asked.
- The existing arrays (`contractor_supplied`, `customer_supplied`) remain and keep their meaning: which specific items, where that was said. They are not replaced by `materials_detail`.

## Risks

None. Both changes are additive schema extensions that parse existing rows unchanged:

- `customer_name` already exists in `SowState`; this promotes it to a required slot without changing its type or storage.
- `quantity_guidance` and `materials_detail` are optional fields on `materialsSupplySchema`. Existing rows with `materials_supply` set will parse with the new fields as `undefined`, which is the correct interpretation of data captured before these fields existed.

No migration is needed.

## Derived criteria

### Customer name promotion

- `customer_name` appears in `CHECKLIST_QUESTION_IDS`
- `customer_name` appears in `REQUIRED_CHECKLIST_QUESTIONS`
- `CHECKLIST_QUESTIONS` has an entry for `customer_name` (the existing `CUSTOMER_NAME_QUESTION` text)
- `CHECKLIST_SLOT_LABELS` has a terse label for `customer_name`
- `getUnansweredChecklistQuestions` treats `customer_name` as unanswered when missing (empty, whitespace-only, or undefined)
- The tool parameters enum for `declined_slots` includes `"customer_name"`
- A SoW with all other required slots answered but no `customer_name` is reported as having one unanswered required slot
- A SoW with `customer_name` set (non-empty, non-whitespace) is not reported as missing it

### Materials widening

- `materialsSupplySchema` gains two new fields: `quantity_guidance` (nullishString) and `materials_detail` (nullishString)
- `materials_supply` is considered unanswered when only `responsibility` is set (no `quantity_guidance`)
- `materials_supply` is considered unanswered when only `quantity_guidance` is set (no `responsibility`)
- `materials_supply` is considered answered when both `responsibility` and `quantity_guidance` are present, regardless of `materials_detail`
- `CHECKLIST_QUESTIONS.materials_supply` mentions all three parts (who supplies, how much, what specifically)
- The tool parameter description for `materials_supply` guides the model to set all three parts
- Existing rows with `materials_supply` set but no `quantity_guidance` parse successfully with `quantity_guidance: undefined`

### Integration

- A SoW with `customer_name` missing and `materials_supply` having only `responsibility` reports two unanswered required slots
- A SoW with `customer_name` set and `materials_supply` having both `responsibility` and `quantity_guidance` reports zero unanswered required slots (among these two)
