# SUB-4: A failed subscription payment leaves the account read-only

## Problem

A subscription payment will fail — an expired card, a declined charge. When this happens, the trade's account must become read-only: existing jobs, quotes, contracts and invoices remain accessible, but nothing new can be created. Locking a trade out of signed contracts over £9.99 is a support call and a bad story.

## Scope

Add a read-only mode triggered by Stripe subscription failure states (`past_due` or `unpaid`):

1. **Predicate** — add `isSubscriptionReadOnly` to `src/lib/subscription.ts` that returns true when `subscription_status` is `'past_due'` or `'unpaid'`. Read state from `subscription_projection` table, never from a local boolean or a live Stripe API call.

2. **Guard creation actions** — refuse these server actions when subscription is read-only:
   - `createInvoice`, `createContract` in `src/app/dashboard/actions.ts`
   - `createManualJob`, `createRealtimeSession`, `sendQuote` in `src/app/jobs/actions.ts`

3. **UI banner** — show a persistent banner explaining the read-only state and linking to payment fix. Similar to `OfflineBanner`, appears app-wide when subscription is in failed state.

4. **Customer surfaces unaffected** — quote acceptance, contract viewing, invoice payment all remain functional. These are reached by the trade's **customer**, not the trade, and Motko's billing dispute with the trade is not the customer's problem.

5. **Restoration** — changing `subscription_status` back to `'active'` or `'trialing'` (via webhook when payment is fixed) restores full access without manual intervention.

## Out of scope

- Dunning schedule (Stripe's responsibility)
- Subscription cancellation (SUB-6)
- Modifying read state of existing resources (all remain viewable as-is)
- Customer-facing actions: `acceptQuote`, `declineQuote` in `src/app/q/[id]/actions.ts` must continue working

## Files

All files that change:

- `src/lib/subscription.ts` (modify) — add `isSubscriptionReadOnly` predicate
- `src/app/dashboard/actions.ts` (modify) — guard `createInvoice`, `createContract`
- `src/app/jobs/actions.ts` (modify) — guard `createManualJob`, `createRealtimeSession`, `sendQuote`
- `src/components/ui/subscription-status-banner.tsx` (new) — banner component explaining read-only state
- `src/app/layout.tsx` (modify) — add `SubscriptionStatusBanner` to root layout

Call sites that import the guarded actions:
- `src/app/dashboard/create-invoice-form.tsx` (no change to file, but will see error from action)
- `src/app/dashboard/create-contract-form.tsx` (no change to file, but will see error from action)
- Any other components calling the guarded actions (errors propagate from action layer)

## Edge cases

- **No subscription projection row** — trade hasn't completed setup or subscription not yet created. Treat as non-blocking (allow creation) since blocking uninitialized state would lock out new signups.
- **Subscription status is null** — same treatment as missing row, allow creation.
- **Subscription status is `'canceled'`** — not a failed payment, so not read-only. Cancellation is SUB-6's scope.
- **Subscription status is `'trialing'`** or `'active'`** — normal states, allow all creation.
- **Customer viewing their own quote/contract/invoice** — never blocked, regardless of contractor's subscription state.
- **Restoring payment** — webhook updates `subscription_status` to `'active'`, predicate immediately returns false, creation actions unblock.

## Risks

- **Incorrect blocking** — if the predicate is too broad (e.g. checking wrong status values) or applied to wrong actions (e.g. customer actions), it breaks legitimate flows.
- **State read timing** — predicate must read current projection state on every check, not cache it, or restored payment won't unblock immediately.
- **Missing call sites** — if any creation action isn't guarded, that path bypasses read-only mode. The acceptance tests exercise each named action.

## Derived criteria

What I understood from the spec:

1. A predicate function `isSubscriptionReadOnly(contractorId, client)` returns true when `subscription_projection.subscription_status` is `'past_due'` or `'unpaid'`, false otherwise.
2. Each creation action (`createInvoice`, `createContract`, `createManualJob`, `createRealtimeSession`, `sendQuote`) reads contractor's subscription state and throws an error when read-only.
3. A banner component renders when subscription is read-only, explaining the state in customer-friendly terms ("update your payment method") with a link to Stripe billing portal or settings.
4. Customer actions (accepting/declining quotes, viewing contracts, paying invoices) continue working regardless of contractor's subscription status.
5. When subscription status returns to `'active'` or `'trialing'`, the predicate returns false and all creation actions resume.
6. Existing resources (jobs, quotes, contracts, invoices already created) remain readable in read-only mode.
