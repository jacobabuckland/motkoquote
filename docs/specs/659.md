# SUB-4: A failed subscription payment leaves the account read-only

## Problem

A subscription payment will fail — an expired card, a declined charge. When Stripe moves the subscription to `past_due` and then `unpaid`, the trade must not be locked out of their signed contracts and existing work. But they also cannot create new jobs or send new quotes/contracts/invoices until payment is restored. The account becomes read-only: existing work remains accessible, new work creation is refused.

## Scope: what changes

### 1. Subscription status predicate

Add `isSubscriptionReadOnly` to `src/lib/subscription.ts` that returns `true` when `subscription_status` is `past_due` or `unpaid`. This reads from the projection table that already exists; it never calls Stripe on page render.

### 2. Server action guards

Four creation paths must check the subscription status and refuse when read-only:

- `src/app/dashboard/actions.ts` — `createInvoice` and `createContract`
- `src/app/jobs/actions.ts` — `createManualJob` and `createRealtimeSession` (voice quote intake)

Each queries `subscription_projection` for the contractor, calls the predicate, and throws a descriptive error when read-only.

### 3. User-facing explanation

The dashboard or the affected forms must explain the read-only state in terms a person can act on: payment failed, update card details, contact support. The exact placement is implementation choice; the criterion is that a trade who hits this state sees why and what to do.

### 4. Customer surfaces remain unaffected

The customer's view of a contract (`src/app/c/[id]/`) and invoice pay page (`src/app/i/[id]/`) must work regardless of the trade's subscription status. Motko's billing dispute with the trade is not the customer's problem.

## Explicitly out of scope

- **The dunning schedule itself** — Stripe controls when `past_due` and `unpaid` are set
- **Cancellation** — that is SUB-6, not this item
- **Viewing existing jobs, quotes, contracts, invoices** — these must remain accessible; only creation is blocked
- **Quote acceptance by a customer** — `src/app/q/[id]/actions.ts` is customer-facing; the customer's action is unaffected by the trade's billing status

## Edge cases

### No subscription projection row

A contractor who signed up before subscription tracking was added has no `subscription_projection` row. Treat the absence as "not read-only" — the default is permissive. A trade without a row is unaffected, and the subscription creation flow (already shipped) populates it for all new signups.

### Subscription status is `null`

A projection row may exist with `subscription_status` null (if created before the webhook fired). Treat `null` as "not read-only". Only the explicit failed-payment states `past_due` and `unpaid` lock the account.

### Restoring payment

When the contractor updates their card and the next charge succeeds, Stripe moves the subscription to `active`. The webhook updates the projection, and the guard sees `active` rather than `past_due` — full access is restored without manual intervention. This is what the projection-based design guarantees.

### Customer attempts to accept a quote

This is explicitly out of scope above but worth calling out: `acceptQuote` in `src/app/q/[id]/actions.ts` is triggered by the customer, not the trade, so it must never check the trade's subscription status. A customer who agreed to a quote is not affected by motko's billing dispute with the trade.

**Where this is verified, and why not in the acceptance file.** The acceptance
test froze this as a structural check on `acceptQuote`'s arity
(`acceptQuote.length === 1`), which cannot prove the function does not query
`subscription_projection` internally — the exact defect the requirement exists
to prevent. That is a weak contract, and it is frozen: only this commit may
touch `tests/acceptance/`, and it was written before the weakness was seen.

The behavioural check therefore lives in
`tests/regression/accept-quote-subscription-independence.test.ts`, which builds
a contractor with `subscription_status: 'past_due'`, calls `acceptQuote`, and
asserts it succeeds. That file is listed under Files above and is part of this
item's deliverable, not incidental maintenance.

This is recorded here because QA raised it four times against an implementation
that was already correct, and the Engineer correctly refused each time — it
cannot edit a frozen file, and no implementation change can satisfy the ask.
The requirement is met; the verification is in the file named above. **A finding
that the behavioural test "should be in the acceptance file" is answered by this
paragraph and is not a defect.**

### Error messaging

The error thrown when a creation action is refused must be actionable: "Your subscription payment failed. Update your card details in Settings → Billing to restore access." Do not expose Stripe's raw status values (`past_due`, `unpaid`) to the user; translate them into user-facing language.

## Risks

- **Customer impact if the guard is placed wrong:** If the check is added to a layout or page that the customer reaches via a capability URL (`/c/[id]`, `/i/[id]`), it blocks the customer from viewing their own contract or paying their invoice. The guard must live in the server actions that **create** new work, not the pages that **view** existing work.
- **Concurrency with SUB-1 merge:** This item modifies `src/lib/subscription.ts`, which SUB-1 created. If SUB-1 is still in flight, coordinate the merge. But SUB-1 shipped as #658 on 6 Sep, so this is clear.

## Derived criteria

A trade with a failed subscription (`past_due` or `unpaid`) can:
- Open and view every existing job, quote, contract, and invoice
- Receive notifications about customer actions (quote accepted, contract signed, invoice paid)

But cannot:
- Create a new job (manual or voice intake)
- Create a new invoice from an accepted quote
- Create a new contract from an accepted quote

A customer of that trade can:
- View their contract at `/c/[id]` regardless of the trade's subscription status
- Pay their invoice at `/i/[id]` regardless of the trade's subscription status
- Accept or decline a quote (if it was sent before the subscription failed)

When the subscription payment is restored (status moves to `active`), the trade regains full access immediately without manual intervention.

The UI explains the read-only state in actionable terms: what happened, and how to fix it.
