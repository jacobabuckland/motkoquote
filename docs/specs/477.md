# FEE-10: Persist the reversed-settlement state the column already holds

## Problem

The `jobs.settlement_state` column exists on production (migration #499), and `planSettlementReversal` computes the correct reversal state, but nothing connects the two. The planner's verdict is computed and discarded, so a reversed settlement is indistinguishable from a live one in every query, on the fees statement, and in the money position. The rules are written down and enforceable — they are just not recorded.

## Scope: what changes

1. **Provide a runnable operator script** that persists a reversal state for a settled job. Reversals are rare and handled manually today, so a script is the proportionate caller.

   RUNNABLE: npx tsx scripts/admin/record-settlement-reversal.ts --job <id> --reversed-at <iso> [--partial]

   The script:
   - Reads the job and its current fee/settlement columns
   - Calls `planSettlementReversal` to compute the correct state
   - Writes `jobs.settlement_state` to the state the planner returned
   - Leaves all fee columns (`fee_amount_pennies`, `fee_net_pennies`, `fee_vat_pennies`) unchanged
   - Is idempotent: running it twice on an already-reversed job changes nothing
   - Refuses an unknown job ID with non-zero exit and writes nothing
   - Distinguishes reversal-before-settlement from reversal-after-settlement

2. **Update the fees statement** (`src/app/settings/fees-statement-section.tsx`) to fetch `settlement_state` alongside fee columns and label reversed settlements as such. The label includes the fee amount (which is kept) and makes clear the settlement was reversed.

3. **Update money position queries** (`src/app/jobs/money-position-actions.ts`) to fetch `settlement_state` and pass it to `summariseAccruedFees`, which already filters reversed settlements via `countsAsFutureRevenue`. This stops reversed settlements being counted as future revenue.

## Explicitly out of scope

- Anything about a processing fee. FEE-7 is dropped (#475). There is no `processing_fee_actual_pennies` column to write or display.
- The Stripe fee-reclaim guard (`tests/regression/settlement-reversal.test.ts` already asserts no call passes `refund_application_fee`). Do not assert the test still exists — that would be a brittle cross-file assertion.
- A refund webhook or any Stripe integration. The script is the only caller.
- Any contractor-facing refund UI. This is a ledger change only.
- The terms clause and PNL exclusion (#496) and the migration (#499) — already shipped.
- Disputes and chargebacks.
- Modifying `src/lib/settle-paid-job.ts`. That function handles initial settlement when a payment arrives, not reversals that happen afterward.

## Files

- `scripts/admin/record-settlement-reversal.ts` (new) — the entry point
- `src/app/settings/fees-statement-section.tsx` (modify) — fetch settlement_state and label reversed rows
- `src/app/jobs/money-position-actions.ts` (modify) — fetch settlement_state and exclude reversed settlements from money position
- `tests/acceptance/477.test.ts` (new) — the acceptance tests

## Edge cases

- **Unknown job ID**: Script exits non-zero, writes nothing.
- **Already-reversed job** (idempotency): Running the script a second time is a no-op — no state change, no error.
- **Reversal before settlement completed**: The script must accept `--reversed-at` timestamps before `jobs.paid_at` and record state `reversed_before_settlement`. No fee was charged, but the state must still be recorded and must differ from post-settlement reversals.
- **Partial reversal** (`--partial` flag): Keeps the full fee, not pro-rated. The state records that it was partial, but the fee columns are unchanged.
- **Free-job credit consumed**: Not restored (FEE-2's rule). The script does not touch credit_events or free_jobs_remaining.
- **Reversal exceeds payout**: Out of scope for this persistence logic, but do not let fee logic mask it. The negative balance surfaces elsewhere.
- **Reversal of partially-waived settlement**: The fee columns are unchanged. FEE-2 already specifies the existing path.

## Risks

- **Money**: This changes what counts as future revenue in the money position. A reversed settlement's fee must not be counted twice (once as collected, once as expected).
- **Statement correctness**: A reversed settlement must be labelled as such on the fees statement. Showing it as an ordinary collection without the reversal label is a trust defect.
- **Idempotency**: The script must be safe to run multiple times on the same job. A second run must not error or change state.

## Derived criteria

1. The script `scripts/admin/record-settlement-reversal.ts` exists and can be invoked via `npx tsx`.
2. Running the script with `--job <id> --reversed-at <iso>` against a settled job writes a `settlement_state` to that job's row.
3. The fee columns (`fee_amount_pennies`, `fee_net_pennies`, `fee_vat_pennies`) remain unchanged after running the script.
4. Running the script a second time on the same job changes nothing (idempotent).
5. Running the script against an unknown job ID exits non-zero and writes nothing.
6. A reversal before settlement completed (`--reversed-at` before `paid_at`) records state `reversed_before_settlement`, differing from a post-settlement reversal (`reversed_after_settlement`).
7. Both reversal states are distinguishable from a live settlement (which has `settlement_state = null`).
8. The fees statement (`/settings` page) shows a reversed settlement with its fee intact and labelled as reversed.
9. A partial reversal (with `--partial` flag) keeps the full fee, not pro-rated.
10. A consumed free-job credit is not restored by the script.
11. The money position (`getMoneyPosition` in `money-position-actions.ts`) does not count a reversed settlement's fee as future revenue.
12. The script requires all mandatory arguments (`--job` and `--reversed-at`) and refuses to run without them.
