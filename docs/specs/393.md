# Issue #393: Card-writing rules: describe behaviour, never the machinery that covers it

## Problem

Three dead acceptance contracts in two days, all from cards that described **implementation artefacts** instead of what a user should observe.

The `/join/<code>` card said:

> Keep `?ref=` working on `/signup`, which it does today and which `tests/regression/signup-referral-field.test.tsx` covers. Do not modify that test to accommodate the new route.

The intent was *"this behaviour is already covered, don't break it, don't touch the test."* What the PM produced was:

```typescript
const testMod = await import("@/../../tests/regression/signup-referral-field.test");
```

which does not resolve, and took the entire acceptance file down with it. The same card had already produced one dead contract by naming a parser without naming the constraint the parser enforces.

#356 is the same shape from another angle: the card said "leave this sentence alone here", and the PM froze an assertion that the sentence is **unchanged** — which deadlocked against #351, whose whole job is to change it. Two frozen tests, mutually unsatisfiable, neither repairable.

Naming a test file by path gives the PM a concrete artefact and an implied relationship to it, and "reference the thing that covers this" is a reasonable reading of a card that does so. The card is the input the whole pipeline is derived from, and it is the one artefact with no gate in front of it.

## Scope: what changes

Three rules added to `AGENTS.md`, in the acceptance-test section, alongside the existing "An acceptance test must be able to fail, and able to pass".

**1. Never import one test file from another.** It executes that suite inside this one, and the path forms that look right mostly are not. If a card tells you some existing behaviour must keep working, assert the behaviour — do not reach for the file that currently asserts it.

**2. State a requirement as behaviour, never as "the test that covers it".** "Signing up with `?ref=CODE` must still work" is checkable by a new test. "The test that covers `?ref=` must still pass" is not something a new test can assert, and the attempt produces either a dead import or a tautology.

**3. "Out of scope" means do not change it — never assert it is unchanged.** Pinning the current state of something another in-flight card is changing deadlocks both. This is the rule with teeth: it is the difference between two cards that can land in either order and two that cannot both land at all.

Each rule is written with the incident that produced it, following the house style of the surrounding sections — every existing rule in that file names the item it cost.

Rule 3 also gets a note for whoever writes the card, not only the PM reading it: an "out of scope" line naming a **file** is safe; one naming a **current value** ("the copy still says X") is the trap, because it is indistinguishable from a requirement.

## Explicitly out of scope: what does not change

- **Any mechanical check.** The checkable half of rule 1 — that an acceptance test does not import another test file — belongs to **#391**, which builds that scanner and carries the rule as `::test-file-import::`. Adding a second rule to the same script from a second card is precisely the collision rule 3 above describes: two items, one file, and an ordering constraint nobody wrote down. This item is documentation only and must add no script, no workflow step, and no test that executes anything.
- **The three dead contracts.** #352 has been re-derived and #356 needs its assertion dropped; both are their own items.
- **Rewriting the existing "Never assert on source text" section.** #391 adds two worked alternatives to it. This item does not touch it, for the same reason: one file, two items, and the later one loses.
- **Any change to how cards are written mechanically** — a template, a linter on Notion, a required-fields check. The failure is in what a card *says*, and no schema catches that.
- **`docs/specs/` or the PM prompt in `factory-pm.yml`.** The PM prompt already tells the agent to read `AGENTS.md`; adding the rules there duplicates them into a second place that will drift.

## Files

- `AGENTS.md` (modify) — the three rules

That is the entire change. No script, no workflow, no migration, no dependencies.

**No `RUNNABLE:` line.** This item is not runnable — it is guidance in a markdown file. `scripts/factory/check-deliverable.sh` reports `no-entry-point` and passes, which is the correct outcome, and `AGENTS.md` says to omit the line rather than invent an entry point the item does not call for.

## Edge cases

- **The acceptance test for a documentation-only item.** It asserts the prose exists — which is asserting on source text, the thing #391 exists to forbid. The distinction is real and must be stated in the spec so the PM does not tie itself in a knot: `AGENTS.md` **is** the deliverable here, not the implementation of one. #391's rule is scoped to reads of files under `src/`; `AGENTS.md` is not under `src/`, so no rule fires and no allowlist entry is needed. This is a consequence of #391's scoping, not a special case carved for this item.
- **The assertion should be on meaning, not on wording.** Match the distinctive phrase each rule turns on (`import one test file from another`, `never assert it is unchanged`), not whole sentences. A test pinning a paragraph verbatim recreates the #351/#356 deadlock inside the file that documents it.
- **Ordering against #391.** Both modify `AGENTS.md`, in different sections. Whichever lands first, the second rebases cleanly; if they collide, both edits are appends to distinct sections and both are wanted. No sequencing constraint is imposed, deliberately — imposing one would be rule 3's failure mode again.
- **A future card that legitimately needs to name a test file.** Naming one as context is fine and often useful ("`tests/regression/foo.test.ts` covers this today"). The rule is about what the PM may then *assert*, not about what a card may mention. The wording must permit the mention.

## Risks

- **Guidance that nobody reads changes nothing.** This is the honest risk and it is unmitigated by design: the mechanical half is #391's, and rule 3 is not mechanically checkable at all. Accepted because the alternative — a gate that tries to detect "this card describes machinery" — would be a heuristic firing on correct cards, and a check that fires on the ordinary case stops being read.
- **No production code, no money, no auth, no migration, no customer-facing surface.** A markdown file.

## Derived criteria

- `AGENTS.md` contains a rule stating that an acceptance test must never import another test file, and gives the reason (it executes that suite inside this one)
- That rule cites the #352 incident
- `AGENTS.md` contains a rule stating that a requirement is written as behaviour rather than as "the test that covers it", with a checkable and an uncheckable example
- `AGENTS.md` contains a rule stating that "out of scope" means do not change it, and never means assert it is unchanged
- That rule names the deadlock it prevents: two frozen tests that cannot both be satisfied
- The three rules appear in the acceptance-test section, not in a new top-level section
- `AGENTS.md`'s existing "Never assert on source text" section is unmodified by this item
- No file under `scripts/` is added or modified
- No file under `.github/workflows/` is added or modified
- No file under `src/` is added or modified
- The spec declares no `RUNNABLE:` entry point, and `scripts/factory/check-deliverable.sh` reports `no-entry-point` against it
