# Issue #216: PAY-2: Stripe Connect Express onboarding for contractors

**Auditing branch:** `factory/216` @ `5a97b1f`  
**Database migration required.**

## Problem

Contractors need Stripe connected accounts before destination charges can route money to them. motko's platform account has Connect capabilities active. Each contractor must be onboarded as an Express connected account with payouts to their own bank. This is the prerequisite for the fee-at-source model: customer pays, Stripe splits motko's application fee automatically, remainder settles to the contractor's connected account.

The schema columns for Stripe Connect already exist (from migration 00000000000021_stripe_connect_payouts.sql) but have zero code references — they are dead columns awaiting activation. This ticket brings them to life by implementing contractor onboarding via Stripe-hosted Account Links.

## Edge cases

1. **Contractor abandons onboarding midway** — Stripe account is created (`stripe_account_id` persisted) but capabilities remain disabled (`stripe_payouts_enabled = false`). State: "in progress". Re-entry works: clicking "Complete onboarding" generates a fresh Account Link for the same account. Account links expire after ~5 minutes (Stripe's TTL), so the re-entry must mint a fresh link each time, not reuse a stored URL.

2. **Webhook arrives before redirect return** — Contractor completes onboarding on Stripe, webhook fires and updates `stripe_payouts_enabled = true`, then redirect lands them on `/settings`. State converges: the StripeConnectSection reads the already-updated database row and shows "Connected ✓" immediately. No race — webhook writes are committed before the redirect lands.

3. **Webhook never arrives (delivery failure)** — Contractor completes onboarding, redirect returns them to `/settings`, but webhook was dropped. State: database still shows `stripe_payouts_enabled = false`, UI shows "in progress". Mitigation: the settings page, on load, calls `refreshStripeStatus()` server action if `stripe_account_id` is set but `stripe_payouts_enabled = false` and more than 10 seconds have elapsed since page load. This polls Stripe API and syncs state, identical to the TrueLayer mandate status refresh pattern in current `src/app/settings/page.tsx` lines 50-61.

4. **Existing contractors predating this feature** — `stripe_account_id IS NULL` is the default state. Every contractor record starts with null. The UI shows "Not started" and clicking "Connect to Stripe" creates their first connected account. No migration backfill required.

5. **Contractor clicks onboarding link after 5-minute expiry** — Stripe account link expired. Stripe-hosted page shows "This link has expired." Contractor returns to `/settings`, clicks "Complete onboarding" again, fresh link minted. No data loss — the connected account ID persists, only the link expires.

6. **Multiple onboarding sessions in parallel** — Contractor opens two tabs, starts onboarding in both. First `createConnectedAccount` call writes `stripe_account_id` to database. Second call sees `stripe_account_id IS NOT NULL`, skips account creation, generates fresh Account Link for existing account. No duplicate accounts created — the database column + unique index on `stripe_account_id` guards this.

7. **Webhook signature verification fails** — Invalid or replayed webhook. Route returns 400, event is ignored, no database write. Contractor's state remains unchanged. Stripe retries webhook delivery (exponential backoff, up to 3 days). The refresh-on-page-load fallback (edge case #3) ensures state converges even if all webhook deliveries fail.

## Risks

- **Money-touching logic** — This ticket sets up the infrastructure for routing customer payments to contractor accounts (PAY-3) and charging application fees (PAY-4). The connected account creation itself does not move money, but misconfiguration (wrong capability requested, wrong country code) blocks downstream payment flows. Mitigation: Test mode validation in CI, manual connected account inspection in Stripe dashboard before production rollout.

- **Webhook authentication** — Stripe webhooks use HMAC-SHA256 signing with `STRIPE_WEBHOOK_SECRET`. If the secret is misconfigured or leaked, an attacker could forge `account.updated` events and flip contractors to `stripe_payouts_enabled = true` without completing onboarding. Mitigation: Signature verification is mandatory (no bypass path), webhook secret rotates with other production secrets, and the refresh-on-page-load fallback re-checks Stripe API as source of truth.

- **Schema already exists but is dead** — Migration 00000000000021 added four `stripe_*` columns with zero code references (confirmed in #193 inventory). This ticket activates them. Risk: If another ticket (e.g., a cleanup) drops those columns before this merges, the schema is gone and must be re-added. Mitigation: Check `supabase/migrations/00000000000021_stripe_connect_payouts.sql` still exists at implementation time.

- **Test mode / live mode key confusion** — If `STRIPE_SECRET_KEY` points to live mode in a preview deployment, contractor onboarding creates real connected accounts against real bank details in Stripe's production environment. Mitigation: Environment variable gating — test keys (prefix `sk_test_`) in CI/previews, live keys (`sk_live_`) only in production. Assertion in `src/lib/stripe.ts`: if `NODE_ENV !== 'production'` and key starts with `sk_live_`, throw error.

- **Migration 00000000000036 may be unnecessary** — If the four existing columns suffice for state tracking (not started / in progress / complete / requirements due), migration 036 reduces to a no-op comment. The PM agent flagged this as "MIGRATION REQUIRED" but should verify during spec review whether new columns are actually needed. Conservative path: include the migration; if the Engineer determines it's not needed, they drop it before committing.
