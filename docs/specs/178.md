# Issue #178: Detect offline from failed fetches rather than navigator.onLine

## Problem

The offline banner currently relies solely on `navigator.onLine`, which reports online in several common real-world failure scenarios: captive portals, connections that associate but carry no traffic, and one-bar connections with no throughput. This leaves users staring at taps that silently do nothing with no indication that connectivity is the issue.

## Scope: what changes

- **offline-banner.tsx**: Extend the component to listen for consecutive fetch failures from a global fetch monitor and treat that as an offline signal independent of what `navigator.onLine` reports. The banner appears after a configurable threshold (starting at 2 consecutive failures) and clears on the first successful fetch.
- **New fetch monitor**: A lightweight global observer that listens to fetch activity (both `window.fetch` calls and Supabase client requests), counts consecutive network-level failures, and emits an offline/online signal that the banner consumes. This does not intercept or modify requests — it only observes outcomes.
- **Configuration**: The threshold for consecutive failures before showing the banner is configurable (exposed as a constant the Engineer can tune if needed).

## Explicitly out of scope

- Request retry or queuing: failed requests still fail immediately as they do today
- Caching or offline data persistence: no IndexedDB, no service worker, no local queue
- Banner appearance or copy: the banner's design and text remain unchanged
- Native offline fallback: Capacitor's native offline screen is a separate concern
- Individual fetch error handling: each fetch's own error handling (toasts, error states) is unchanged

## Files

- `src/components/ui/offline-banner.tsx` — consume the fetch monitor's signal
- `src/lib/fetch-monitor.ts` (new) — observe fetch outcomes, count consecutive failures, emit offline/online events
- `tests/acceptance/178.test.tsx` — acceptance tests

## Edge cases

- **Server errors (500, 503)**: Not counted as offline. The banner does not show. A server returning an error proves the network is working.
- **Authentication errors (401)**: Not counted as offline. Session handling applies, not the offline banner.
- **Aborted requests**: Not counted as failures (user navigated away or explicitly cancelled).
- **Captive portal**: Counted as offline. Detected by content-type mismatch — an HTML login page returned when JSON was expected. Detection is content-type only, deliberately: the app has no connectivity-check endpoint, so there is no request for which a `204` is the "wrong" answer. `204 No Content` is the ordinary success status for a `DELETE` or a bodyless `PUT`, and treating it as a network failure would tell a user they are offline after two successful deletes. If a dedicated connectivity check is ever added, a `204` from *that* URL can be reinstated as a signal — scoped to it, never blanket.
- **204 No Content**: Not counted as offline. See above.
- **All fetches failing because the API is down**: This will show the offline banner. This is a known imprecision and is acceptable — telling a user they are offline when the server is down is better than showing nothing.
- **Recovery**: The banner clears on the next successful fetch, not on a timer. The counter resets immediately.
- **navigator.onLine reports offline**: The banner still appears immediately without waiting for fetch failures. This remains a fast path.
- **Mixed success/failure**: A single failure followed by a success does not show the banner. Only consecutive failures count.

## Risks

- **Global fetch interception**: Wrapping `window.fetch` and the Supabase client could introduce side effects if done incorrectly. The monitor must be read-only and never modify request/response behavior.
- **False positives**: If the threshold is too low (e.g., 1 failure), transient network blips will trigger the banner unnecessarily. Starting at 2 consecutive failures balances sensitivity with stability.
- **Performance**: Adding a global listener to every fetch could introduce overhead. The monitor must be lightweight (simple counters, no heavy computation).
- **Supabase client compatibility**: The Supabase client may change its internal request mechanism in future versions. The monitor should wrap `window.fetch` first (which Supabase uses under the hood) rather than trying to instrument the client directly.

## Derived criteria

Based on the issue body, the implementation must:

1. Show the offline banner after N consecutive failed fetches (configurable, defaulting to 2), regardless of `navigator.onLine`
2. Clear the banner on the first successful fetch
3. Not show the banner for a single transient failure (one failure followed by success)
4. Treat server error responses (500, 503, 401) as "online" — only network-level failures count
5. Detect and treat captive portal responses as offline (HTML returned when expecting JSON)
6. Preserve the existing behavior where `navigator.onLine` reporting offline shows the banner immediately
7. Not add request retry, queuing, or caching
8. Not change the banner's appearance or copy
9. Not change individual fetch error handling
10. Accept the known imprecision where an API being down shows the offline banner (this is preferable to showing nothing)
