# Issue #239: PAY-7: Define a fee collection mechanism for fees not attached to a live customer payment

**Auditing branch:** `factory/239` @ `4e19eb1`  
**Database migration required:** No — detection-only, reads existing tables

## Problem

PAY-4 delivered fee collection at source via Stripe `application_fee_amount` on destination charges. This works only when there is a live customer payment to ride on. motko now has no mechanism to collect a fee that is owed but not attached to a payment — specifically: (1) fees lost to partial `settlePaidJob` settlement before PAY-4, (2) fees lost to concurrent over-waiving of free jobs, and (3) stranded pending fee collections that can never be charged via the removed TrueLayer VRP rail, whether or not they carry a `provider_collection_ref`.

PAY-5 removed the VRP collection path entirely. The stated policy (BACKFILL specs #184, #185) is to correct legacy money records retroactively rather than fix-forward. That policy is currently unimplementable: there is no collection rail for fees owed but not attached to a payment.

## Scope: what changes

This is a **detection and quantification** phase only. No collection mechanism is implemented. The deliverable is a reporting function that answers: how much is actually at stake, across how many contractors, before deciding whether to build exception-path collection at all.

### 1. Stranded fee collection detection

A new function `detectStrandedFeeCollections` in `src/lib/detect-uncollectable-fees.ts` (or similar) identifies fee collections that can never be charged:
- Query `fee_collections` where `status = 'pending'`, **regardless of whether
  `provider_collection_ref` is set**
- Two kinds of row qualify, and both are stranded. Collections created by the
  backfills or by early VRP attempts that never reached TrueLayer carry no
  payment ID. Collections that did reach TrueLayer carry a ref but never
  completed before PAY-5 removed the rail — see edge case 4. Neither can be
  charged now, because the rail they would have been charged on is gone.
- Report: count of rows, total gross/net/VAT pennies, set of affected contractor IDs

### 2. Lost fee aggregation

A new function `aggregateUncollectableFees` that composes:
- `recoverLostFees` from `src/lib/recover-lost-fees.ts` (already exists, dry-run mode)
- The new `detectStrandedFeeCollections` from step 1
- Any other detection sources added later

Returns one unified report:
```typescript
type UncollectableFeesReport = {
  lostFeesFromPartialSettlement: LostFeeReport;  // from recover-lost-fees.ts
  strandedPendingCollections: StrandedCollectionsReport;
  totalGrossPennies: number;  // sum across all sources
  totalAffectedContractors: number;  // deduplicated count
  totalAffectedJobs: number;  // count of jobs with uncollectable fees
  message: string;
};
```

### 3. Contractor-level breakdown

The report groups by contractor and shows:
- Total uncollectable fees per contractor (gross pennies)
- Breakdown by source: partial settlement / stranded collection / other
- Whether they have a `stripe_account_id` (indicates whether Stripe invoicing is possible)
- Whether they are deleted or anonymised

## Explicitly out of scope: what does not change

- **No collection mechanism is built.** No Stripe invoices, no account balance charges, no netting against future fees. This is pure detection.
- **No change to fee amounts or calculation.** The existing fee engine (`motkoFeePennies`, `splitFeeVat`) is unchanged.
- **No database writes.** Detection is read-only; nothing is corrected, charged, or waived.
- **No user-facing changes.** Contractors see nothing; this is internal reporting only.
- **No decision on write-off.** That decision requires the numbers this ticket produces.

## Edge cases

1. **Deleted or anonymised contractors**

   A fee may be owed by a contractor whose record was deleted (GDPR right-to-erasure) or anonymised. The report counts these separately and flags them — collection may be impossible or legally prohibited.

2. **Duplicate counting across sources**

   A single job could theoretically appear in both lost fees (partial settlement) AND have a stranded pending collection created for it later. The aggregation must deduplicate by job ID when summing totals, or explicitly note that sources may overlap.

3. **Zero-value stranded collections**

   A `fee_collections` row with `gross_pennies = 0` (free jobs bundled into a batch) should be excluded from the "uncollectable" total — there is nothing to collect.

4. **Collections with a `provider_collection_ref` but status still `pending`**

   These are in-flight TrueLayer charges that never completed before PAY-5 removed the rail. They **are** included in the stranded count — the ref exists but the charge can never settle now.

   > **Amended after a spec dispute.** As first written, this spec said three
   > separate times that the query filters on `provider_collection_ref IS NULL`,
   > while this edge case said the opposite. The Engineer reported the
   > contradiction rather than picking a side, and QA independently raised the
   > same point from the other direction.
   >
   > Resolved in favour of this edge case, on the money. The premise of the whole
   > item is that PAY-5 removed the rail these would have been charged on, so a
   > pending collection is uncollectable whether or not a payment ID was ever
   > minted. Filtering on `IS NULL` would silently underreport what is at stake,
   > and quantifying what is at stake is the only thing this item does.

5. **Very old fees (> 6 months)**

   Fees owed for jobs paid more than 6 months ago may be legally or commercially uncollectable (statute of limitations, or motko's own "we won't chase aged debt" policy). The report should flag these separately, even if no policy exists yet.

## Risks

- **Detection logic diverges from correction logic.** If `recoverLostFees` and this module query differently, they will count different sets. Mitigation: reuse the exact same query logic where possible, and write shared tests that assert they agree.

- **Overlapping sources double-count the total.** A job in both "lost fees" and "stranded collection" would be summed twice. Mitigation: either deduplicate by job ID when aggregating, or document the overlap explicitly in the report message ("totals may overlap if the same job appears in multiple sources").

- **Report run on stale data.** If run against a database snapshot rather than live production, the numbers are fiction. Mitigation: timestamp the report and label it with the environment it ran against.

- **No decision framework.** The numbers alone don't say whether to write off, invoice, or net against future fees. Mitigation: this is out of scope — the decision comes after the report, not during it.

## Derived criteria

- A function exists that detects fee collections with `status = 'pending'`, including those that carry a `provider_collection_ref` (edge case 4)
- The detection report includes: count of stranded collections, total gross pennies, total net pennies, total VAT pennies, set of affected contractor IDs
- A function exists that aggregates uncollectable fees from all sources (lost fees + stranded collections) into one unified report
- The aggregated report shows: total gross pennies across all sources, total affected contractors (deduplicated), total affected jobs, breakdown per source
- The aggregated report identifies contractors who are deleted/anonymised separately from active contractors
- The aggregated report flags contractors with no `stripe_account_id` (indicating Stripe invoicing may not be possible)
- Running `aggregateUncollectableFees` in dry-run (read-only) produces no database writes
- The report is timestamped and includes a human-readable summary message
- Zero-value stranded collections (`gross_pennies = 0`) are excluded from the uncollectable total
- Very old fees (jobs paid > 6 months ago) are flagged separately in the report

## DECISION NEEDED

**Question:** Given the total value of uncollectable fees across all sources and the count of affected contractors, which collection mechanism should motko implement for fees not attached to a live customer payment?

**Options:**  
(a) One-off Stripe invoice to the contractor — clean, auditable, visible to them, but highest friction  
(b) Charge against the Stripe connected account balance (transfer reversal) — fastest, least visible, highest risk of user trust damage  
(c) Net against future application fees — invisible unless surfaced, no new rail required  
(d) Write off everything pre-cutover and go fix-forward only — cheapest, requires quantifying what is being written off first

**Recommendation:** Run `aggregateUncollectableFees` against production first. If the total is under £500 and affects fewer than 10 contractors, option (d) is the correct answer — write it off and unblock three downstream cards immediately. If the total is material (£1000+, or 20+ contractors), lean toward option (c) for active contractors with ongoing invoices (invisible, low friction) and option (d) for deleted/anonymised contractors or one-off users.
