# JOB-2: An archived job says so on its own page

From the pass-7 review, 15 Sep — SERIOUS 2. Audited against main @ 44db45c.

## Problem

There are two independent archive mechanisms: archiving a quote (via `quotes.status = 'archived'`) and archiving a job (via the "Archive job" button, which sets `jobs.archived_at`). The job page derives its state from the quote's status and never reads `archived_at`. So a job archived with the Archive job button shows no archived state at all: no banner, no Restore button, still offering "Archive job" again, and still showing full payment actions like mark-as-paid — while the job correctly appears in the Archived tab. Two mechanisms, one surface aware of only one.

## Scope

1. The job page reads `jobs.archived_at` in its query.
2. Job state derivation accounts for both archive mechanisms: a job is archived if `archived_at` is set OR if `quote.status === 'archived'`.
3. An archived job's page shows a status panel or banner stating it is archived, matching the clarity of the current `quote.status === 'archived'` surface.
4. An archived job's page offers a Restore button to bring it back.
5. An archived job's page does not offer the Archive job button (already archived) or the mark-as-paid flow (doesn't make sense on a filed-away job).
6. Both archive routes land on one honest answer — the page reads as archived whichever mechanism produced it.

## Explicitly out of scope

- Unifying the two archive mechanisms into one. They remain separate; this item makes the job page aware of both.
- The chase cron, which already guards on both `archived_at` and `UNCHASEABLE_QUOTE_STATUSES` (which includes "archived").
- The money panel's "Coming in" and "Owed" figures. The recommendation in the issue body is to leave them unchanged (unpaid invoices genuinely are still owed), and the chaser already stops. If this is wrong, it becomes a separate criterion — say so on the card.
- Cancelling or voiding an invoice. Archiving is filing, not forgiveness.

## Files

- `src/app/jobs/[id]/page.tsx` (modify) — reads `archived_at`, passes it to state derivation, handles the archived case in the switch statement, conditionally renders Archive/Restore buttons
- `src/lib/job-stages.ts` (modify) — `deriveSituation` and/or `deriveJobState` account for `archived_at` in addition to quote status
- `src/lib/job-status-panel.ts` (modify, conditionally) — if a new situation is needed, add its headline/detail here
- Any call sites of `deriveJobState` or `deriveSituation` that need to pass the new `archived_at` parameter (modify as needed)

## Edge cases

- A job where BOTH mechanisms are true (quote archived AND `archived_at` set): reads as archived. The restore path clears `archived_at`; the quote status is independent.
- A job that has been restored (archived_at cleared): no longer reads as archived. It returns to the stage it was at.
- An archived job with an unpaid invoice: the figure still appears in the money panel (per the recommendation), but the job page says it is archived and offers no chase/mark-as-paid actions.

## Risks

- Display-only; no money, no migrations, no irreversible writes. The restore path already exists and is tested.

## Derived criteria

1. A job archived via the "Archive job" button (archived_at set, quote status not 'archived') reads as archived on its job page, with a status panel stating so.
2. That job's page offers a Restore button to bring it back.
3. That job's page does not offer the "Archive job" button again.
4. That job's page does not offer mark-as-paid or payment-link actions (archived jobs don't belong in the active pipeline).
5. A job archived via quote status (quotes.status = 'archived', archived_at null) continues to read as archived exactly as it does today.
6. A job archived via both mechanisms (both archived_at set AND quote archived) reads as archived.
7. A job restored from archived_at (archived_at cleared) no longer reads as archived and returns to its actual stage.
