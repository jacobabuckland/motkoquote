# Issue #355: Get the app — a post-signup step for web signups

## Problem

When a user signs up on the web and gets a session immediately, they proceed straight to `/setup` without ever learning that a native iOS app exists. This gap is universal — referral links only surface it because shared links reliably land users in mobile browsers, but any web signup faces the same problem. A trade who signs up in a browser and never discovers the app ends up using a different product from the one they were sold.

The fix is a single post-signup step, shown once: "Get the app" → link to App Store → "Continue to setup". It appears only when appropriate — web users with a configured App Store URL — and is entirely absent otherwise.

## Scope: what changes

### New route: `/get-app`

Create `src/app/get-app/page.tsx` and `src/app/get-app/loading.tsx`:

- **Server component** that checks:
  1. Is the App Store URL configured? (via `resolveAppStoreHref()`)
  2. Is the user in a browser, not the native shell? (via headers, using `NATIVE_SHELL_UA_TAG` from `src/lib/app-home.ts`)
  
- **If either check fails**, redirect to `/setup` immediately — never render a page that names the app but offers no way to get it.

- **Otherwise render**:
  - Heading: "Get the app" or similar
  - Body copy explaining the iOS app exists and is the intended way to use Motko
  - A link/button to the App Store (using the URL from `resolveAppStoreHref()`)
  - A "Continue to setup" or "Skip for now" button that navigates to `/setup` (using `router.push`, not `window.location.href`)
  
- **Loading state** (`loading.tsx`): branded spinner/skeleton matching the app's loading pattern.

### Modified signup flow

Update `src/app/signup/page.tsx`:

Currently, when a session is returned immediately (line 105-109):
```typescript
if (data.session) {
  router.push("/setup");
  router.refresh();
  return;
}
```

Change to:
```typescript
if (data.session) {
  router.push("/get-app");  // ← was "/setup"
  router.refresh();
  return;
}
```

The `/get-app` page's own checks will decide whether to render or redirect to `/setup`, so the signup page can unconditionally send session-holding users there.

### Design and component usage

- Use design tokens (`bg-ground`, `text-text-secondary`, `border-border`), not raw Tailwind classes like `bg-gray-50`.
- Use the `Button` component from `@/components/ui/button`, not bare `<button>` tags.
- Use `router.push("/setup")` for navigation, not `window.location.href = "/setup"`.
- Must NOT mention "search", "Google Play", or "Android" anywhere in the rendered output.

## Explicitly out of scope

- **Referral code handling**: Already fixed in PR #350 (`src/lib/referral-capture.ts`). The code is stashed on arrival and read back at submit, so it survives the browser-to-app journey without help from this step. Do not add referral-specific logic here.

- **Android support**: There is no `android/` directory and no Android build. The page is iOS-only. No mention of Google Play.

- **Binary changes**: The app points at the live origin (`server.url` in `capacitor.config.ts`), so web-side changes reach existing installs on deploy. No app rebuild needed.

## Edge cases

1. **App Store URL not configured** (`NEXT_PUBLIC_APP_STORE_URL` is empty or invalid):
   - `resolveAppStoreHref()` returns `null`
   - Page redirects to `/setup` immediately
   - User never sees the get-app step
   - This is the default state in `.env.example`, so the feature is off until the URL is set

2. **User in native app** (User-Agent contains `MotkoApp`):
   - Detected server-side via headers
   - Page redirects to `/setup` immediately
   - App users skip this step entirely (they already have the app)

3. **User clicks App Store link**:
   - External navigation to App Store listing
   - User downloads app, opens it, creates account fresh OR signs in to existing account
   - No automatic continuation — this is an exit from the web flow

4. **User clicks "Continue to setup"**:
   - Navigates to `/setup` in the browser
   - They can get the app later if they change their mind

5. **User refreshes the page**:
   - Checks run again: if URL is still configured and still in browser, page renders again
   - If they've opened the app in a new context, they won't hit this URL

## Risks

None. This is a display-only change:
- No money, pricing, or payment logic
- No migrations or data writes
- No customer-facing legal copy
- Not a public route (requires authenticated session from signup)
- Not touching auth or permissions

The only behaviour change is where signup redirects, and the destination (`/get-app`) either renders an informational page or immediately redirects to the original destination (`/setup`).

2. ✓ A loading state `/app/get-app/loading.tsx` exists
3. ✓ The signup page redirects to `/get-app` instead of `/setup` when a session is returned

6. ✓ When the App Store URL is configured AND user is on web, the page renders with a link to the App Store
7. ✓ When the App Store URL is NOT configured, the page redirects to `/setup` (never renders)
8. ✓ When the user is in the native app, the page redirects to `/setup` (never renders)
9. ✓ The rendered page uses design tokens (`bg-ground`, `text-text-secondary`, etc.), not raw colors
10. ✓ The rendered page uses the `Button` component, not bare `<button>` tags
11. ✓ Navigation to `/setup` uses `router.push()`, not `window.location.href`
12. ✓ The rendered output contains none of: "search", "Google Play", "Android"
13. ✓ The App Store link uses the exact URL returned by `resolveAppStoreHref()`, unchanged
14. ✓ There is a way for the user to continue to `/setup` without visiting the App Store (skip/continue button)
