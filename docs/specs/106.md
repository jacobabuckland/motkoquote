# Issue #106: Normalise UK postcodes to a canonical form when an address is captured

## Problem

Google Places returns UK postcodes in inconsistent formats (varying casing and spacing: `SW1A 1AA`, `sw1a1aa`, `sw1a  1aa`). The same building can be saved with different postcode representations across jobs, making the stored postcode unreliable for comparison, grouping, display, or any feature that depends on the postcode as a stable identifier. The postcode is the one part of a structured address that should be directly comparable without re-parsing.

## Scope: what changes

- A new pure helper function `normalizeUkPostcode(postcode: string): string` is introduced in `src/lib/normalize-postcode.ts`
- The helper normalizes a UK postcode to canonical form: uppercase, exactly one space before the final three characters, no leading or trailing whitespace
- `placeToStructuredAddress` in `src/lib/google-maps.ts` calls this helper on the `postal_code` component before storing it on the address
- The helper is unit-tested directly in the acceptance test file, covering valid UK postcodes and unrecognised inputs
- An input that is not a recognizable UK postcode is returned unchanged — the address still saves with the original string, nothing is dropped

## Explicitly out of scope

- Do not parse postcodes out of free-text addresses that Places did not resolve
- Do not validate postcodes against a real postcode database or any external service  
- Do not add UI, warnings, or any blocking behaviour on an unrecognised postcode
- Do not change how addresses are entered, displayed, or stored anywhere else
- Do not touch existing rows — this applies only to addresses captured from now on
- No database migration is required (the stored shape of addresses is unchanged)

## Files

The Engineer is expected to touch:

- `src/lib/normalize-postcode.ts` (new file): the pure helper function
- `src/lib/google-maps.ts`: call the helper in `placeToStructuredAddress` before assigning the postcode
- `tests/acceptance/106.test.ts`: acceptance tests (created by PM, implementation tested by Engineer)

## Edge cases

- **Places returns no postcode at all**: unchanged, the field stays absent
- **Places returns an empty or whitespace-only postcode**: unchanged, the field stays absent (exactly as today)
- **A non-UK postcode** (e.g. `75008` on a Paris address): not recognisable as UK, so it is stored as it arrived — never dropped, never mangled
- **An already-canonical postcode** (e.g. `SW1A 1AA`): unchanged (the normalizer is idempotent)
- **Both outward-code lengths are handled**: `m11ae` → `M1 1AE` (3-char outward) and `dn551pt` → `DN55 1PT` (4-char outward)
- **Whitespace variants** (`  sw1a  1aa  `, `SW1A1AA`, `Sw1a 1Aa`): all normalize to `SW1A 1AA`
- **User-visible impact**: none — this is purely the shape of what is written to the database; no screen changes

## Risks

- **User data**: the postcode field is written for every captured address. The helper must handle unrecognised inputs gracefully (return as-is) so that non-UK postcodes and edge-case inputs are never dropped
- **No migration**: existing postcodes are not touched. Future features that compare postcodes will need to handle mixed data (some canonical, some not) until the legacy rows age out or are updated through normal use
- **Testing**: the helper must be tested with both valid UK postcodes and unrecognised inputs to confirm nothing is dropped

## Derived criteria

Based on the Notion spec, I understand the requirement to be:

1. A pure helper function normalizes UK postcodes to: uppercase, exactly one space before the final three characters, no surrounding whitespace
2. The helper handles both 3-character and 4-character outward codes (e.g. `M1 1AE` and `DN55 1PT`)
3. The helper is tolerant: any input that doesn't match the UK postcode pattern is returned unchanged (not dropped, not mangled)
4. The helper is called in `placeToStructuredAddress` before the postcode is stored on the address
5. Empty or whitespace-only postcodes are treated as absent (no postcode stored)
6. The helper is unit-tested directly, including the unrecognised-input case
7. No UI changes, no warnings, no blocking behaviour
8. No database migration — this applies to new addresses only
9. The acceptance tests confirm both the helper behavior and the integration point
