# PAY-8: Close the off-rail fee gap — measurement instrument

## Problem

Motko earns fees only when money moves through the Stripe Pay by Bank rail. Two paths currently bypass it by design: invoices above £10,000 (where Pay by Bank falls back to manual bank transfer details) and the bank transfer details displayed on every public invoice page (where any customer can choose to pay manually). Both paths were designed when the fee was billed separately via TrueLayer VRP, so the payment method did not affect revenue. Under fee-at-source, payment method and revenue are the same event — but these two paths were never reconsidered, creating an unmeasured revenue leak structurally biased toward the highest-value jobs.

## Scope

Build the measurement instrument first. Add a cron endpoint that queries the database and reports:
- Count of paid invoices with no associated Stripe payment, split by value band
- Total value of those invoices

The report excludes legacy TrueLayer-paid invoices (which legitimately have no Stripe payment because they used a different rail).

Future enhancement (out of scope for this ticket): the report could also break down whether each off-rails invoice was above the £10k ceiling (forced off-rails) or below it (customer chose manual), but that distinction is not required yet.

Detection criteria for an off-rails invoice:
- Invoice status is 'paid'
- Job has NO `payment_provider_ref` set (meaning no Stripe PaymentIntent was created), OR invoice `payment_method` is not 'stripe_bank'
- Exclude where invoice `payment_method` is 'motko_bank' (legacy TrueLayer)
- Exclude where invoice `payment_method` is NULL and `paid_at` is before 2026-08-15 (paid before the payment_method column existed, likely TrueLayer)

Value bands for the split:
- £0-£2,500
- £2,501-£5,000
- £5,001-£10,000
- £10,001-£25,000
- £25,001+

## Edge cases

**Legacy data:**
- Invoices paid before `payment_method` column existed (2026-08-15, migration 27) have `payment_method = null`. These were paid via TrueLayer and should be excluded from the leak count. The cutoff check ensures this.
- Invoices with `payment_method = 'motko_bank'` are TrueLayer payments and must be excluded.

**Staged invoices:**
- A deposit+final job has two invoices but one `payment_provider_ref` on the job. If the deposit was paid via Stripe but the final was marked paid manually, the final invoice is off-rails and should be counted. Detection via `payment_method` on each invoice, not just the job-level ref.

**Concurrent payment methods:**
- If an invoice was created with a Stripe PaymentIntent but the customer ignored it and paid manually, the contractor marks it paid manually. The job will have a `payment_provider_ref` (from the abandoned PaymentIntent) but the invoice's `payment_method` will be 'cash'/'bank_transfer'/'other'. This IS off-rails and should be counted — detect via `payment_method`, not just presence of `payment_provider_ref`.

**Empty state:**
- If zero off-rails invoices exist, the report should return empty arrays for each band, not fail.

**Value band calculation:**
- Use the invoice `amount` for banding, not the job total. A £30k job with a £9k deposit invoice has that deposit in the £5,001-£10,000 band, not the £25,001+ band.

## Risks

**Money visibility:**
- The report exposes which invoices bypassed the fee rail. This is diagnostic data for internal use, not a customer-facing surface. The cron endpoint must be protected by `CRON_SECRET` like other scheduled reports.

**Performance:**
- The query joins invoices → quotes → jobs to get `payment_provider_ref` and filter by invoice status and payment method. With proper indexes on `invoices.status` and `invoices.payment_method` this should be fast, but the join to jobs may be expensive on a large dataset. Acceptable for a diagnostic report run manually or nightly, not for a request-path query.

**Data interpretation:**
- A high count in the £0-£10,000 bands means customers are choosing manual transfer even when Pay by Bank is available — a UX or trust signal issue. A high count in the £10,001+ band is expected (there's no other path) and only matters if the ceiling can be raised. The report must split these clearly so each can be addressed separately.

## Derived criteria

What I understood the human to be asking for:

1. A cron endpoint at `/api/cron/report-off-rails-invoices` that requires `CRON_SECRET` authorization
2. Returns JSON with counts and totals of invoices that were paid but earned no Stripe fee
3. Splits results by five value bands: £0-£2.5k, £2.5k-£5k, £5k-£10k, £10k-£25k, £25k+
4. Detects off-rails by: invoice is paid AND `payment_method` is not 'stripe_bank'
5. Excludes legacy TrueLayer invoices: `payment_method = 'motko_bank'` OR (`payment_method` is null AND `paid_at` before 2026-08-15)
6. Uses invoice `amount` for banding, not job total (so each invoice in a staged job is banded independently)
7. Returns zero/empty when no off-rails invoices exist, not an error
8. The report is a diagnostic tool to answer "how much is this costing?" before making decisions about the £10k ceiling or bank details display
