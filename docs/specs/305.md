# Issue #305: Jobs list defaults to active work

## Problem

The jobs list renders every job regardless of status in a single reverse-chronological feed. Paid and archived jobs — both terminal states requiring no action — are displayed with identical visual weight and identical prime position to work that needs the contractor today. The top row, the most valuable real estate in the product, is currently occupied by a job that was paid yesterday and needs nothing. This makes the list unscannable on a phone and buries live work that actually needs attention.

## Scope

1. Change the default filter from "all" to "active" (jobs that are not paid and not archived)
2. Replace current filter options with: Active (default) · Paid · Archived · All
3. Active includes: drafts, sent quotes, accepted quotes, jobs awaiting payment, and declined/expired jobs
4. Filter choice persists for the session (in-memory/sessionStorage) but not across app restarts — the list always reopens on Active
5. The active filter must be visually distinguishable from inactive filters without relying on colour alone
6. Add appropriate empty states for each filter when no jobs match

## Explicitly out of scope

- Sort order within any filtered list (stays as reverse-chronological by last activity)
- Search functionality (unchanged)
- Job card layout or contents (unchanged)
- What sets a job to archived status (unchanged)
- Whether archiving is manual (unchanged)
- Bulk actions
- Counts/badges on filter chips

- `src/app/jobs/page.tsx` — update empty state copy for new filters, update default filter handling

## Edge cases

**Zero active jobs:**  
Likely for a new contractor or one who is fully paid up. The empty state must read as success, not breakage: "Nothing needs you right now" with a route to start a new job and a route to view Paid jobs. A blank screen reads as a bug.

**Only archived jobs:**  
Same pattern — empty state with route to Archived filter and route to start new job.

**Only paid jobs:**  
Empty state with route to Paid filter and route to start new job.

**Job moves to paid while contractor is viewing Active list:**  
The job leaves the list on next page load/navigation, not mid-scroll. The filter governs what is rendered, not what is fetched.

**Deep link to a job filtered out of current view:**  
Opens the job detail page normally (`/jobs/[id]`). Filtering governs the list page only, never the detail page navigation.

**Guest mode:**  
Same default filter (Active) applies.

**Session persistence:**  
If a contractor switches to "Paid" view, that choice persists while they navigate within the app during that session. When they close and reopen the app, it resets to "Active". Implementation: sessionStorage, not localStorage.

**URL state:**  
The `?filter=` query param continues to work. If a contractor bookmarks `/jobs?filter=archived`, that link should respect the filter. The "Active" filter is represented by the absence of the filter param (or `?filter=active`), matching the current pattern where "all" is the default.

## Risks

**None.** This is a pure UI filtering change with no schema migration, no money calculations, and no data writes. The underlying data model (job buckets: in_progress, completed, declined, archived) is unchanged. The change affects only which jobs are visible by default.

## Derived criteria

1. On initial page load (no query params), only jobs that are not paid and not archived are rendered
2. Draft jobs appear in the Active view
3. Declined/expired jobs appear in the Active view (they are not paid and not archived)
4. Jobs awaiting payment appear in the Active view
5. Paid jobs appear only in the Paid and All views
6. Archived jobs appear only in the Archived and All views
7. Filter chips render as: Active · Paid · Archived · All
8. The active filter is indicated by: border colour, background colour, font weight, AND aria-current="page"
9. Clicking a filter chip navigates to that filter's view
10. The URL reflects the current filter via query param (`?filter=paid`, `?filter=archived`, `?filter=all`) or no param for Active
11. Filter choice persists in sessionStorage while navigating within the app
12. On app restart, the filter resets to Active regardless of what was selected before
13. Empty state for Active reads as success ("Nothing needs you right now") with routes to start a new job and view other filters
14. Empty state for Paid shows "No completed jobs yet" with route to view all jobs
15. Empty state for Archived shows "Nothing archived" with route to view all jobs
16. Totals band (Jobs, Billed, Collected) reflects the currently filtered set
17. Search continues to work within the selected filter
18. "Load more" pagination respects the current filter
