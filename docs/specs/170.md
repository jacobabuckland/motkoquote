# Issue #170: Anchor every acceptance criterion to a named test assertion

**No database migration required.**

## Problem

QA judges spec fidelity by reading prose, so a criterion that can be read two ways has no decidable answer. #93 ran three QA-Engineer cycles and hit the iteration cap without converging on one criterion: "wrap chargeMandate in withTimeout". Cycle 1 demanded one reading, cycle 2 objected to that reading's consequence, cycle 3 moved to the other reading. Every cycle was defensible and none was decidable, because nothing in the contract said which location satisfied the criterion. An ambiguous criterion costs a full three-cycle loop plus human adjudication. This is the cure: it removes the need for QA to hold an opinion by making the test assertion the single source of truth.

## Scope: what changes

1. **PM prompt requires anchored criteria**: The PM agent prompt in `.github/workflows/factory-pm.yml` is updated to require every acceptance criterion in a spec to carry a reference to the specific test assertion that proves it — test file plus describe/it block names or line number.

2. **Guard validates anchored criteria**: A new validation step in the PM workflow checks that all acceptance criteria in the spec are anchored. The guard rejects specs with unanchored criteria and names which specific criteria are missing anchors.

3. **QA prompt respects anchored assertions**: The QA agent prompt in `.github/workflows/factory-qa.yml` is updated to state that a criterion whose anchored assertion exists and passes is satisfied and may not be re-raised on prose grounds.

4. **QA retains non-criterion findings**: The QA prompt explicitly preserves QA's ability to raise findings that are not about criteria satisfaction — files touched outside the declared set, error handling, statement ordering, migration safety, secrets in the diff — none of which require criterion anchors.

5. **AMBIGUOUS: route for unanchorable criteria**: A criterion that genuinely cannot be anchored (e.g., "nothing else changes") takes the existing AMBIGUOUS: route, naming what cannot be expressed, rather than being written unanchored.

6. **Worked example from #93**: The spec includes a re-expression of #93's timeout criterion with an anchor, showing how it becomes decidable without reading prose.

## Explicitly out of scope: what does not change

- The QA iteration cap (remains three cycles)
- The label state machine (needs-spec → spec-derived → verify → qa-changes → previewed → shipped)
- The rework loop mechanics
- The acceptance-test immutability rule
- The spec immutability rule (first commit on the branch)
- Retrofitting specs for items already shipped
- Making the Engineer responsible for anchoring — the PM writes the spec once
- Any product code paths — this is factory-only

    - Checks each criterion has an anchor reference

    - QA retains the ability to raise non-criterion findings (scope, files touched, error handling, secrets, migration safety, etc.)

### Created

- `scripts/factory/validate-anchored-criteria.sh`
  - Bash script that:
    - Takes the issue number as an argument
    - Reads `docs/specs/N.md` and `tests/acceptance/N.test.ts*`
    - Extracts acceptance criteria from the spec (section titled "Acceptance criteria")
    - For each criterion, checks it contains an anchor reference pattern like:
      - `tests/acceptance/N.test.ts: "describe block > it block"`
      - `tests/acceptance/N.test.ts:123` (line number)
      - `→ <test-file>: "<assertion-name>"`
    - If unanchored criteria exist, outputs which ones and exits 1
    - If a referenced test/assertion does not exist in the test file, treats it as unanchored

- `tests/acceptance/170.test.ts`
  - Tests that the PM prompt contains the anchoring requirement
  - Tests that the validation script correctly identifies unanchored criteria
  - Tests that the QA prompt mentions anchored criteria
  - Tests the worked example from #93

## Edge cases

1. **A criterion anchored to a test that does not exist**: The guard treats it as unanchored by checking the test file for the referenced describe/it blocks or line number. An anchor cannot be faked with a plausible name.

2. **The anchored assertion passes but plainly tests the wrong thing**: QA may still raise it — as a finding against the test, not the implementation. This is the deliberate escape hatch, and it is how a bad anchor gets corrected rather than enforced.

3. **Several criteria anchored to one assertion**: Allowed. One assertion can prove more than one thing.

4. **A criterion about absence** ("nothing else changes"): Anchor it to the files-touched check in the spec's "Files" section, or to a test that asserts `git diff` shows only the declared files, rather than leaving it as prose.

5. **An item with no testable criteria at all**: That is the AMBIGUOUS: route, not a spec full of unanchored prose. The PM declares it ambiguous and writes no tests.

6. **Criterion that genuinely cannot be anchored**: Takes the AMBIGUOUS: route naming what is missing from the test harness, rather than being written unanchored.

7. **User-visible**: No. Factory contract only. No product code paths change.

## Risks

- **PM adoption**: If the PM agent does not reliably write anchored criteria in the new format, every spec will block at the guard. The mitigation is the prompt clarity and the worked example from #93 showing the exact format.

- **Validation false positives**: If the anchor validation script is too strict (e.g., regex too narrow), it will reject correctly-anchored specs. The mitigation is testing the script against #93's re-expressed criteria before deploying.

- **Anchor format divergence**: If the PM uses one anchor format and the validation expects another, every spec blocks. The mitigation is documenting the canonical format in the prompt with examples.

- **QA escape hatch overuse**: If QA uses "the test is wrong" as a backdoor to re-raise every criterion on prose grounds, anchoring gains nothing. The mitigation is the prompt framing it as an escape for genuinely incorrect tests, not an opinion override.

## Worked example: #93's timeout criterion with an anchor

**Old criterion (prose, ambiguous):**
> Wrap `chargeMandate` in `withTimeout` using `TIMEOUT_MS.truelayer` (12,000ms)

Three cycles disagreed on:
- Cycle 1: demanded the call-site in `collect-fees.ts` wrap it
- Cycle 2: objected that doing so broke error handling
- Cycle 3: wanted it wrapped inside `truelayer-vrp.ts` instead

**New criterion (anchored, decidable):**
> `chargeMandate` is wrapped in `withTimeout` with a 12-second timeout
> → tests/acceptance/93.test.ts: "Issue #93: chargeMandate wrapped in withTimeout > throws TimeoutError when chargeMandate times out"

The assertion exists and passes when the implementation is correct. QA checks the assertion passes, not whether the wrap is at the call-site or in the function body. The location ambiguity is gone; the test decides it.
