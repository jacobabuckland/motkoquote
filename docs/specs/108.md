# Spec: Show dates in Europe/London rather than UTC

**Issue:** #108  
**No database migration required.**

## Problem

The shared display helpers `formatDate` and `formatRelative` in `src/lib/format.ts` format dates in UTC. Every date shown to a UK contractor — job dates, invoice dates, timeline entries, dates on PDFs and emails — therefore reflects the UTC calendar day, not the London one. Between midnight and 1am British Summer Time, these differ: an event at 23:30 UTC on 1 June happened at 00:30 on 2 June in London, but the app displays it as 1 June. The app has already answered this question correctly in `src/lib/overdue.ts`, which deliberately compares London calendar days so invoices aren't flagged overdue at UTC midnight. Display formatting never caught up, creating an internal inconsistency where the same instant can be described as two different days by different parts of the same screen.

## Scope: what changes

- **`formatDate`**: change the timezone from UTC to Europe/London so an instant renders as its London calendar day (e.g. `2026-06-01T23:30:00Z` renders as `2 Jun 2026` because in London that instant is 00:30 on 2 June)
- **`formatRelative`**: change the day-comparison logic to count whole London calendar days, so "today", "yesterday", "tomorrow" and the N-days-ago/in-N-days wording all change over at London midnight rather than UTC midnight
- **Tests**: unit tests covering instants either side of London midnight during British Summer Time (when UTC and London differ by one hour) and during GMT (when they align), plus tests for date-only input (Postgres `DATE` format like `2026-06-01`) to ensure it never shifts by a day

## Explicitly out of scope: what does not change

- How dates are stored in the database: no change
- How dates are parsed on input or written to the database: no change
- `src/lib/overdue.ts`: already correct, not touched
- The output format: `12 Jul 2026` style, the exact wording of relative phrases ("today", "3 days ago"), and the empty-string fallback for unparseable input all remain unchanged
- No date library introduced
- No per-user timezone setting; Europe/London is assumed for all users
- No database migration required

## Files

- `src/lib/format.ts` — change `formatDate` and `formatRelative` to work in Europe/London
- `src/lib/format.test.ts` — add unit tests for BST/GMT edge cases

## Edge cases

1. **Unparseable input**: unchanged — both `formatDate("")` and `formatRelative("not-a-date")` return an empty string
2. **Date-only value** (like `2026-06-01` from a Postgres `DATE` column): must render as `1 Jun 2026` and must never shift by a day in either direction. A date-only string has no timezone, so it represents a calendar day that must be preserved as-is.
3. **Instant falling exactly on London midnight**: belongs to the day that is beginning (e.g. `2026-06-01T23:00:00Z` during BST is midnight in London on 2 June, and renders as `2 Jun 2026`)
4. **Date during GMT ↔ BST transition**: the runtime's timezone database (via `Intl.DateTimeFormat` with `timeZone: "Europe/London"`) handles the switch; no hand-rolled offset
5. **British Summer Time vs GMT**: during BST (late March to late October), London is UTC+1; the rest of the year it's UTC+0. An instant one hour before UTC midnight during BST falls on the next London day; the same instant during GMT falls on the same London day.

## Failure modes and empty states

- Invalid ISO string input to `formatDate` or `formatRelative`: already returns `""`, unchanged
- `null` or `undefined` passed in: would fail the `new Date()` parse and return `""` as before
- No new failure modes introduced

## Risks

- **User-visible behaviour change**: dates within an hour of UTC midnight during British Summer Time will read one day later than they do today. This is the intended correction, not a bug. Example: an invoice created at `2026-06-01T23:30:00Z` currently shows as `1 Jun 2026` (wrong) and will show as `2 Jun 2026` (correct).
- **No money impact**: dates are display-only; no calculations (payment amounts, overdue counts) are affected. The overdue calculation already uses London days and is untouched.
- **No migration required**: this is pure display logic; no database schema or stored data changes.
- **Test risk**: if the tests are not comprehensive enough at the BST/GMT boundary, a regression could reintroduce the UTC behaviour. The acceptance tests must cover instants just before and after London midnight in both summer and winter.

## Derived criteria

What I understood the human to be asking for:

1. `formatDate(iso)` renders the Europe/London calendar day for that instant, not the UTC day
2. During British Summer Time (UTC+1), an instant like `2026-06-01T23:30:00Z` is `00:30` on 2 June in London, so it renders as `2 Jun 2026` rather than `1 Jun 2026`
3. During GMT (UTC+0), the same instant `2026-01-15T23:30:00Z` is still `23:30` on 15 January in London, so it renders as `15 Jan 2026` (no change from current behaviour)
4. `formatRelative(iso)` counts whole London calendar days, so "today" means the current London day, and "yesterday" / "tomorrow" / "N days ago" / "in N days" all change over at London midnight, not UTC midnight
5. A date-only string like `2026-06-01` (from a Postgres `DATE` column) always renders as `1 Jun 2026` and never shifts by a day, because it has no timezone and represents a pure calendar day
6. The output format, wording, and empty-string fallback remain unchanged — only the timezone interpretation changes
7. Unit tests must cover instants either side of London midnight during both British Summer Time and GMT
8. `src/lib/overdue.ts` is already correct and is not touched
9. No database migration, no new date library, no per-user timezone setting
10. This is a display-only change; no stored data, parsing, or calculation logic changes
