# Spec: Add motion and elevation design tokens

**Issue:** #119  
**Module:** ui

## Problem

The `globals.css` stylesheet defines no motion tokens (easing curves or durations), and elevation consists of a single flat grey shadow applied uniformly regardless of surface depth. The product app contains roughly 16 transitions total, with most `@keyframes` being marketing-page decoration not referenced by product surfaces. This forces every card, input, button and sheet to either have no motion or invent its own, making the app impossible to feel consistent through per-screen work alone. For a product with no photography, flat single-layer shadows are the main reason the interface reads as cheap, because there is nothing else carrying visual weight.

## Scope

Add motion and layered elevation CSS custom properties to the `:root` block in `src/app/globals.css`, and replace existing shadow token values with layered equivalents so all consuming components inherit them without individual edits.

**Changes:**
- Add motion easing tokens: `--ease-standard`, `--ease-out`, `--ease-spring`
- Add motion duration tokens: `--dur-instant`, `--dur-fast`, `--dur-base`, `--dur-slow`
- Add layered elevation shadow tokens: `--shadow-hairline`, `--shadow-resting`, `--shadow-raised`, `--shadow-hover`, `--shadow-overlay`
- Replace existing shadow token values (currently flat grey) with dual-offset, green-tinted layered shadows
- Add duration token overrides inside the existing `@media (prefers-reduced-motion: reduce)` block at `globals.css:252`

All shadows use British Racing Green `rgb(0, 66, 37)` tint instead of neutral black, with dual-offset construction (tight contact layer + broader ambient layer).

## Explicitly out of scope

- Do NOT add or change any color token, spacing token, radius, or font token
- Do NOT apply motion (transitions or animations) to any component
- Do NOT modify the marketing-page `@keyframes` animations
- Do NOT change the existing `@media (prefers-reduced-motion: reduce)` block beyond adding the duration token overrides
- Do NOT restructure the stylesheet or reorder existing declarations
- Do NOT implement dark-mode-specific shadow values (dark mode elevation is a separate design decision)

## Files

**Modified:**
- `src/app/globals.css` — add motion and shadow tokens to `:root`, update shadow token values, add duration overrides to reduced-motion block

**Potentially affected (if hardcoded shadows exist):**
- Any component in `src/components/ui/*` with hardcoded `box-shadow: rgba(...)` values

## Edge cases

**Component with hardcoded shadow that maps to no token:**  
Use `--shadow-resting` as the default replacement and document the component in the PR description.

**Reduced motion preference:**  
Under `@media (prefers-reduced-motion: reduce)`, all duration tokens (`--dur-*`) collapse to `0.01ms`. Easing curves and shadow tokens remain unchanged — elevation is not motion.

**Dark mode:**  
Shadow tokens keep their light-mode values in this item. Dark-mode elevation is a future design decision and explicitly out of scope.

**Legacy persisted data:**  
None. This change affects presentation only; no database schema, API contracts, or stored user data are involved.

**User-visible changes:**  
Yes. Every surface gains layered, green-tinted shadows instead of the current flat grey shadow. No layout, copy, or behavior changes.

**Failure modes:**
- If motion tokens are applied to components before this item ships, those components will reference undefined variables and have no transition
- If a component has a hardcoded shadow with a non-standard opacity/offset, mapping it to a token may change its appearance

**Empty states:**  
Not applicable. These are global design tokens; they exist whether or not any component currently uses them.

## Risks

**Low risk.** This is purely presentational CSS:
- No database migrations required
- No user data or money-related logic affected
- No API or behavioral changes
- Existing component tests serve as a visual regression safety net (any unintended changes will show in snapshots)

The only risk is unintended visual change if a component's hardcoded shadow differs significantly from its mapped token. This is caught during PR review and component visual testing.

## Derived criteria

I understand the human to be asking for:

1. **Define motion easing tokens** in `:root` with the exact cubic-bezier values from the design review (`--ease-standard`, `--ease-out`, `--ease-spring`)
2. **Define motion duration tokens** in `:root` with the exact millisecond values from the design review (`--dur-instant`, `--dur-fast`, `--dur-base`, `--dur-slow`)
3. **Define layered shadow tokens** in `:root` using dual-offset construction with British Racing Green tint (`--shadow-hairline`, `--shadow-resting`, `--shadow-raised`, `--shadow-hover`, `--shadow-overlay`)
4. **Replace existing shadow values** so that the current tokens (`--shadow-resting`, `--shadow-raised`, `--shadow-hover`) use the new layered definitions instead of flat grey
5. **Ensure no hardcoded shadows remain** in `src/components/ui/*` or `globals.css` (grep for literal `rgba` in `box-shadow` declarations returns zero results in those paths, excluding the focus ring)
6. **Reduced motion support** where all `--dur-*` tokens resolve to `0.01ms` inside the existing `@media (prefers-reduced-motion: reduce)` block
7. **Preserve existing visual tests** by either passing them unchanged or updating snapshots with documented diff in PR body
8. **No behavior changes** — this adds tokens but does not apply motion or modify component logic
