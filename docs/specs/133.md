# Issue #133: Promote the outstanding total to a dashboard hero

## Problem

The dashboard renders `outstandingTotal` at text-sm (line 428), smaller than the navigation links above it and identical in weight to surrounding body copy. Cash owed is the primary number a sole trader opens the app to see — it carries more weight than any other figure on the screen — yet it is currently the least prominent element on the page. Cash flow is the primary failure mode for trade businesses, so this figure deserves hero treatment rather than being buried in the "Unpaid invoices" triage group label.

## Scope: what changes

- A new hero section renders above the existing triage groups ("Your move", "Waiting on customers", etc.) on the dashboard
- The hero displays the outstanding total as a text-4xl tabular-nums figure
- A greeting line renders alongside the amount, varying by local time: "Good morning", "Good afternoon", or "Good evening", followed by "— you're owed [amount]"
- The value counts up from zero on mount, animated over a new CSS custom property `--dur-slow` (to be added to `globals.css`)
- When `outstandingTotal` is zero, the hero renders "You're all square" with no amount and no count-up
- Under `prefers-reduced-motion: reduce`, the final value renders immediately with no animation
- A new reusable `<CountUp>` primitive is introduced to handle the count-up animation, accepting a target number, duration, and format function
- The existing "Unpaid invoices" section's inline total display (line 428-430) is removed, since the hero now surfaces this prominently

## Explicitly out of scope

- Do not change how `outstandingTotal` is calculated, queried, or aggregated (it remains the sum of open invoices, line 197)
- Do not change the triage grouping, ordering, or the "Your move / Waiting on customers / history" structure
- Do not add any other metric to the hero (no "paid this week", no invoice count, no other figures)
- Do not change any other figure's typography elsewhere on the dashboard
- Do not add animation between changing values (if `outstandingTotal` updates while the page is open, the new value replaces the old immediately)
- Do not add a paid-this-week tally or any retrospective metric
- No database migration required (this is display-only)

## Files

The Engineer is expected to touch:

- `src/app/dashboard/page.tsx`: render the new hero section above the triage groups, remove the inline total from the "Unpaid invoices" header (lines 428-430)
- `src/components/ui/count-up.tsx` (new file): the `<CountUp>` primitive component
- `src/app/globals.css`: add `--dur-slow` CSS custom property (e.g. `600ms` or similar)
- `tests/acceptance/133.test.tsx`: acceptance tests (created by PM, validated by Engineer)

## Edge cases

- **`outstandingTotal` is zero**: render "You're all square" with no amount, no greeting about money owed, and no count-up animation
- **Value is still loading**: not applicable — the page is server-rendered and `outstandingTotal` is computed from the already-fetched `openInvoices` array. The value is always available when the page renders
- **Value is negative** (if the calculation can produce one, e.g. due to overpayment or credit): render it as-is with the negative sign. Do not clamp, hide, or treat as zero
- **Value changes while the page is open** (e.g. via live updates or a manual refresh): the new value replaces the old immediately, without re-running the count-up animation
- **User has `prefers-reduced-motion: reduce`**: the final value renders immediately with no count-up animation
- **Very large values** (e.g. £100,000+): `formatGBP` already handles this correctly; `tabular-nums` ensures alignment is maintained
- **First run / empty state**: if `isFirstRun` is true (line 211-217), the "Send your first quote" card renders instead of the pipeline, so the hero does not appear at all. This item does not change that behavior

## Risks

- **User-visible prominence**: this is the most prominent change in the tranche. The hero will be the first thing users see when opening the dashboard. If the value is unexpectedly high or low (e.g. due to a bug in invoice status filtering), it will be immediately obvious
- **Animation performance**: the count-up animation must not jank or block interaction. Use `requestAnimationFrame` and respect `prefers-reduced-motion`
- **Currency formatting**: the count-up must produce well-formed currency strings at every frame. Partial counts (e.g. "£1,23" mid-animation) would look broken. The `<CountUp>` primitive should format the value at each step using `formatGBP`
- **No migration, no data risk**: this is purely a display change. No database writes, no schema changes, no stored data is affected
