# DATA-1: A failed contractor lookup sends a signed-in user to onboarding

## Problem

Four page components look up the contractor for a signed-in user but drop the error from the Supabase query. When a query fails (network blip, RLS change, column typo), it returns `{ data: null, error: {...} }` — identical to `{ data: null, error: null }` (no row found) if you only read `data`. The pages treat both as "this person has not onboarded" and redirect to `/setup`, making any transient failure indistinguishable from a missing contractor account.

The defect is silent: the error is discarded, nothing is logged, and the contractor sees "your account is gone" with no way to diagnose it afterward.

## Scope: what changes

1. Add `src/lib/require-contractor.ts` exporting an async `requireContractor` function that:
   - Takes the Supabase client, user ID, and column list (e.g. `"id, company_name"`)
   - Throws when the query errored, with a message naming the lookup (so it's diagnosable from logs)
   - Redirects to `/setup` when it succeeded with no row (genuine "not onboarded")
   - Returns the contractor otherwise

2. Replace the contractor lookup in four pages with calls to the helper:
   - `src/app/jobs/page.tsx` — currently selects `id, company_name`
   - `src/app/dashboard/page.tsx` — currently selects `id, company_name, business_profile, free_jobs_remaining`
   - `src/app/costs/voice/page.tsx` — currently selects `id, company_name`
   - `src/app/motko/page.tsx` — currently selects `company_name`

Each page continues to select exactly the columns it needs (do not widen the select to fit one signature).

The helper centralizes the three-outcome decision (error / no row / found) in one testable place, so the same defect cannot recur at another call site.

## Explicitly out of scope

- **`src/app/api/`** routes, including `stripe/webhook/route.ts`. Same pattern, but money and webhook paths; a webhook has no user to redirect. Their own item.
- **Server actions** in `src/app/jobs/actions.ts` and elsewhere that already `throw new Error("No contractor profile…")` rather than redirecting. Lower severity, separate item.
- **`src/app/costs/actions.ts:43`** — that is #409, blocked on a schema question (`job_reference` exists in no migration). Do not touch it.
- Changing what `/setup` does, or the auth redirect on `!user`.
- The other 25 call sites that drop a Supabase error.

## Edge cases

- **RLS returns zero rows for a real contractor** → indistinguishable from "no row" at this layer, still redirects. Correct for this item: the helper reports what the database said. Do not try to detect it.
- **`maybeSingle()` with more than one row** → PostgREST returns an error, so it takes the throw path (not silently picking one).
- **The error boundary** — `src/app/error.tsx` already exists and catches thrown errors. Do not add one.

## Risks

Low. The change is defensive: queries that succeed behave identically, and queries that fail now throw instead of silently redirecting (which is strictly better — the existing boundary surfaces it).

## Derived criteria

1. A helper function `requireContractor` that takes a Supabase client, user ID, and column list, and either throws, redirects, or returns the contractor
2. When the contractor query returns an error, the helper throws (does not redirect)
3. The thrown error names the lookup so it is diagnosable from logs
4. When the query succeeds but finds no row, the helper redirects to `/setup`
5. When the query succeeds and finds a row, the helper returns it
6. The requested columns are passed through to the `.select()` call unchanged
7. All four pages (jobs, dashboard, costs/voice, motko) call the helper instead of querying directly
8. When a page's contractor lookup fails, the page throws (via the helper) instead of redirecting to `/setup`
