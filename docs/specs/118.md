# Issue #118: Add loading and success states to the Button primitive

## Problem

The Button component at `src/components/ui/button.tsx` has no visual loading state. When a button is disabled during an async operation (e.g. sending a quote), it receives `opacity-50` and nothing else — visually indistinguishable from a button that is permanently unavailable. On a slow connection, a user taps send, the button dims, and there is no signal that work is happening. The common next action is tapping again. The component also lacks a success state needed by the settled end-state pattern, which requires a button to dwell on "Sent ✓" before navigation fires.

## Scope: what changes

1. **Button accepts a `loading?: boolean` prop.** When true:
   - Renders an inline spinner (size and position matched to the button's text)
   - Sets `aria-busy="true"` on the button element
   - The button is non-interactive (cannot be clicked)
   - The button's rendered width does not change when the spinner appears

2. **Button accepts a `success?: boolean` prop.** When true:
   - Renders a green wash (using `--success` or `--color-success` token)
   - Renders a check glyph
   - Animates into view using the `--ease-spring` timing token (or equivalent spring curve if that token does not exist)

3. **Transition between loading and success is seamless.** Setting `loading={true}` then `success={true}` transitions directly from spinner to check without flashing the resting button state in between.

4. **`disabled` and `loading` remain independent props with distinct visual results.** A disabled button shows `opacity-50` with no spinner. A loading button shows a spinner with no opacity change (unless also disabled).

5. **Reduced motion compliance.** When `prefers-reduced-motion: reduce` is active:
   - The spinner renders static (no rotation)
   - The success state applies without transition (instant)

## Explicitly out of scope

- **No changes to existing button variants, sizes, colours, or padding.** The three variants (primary, secondary, tertiary) and their visual treatments remain unchanged.
- **No call sites are updated in this item.** The new props are added to the primitive, but no existing usage of `<Button>` is modified to pass `loading` or `success`.
- **No timer inside the component.** The success state duration is controlled by the caller — the component does not self-clear after a timeout.
- **No haptics inside the component.** Call sites own interaction feedback.
- **No other primitives are modified.** This change touches only `button.tsx`.

## Files

- `src/components/ui/button.tsx` — add `loading` and `success` props, render spinner and check, apply animations
- `src/app/globals.css` — add `--ease-spring` timing token if it does not exist (check first; may already be defined or use an alternative)
- `tests/acceptance/118.test.tsx` — new acceptance tests covering all criteria and edge cases

## Edge cases

1. **Both `loading` and `success` are true.** Loading wins: the spinner is shown, not the check. This is the most sensible fallback since the caller can control the sequence by unsetting `loading` before setting `success`.

2. **`loading` set on a button with an icon and no text.** The spinner replaces the icon. The button's width does not change (it was already sized to the icon).

3. **Button unmounts while `loading={true}`.** No cleanup required, no React warning. The component does not set up timers or subscriptions that need teardown.

4. **`success` set and never unset.** The success state persists. The component does not self-clear — that is the caller's responsibility.

5. **Legacy usage (neither `loading` nor `success` passed).** Buttons that pass neither prop render exactly as they do now. The DOM output is byte-identical to the current implementation.

6. **User-visible.** The new props are not user-visible until a call site adopts them. This change is a pure additive API — existing buttons are unaffected.

## Risks

- **No database migration required.**
- **No user data or money risk.** This is a UI primitive enhancement with no backend changes.
- **Breaking change risk: none.** The new props are optional and default to `undefined` / falsy, so all existing usage remains valid.
- **Adoption risk.** The component gains the capability, but every submitting surface needs to be updated separately to use it. That work is out of scope for this item but should be tracked separately.

## Derived criteria

What I understood the spec to be asking for:

1. `<Button loading>` renders a spinner inline and sets `aria-busy="true"`.
2. A loading button is non-interactive (cannot be clicked).
3. The button's width is stable — setting `loading={true}` does not cause a layout shift.
4. `<Button success>` renders a green wash and a check glyph.
5. The success state animates in with a spring curve (using `--ease-spring` or equivalent).
6. Transitioning from `loading={true}` to `success={true}` is seamless — no intermediate flash of the resting state.
7. `disabled` and `loading` are independent: a disabled button shows dimmed with no spinner, a loading button shows a spinner with no dimming (unless also disabled).
8. Under `prefers-reduced-motion: reduce`, the spinner is static and the success state applies instantly.
9. When both `loading` and `success` are true, the spinner is shown (loading wins).
10. An icon-only button (icon, no text) with `loading={true}` shows the spinner in place of the icon, with no width change.
11. Setting `success={true}` and never unsetting it: the state persists; the component does not self-clear.
12. Buttons that pass neither prop render exactly as they do today (no visual or DOM change).
