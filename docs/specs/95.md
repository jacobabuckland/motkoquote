# Spec: Add app lifecycle resume handling with session revalidation

**Issue:** #95  
**No database migration required.**

## Problem

`@capacitor/app` is installed but no `appStateChange` listener is registered. A trade who backgrounds the app to check their diary or answer a call returns to a stale dashboard showing yesterday's figures. Worse, if their Supabase session expired while the app was backgrounded, the next tap routes them to `/login` with no warning and no explanation, discarding whatever they were about to do. The app has no foreground-resume hook, so it cannot revalidate the session or refresh the data — it just sits there showing the last server render until they pull-to-refresh or navigate elsewhere, and expired-session handling only happens after they've already interacted with stale state.

## Scope: what changes

- **App lifecycle listener**: register an `appStateChange` listener in `NativeAppInit` that fires when the app transitions from background or inactive to active
- **Session revalidation**: on becoming active, revalidate the Supabase session (call `getSession()`) before any refresh is attempted
- **Expired session handling**: if the session is expired, preserve the current pathname and route to `/login?redirect=<pathname>` so the user returns to where they were after authenticating (mirror the existing middleware redirect pattern for unauthenticated page views)
- **Route refresh**: if the session is valid, trigger `router.refresh()` to re-fetch server components from the current route
- **Time threshold**: do not refresh if the app was backgrounded for less than a configurable threshold (e.g. 30 seconds), so app-switching to copy a phone number or check a message does not cause a reload
- **Explicit exemptions**: never refresh the voice route (`/setup/voice`, `/jobs/new`) even if the threshold is met, because refreshing destroys the WebRTC connection and loses the transcript. List these routes explicitly in code.
- **Listener teardown**: remove the listener on unmount so it does not accumulate across component re-mounts

## Explicitly out of scope: what does not change

- **No background sync**: do not add background fetch, background execution, or any background data sync
- **No push-triggered refresh**: push notification handling already works through the existing deep-link path in `NativeAppInit` and is not touched
- **Session duration**: do not change Supabase session duration, refresh token handling, or auth configuration
- **Login route**: do not change the `/login` route or its behaviour (it already supports `?redirect=` for post-auth navigation)
- **No pull-to-refresh**: do not add a pull-to-refresh gesture
- **Public routes**: do not change which routes are public or protected; the middleware already defines the public route list and is not touched
- **Web platform**: the listener only registers on the native platform (`isNativeApp()` guard), so the web app is completely unaffected

## Files

- `src/components/native-app-init.tsx` — add the `appStateChange` listener, session revalidation, and router refresh logic
- `src/lib/supabase/client.ts` — may add a helper function for session revalidation if the logic becomes complex enough to warrant extraction (but may stay inline if simple)
- `tests/acceptance/95.test.tsx` — acceptance tests covering the listener registration, session revalidation, route refresh, threshold behaviour, and exempted routes

## Edge cases

1. **App resumes during an active voice session** (user is on `/setup/voice` or `/jobs/new`): the voice route is in the exemption list, so no refresh fires. The WebRTC connection stays intact and the transcript is preserved.

2. **App resumes mid-payment redirect** (user switched to their bank app and back): the payment flow routes are exempted from refresh so the return-leg navigation (`/i/[id]/paid`) can complete without racing a refresh. Exempted routes: `/i/[id]` (invoice payment page).

3. **App resumes with an unsaved form in progress**: certain routes are marked refresh-exempt to preserve form state. Exempted routes: `/jobs/[id]` (quote editor with unsaved line items), `/setup` (business setup form with unsaved fields). The list is explicit in code, not inferred from form state.

4. **Rapid background/foreground within the threshold** (e.g. user backgrounds the app for 5 seconds to check a message): the time since last backgrounded is less than the threshold, so no session check and no refresh fires.

5. **Session expired and the user is on a customer-facing public route** (`/q/[id]`, `/i/[id]`, `/c/[id]`): these routes require no session, so even if `getSession()` returns no user, the app stays on the current route and does not redirect to `/login`.

6. **Network unavailable on resume**: the session revalidation call fails (network error or timeout). This is NOT an expired session — it's a connectivity failure. The app does not redirect to `/login`; instead it relies on the existing `OfflineBanner` to surface the connectivity issue. The offline banner already listens to `navigator.onLine` and shows when offline; this case is no different.

7. **User is already on the login page when the app resumes**: do not attempt to refresh the login route (it is a server-rendered page with no authenticated data to revalidate). The exemption list includes `/login`, `/signup`, `/auth/*`.

8. **App is foregrounded but was never backgrounded** (first launch, or the user kept the app active the whole time): the listener fires on first transition to active, but there is no "last backgrounded" timestamp yet, so the threshold check cannot pass and no refresh fires. The timestamp is recorded the first time the app backgrounds.

9. **Listener registered multiple times** (component re-mounts due to a parent re-render): the cleanup function removes the previous listener before the new one registers, so only one listener is ever active at a time.

## Failure modes and empty states

- **Session revalidation call throws** (network error, timeout, Supabase client misconfigured): catch the error, log it, and do not refresh. The user sees the offline banner (if they're actually offline) or the stale data (if it's a transient error). Do not route to `/login` on a failed session check — only on a successful check that returns no user.

- **Router refresh fails** (Next.js router error, network error during server component re-fetch): the refresh call itself does not throw in Next.js 14/15 App Router — it queues a fetch that may fail silently. No action required from this feature; the user sees the existing data and can manually navigate if needed.

- **Threshold value is 0 or negative**: treat as "always refresh" (no time filter).

- **Exempted route list includes a route pattern with dynamic segments** (e.g. `/jobs/[id]`): the check matches by pathname prefix (`pathname.startsWith("/jobs/")`), so all job detail pages are exempted.

## Risks

- **WebRTC disruption**: refreshing during a voice session destroys the connection and loses the transcript. The exemption list MUST include `/setup/voice` and `/jobs/new` (the two voice-intake routes), and this must be tested.

- **Payment flow race**: refreshing mid-payment could race the redirect back from the bank app and leave the user on a stale invoice page instead of the success confirmation. The exemption list MUST include `/i/[id]`.

- **Form data loss**: refreshing a page with unsaved form state discards the user's work. The exemption list includes routes with long-lived forms: `/jobs/[id]` (quote editor), `/setup` (business setup form).

- **Threshold too low**: if the threshold is set to something like 5 seconds, every brief app-switch (to copy a phone number, to check a notification) triggers a refresh, which is disruptive and burns battery. The default should be high enough to filter out short switches (suggested: 30 seconds).

- **Threshold too high**: if the threshold is set to something like 10 minutes, returning to the app after a coffee break still shows stale data. The user expects the data to be current after a significant absence. The threshold is a tradeoff; the spec suggests 30 seconds as a starting point, but it should be tunable without a code change (e.g. a constant at the top of the file).

- **No user-visible feedback**: the refresh is silent — the user does not see a loading spinner or a toast confirming the refresh happened. This is by design (the app should feel instant, not like it's reloading), but it means a slow refresh could be confusing. Out of scope for this issue; if it becomes a problem, a follow-up could add a subtle loading state.

## Derived criteria

What I understood the human to be asking for:

1. An `appStateChange` listener is registered in `NativeAppInit` and fires when the app transitions to the active state
2. On becoming active, the listener revalidates the Supabase session (calls `getSession()`) before attempting any refresh
3. If the session is expired (no user returned), the app routes to `/login?redirect=<current-pathname>` so the user can authenticate and return to where they were
4. If the session is valid and the app was backgrounded for more than a configurable threshold (e.g. 30 seconds), the listener calls `router.refresh()` to re-fetch server components from the current route
5. Voice routes (`/setup/voice`, `/jobs/new`) are explicitly exempted from refresh, even if the threshold is met, so the WebRTC connection is not destroyed
6. Payment flow routes (`/i/[id]`) are exempted so the return-leg redirect can complete without racing a refresh
7. Form-heavy routes (`/jobs/[id]`, `/setup`) are exempted to preserve unsaved work
8. The login/signup/auth routes are exempted because there is no authenticated data to refresh
9. Public customer-facing routes (`/q/[id]`, `/i/[id]`, `/c/[id]`) do not redirect to `/login` on expired session, because they require no session
10. A failed session revalidation call (network error) does not redirect to `/login`; it leaves the user on the current route and lets the offline banner surface connectivity issues
11. The listener is removed on component unmount to prevent accumulation across re-mounts
12. The listener only registers on the native platform (`isNativeApp()` guard), so the web app is unaffected
13. The threshold is configurable (a constant at the top of the file) and can be tuned without changing the logic
14. If the app was backgrounded for less than the threshold, no session check and no refresh fires
15. The timestamp tracking when the app was last backgrounded is recorded each time the app moves to the background or inactive state
