# CFIX-2: A contract that was already sent leaves the contractor stranded on the form

## Problem

CFIX-1 fixed the duplicate-contract case to show a useful error message naming the existing contract and offering its link, but it does so by throwing an exception. The client catches this and renders red error text on the form. According to CLAUDE.md, "every completing action navigates deliberately — never rest on a spent form." The successful send already navigates to `/jobs/[id]?sent=contract`; the already-sent case should do the same. The contractor is looking at a red error for a task that is complete (the contract exists and was sent), with no clear route to the contract being referenced.

## Scope: what changes

1. **Server action** (`src/app/dashboard/actions.ts`):
   - When a duplicate contract is detected (error code 23505), query for the existing contract
   - If the query succeeds, return the existing contract's ID and URL instead of throwing
   - Add an `alreadySent: true` flag to the response so the client can distinguish this case
   - Only throw if the existing contract cannot be read back (edge case: RLS, race, deleted row)

2. **Client form** (`src/app/dashboard/create-contract-form.tsx`):
   - Handle the `alreadySent` flag in the response
   - Navigate to the job page with `sent=contract&already=1` when `alreadySent` is true
   - The existing navigation logic already handles `contractId` — it just needs the new query param

3. **Banner builder** (`src/app/jobs/[id]/sent-banner.ts`):
   - Add an `already` field to `SentBannerInput`
   - Add a new case for `sent=contract` with `already=1`
   - The banner title distinguishes "already sent" from "just sent"
   - The banner body explains the contract was already sent and offers the link

4. **Job page** (`src/app/jobs/[id]/page.tsx`):
   - Read the `already` query param from searchParams
   - Pass it to `buildSentBanner`

5. **Banner tests** (`src/app/jobs/[id]/sent-banner.test.ts`):
   - Add test cases for the "already sent" variant
   - Ensure it's distinguishable from "just sent"

## Explicitly out of scope

- The `contracts_quote_id_key` unique constraint — it stays as the backstop
- Any change to how contracts are cancelled, replaced, or re-issued
- The copy-link fallback rendered on the form when there's no job to navigate to
- The first successful send flow (including the `delivered=0` variant)

## Files

- `src/app/dashboard/actions.ts` (modify) — change duplicate-contract handling to return instead of throw
- `src/app/dashboard/create-contract-form.tsx` (modify) — handle `alreadySent` flag and add `already=1` query param
- `src/app/jobs/[id]/sent-banner.ts` (modify) — add "already sent" banner variant
- `src/app/jobs/[id]/sent-banner.test.ts` (modify) — test the new banner variant
- `src/app/jobs/[id]/page.tsx` (modify) — read and pass `already` query param

## Edge cases, including failure modes and empty states

1. **Existing contract cannot be read back** (RLS, race, deleted row):
   - No link to offer, no confident claim to make
   - Stay a failure on the form with an authored message
   - Never a sentence that trails off into nothing
   - Never a navigation that promises a contract the page cannot show

2. **Existing contract is already signed**:
   - Still navigate to the job page
   - Banner must not imply it's awaiting signature when it's not
   - The job page already handles signed contracts correctly

3. **Two sends race**:
   - Unique constraint backstop catches the second one
   - Loser navigates rather than erroring
   - Both contractors see the same contract

4. **No jobId** (shouldn't happen in practice, but defensively coded):
   - Fall back to the inline copy-link result state
   - This path already exists in the form

## Risks

- None. This is a routing change that doesn't touch data persistence, money, or auth.
- The server action already queries the existing contract (CFIX-1); this just returns it instead of throwing.
- No database migrations required.

## Derived criteria

1. Attempting to send a contract for a quote that already has one navigates to the job page with `sent=contract&already=1`
2. The form is never left mounted showing an error for the already-sent case
3. The job page banner says "A contract has already been sent" (or similar) — distinguishable from "Contract sent to [name]"
4. The banner carries the copy-link button for the existing contract
5. No second contract row is created
6. The existing contract's `status`, `sent_at`, and signature state remain untouched
7. A genuine failure (insert fails for a different reason, quote not found) still shows an error on the form with retry available
8. If the existing contract cannot be read back, it stays an error on the form (no navigation)
9. The first successful send flow is unchanged, including the `delivered=0` variant
10. The unit tests for `buildSentBanner` cover the new "already sent" case
