# Issue #182: Remove the stale pnpm-lock.yaml and settle on one package manager

**Auditing branch `factory/182` @ `a65e39a7`**

## Problem

The repository tracks two lockfiles that are three weeks out of sync: package-lock.json (last updated 2026-08-09) and pnpm-lock.yaml (last updated 2026-07-22). GitHub Actions builds against the npm lockfile while Vercel detected the pnpm lockfile and installed from it until PR #117 pinned the installCommand. This divergence caused #113 to pass CI with happy-dom in package-lock.json but fail its Vercel preview deploy with ERR_PNPM_OUTDATED_LOCKFILE. A green gate stopped meaning a deployable branch. The stale lockfile remains tracked and is the file a contributor or agent will naturally update instead of the maintained one.

## Scope

1. Delete `pnpm-lock.yaml` from the repository
2. Add an explicit `packageManager` field to `package.json` declaring npm as the intended package manager, so the choice is stated rather than inferred from which lockfile a tool notices first
3. Verify no workflow, script, config file, or user-facing documentation invokes pnpm (with known exceptions: generated iOS files in `ios/App/Podfile*`, Xcode Cloud script `ci_scripts/ci_post_clone.sh` which is iOS-specific, historical docs like `docs/bug-hunt-2026-07-26.md`, and `.gitignore` patterns)
4. Review the `installCommand` pin in `vercel.json`: either keep it deliberately with a comment explaining why, or remove it because detection is now unambiguous
5. Run a clean `npm ci` from a removed `node_modules` to verify a fresh install succeeds
6. Verify the full test suite and production build pass after removal

## Explicitly out of scope

- Do NOT migrate the project to pnpm — the maintained lockfile and all GitHub Actions workflows are npm; this item removes the stale lockfile, not relitigates the choice
- Do NOT upgrade, add, or remove any dependency
- Do NOT regenerate package-lock.json from scratch (would produce an unreviewable diff and silently move transitive versions)
- Do NOT migrate vercel.json to vercel.ts
- Do NOT change the cron entries in vercel.json
- Do NOT modify the iOS-specific Xcode Cloud script `ci_scripts/ci_post_clone.sh` which uses pnpm for iOS builds

## Edge cases

1. **Cached Vercel build holding a pnpm store**: The first deploy after this change must clear caches, not inherit a warm pnpm store. The `installCommand` pin already forces npm, but verify the first deploy after merging actually runs npm and succeeds.

2. **Transitive version disagreement between lockfiles**: package-lock.json wins — it is what CI has been building and testing against. The pnpm lockfile may have resolved different transitive versions, but those were never tested by CI.

3. **External tooling expecting pnpm**: The `packageManager` field is what makes the expectation fail loudly (e.g., Corepack will error) rather than silently installing a different dependency tree. This is the desired outcome.

4. **Dependency that only resolved through pnpm's flatter layout**: If removal surfaces such a dependency, that is a real bug being uncovered, not a reason to restore the lockfile. Fix the import or dependency declaration.

5. **Developer's local habit or IDE config**: Documentation changes to README.md and other files will guide developers to use npm. The `packageManager` field will cause package managers that respect it (like Corepack-enabled yarn/pnpm) to error rather than silently diverge.

6. **Empty state**: If `pnpm-lock.yaml` has already been deleted (though it exists now at `a65e39a7`), the test should pass and the other changes (packageManager field, doc updates) should still proceed.

## Risks

- **No user-visible changes**: This affects build and deploy tooling only. No production code paths are touched.
- **No money risk**: No payment, pricing, or financial logic is involved.
- **No data risk**: No migrations, no schema changes, no data transformation.
- **No secrets risk**: Deleting a lockfile and updating documentation carries no credential exposure risk.

The only operational risk is a deploy failing if the change is incomplete, but that risk is contained: the `installCommand` pin in vercel.json already forces npm, so Vercel builds won't break. The real risk this item addresses is the *existing* state where a stale lockfile misleads contributors and can cause future items to fail their preview deploys.

## Derived criteria

What I understand the human is asking for:

1. ✓ `pnpm-lock.yaml` file is deleted from the repository
2. ✓ `package.json` declares the intended package manager via the `packageManager` field (e.g., `"packageManager": "npm@10.x.x"` or similar)
3. ✓ No script, workflow, or documentation file invokes pnpm for web builds (exception: iOS-specific scripts like `ci_scripts/ci_post_clone.sh`, generated iOS files, and historical docs)
4. ✓ The `installCommand` pin in `vercel.json` is reviewed: either explicitly kept with a comment or removed because detection is unambiguous
5. ✓ A fresh `npm ci` succeeds when run with `node_modules` removed, proving the maintained lockfile is complete
6. ✓ The full test suite passes after the removal
7. ✓ The production build succeeds after the removal
8. ✓ A future PR that adds a dependency will reach a working Vercel preview deploy (the class of failure from #113 is fixed)

The intent is to eliminate ambiguity in the build toolchain by removing the stale lockfile and making the package manager choice explicit, so that CI, Vercel, and local development all install from the same dependency tree.
