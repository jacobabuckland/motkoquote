# 78 — Gate the pricing slot on `pricing.mode` being explicitly set

**Module:** voice
**Source:** [Notion roadmap item](https://app.notion.com/p/Gate-the-pricing-slot-on-pricing-mode-being-explicitly-set-3b71e4f908b480e58f9dd9cd464eaa77)
**Read against:** branch `factory/78` @ `a58ee66` (identical to `origin/main` for every file below).

**No database migration is required.** No schema DDL, no `sow_json` backfill. The
change is pure TypeScript over the existing persisted shape.

---

## ⚠️ Decision required before the third acceptance criterion can be implemented

Three of the four acceptance criteria are unambiguous and are covered by
`tests/acceptance/78.test.ts`. The third one is not:

> *"resolvePricingMode no longer defaults silently — unset is an error state, not
> a fallback"*

There are two materially different readings, and the issue's own template
questions that would have settled it were left as unfilled placeholders
("Behaviour when unset: `[not filled / stays pending / falls back / errors]`",
"Where the gate lives: `[slot-filling logic / quote generation / both]`",
"User-visible behaviour: `[does anything surface, or is it silent]`").

- **Reading A — `resolvePricingMode` throws when the mode is unset.**
- **Reading B — `resolvePricingMode` returns `null`** (signature becomes
  `PricingMode | null`), and each of its four call sites handles unset
  explicitly instead of inheriting a hidden default.

This is not a stylistic choice. `pricing === null` is not only a
*new-conversation* state — it is the **persisted state of every job whose SoW was
captured before the pricing-mode slot existed**, plus every call that ended on a
hard cap before the slot landed. Those `jobs.sow_json` rows have `pricing: null`
today and are read on ordinary page loads.

Under Reading A, `src/app/jobs/[id]/page.tsx:656` and
`src/app/jobs/actions.ts:997` throw for those jobs: a job page that renders today
starts 500ing, and sending a quote on a legacy job fails. That is a user-visible
regression, and the issue lists "No UI changes" as out of scope — so Reading A as
stated contradicts the issue's own scope line unless the call sites are given
explicit unset handling anyway.

**Recommended translation (what the tests assume): Reading B.** The function stops
manufacturing an answer; unset becomes a value the caller must confront. The
gate in `getUnansweredChecklistQuestions` is what makes unset stop happening on
new calls, which is the actual fix. What each call site *does* with `null` is
left to the human's answer, and is deliberately **not** pinned by the acceptance
tests — see "Explicitly out of scope" below.

**Question for the human:** when a legacy job with `pricing: null` reaches
quote generation (`applyPricingMode`), should it (a) keep producing the
calculated breakdown, as it does today — an explicit, commented decision rather
than a silent `??`; or (b) hard-fail? (a) is the only answer that does not change
money on existing jobs.

**Secondary edge case that the gate does not close (flagged, not fixed here).**
`pricingSchema.mode` carries `.default("calculated")` (`sow.ts:81`) and the
`update_sow` tool parameters do not list `mode` as required (`sow.ts:304-319`).
So a Realtime tool call of `pricing: {}` or `pricing: {fixed_amount: 2000}`
parses to `mode: "calculated"` — a mode nobody chose, filed as if they had.
That is the same "infer, don't ask" class of bug, but closing it means changing
the delta schema's parse behaviour, which risks throwing away a whole turn's
delta on a malformed tool call, and brushes against "No change to how
`pricing.mode` gets set". Left out of this spec on purpose; it wants its own
issue. No acceptance test asserts on it.

## Problem

`getUnansweredChecklistQuestions` (`src/lib/schemas/sow.ts:725`) treats the merged
duration/pricing-mode slot as answered when `sow.pricing != null` **or**
`sow.labour_plan.duration_days != null`. A contractor who mentions a duration in
passing while describing the job — "it'll be about four days" — fills
`duration_days`, which drops the slot out of the natural follow-up queue *and*
out of the `concludeOrAskRequired` safety net in `src/app/jobs/new/page.tsx:521`.
The pricing question is then never asked, `sow.pricing` stays `null`, and
`resolvePricingMode` (`sow.ts:92-94`) quietly answers `"calculated"` for a
decision the contractor never made and is never told about. CLAUDE.md's voice
invariant forbids exactly this: the pricing-mode question is mandatory once scope
is clear, and assumptions are a last resort after an explicit deflection — not a
side effect of a passing remark.

## Scope: what changes

1. **The gate** (`sow.ts:725`). The `duration` slot is answered only when the
   contractor explicitly chose a pricing mode — i.e. `sow.pricing?.mode` is set.
   A `duration_days` value on its own no longer satisfies it. Everything
   downstream of `getUnansweredChecklistQuestions` inherits this for free:
   the natural follow-up queue (`new/page.tsx:490`), the required-slot subset
   (`getUnansweredRequiredChecklistQuestions`, `sow.ts:749`) which
   `concludeOrAskRequired` uses, and `summarizeRequiredSlotCoverage`
   (`sow.ts:757`), where a duration-only session now correctly counts the
   pricing slot as `unknown` rather than `answered`.
2. **`resolvePricingMode`** (`sow.ts:92-94`) stops returning `"calculated"` for
   an unset mode — per the decision above, recommended as returning `null` with
   the return type widened to `PricingMode | null`.
3. **Call-site handling** for the widened return, at the four sites listed under
   Files. Each must handle unset visibly and with a comment saying why, rather
   than re-introducing `?? "calculated"` one layer up — that would reproduce the
   exact bug being fixed, just somewhere less obvious.
4. **The comments that state the old contract** (`sow.ts:89-91`, `sow.ts:128-131`,
   `sow.ts:722-724`). They currently document the defaulting behaviour as
   intentional; leaving them is worse than leaving the bug.
5. **Existing unit tests that encode the old contract** must be updated to the
   new one (listed under Files). They are correct assertions about the old
   behaviour, not accidental coupling — they are supposed to fail.

## Explicitly out of scope

- **How `pricing.mode` gets set.** No change to `update_sow`, its tool
  parameters, the delta merge, or the prompt/question wording.
  `CHECKLIST_QUESTIONS.duration` (`sow.ts:707`) stays exactly as written.
- **UI.** No component, layout, copy, or navigation change. In particular
  `concludeOrAskRequired` in `src/app/jobs/new/page.tsx` should need **no edit** —
  it already asks whatever `getUnansweredRequiredChecklistQuestions` returns.
  A diff there is a signal something has been solved in the wrong layer.
- **Migrations / backfill.** Legacy rows keep `sow_json.pricing = null`.
- **What price a job with an unset mode ends up at.** Pending the human's answer
  on the open question, the pricing *outcome* of `applyPricingMode` for
  `pricing === null` is not asserted by these tests. Changing it changes money on
  live jobs.
- **The `pricingSchema.mode` default / `pricing: {}` hole** described above.

## Edge cases

- **Incidental duration, no pricing statement** — `duration_days: 4`,
  `pricing: null`. Slot stays unanswered; asked in follow-ups and by the wrap
  safety net. *(The headline case.)*
- **`days` mode answered properly** — "four days, me and Liam" sets both
  `pricing.mode = "days"` and `duration_days`. Slot answered. Must not regress
  into asking twice.
- **`fixed` / `calculated` with no duration at all** — mode is explicit, so the
  slot is answered even though `duration_days` is `null`. `"calculated"` chosen
  by deflection ("you work it out") is still a real answer and still counts.
- **Asked but never landed** — `concludeOrAskRequired` marks a slot as asked
  before the answer arrives (`new/page.tsx:530-533`), so a contractor who
  deflects without the model filing a mode still wraps. The wrap does **not**
  loop. That behaviour is unchanged and must stay unchanged: the fix is
  "ask once", not "block until answered".
- **Empty SoW** — `EMPTY_SOW_STATE` already lists `duration` unanswered; no change.
- **Legacy persisted SoW** — `pricing: null` with a duration from a pre-slot
  session. Job page must render; quote send must not throw. See the open question.
- **`labour_plan` present but `duration_days: null`** — already unanswered today;
  stays unanswered.
- **Failure mode if implemented as a throw** — `getJobPage` render and
  `sendQuote` fail for legacy jobs. Covered above.
- **Failure mode if the default moves rather than dies** — a `?? "calculated"`
  added at any call site restores the silent inference with a longer paper
  trail. The acceptance tests cannot catch this at every call site; reviewers
  should grep the diff for `?? "calculated"`.

## Risks

- **Money.** `resolvePricingMode` feeds `applyPricingMode`, which decides whether
  a quote is the full calculated breakdown or a single collapsed works line at a
  stated total. Any change to its unset behaviour that reaches
  `completeSowConversation` (`actions.ts:567`), `redraftJob` (`:713`) or the mode
  switch (`:799`) changes what a customer is billed. The recommendation is that
  the *priced output* for unset stays byte-identical to today.
- **User data.** Live `jobs.sow_json` rows carry `pricing: null`. Nothing writes
  to them here, but everything that reads them must keep working. No backfill.
- **Migrations.** None.
- **Call length.** Contractors who previously satisfied the slot by accident now
  get one extra question, against a fixed `MAX_ASSISTANT_QUESTIONS = 12` budget.
  Expect marginally more sessions wrapping on `cap_questions`. Intended cost of
  asking rather than inferring, but worth watching in the events data.
- **Telemetry step change.** `required_slots_answered` will fall and
  `required_slots_unknown` rise for duration-only sessions from the deploy
  onward. That is the bug becoming visible, not a regression — but it will look
  like one on a dashboard, so it is worth calling out in the PR.

## Derived criteria

Plain-language checklist of what I understood the human to be asking for:

1. A contractor mentioning how long the job will take, in passing, must **not**
   count as having answered how they want the job priced.
2. The pricing question is therefore still asked in the ordinary follow-up flow
   after an incidental duration mention.
3. It is also still asked by the end-of-call safety net
   (`concludeOrAskRequired`) — a call cannot wrap cleanly with the mode unset
   and unasked.
4. Answering the pricing question — with days, a fixed total, or "you work it
   out" — satisfies the slot exactly as it does today. No new asking loop; a
   slot asked once is done, even if the answer never lands.
5. `resolvePricingMode` no longer invents `"calculated"` out of nothing. Unset is
   a state the caller has to deal with in the open, not a value silently
   substituted.
6. There is a test reproducing the exact reported case: an incidental duration
   mention with no pricing statement anywhere in the conversation.
7. Nothing about how the mode is captured, no UI change, no migration, and no
   change to what an existing job gets charged.
