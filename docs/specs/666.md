# SUB-6: Cancellation — stops renewal, access runs to period end

**Source:** [Notion roadmap item](https://app.notion.so/p/SUB-6-Cancellation-stops-renewal-access-runs-to-period-end-3d21e4f908b481449fefe115ff6ec794)

## Problem

A trade must be able to leave. Nothing covers cancellation today — the subscription work (SUB-1, SUB-4) covers creation and failure and stops there. There is no way to cancel from within the product.

## Scope

Add subscription cancellation to the product:

- **Predicates in `src/lib/subscription.ts`** for checking cancelled and cancelling states from the subscription projection, alongside the existing `shouldEndTrial`.
- **A subscription section in Settings** showing the current subscription status and offering the cancellation control.
- **A cancellation confirmation surface** explaining what cancelling does: renewal stops, access continues to the end of the paid period, then ends.
- **A Server Action** that calls Stripe's subscription cancellation API with `cancel_at_period_end: true`.

State is read from `subscription_projection.subscription_status`, the same table SUB-4 reads. Stripe's cancellation states are:
- `canceled` — the subscription has ended
- `cancel_at_period_end` — cancellation is scheduled; the subscription is still active until the end of the current period

The projection derives from Stripe via the webhook (`src/lib/subscription.ts` already projects `subscription_status`), so this item adds no new stored state.

## Explicitly out of scope

- **Account deletion**, which is a different act with different consequences (handled by a separate flow).
- **Involuntary failure** (SUB-4 covers that — payment failure, expired card).
- **Banked referral months and what becomes of them.** That moved to REF-3 on 7 Sep per the issue body — the referral scheme credits free jobs today, months are a future currency. When REF-3 invents months, it says what they are worth on cancellation. If that lands first, this item reads the outcome; if this lands first, the play-out rule lives on REF-3.

## Files

The complete list of files this item touches:

- **src/lib/subscription.ts** (modify) — add predicates for cancelled and cancelling state
- **src/app/settings/page.tsx** (modify) — fetch subscription status from subscription_projection
- **src/app/settings/subscription-section.tsx** (new) — the Settings section showing status and the cancellation control
- **src/app/settings/actions.ts** (modify, or new if it does not exist) — Server Action to cancel the subscription via Stripe API
- **tests/acceptance/666.test.ts** (new) — acceptance tests

## Edge cases and behaviour

- **A trade who cancels and changes their mind before the period ends** is still a paying trade at period end. They retain access throughout, and the subscription naturally renews unless they actively re-cancel.
- **Signed contracts, unpaid invoices, job history** remain accessible throughout and after cancellation. A cancelled trade can still reach the evidence of work they did.
- **Customer surfaces are unaffected.** A signed contract stays viewable at its link (`src/app/c/[id]/`), an unpaid invoice stays payable (`src/app/i/[id]/`). These are reached by the trade's customer, not the trade, and Motko's billing relationship with the trade is not the customer's problem. A route-level guard bolted onto a layout would break these surfaces — this is a check on access to contractor features, not on public document routes.
- **Cancelling is not instant destruction.** The subscription status becomes `cancel_at_period_end` immediately, but access continues until the period actually ends, at which point the status becomes `canceled`.

## Risks

- **Subscription status will gate access to contractor features** in a future item. Getting the cancelled/cancelling check wrong could lock paying users out or let cancelled users continue indefinitely.
- **Stripe webhook projection must work correctly.** The `canceled` and `cancel_at_period_end` statuses must be projected from Stripe events into `subscription_projection.subscription_status` via the existing `applySubscriptionEvent` path.
- **Customer-facing surfaces must remain unaffected.** Quote, contract and invoice links handed to customers must keep working regardless of the trade's subscription status.

## Derived criteria

What I understood the spec to be asking for:

1. A predicate in `src/lib/subscription.ts` checks whether a subscription is cancelled (`canceled`) or cancelling (`cancel_at_period_end`), consuming a `SubscriptionProjection` row.
2. Settings page fetches the contractor's subscription projection row.
3. A new Subscription section in Settings shows the current status (active, cancelling, cancelled) and the cancellation control.
4. A Server Action calls Stripe's subscription update API with `cancel_at_period_end: true`.
5. The cancellation control shows a confirmation explaining: renewal stops, access continues to period end, then ends. Signed contracts, invoices and job history remain accessible.
6. The predicates differentiate between `canceled` (already ended) and `cancel_at_period_end` (ending at period end, but still active now).
7. The customer surfaces (`/c/[id]`, `/i/[id]`) are NOT touched and remain accessible to anyone with the link.
