# Issue #185: [BACKFILL] Recover fees lost to partial settlePaidJob settlement

**Auditing branch:** `factory/185` @ `a65e39a`

## Problem

Where `settlePaidJob` crashed between the `paid_at` claim (line 89) and the fee write (line 136), jobs are marked paid with `fee_status` at its `not_applicable` default and no ledger row. The fee was never accrued and never charged. On the allowance branch, the free-job burn was also lost, so the contractor retained a credit they should have spent. This is a money bug: contractors received fee-free processing for jobs that should have either accrued a fee or consumed a free-job allowance.

Policy is to correct legacy money records retroactively, but this is the one backfill that bills trades for fees they were never charged, potentially several months late, so it carries the highest risk of damaging a relationship with a small user base.

## Scope: What changes

1. A new server-side RPC function at `src/lib/recover-lost-fees.ts` containing:
   - Dry-run mode (default): lists affected jobs per contractor, no writes
   - Write mode: applies corrections for a single named contractor
   
2. The dry-run report distinguishes:
   - Jobs that should have **accrued a fee** (contractor had zero free jobs remaining)
   - Jobs that should have **burned a free credit** (contractor had free jobs remaining)
   
3. For jobs that should have accrued a fee:
   - Update the job's `fee_amount_pennies`, `fee_net_pennies`, `fee_vat_pennies`, `fee_status='accrued'`
   - Create a **one-off collection** with a distinct `period_start` (not part of any monthly batch)
   - The collection status is `pending` (enters normal collection flow)

4. For jobs that should have burned a free credit:
   - Write the missing `credit_events` row with `delta=-1`, `reason='job_consumed'`
   - Call `increment_free_jobs_remaining` with `delta=-1` to update the cache
   - Set the job's `fee_status='not_applicable'`, `fee_waived_reason='free_allowance'`

5. The backfill is **idempotent**: re-running for a contractor already corrected reports zero affected rows.

6. The backfill processes **one contractor per invocation** when run in write mode (takes `contractorId` as required parameter).

7. Affected jobs are detected by the query:
   ```sql
   SELECT * FROM jobs 
   WHERE paid_at IS NOT NULL 
   AND fee_status = 'not_applicable'
   AND <NOT legitimately exempt>
   ```

8. Legitimately exempt jobs are excluded using the same logic that `planPaidJobSettlement` uses (none exist in the current codebase, but the exclusion is future-proof).

## Explicitly out of scope

- Do NOT add recovered fees to the next monthly batch. They ride a separate collection by design.
- Do NOT modify `settlePaidJob` or any settlement logic. This backfill assumes the bug is already fixed.
- Do NOT charge the created collection from this code. It enters the normal collection flow once approved.
- Do NOT notify contractors from this code. That is a manual step done per contractor before running the backfill.
- Do NOT correct jobs that are legitimately fee-exempt (if any such exemption logic exists).
- Do NOT process more than one contractor per invocation in write mode.

## Edge cases

### Very old jobs (>3 months)
Include in the dry-run report but flag separately. A fee charged half a year late may be better written off — that is a manual decision per contractor, not a rule this code applies.

### Contractor has cancelled their mandate
Accrue the fee and create the collection, which will fail to charge and enter dunning as normal. Flag these in the dry-run report so the manual review can decide whether to pursue them at all.

### Contractor's allowance at the time would have covered the job, but current balance would not
Apply the **historical position** (what the allowance was when the job was paid), because that is what should have happened. The dry-run report must state the resulting balance.

Reconstructing historical allowance is non-trivial: the cache (`free_jobs_remaining`) reflects the current state, but the append-only `credit_events` ledger is the source of truth. To determine what the allowance was at a given `paid_at` timestamp, sum all `credit_events` for that contractor with `created_at <= paid_at`.

### Job legitimately exempt
Exclude entirely. The exemption condition must be read from the same source the settlement path uses (`planPaidJobSettlement`), never re-derived. Currently no exemptions exist, but the code must check.

### Contractor account deleted or anonymised
Skip and list separately in the dry-run report. Do not attempt to correct.

### Re-running for a contractor already corrected
Should report zero affected rows. Idempotency is achieved by the same query: once `fee_status` is updated to `accrued` or the `fee_waived_reason` is set to `free_allowance`, the job no longer matches the filter.

### Job has staged payments (deposit + final)
The fee accrues **once** per job, banded on the job's total value. The lost-fee scenario can only occur once per job (on the first payment that set `paid_at`), so this is not a special case — treat it like any other affected job.

### Empty state
If no affected jobs exist (either globally or for a specific contractor), the dry-run report should state "No lost fees found" rather than silently returning empty output.

## Risks

**This backfill bills contractors for fees they were never charged.** Unlike other money corrections, this is not fixing an overcharge or refunding — it is collecting money that was never collected before, potentially months after the fact.

**User-visible:** Yes, strongly. Trades receive a charge for work already completed and already paid for by their customer. Each contractor must be contacted before executing the backfill for them.

**Data integrity:** The one-off collection must have a distinct `period_start` that does not overlap any monthly period, or period accounting will be corrupted. Use a synthetic date like `1970-01-01` for the backfill period to ensure it never collides.

**Historical allowance reconstruction:** The calculation must use the append-only `credit_events` ledger, not the cached `free_jobs_remaining`, because the cache reflects the current state. Summing `credit_events` up to the job's `paid_at` gives the historical balance.

**Timing:** This backfill MUST NOT run while the bug that creates these records is still live. It depends on the settlePaidJob RPC item being deployed first.

## Derived criteria

I understood the spec to be asking for:

1. A server-side RPC function that identifies jobs marked paid but with no fee accrued and no free credit burned due to a partial settlement failure.

2. A dry-run mode (the default) that reports affected jobs grouped by contractor, showing:
   - Each job's ID, paid date, and whether it should have accrued a fee or burned a credit
   - The fee amount or credit delta for each job
   - The contractor's total recovered fees
   - Flags for edge cases (very old jobs, cancelled mandates, deleted accounts)

3. A write mode that corrects one contractor at a time:
   - For jobs that should have accrued a fee: update the job's fee columns and create a one-off collection
   - For jobs that should have burned a credit: write the missing credit_events row and update the cache
   
4. The backfill must reconstruct the historical free-job allowance at the time each job was paid, not use the current balance.

5. The backfill must be idempotent: running it twice for the same contractor does nothing the second time.

6. The one-off collection must have a distinct period that never collides with monthly batches.

7. Legitimately exempt jobs (if any exemption logic exists) must be excluded using the same logic that the settlement path uses.

8. The backfill runs manually per contractor after approval, never in bulk.
