# Issue #219: PAY-3: Replace TrueLayer pay-by-bank with Stripe Pay by Bank destination charges

**No database migration required.** (Stripe columns already exist from migration 021; new payment method enum value is backwards-compatible)

## Problem

The customer payment flow currently creates a TrueLayer payment and is broken (provider rejected motko). TrueLayer must be replaced with Stripe Pay by Bank using Payment Intents with destination charges to the contractor's Stripe connected account. The fix preserves the existing customer-facing payment page's URL structure and capability-token security while swapping the underlying payment rail from TrueLayer to Stripe. Webhook-driven settlement ensures the job ledger reflects paid state independently of redirect flow.

## Scope: what changes

### New Stripe Payment Intent creation route

A new API route at `src/app/api/stripe/create-payment-intent/route.ts` replaces the TrueLayer payment creation path. It:

- Accepts `{ invoiceId: string }` POST body (same contract as TrueLayer route)
- Validates invoice is in `sent` status and contractor has completed Stripe Connect onboarding (`stripe_account_id` present, `stripe_charges_enabled: true`)
- For invoices ≤£10,000: creates a Stripe Payment Intent with `payment_method_types: ['customer_balance']` (Pay by Bank), destination charge to `contractor.stripe_account_id`, `application_fee_amount: 0`
- For invoices >£10,000: returns `{ error: "Amount exceeds Pay by Bank limit", code: "AMOUNT_TOO_HIGH" }` with 422 status
- Returns `{ clientSecret: string, publishableKey: string }` for frontend to initialize Stripe.js
- Added to `PUBLIC_API_ROUTES` in middleware

### Customer payment page updates

The existing invoice payment page at `src/app/i/[id]/page.tsx` and related components:

- `src/app/i/[id]/pay-button.tsx` changes fetch target from `/api/truelayer/create-payment` to `/api/stripe/create-payment-intent`
- On 422 response (amount too high), shows bank transfer fallback instead of broken button
- On success, initializes Stripe.js and confirms Payment Intent client-side
- Preserves existing URL structure (`/i/[id]`), capability-token security, and branding customization
- `src/app/i/[id]/pay-panel.ts` updated to check Stripe Connect readiness instead of TrueLayer config

### Stripe webhook handler

A new webhook route at `src/app/api/stripe/webhook/route.ts` handles payment lifecycle events:

- Verifies webhook signature using `STRIPE_WEBHOOK_SECRET` and `stripe` SDK
- Maps `payment_intent.succeeded` → calls `settlePaidJob` with `source: "stripe_webhook"`, `paymentMethod: "stripe_bank"`
- Maps `payment_intent.payment_failed` → logs for observability, leaves invoice payable for retry
- Maps `payment_intent.processing` → logs as pending, no ledger write (settlement on succeeded only)
- Idempotent under duplicate delivery: `settlePaidJob` already guards via `.neq("status","paid")` flip (carries #93 learnings)
- Stores `payment_intent.id` to `invoices.payment_provider_ref` (reuses existing provider-agnostic column)
- Added to `PUBLIC_API_ROUTES` in middleware

### Settlement path updates

- `src/lib/settle-paid-job.ts` updated to handle new `paymentMethod: "stripe_bank"` enum value (no schema change needed)
- No changes to fee accrual, credit events, or referral firing logic — settlement behavior identical to TrueLayer path

### Payment panel routing logic

- `src/app/i/[id]/pay-panel.ts` updated: `railsAvailable` now checks Stripe Connect readiness (contractor has `stripe_account_id` AND `stripe_charges_enabled: true`) instead of TrueLayer config
- Amounts >£10,000 detected at panel-build time, forcing `mode: "transfer_only"` with clear message

### Stripe SDK integration

- Add `stripe` npm package to dependencies
- Environment variables: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` (already documented in .env.example)
- Initialize Stripe client in new `src/lib/stripe-client.ts` helper

## Explicitly out of scope: what does not change

- **No fee collection** — `application_fee_amount` hardcoded to `0`. Fee logic lands in PAY-4.
- **No TrueLayer code removal** — The old TrueLayer routes, libraries, and webhook handler remain in the codebase but are bypassed by the updated payment page. Deletion is PAY-5.
- **No database migrations** — `invoices.payment_provider_ref` already exists (provider-agnostic). `contractors.stripe_account_id`, `stripe_charges_enabled`, `stripe_payouts_enabled` exist from migration 021. New `payment_method` enum value `"stripe_bank"` is a data-level change, not a schema change.
- **No changes to invoice creation, amounts, or quote flow** — Only the payment rail changes; invoice lifecycle unchanged.
- **No Stripe Connect onboarding UI changes** — This ticket assumes contractors already have `stripe_account_id` populated (from earlier onboarding work). If missing, payment button shows "setup incomplete" message (existing behavior).
- **No refund UI** — Refund path mentioned in edge cases for ledger correctness, but no admin refund interface lands here.

## Edge cases

### Customer abandons at bank authorization

When a customer reaches the Stripe-hosted bank selection UI but abandons before completing authorization:

- Payment Intent transitions to `canceled` or `requires_payment_method`
- No `payment_intent.succeeded` webhook delivered
- Invoice remains in `sent` status, fully payable
- No ledger writes occur
- Customer can retry by revisiting payment link

### Duplicate webhook delivery

Stripe may deliver the same `payment_intent.succeeded` event multiple times (network retry, internal replay):

- `settlePaidJob` guards via atomic `.neq("status","paid")` invoice flip (carries #93 idempotency learnings)
- First webhook delivery wins; subsequent deliveries return early with zero rows updated
- No double-accrual of fees, credits, or referral activation
- Idempotent without requiring stable keys (invoice ID is the natural key)

### Payment 'processing' state

When the customer completes bank authorization but settlement is pending:

- `payment_intent.processing` webhook delivered
- Logged for observability ("payment pending settlement")
- Invoice remains in `sent` status (not flipped to `paid` until `payment_intent.succeeded`)
- UI shows invoice as "payable" until settlement completes (typically seconds to minutes)

### Invoice amount >£10,000

Stripe Pay by Bank default limit is £10,000. For invoices above this threshold:

- `buildPayPanel` detects amount and forces `mode: "transfer_only"` (bank transfer details shown, no pay button)
- If customer somehow bypasses UI (direct API call), `POST /api/stripe/create-payment-intent` rejects with 422 status and `{ error: "Amount exceeds Pay by Bank limit", code: "AMOUNT_TOO_HIGH" }`
- Clear message in UI: "This invoice amount exceeds the online payment limit. Please use bank transfer."
- Fallback path: existing bank transfer details are shown (trade's payout account)

### Contractor without completed connected account

When a contractor has not finished Stripe Connect onboarding or `stripe_charges_enabled: false`:

- `buildPayPanel` returns `mode: "setup_incomplete"` (same as TrueLayer path today)
- UI shows warning: "[Company] hasn't finished setting up payments yet. Please get in touch with them to pay."
- If customer bypasses UI, `POST /api/stripe/create-payment-intent` rejects with 409 status: "Contractor has not completed payout setup"
- Consistent with PAY-2 (Stripe Connect onboarding prerequisite)

### Payment failed asynchronously

When the bank declines after initial authorization (insufficient funds, account closed):

- `payment_intent.payment_failed` webhook delivered
- Logged with failure reason for contractor visibility (future: notification)
- Invoice remains in `sent` status, fully payable for retry
- No ledger writes

### Refund (full or partial)

When a contractor initiates a refund via Stripe Dashboard or future admin UI:

- `charge.refunded` / `payment_intent.refunded` webhook delivered
- Ledger update: decrement `invoices.amount` or create a `refund_events` table entry (design TBD in PAY-6)
- For now: webhook is logged but not acted upon (refund path is out of scope; mentioned here for completeness)

### Stripe webhook signature verification failure

When an unauthenticated or replayed webhook is received:

- Signature verification via `stripe.webhooks.constructEvent` throws
- Route returns 400 Bad Request
- No ledger writes occur
- Logged as potential security event

### Missing environment variables

When `STRIPE_SECRET_KEY` or `STRIPE_WEBHOOK_SECRET` is not configured:

- Payment Intent creation route returns 503 Service Unavailable
- Payment panel falls back to `mode: "transfer_only"` (same as TrueLayer outage today)
- Webhook route returns 500 (signature verification requires secret)

## Risks

### Money: destination charge routing

**Risk:** A misconfigured destination charge could route customer money to the wrong account or fail to settle to the contractor at all.

**Mitigation:** 
- Payment Intent creation route validates `contractor.stripe_account_id IS NOT NULL` and `stripe_charges_enabled: true` before creating intent
- Stripe API enforces that destination account must be a valid connected account in `active` state
- Test in Stripe test mode end-to-end before production deploy
- First production transaction manually verified in Stripe Dashboard before announcing to users

### Money: idempotency on webhook redelivery

**Risk:** Duplicate `payment_intent.succeeded` webhooks could double-settle a job (double fee accrual, double credit events, double referral activation).

**Mitigation:**
- Carries forward the #93 idempotency fix: `settlePaidJob` uses atomic `.neq("status","paid")` guard
- First webhook wins, subsequent deliveries no-op (zero rows updated)
- Job-level `paid_at IS NULL` guard ensures fee/credit/referral effects fire exactly once per job
- Acceptance test explicitly covers duplicate delivery scenario

### Money: amount exceeds Stripe limit

**Risk:** An invoice >£10,000 slips through UI validation and attempts to create a Payment Intent, which Stripe rejects, leaving customer with a broken payment flow.

**Mitigation:**
- Dual validation: UI (pay panel) AND server (Payment Intent creation route) both enforce £10k cap
- Server rejection returns clear error code `AMOUNT_TOO_HIGH` with 422 status for graceful UI handling
- Acceptance test explicitly covers >£10k invoice scenario

### User data: webhook payload logging

**Risk:** Logging raw Stripe webhook payloads could expose sensitive customer bank details or payment method tokens.

**Mitigation:**
- Webhook handler logs only essential identifiers: `payment_intent.id`, `event.type`, `metadata.invoice_id`
- Never log `payment_intent.payment_method_details` or full event object
- Stripe Dashboard retains full event history for 30 days (no need to duplicate in our logs)

### Migration boundary: TrueLayer → Stripe handoff

**Risk:** Some invoices created before deploy reference TrueLayer, some after reference Stripe. Mixed state could break reports or reconciliation.

**Mitigation:**
- `invoices.payment_provider_ref` is provider-agnostic (stores TrueLayer payment ID or Stripe Payment Intent ID)
- `invoices.payment_method` distinguishes `"motko_bank"` (TrueLayer) from `"stripe_bank"` (Stripe) for reporting
- Both webhooks (`/api/truelayer/webhook` and `/api/stripe/webhook`) remain live during transition
- No backfill needed: old invoices stay TrueLayer-settled, new invoices are Stripe-settled

### Schema: Connected account columns unpopulated

**Risk:** `contractors.stripe_account_id` is `NULL` for contractors who haven't onboarded yet, breaking payment creation.

**Mitigation:**
- Payment Intent creation route explicitly checks `stripe_account_id IS NOT NULL` and `stripe_charges_enabled: true`, returns 409 if missing
- Pay panel shows "setup incomplete" message (existing UX pattern)
- Acceptance test explicitly covers this edge case

## Derived criteria

The human is asking for:

- A customer can complete an invoice payment end-to-end via Stripe Pay by Bank in test mode, from button press through bank authorization to webhook-driven ledger settlement
- The payment state transitions are idempotent: delivering the same `payment_intent.succeeded` webhook twice results in exactly one settlement (no double fee, no double credit)
- An invoice with amount >£10,000 never shows a pay button; the UI displays bank transfer fallback with a clear "exceeds online payment limit" message
- A contractor without a completed Stripe connected account (`stripe_account_id` NULL or `stripe_charges_enabled` false) cannot generate a payment link; the UI shows a "setup incomplete" warning
- The customer payment page preserves its existing URL structure (`/i/[id]`), capability-token security (no session required), and branding customization (logo, brand color, company name)
- The old TrueLayer payment creation route and webhook handler remain in the codebase but are not deleted
- No changes to invoice creation flow, quote flow, or invoice amounts
- Application fee is hardcoded to zero (fee collection logic deferred to PAY-4)
- Settlement writes `payment_method: "stripe_bank"` to distinguish from TrueLayer-settled invoices in analytics and reporting
- Webhook route is added to `PUBLIC_API_ROUTES` middleware list so it bypasses authentication (same pattern as TrueLayer webhook)
- A `payment_intent.processing` event is logged but does not flip invoice to paid (settlement only on `succeeded`)
- A `payment_intent.payment_failed` event is logged but leaves invoice payable for retry
- Customer abandonment (leaving bank authorization incomplete) does not alter invoice state; invoice remains payable
