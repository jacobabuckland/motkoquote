# Issue #196: Bundle a native offline fallback screen for cold start

## Problem

The Capacitor app points its WKWebView at https://motko.app. The bundled payload at `native/www/` contains only a minimal splash screen (`index.html`). The `OfflineBanner` component lives in the remote application at motko.app, so it can only render if the app has successfully loaded. When a user cold-starts the app with no network access, the WKWebView's initial load of https://motko.app fails and shows the browser's native error page — an unbranded, generic "Cannot connect to the internet" screen with no context, no Motko branding, and no clear path forward. This is a critical failure for an app-first tool designed for tradespeople working in basements, plant rooms, and new-builds where signal is worst.

## Scope: what changes

Bundle a minimal, self-contained offline fallback HTML page in the native payload (`native/www/`) that renders when the initial remote load fails. The page must:

- Display Motko branding (name, brand color) so the user knows they are in the Motko app
- Show a clear message explaining the network failure
- Provide a retry button that re-attempts the remote load when tapped
- Be entirely self-contained: all CSS inlined, no external fonts, images, or scripts that require network access
- Only appear after the load has genuinely failed, not while a slow load is still in progress

Add JavaScript to detect when the remote load fails and show the offline fallback. The detection mechanism must wait for an actual failure, not timeout optimistically. The chosen threshold must be stated in the PR.

When the user taps retry, re-attempt the remote load. If successful, the normal application loads with no further user action.

When the app is backgrounded on the offline screen and then resumed, re-attempt the load automatically (the user's explicit return is the retry signal).

## Explicitly out of scope: what does not change

- Do not build offline data caching, a cached dashboard, or any offline read of user data
- Do not add a service worker for offline caching
- Do not change `OfflineBanner` (the in-app banner shown when connection drops after the app has loaded)
- Do not change the remote-shell architecture or bundle the full Next.js application into the native payload
- Do not add offline write queuing or sync mechanisms
- Do not add auto-retry loops while the offline screen is displayed (user must tap retry)
- Do not add captive portal detection (that belongs to the failed-fetch item)
- Do not change how the remote app handles partial load failures (where the shell loads but subsequent requests fail)

## Files

The Engineer is expected to touch:

- `native/www/offline.html` (new) — the offline fallback page, entirely self-contained
- `native/www/index.html` — add JavaScript to detect remote load failure and show the offline fallback
- Possibly `capacitor.config.ts` — if configuration changes are needed to support the fallback mechanism
- Possibly `scripts/build-native.sh` or similar — if build steps are needed to ensure the offline page is bundled correctly
- Possibly native code (`ios/App/App/AppDelegate.swift` or similar) — if iOS-specific hooks are needed to detect app resume and retry the load

## Edge cases

**Slow but working connection:** Must not show the offline screen while a slow load is in progress. Wait for the load to genuinely fail. The chosen threshold (e.g., timeout duration, error type) must be stated in the PR and should be conservative enough to avoid false positives on slow 3G.

**Captive portal:** A captive portal returns a login page (HTTP 200) rather than failing. The remote load technically succeeds (status 200), but the content is not the Motko app. Detecting and handling this case is explicitly out of scope for this item — it belongs to the failed-fetch item. The offline screen only handles true network failures.

**Connection returns while offline screen is displayed:** Do not auto-retry silently. Auto-retry loops burn battery in a no-signal basement. The user must tap the retry button to re-attempt the load.

**App backgrounded on offline screen and resumed later:** Re-attempt the load on resume. The user's explicit return to the app is a retry signal. This is the one case where auto-retry is appropriate.

**Partial load failure:** The remote shell loads, but subsequent requests (API calls, chunk loads) fail. This is not this item. The remote app is running, and its own error handling (including `OfflineBanner`) applies.

**Network failure after successful load:** This is already handled by `OfflineBanner` in the remote app. The offline fallback only handles cold-start failures before the remote app has loaded.

**Multiple rapid retries:** Do not rate-limit retry attempts. If the user taps retry five times in rapid succession, attempt the load five times. The user is in control.

**Offline screen shown while remote app is loading in background:** This should not be possible if the detection logic is correct. If the remote load succeeds, the offline screen must not appear. If the load fails, the offline screen appears. There is no intermediate state.

**User-visible:** Yes. This is the most visible failure in the product, shown when the app is used in the most likely failure scenario (no signal in a basement or new-build). The change converts a generic browser error into a branded, recoverable state.

## Risks

**Native platform specifics:** WKWebView error handling differs between iOS and Android (if Android support is planned). The solution must work on iOS (the current platform). If Android support is planned, the Engineer should flag any platform-specific assumptions.

**Timeout threshold:** Choosing too short a timeout will show the offline screen on slow-but-working connections, frustrating users with slow networks. Choosing too long a timeout means users wait longer before seeing the fallback on genuinely failed loads. The threshold must be stated and justified in the PR.

**Resume behavior:** Automatically retrying on app resume could surprise users who backgrounded the app intentionally to check signal or open Settings. However, the alternative (making users tap retry after every resume) is more friction. Defaulting to auto-retry on resume is the right call, but the Engineer should flag this decision in the PR if there are edge cases.

**Build changes:** If the offline page requires build steps (copying, minifying, asset inlining), ensure those steps run in CI and local dev builds. A missing build step will cause the offline page to be absent or broken in production.

**Capacitor upgrade path:** The solution should not rely on Capacitor internals that could change in future upgrades. Prefer documented APIs and standard WKWebView error handling patterns.

**No database migration required.**
