# Issue #193: PAY-1: Inventory TrueLayer surface area and legacy Stripe code (migration prerequisite)

**Auditing branch:** `factory/193` @ `f3cec19`  
**No database migration required.**

## Problem

TrueLayer has declined to onboard motko (rejection email received 12 Aug 2026), so the current pay-by-bank flow is dead-ended. The Stripe account remains fully active (verified in dashboard: no re-verification needed, Payments/Payouts/Transfers capabilities live, Pay by Bank already enabled). Legacy Stripe code exists in the codebase from the pre-TrueLayer era. Before any migration work is specced, we need an accurate inventory of both surfaces.

Every subsequent migration ticket (payment flow replacement, webhook migration, fee collection replacement, deprecation) depends on knowing exactly what exists. Guessing produces specs that fail pre-flight review.

## Scope: what changes

A single documentation file is created at `docs/payments-migration-inventory.md` containing:

### 1. TrueLayer surface area

Every file, route, function, environment variable, webhook handler, and database column that touches TrueLayer, organized into:

- **Environment variables** (7 variables: client credentials, signing material, merchant account, beneficiary name)
- **Core library files** (4 files: config/URL builders, payment creation, VRP/mandate handling, tests)
- **API routes** (2 routes: create-payment, webhook)
- **Integration points** (all files that import from the above or reference TrueLayer identifiers)
- **Database columns** (9 columns across 3 tables: invoices, contractors, fee_collections — with table names, column names, types, nullability, constraints)
- **Idempotency work from #93** (stable keys, timeout wrapper, status pre-check, error distinction)
- **Public middleware allowlist from #99** (2 TrueLayer routes in the explicit public API list)

Each entry includes file:line references where the touchpoint exists. Functions are listed with their signatures. Database columns are listed with their types and constraints.

### 2. Legacy Stripe code classification

Every remnant of the pre-TrueLayer Stripe integration, classified as:

- **Reusable:** concepts that inform the Stripe Pay by Bank migration (webhook verification patterns, environment variable structure, error handling approaches)
- **Delete:** code/columns that serve no purpose and should be removed (7 DB columns, 4 env vars in .env.example that reference Stripe but have no code using them)
- **Replace:** active integrations that must be swapped (none exist — no Stripe SDK dependency, no active routes)

Each item in the "Delete" category includes the table/file location so a cleanup ticket can be scoped.

### 3. Data model surface

Which tables and columns store TrueLayer provider identifiers, payment states, and mandate references:

- **Must preserve for historical records:** `invoices.truelayer_payment_id`, `jobs.payment_provider_ref`, `fee_collections.provider_collection_ref` (these reference settled money and cannot be dropped even after migration)
- **Migration-scoped:** `contractors.fee_mandate_id`, `contractors.fee_mandate_status`, `contractors.fee_collection_status` (these drive active fee collection and must be migrated to the Stripe equivalent)
- **Transient:** `fee_collections.attempts`, `last_attempt_at`, `failure_reason` (dunning state that resets per collection)

### 4. Dependency map

Which later migration tickets touch which files, so specs can declare accurate file lists:

- **Payment flow replacement** (PAY-2): touches `src/app/api/truelayer/create-payment/route.ts`, `src/lib/truelayer-payments.ts`, `src/app/i/[id]/pay-button.tsx`, `src/app/i/[id]/pay-panel.ts`, plus the webhook route
- **Webhook migration** (PAY-3): touches `src/app/api/truelayer/webhook/route.ts`, `src/lib/truelayer-payments.ts` (verification logic)
- **Fee collection replacement** (PAY-4): touches `src/lib/truelayer-vrp.ts`, `src/lib/collect-fees.ts`, `src/app/settings/fee-billing-section.tsx`, cron routes
- **Deprecation & cleanup** (PAY-5): drops the 7 legacy Stripe columns, removes unused env vars, deletes TrueLayer files after confirming zero references remain

### 5. In-flight and historical payment count

A count (or "unknown — needs production DB query") of:

- Invoices with `truelayer_payment_id IS NOT NULL`
- Jobs with `payment_provider_ref IS NOT NULL`
- Fee collections with `provider_collection_ref IS NOT NULL` and `status = 'collected'`
- Fee collections with `status IN ('pending', 'failed')` (stranded collections that would be orphaned by deprecation)

This determines whether the deprecation ticket needs a backfill/reconciliation step or can simply halt new TrueLayer operations.

## Explicitly out of scope: what does not change

- **No application code changes** — this is inventory only; no routes, no libraries, no migrations are modified
- **No TrueLayer operations** — the integration continues to function as it does today until a later ticket replaces it
- **No Stripe integration work** — this documents what exists, it does not build the replacement
- **No decisions on migration strategy** — whether to migrate mandate-by-mandate, how to handle in-flight collections, what Stripe product to use — all deferred to PAY-2 through PAY-5

## Edge cases

1. **In-flight TrueLayer payments in the database:** The inventory must report the count of non-null `truelayer_payment_id`, `payment_provider_ref`, and `provider_collection_ref` rows, or explicitly state "count unknown — requires production DB query". The deprecation ticket (PAY-5) needs this to know whether a backfill is required.

2. **Stranded fee collections:** Collections in `pending` or `failed` state that reference a TrueLayer mandate. The count (or "unknown") determines whether PAY-5 must reconcile them or can simply mark them as "manual resolution required".

3. **Legacy Stripe columns with non-null values:** The inventory must note whether the 7 Stripe columns (`stripe_payment_link_id`, `stripe_invoice_id`, `stripe_account_id`, etc.) contain any non-null data in production. If they do, PAY-5's cleanup becomes a migration (preserve the data) rather than a simple DROP COLUMN.

4. **TrueLayer code referenced from untested paths:** Acceptance tests (`tests/acceptance/*.test.ts`) import TrueLayer modules for mocking but do not execute them in production. These references must be listed in the integration points section, distinguished from production call sites.

5. **Middleware allowlist from #99:** The inventory must note that `/api/truelayer/create-payment` and `/api/truelayer/webhook` are explicitly listed in `PUBLIC_API_ROUTES` (src/lib/supabase/middleware.ts), so PAY-2 and PAY-3 must update that list when they add Stripe equivalents.

6. **Rate limiting / IP allowlisting:** If Vercel or Supabase apply rate limits or IP allowlists to the TrueLayer webhook route, those must be documented so PAY-3 can replicate them for the Stripe webhook. (Current state: no evidence of rate limiting beyond the fail-closed cron secret for `/api/cron/*`.)

## Risks

- **Incomplete inventory:** A file or column missed here propagates into every downstream spec, causing rework. Mitigation: exhaustive grep for `truelayer`, `TrueLayer`, `TRUELAYER`, `stripe`, `Stripe`, and `STRIPE` (case-insensitive), plus manual review of supabase/migrations/*.sql for all payment-related columns.

- **Stale dependency map:** If the inventory's file lists are accurate today but a concurrent ticket modifies the surface before PAY-2 starts, PAY-2's spec will reference files that have moved or been renamed. Mitigation: the dependency map is guidance, not contract; PAY-2's PM agent re-audits before speccing.

- **Historical data unknown:** If the inventory cannot query production to count non-null TrueLayer references, it states "unknown — requires production query" and pushes that discovery into PAY-5's pre-implementation. This is acceptable; speccing a backfill strategy without knowing the row count is worse.
