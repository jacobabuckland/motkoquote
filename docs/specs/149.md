# Issue #149: Brand the payment receipt page

**Issue:** #149  
**No database migration required.**

## Problem

The payment receipt page at `i/[id]/paid/page.tsx` shows only a generic checkmark and "Payment received" heading with no identifying information about the trade or the transaction. Customers land here after paying an invoice (on-rails via TrueLayer, or off-rails after the trade marks it paid) and later return to it as proof of payment. In its current state it cannot serve as a receipt because it shows neither who was paid, how much, nor when — it is indistinguishable from any other trade's receipt page. A customer opening this page days later has no way to confirm which payment it represents.

## Scope: what changes

1. **The page queries additional fields from the database.** The existing query (`invoices.payment_method, paid_at`) expands to join through `quote_id` to reach `jobs` and then `contractors`, fetching:
   - `invoices.amount` (the payment amount, stored in pounds)
   - `contractors.company_name` (the payee)
   - `contractors.branding` (which contains `logo_url`)

2. **The page renders the trade's logo or a monogram fallback.** When `logo_url` exists, render it as an `<img>` with `src={logo_url}`, sized `h-12 w-12`, rounded (`rounded-md`), and `object-contain`. The `alt` attribute is set to the company name (or empty string if company name is missing). When `logo_url` is absent, render a monogram: a `div` with the first letter of `company_name`, uppercase, styled as a `h-12 w-12` square with centered text, using the existing brand color or a default.

3. **The page renders the amount and payee in the form "You paid £8,132 to Smith Joinery".** Use `formatGBP(amount)` to format the amount. If `company_name` is present, render "You paid {amount} to {company_name}". If `company_name` is missing, render "You paid {amount}" (omitting "to" rather than showing an empty name).

4. **The page renders the payment date.** Use `formatDate(paid_at)` to render the date. This replaces or augments the existing subtitle logic.

5. **Edge-case rendering rules:**
   - When `logo_url` is absent: render the monogram fallback (first letter of company name, uppercase)
   - When `company_name` is missing: omit "to X" from the amount line, and render an empty alt on the logo
   - When `paid_at` is null (legacy records): omit the date entirely rather than rendering a placeholder
   - When `amount` is null (legacy records): render the check and payee without an amount line (do not render "£0" or a placeholder)

## Explicitly out of scope: what does not change

- **No changes to payment processing, state, or how amounts are recorded.** This reads existing data only.
- **No download, print, or PDF generation.**
- **No shareable receipt link or receipt email.**
- **No changes to the invoice page** (`i/[id]/page.tsx`).
- **No Motko branding or promotional content** (the existing `<MadeWithMotko />` may remain as-is or be removed, but no new Motko branding is added).
- **The checkmark icon may remain** if it fits the design, or be removed in favor of the logo — this is an implementation detail, not a requirement.
- **The "Payment received" heading may remain** or be replaced — this is an implementation detail.

## Files

- `src/app/i/[id]/paid/page.tsx` — expand the query, render logo/monogram, amount, payee, and date
- `tests/acceptance/149.test.tsx` — acceptance tests covering logo rendering, monogram fallback, amount formatting, payee display, date rendering, and all edge cases

## Edge cases

1. **Trade has no logo** (`logo_url` is null): render the monogram fallback (a square div with the first letter of `company_name`, uppercase, centered).

2. **Company name is missing or empty**: omit "to X" from the amount line (render "You paid £8,132" instead of "You paid £8,132 to "). The logo alt is set to empty string. The monogram fallback cannot be rendered (no letter to show) — this case may require a generic placeholder or the logo space is left empty.

3. **Payment date is null** (legacy records created before `paid_at` was added): omit the date from the page entirely. Do not render "Paid on " with no date, and do not render today's date or a placeholder.

4. **Amount is null** (should not happen in practice, but could exist on a legacy record): render the checkmark and payee (if present) but omit the amount line entirely. Do not render "You paid £0" — null and zero are semantically different.

5. **Invoice does not exist** (invalid or deleted invoice ID in the URL): the page should handle this gracefully (likely showing a "not found" state or redirecting), but this is outside the scope of the visual branding requirements. The query uses `.maybeSingle()` so it won't throw, but the component must handle the null case.

6. **Receipt opened later** (not immediately after payment): the page must render correctly from the persisted data. It does not re-query payment status from TrueLayer or recalculate the amount — it renders what was recorded at payment time.

7. **Logo image fails to load** (URL is set but the image file is missing from storage): the browser will show a broken image icon. This is acceptable — the component does not need to detect load failures or fall back to the monogram in this case. The monogram is used only when `logo_url` is absent in the database, not when the image fails to load.

## Failure modes and empty states

- **Invalid invoice ID** (UUID that doesn't match any row): `maybeSingle()` returns null, the page renders a minimal state (or redirects). This is out of scope for the branding requirements.
- **Missing join data** (invoice exists but has no job/contractor, due to a cascade delete or data inconsistency): the query returns null for contractor fields. Handle as per edge case #2 (missing company name).
- **Amount is zero** (valid state for a fully-discounted invoice): render "You paid £0.00 to X" — this is semantically different from null amount (which is omitted).

## Risks

- **No money risk.** This item reads the recorded payment amount; it does not calculate, validate, or write it. Rendering the wrong amount is a display bug, not a financial bug.
- **No user data risk.** Contractor logo and company name are already public (visible on quotes and invoices to customers).
- **User-visible change.** The receipt page will look different, and customers will see the trade's branding. This is the intended outcome.
- **Image loading.** Contractor logos are served from Supabase Storage; if the storage URL is inaccessible or the image is deleted, the page will show a broken image. This is the same risk as the existing quote and invoice pages.
- **No database migration required.** All fields already exist; this is a pure read-path change.

## Derived criteria

What I understood the human to be asking for:

1. The receipt page queries `invoices.amount`, `contractors.company_name`, and `contractors.branding.logo_url` by joining through `quote_id -> jobs -> contractors`.
2. When `logo_url` is present, render it as an image (`<img src={logo_url} alt={company_name} className="h-12 w-12 rounded-md object-contain" />`).
3. When `logo_url` is absent, render a monogram fallback: a square div (`h-12 w-12`) containing the first letter of `company_name` (uppercase), centered.
4. Render the amount and payee as "You paid £8,132 to Smith Joinery", using `formatGBP(amount)` for the amount formatting.
5. If `company_name` is missing, render "You paid £8,132" (omitting "to X").
6. Render the payment date using `formatDate(paid_at)`.
7. If `paid_at` is null, omit the date entirely (do not render a placeholder or today's date).
8. If `amount` is null, omit the amount line entirely (do not render "You paid £0").
9. The amount rendered equals `invoices.amount` — this item does not calculate or derive it.
10. The page renders correctly when opened later (from persisted data), not only immediately after payment.
11. The logo image has `alt` set to the company name (or empty string if company name is missing).
12. When `company_name` is missing and there's no logo, the monogram cannot be rendered (no letter to show) — the logo space may be left empty or show a generic placeholder.
13. No changes to payment processing, PDF generation, or the invoice page.
14. No new Motko branding or promotional content (the existing MadeWithMotko component may remain or be removed, but this is not the focus).
