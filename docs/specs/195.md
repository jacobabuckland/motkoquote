# Issue #195: Add a post-deploy health check gating promotion to production

## Problem

The native shell loads live motko.app with no buffer between deploy and every installed phone. A deploy that builds cleanly but fails in production configuration breaks every installed app simultaneously with no staged rollout, no canary, and no rollback path other than rolling forward. PR-level CI gates merges but cannot detect runtime failures that only surface in the production environment.

## Scope: what changes

**GitHub Actions workflow** (`.github/workflows/deploy-health-check.yml` or similar)
- Runs after a successful deploy to preview but before promotion to the production alias
- Executes a health check script against the preview deployment URL
- Blocks promotion if any check fails
- Raises an alert through an existing notification channel on failure
- Completes within 3 minutes of deploy
- Ensures only one deployment is promoted at a time (handles concurrent deploys by queuing)

**Critical paths configuration** (e.g., `deploy-health-check.json` or similar in repository root or `.github/`)
- Lists all critical paths to verify, one per entry
- Each entry specifies: the path, whether it requires authentication, and the expected success condition
- At minimum includes:
  - Dashboard page (authenticated session required)
  - Customer-facing quote page (public, no auth)
  - TrueLayer webhook endpoint (responds successfully)
- Structured so new paths can be added without changing the workflow code

**Health check script** (e.g., `.github/scripts/health-check.sh` or similar)
- Reads the critical paths configuration file
- Makes HTTP requests to each path against the provided deployment URL
- For authenticated paths, uses a dedicated test account (credentials in repository secrets)
- Implements warm-up request before actual check for cold-start tolerance
- Returns exit code 0 on success, non-zero on failure
- Outputs clear failure messages indicating which path failed and why

**Documentation** (`FACTORY.md` in repository root)
- Documents the rollback procedure including how to promote a known-good previous deployment manually
- Lists the override path for manual emergency deploy when check is failing
- Requires override to be explicit and logged, with no silent bypass
- Explains the warm-up behaviour and cold-start handling

## Explicitly out of scope

- Do not build staged rollout, canary deployment, or percentage-based traffic splitting
- Do not change the build process or build configuration
- Do not change the PR CI gate (this is post-deploy, not pre-merge)
- Do not add synthetic monitoring or ongoing uptime checks. This runs at deploy time only
- Do not add the ability to pin the native shell to a specific build version
- Do not change how Vercel handles deployments or aliases
- Do not add health checks to the application code itself (e.g., a `/health` endpoint) unless absolutely required for the check to function

## Files

Expected to create:
- `.github/workflows/deploy-health-check.yml` - workflow that gates promotion
- `.github/scripts/health-check.sh` (or `.ts`/`.js`) - the check script itself
- `deploy-health-check.json` (or similar location) - critical paths configuration
- `FACTORY.md` - rollback and override documentation

Expected to modify:
- Existing deployment workflow (if promotion logic needs to be conditional on health check)
- `.github/workflows/factory-deploy.yml` or similar - may need to integrate with existing deploy process
- `src/lib/supabase/middleware.ts` - accept an `Authorization: Bearer` token in addition to the session cookie. This is the "unless absolutely required" case named above: the check authenticates the test account through the Supabase auth API, which returns an access token and no session cookie, so a cookie-only middleware would reject every authenticated path despite valid credentials. The token must be validated the same way the cookie is, via `supabase.auth.getUser(token)` — never trusted because it is present. Note the consequence explicitly, since it is a permanent change to production for the benefit of a CI check: every route accepts bearer tokens from that point on, so a leaked access token is usable without the cookie.

May also touch:
- Repository secrets configuration (documented, not in code)
- Notification configuration (for alerting on failure)

## Edge cases

**The health check itself errors rather than returning pass or fail**
- Treat as failure and do not promote
- Fail closed: if the check cannot run, assume the deployment is broken
- Log the error clearly so a human can diagnose
- This prevents a broken check from silently passing bad deployments

**A critical path is slow on first request because of a cold start**
- Make a warm-up request to each path that is not counted toward the check result
- Wait a reasonable time (e.g., 10-15 seconds) after warm-up before running the actual check
- Document this warm-up behaviour in FACTORY.md
- If the actual check (post-warm-up) still fails due to timeout, treat as failure

**Health check requires an authenticated session**
- Use a dedicated test account whose credentials are stored as repository secrets
- Ensure the test account cannot affect production data (read-only or isolated test data)
- Document which secret names are required
- If authentication fails, treat as health check failure (fail closed)

**Deploy succeeds, check passes, but the app breaks minutes later**
- Outside this item's scope
- This is a deploy gate, not ongoing monitoring
- Consider separately as a monitoring requirement if it becomes a pattern

**Two deploys in quick succession**
- The second deployment waits for the first to complete (including health check and promotion) before starting its own check
- Implemented via workflow concurrency control
- No concurrent promotions to avoid race conditions

**Manual emergency deploy needed with the check failing**
- Document the override path in FACTORY.md
- Require the override to be explicit (e.g., a manual workflow dispatch with confirmation)
- Log the override action (who, when, why) to a notification channel
- Do not leave a silent bypass that could be triggered accidentally
- The override should promote the deployment directly, bypassing the health check

**Health check fails on a non-critical issue**
- No distinction between critical and non-critical paths in the initial implementation
- All configured paths must pass for promotion to proceed
- If a path should be allowed to fail, remove it from the configuration
- Finer-grained control (warnings vs blocking failures) is out of scope

**Preview deployment URL is not available or takes too long**
- The check waits up to the 3-minute timeout
- If no URL is available by then, fail the check (do not promote)
- This is already handled by the existing preview deployment wait logic in factory-deploy.yml

**User-visible behaviour**
- None when deploys are healthy — users see no difference
- Prevents a broken deploy from reaching production, so users never see the broken version
- If a deploy is blocked, the previous deployment continues serving production traffic with no interruption

## Risks

**Money/payment flow**
- The TrueLayer webhook endpoint is verified as part of the health check
- A broken webhook would prevent payment confirmations from reaching the system
- Catching this before promotion prevents payment processing failures
- Risk: if the health check itself is misconfigured, it could block valid deployments

**Migrations**
- No database migrations are part of this item
- The health check runs against the preview deployment, which shares the same database as production
- A migration must be applied manually before merge (existing process, unchanged)

**Authentication and secrets**
- The health check uses a test account stored in repository secrets
- Risk: if the test account credentials leak or expire, the health check will fail and block all deploys
- Mitigation: document the secret names clearly, use a dedicated service account with minimal permissions

**Deployment blocking**
- A misconfigured or over-sensitive health check could block valid deployments
- Risk: if the check has false positives, it could prevent urgent fixes from reaching production
- Mitigation: document the override procedure clearly, make it accessible to authorized users

**Critical path coverage**
- The initial set of paths is minimal (dashboard, quote page, webhook)
- Risk: a deployment could pass the health check but break on an unchecked path
- Mitigation: the configuration is in a single file and can be extended as gaps are discovered

## Derived criteria

- A health check workflow runs automatically after each successful preview deployment
- The workflow verifies at least three critical paths: authenticated dashboard, customer quote page, and TrueLayer webhook endpoint
- The critical paths are defined in a single configuration file, not hardcoded in the workflow
- A failing health check prevents the deployment from being promoted to the production alias
- A failing health check triggers an alert (comment on issue, notification, or similar)
- The health check completes within 3 minutes of the preview deployment being ready
- Cold starts are handled by making a warm-up request before the actual check
- Authentication for protected paths uses a dedicated test account (credentials in secrets)
- Concurrent deployments are serialized — only one can run the health check and promote at a time
- The rollback procedure is documented in FACTORY.md, including manual promotion of a previous deployment
- The manual override procedure is documented in FACTORY.md and requires explicit, logged action
- The test account used for health checks cannot modify production data
