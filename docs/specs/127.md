# Issue #127: Add exit animation and success variant to Toast

## Problem

The toast component at `src/components/ui/toast.tsx:47` animates on entry but disappears instantly with no exit transition, which reads as a bug rather than intentional dismissal. More critically, all toasts render in the same grey visual register regardless of whether they confirm success or signal an error, forcing users to read every message to know if something went wrong. This wastes attention on routine confirmations and risks users missing actual failures.

## Scope

Add an exit animation and visual variants to the toast component:

1. **Exit animation**: When a toast dismisses (either by timeout or user action), it plays a fade+fall transition before removal. The element stays in the DOM during the exit and is removed only after the transition completes.

2. **Visual variants**: Toast accepts an optional `variant` prop with three values:
   - `"default"` (or omitted): current grey appearance, no icon
   - `"success"`: green background with checkmark glyph
   - `"error"`: red background with warning glyph

3. **Timing tokens**: Add CSS custom properties `--ease-out` and `--dur-fast` to `globals.css` for consistent motion timing across the design system.

4. **Sequential presentation**: When two toasts are queued in quick succession, the second waits for the first's exit to complete before entering. No overlapping toasts.

5. **Reduced motion**: Under `prefers-reduced-motion`, both enter and exit apply instantly with no transition duration.

## Explicitly out of scope

- Do NOT change toast positioning, auto-dismiss duration (still 3s), stacking limit, or dismissal timing
- Do NOT change any existing `toast(message)` call sites to pass a variant — they continue to work unchanged
- Do NOT add manual dismiss buttons or user-triggered close actions
- Do NOT add haptics inside the toast component itself
- Do NOT implement a toast queue UI, history, or replay mechanism
- Do NOT change the toast hook signature beyond accepting an optional second parameter for options

## Files

The Engineer is expected to touch:

- `src/components/ui/toast.tsx` — add exit state tracking, variant support, icon rendering, and staggered queue logic
- `src/app/globals.css` — add `--ease-out`, `--dur-fast` tokens and `@keyframes toast-out` animation definition

No migration required. No database changes.

## Edge cases

1. **Component unmounts mid-exit**: If the `ToastProvider` unmounts while a toast is mid-exit animation, the element is removed immediately without error or warning. No memory leak, no stale timers.

2. **Duplicate toast while visible**: If `toast("Saved")` is called twice in quick succession while the first "Saved" toast is still visible, existing behavior is retained unchanged. This spec does not define deduplication — the implementation may show both, replace, or extend, as long as it doesn't break.

3. **Reduced motion with queued toasts**: When two toasts are queued and `prefers-reduced-motion` is set, both still present sequentially (second after first exits), even though the transitions are instant. The sequencing logic is timing-agnostic.

4. **Variant on legacy call sites**: Every existing `toast(message)` call in the codebase renders identically to today (grey, no icon). The `variant` parameter is optional — omitting it is the default path.

5. **Exit triggered during enter**: If a toast's 3s timeout expires while the toast is still mid-enter animation, the exit animation still plays. Enter and exit do not cancel each other.

6. **Empty message with variant**: `toast("", { variant: "success" })` is permitted — it renders an icon in a colored box with no text. Not recommended, but not an error.

## Risks

None. This is a presentational enhancement to an existing UI component. It does not touch:
- User data or database schema
- Authentication or authorization
- Payment or money flows
- External API contracts

The change is additive (new prop, new animations) and backward-compatible (all existing call sites work unchanged).

## Derived criteria

From the Notion spec, I understand the request to be:

1. Toast elements fade and fall out (inverse of the current fade+rise in) over `--dur-fast` timing
2. The DOM element is removed only after the exit transition completes, not during it
3. `toast(message, { variant: "success" })` renders with a green background and checkmark
4. `toast(message, { variant: "error" })` renders with a red background and warning glyph
5. `toast(message)` or `toast(message, { variant: "default" })` renders the current grey appearance with no icon
6. When multiple toasts are triggered rapidly, they present one at a time — the second enters only after the first has exited
7. Under `prefers-reduced-motion`, both enter and exit happen instantly with no animated transition
8. CSS timing tokens `--ease-out` and `--dur-fast` are defined in `globals.css` so the toast animation (and future components) can reference them
9. The toast hook signature remains `(message: string) => void` or is extended to `(message: string, options?: { variant?: "default" | "success" | "error" }) => void` — existing call sites are unaffected
10. No existing call site in the codebase is modified to pass a variant — adoption is opt-in for future work
