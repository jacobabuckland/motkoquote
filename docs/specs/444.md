# UI-3: The backdate picker offers dates the server refuses, and hides today after midnight

## Problem

The "when did they pay?" date picker computes its bounds in UTC (`new Date().toISOString().slice(0, 10)`), while the server anchors picked dates at noon UTC to make them unambiguous across timezones. This causes the picker to offer dates the server will reject for most of every day, and to hide today between 00:00 and 01:00 BST.

## Scope: what changes

1. Add a pure helper to `src/lib/mark-paid-date.ts` that computes local `yyyy-mm-dd` strings from epoch milliseconds, and a variant that returns a date N days before a given instant. The helper derives from local calendar components (`getFullYear` / `getMonth` / `getDate`), not by subtracting milliseconds from an ISO string.

2. Replace the inline `todayIso()` and `minIso()` helpers in `src/app/jobs/[id]/mark-as-paid-button.tsx` with calls to the new helper, passing `MAX_BACKDATE_DAYS` rather than a literal 90.

3. Export `MAX_BACKDATE_DAYS` from `mark-paid-date.ts` if it is not already exported.

The requirement is the round trip: **every date the picker offers must be one `resolveManualPaidAt` accepts, and today must always be offered.**

## Explicitly out of scope

- `resolveManualPaidAt` itself and its noon-UTC anchoring. It is correct and makes date-only strings unambiguous; this item brings the client into line with it.
- The `MAX_BACKDATE_DAYS` value (whether 90 days is right).
- Everything the action does after the date is resolved — settlement, fees, reminder cancellation. All money paths untouched.
- The terminal-state and navigation behaviour in the same file (#442 shipped that).
- `src/lib/invoice-due-date.ts` and `src/lib/contracts/dates.ts`, which use similar patterns. They may have the same defect, but they are different flows with different semantics.
- The DST transition days themselves (a 23- or 25-hour day). Counting back in whole calendar days is the intended behaviour.

## Files

- `src/lib/mark-paid-date.ts` (modify) — add the local-date helper functions
- `src/app/jobs/[id]/mark-as-paid-button.tsx` (modify) — use the helper for both `min` and `max`
- `src/hooks/use-toast.ts` (new) — a two-line re-export of `useToast` from
  `@/components/ui/toast`. Required because the acceptance tests mock that
  path, and a frozen test cannot be repointed at the original module.
- `tests/acceptance/444.test.tsx` (new) — acceptance tests

## Edge cases

- **Timezone west of UTC** — `max` could be tomorrow in UTC terms. Local computation fixes both directions.
- **Exactly 90 days ago** — must be selectable and accepted. This is the boundary that fails today.
- **Blank date** — unchanged: the server reads it as "now".
- **DST boundary within the 90 days** — the offered `min` moves by a calendar day, not by 86,400,000 ms.
- **BST midnight (00:00–01:00 local)** — today must still be offered, not hidden because UTC is yesterday.
- **After noon UTC** — the earliest date must still be accepted, not rejected for being >90 days old by the server's noon-anchored reckoning.

## Risks

This touches the mark-as-paid flow, which gates job closure and payment reminders. However, the fix only affects date validation — it makes the picker offer exactly the dates the server already accepts, rather than changing what the server accepts.

The change is local and reversible: if the helper produces the wrong bounds, reverting the PR restores the current (broken) behaviour immediately.

## Derived criteria

I understood the spec to be asking for:

1. A pure helper function that returns local `yyyy-mm-dd` strings, testable in isolation.
2. The helper takes an epoch timestamp as input (not reading the clock internally) so tests can drive it.
3. Two exports: one returning the local date for a given instant, one returning the date N days before that instant.
4. Both `min` and `max` in the picker use the helper, passing `MAX_BACKDATE_DAYS` for the window.
5. The round-trip property holds: every offered date is accepted, and today is always offered.
6. The fix is measured at specific times across a day (06:00, 18:00, 23:30 UTC) to prove it handles the cases that fail today.
7. Unit tests on the helper (node environment) plus rendered assertions on the picker (DOM environment).
8. No test may read a file under `src/` — all assertions are on observable behaviour or function return values.
