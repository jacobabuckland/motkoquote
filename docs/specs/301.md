# #301: "Untitled job" rows are not identifiable in the jobs list

## Problem

Four of eight rows in the jobs list read "Untitled job". Two of these carry real money — £933.75 and £937.50 — and one has no job type either, so the row's entire identifying content is the word "Untitled" and a timestamp. Two drafts show job type "Job", which is a placeholder rather than a description. This makes it impossible for contractors to identify jobs from the list without opening each one, undermining the utility of the jobs list and the recently-added filter feature.

## Investigation required

**Before implementing the labelling fix, the Engineer must investigate what makes a job "Untitled":**

1. Establish whether "Untitled job" results from: no customer record, a customer with an empty name, or a job created before the customer step
2. Focus on the two archived £900-odd jobs as the informative case: how did they reach a priced state with no customer?
3. Record the finding in a comment on this issue before proceeding with implementation

The investigation determines whether the fix is purely a render-time fallback or whether there's a data-flow issue that needs addressing separately.

## Scope

### What changes

1. **Primary label fallback hierarchy** in `normalizeHistoryJob`:
   - Customer name (if present and non-empty)
   - Job type from `extracted_json.job_type` (if present and not "Job")
   - First line of `sow_json.overview_narrative` or first meaningful text from the SoW (if available)
   - Formatted creation date as "Job from [date]"
   - "Untitled job" only as absolute last resort

2. **Job type descriptor handling**:
   - Stop rendering "Job" as a job type descriptor
   - If job type is absent or equals "Job", omit the descriptor field entirely rather than showing a placeholder

3. **Data fetching** in `/jobs` page:
   - Add `sow_json` to the Supabase select to enable the overview_narrative fallback

4. **Helper imports**:
   - Import `formatDate` from `@/lib/format` into `job-history.ts` for the creation date fallback

### Files expected to change

- `src/lib/job-history.ts` — `normalizeHistoryJob` function to implement fallback hierarchy, `RawHistoryJob` type to add `sow_json` field
- `src/lib/job-history.test.ts` — tests for the new fallback logic
- `src/app/jobs/page.tsx` — Supabase query to include `sow_json` in the select
- `tests/acceptance/301.test.tsx` — acceptance tests (already written)

## Explicitly out of scope

- Preventing jobs from reaching a priced state without a customer (raise separately if investigation shows this is routine)
- Any change to the job creation flow
- Backfilling labels on existing rows (this is a render-time fallback only)
- Changing the database schema

## Edge cases

1. **Customer exists with empty-string name**: Treated as absent, falls through the chain
2. **Derived descriptor longer than the row**: Component already truncates with `truncate` class; full value accessible via browser tooltip
3. **Guest mode jobs with in-memory state only**: Same fallback chain applies (though `sow_json` may not be available)
4. **Archived jobs**: Same treatment as active jobs, no special case
5. **Job type is literally "Job"**: Treated as placeholder, omitted from descriptor
6. **Multiple fallback sources available**: Use the first available in priority order, don't concatenate
7. **`overview_narrative` is very long**: Extract first sentence or first ~50 characters, not the whole paragraph
8. **`sow_json` is null or malformed**: Safely fall through to creation date without crashing

## Risks

- **Breaking existing test fixtures**: `job-history.test.ts` fixtures may need updating if they relied on "Job" or "Untitled job" appearing
- **Query performance**: Adding `sow_json` to the jobs list query increases payload size; monitor for slowdown on large job lists
- **Null safety**: Ensure all new field accesses are safely chained (e.g., `sow_json?.overview_narrative`)

## Derived criteria

What I understood this spec to require:

1. A job with a customer name shows that customer name as the primary label (unchanged from current behavior)
2. A job with no customer but a valid job type (not "Job") shows the job type as the primary label
3. A job with neither shows a derived descriptor from the SoW overview_narrative if available
4. A job with no customer, no job type, and no overview shows a formatted creation date like "Job from 20 Aug 2026"
5. "Untitled job" only appears when absolutely nothing else is available (the last resort)
6. The literal string "Job" never renders as a job type descriptor (it's omitted entirely)
7. Empty-string customer names are treated as missing and trigger the fallback chain
8. The fallback logic works consistently for draft, active, archived, and guest-mode jobs
9. Long descriptors are truncated visually but accessible in full via standard browser mechanisms
10. Investigation findings about why jobs lack customers are documented before implementation begins
