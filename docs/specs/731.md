# check-acceptance-types cannot tell an unfixable type error from a correct failing-first one

**Source:** [Notion roadmap item](https://app.notion.com/p/check-acceptance-types-cannot-tell-an-unfixable-type-error-from-a-correct-failing-first-one-3da1e4f908b481bb9542f1cf81d0d4a3)

**Module:** factory

**Audited against:** main @ 9f1ae79

## Problem

Three items (#718, #719, and one other) were killed at spec stage by type errors `check-acceptance-types.sh` was built to catch, and it passed all three. The check currently classifies diagnostics by code alone (TS2554, TS2493, TS2339 on `never`), which cannot distinguish:

- TS2322 on a field whose type the spec is changing (correct failing-first test) → should be SILENT
- TS2322 on a field whose type the spec is NOT changing (test is wrong) → should be REPORTED
- TS18046 (property access on `unknown`) → should be REPORTED (almost always a poorly-typed mock)

Both of the TS2322 cases produce identical diagnostic codes on identical expression shapes. The only difference is *what the spec says the item changes*.

Example from #719: `w.payload.stage_number` where `payload` is `unknown` from `getWrites()` (a test helper) → TS18046. This is a test bug (the helper returns `unknown` for untyped fields), not a failing-first assertion, but the check stayed silent.

Example from #718: `{ ...EMPTY_SOW_STATE, customer_name: null }` annotated as `SowState`, where the spec changes a different part of that schema → TS2322. The test asserts a type change the item isn't making, but the check stayed silent.

The check needs the spec's `## Files` section to know what the item is changing, the same way `check-acceptance-run.sh` uses it to distinguish "module not written yet" from "broken import".

## Scope: what changes

1. **`check-acceptance-types.sh` takes the spec path as its first argument**, matching `check-acceptance-run.sh`'s signature:
   ```bash
   scripts/factory/check-acceptance-types.sh <spec.md> <tests-file> [tsc-log]
   ```

2. **Read the `## Files` section** from the spec to extract all files the item touches (both `(new)` and `(modify)`), using the same parsing logic as `check-acceptance-run.sh`.

3. **Add TS18046 to the reporting list** ("`'X' is possibly 'never'`" / "`Object is of type 'unknown'`"). These diagnostics indicate property access on `unknown` or `never`, almost always from a poorly-typed mock. A correct failing-first test does not produce this — it means the test helper itself is wrong.

4. **Keep TS2322 on the allowlist for now**, documented as a known limitation: without the TypeScript compiler API, we cannot reliably extract where a type is declared from `tsc --noEmit` output alone. The diagnostic text does not name the declaring file. Future enhancement would use `tsserver` or the compiler API to resolve symbols, but that's out of scope for this fix.

The practical result: TS18046 (case 3 from #719) is caught immediately. TS2322 (case 4 from #718) remains a known gap, documented in the script's header so the next attempt doesn't re-discover the same difficulty.

## Explicitly out of scope

- Fully resolving TS2322 based on declaration location (would require TS compiler API or tsserver, substantially more complex)
- Changing the PM workflow's call sites (they'll be updated in the same PR, but that's mechanical)
- Modifying how tsc output is captured or formatted
- Any diagnostics other than TS18046 (the one clear win from this change)

## Files

The complete list of files expected to change:

- `scripts/factory/check-acceptance-types.sh` (modify) — accept spec path, parse `## Files`, add TS18046 to reporting logic
- `tests/regression/factory-acceptance-types.test.ts` (modify) — add corpus cases for TS18046 being reported, document TS2322 limitation
- `.github/workflows/factory-pm.yml` (modify) — update call site to pass spec path

## Edge cases

- **Spec with no `## Files` section**: Script should handle gracefully (empty file list), same as `check-acceptance-run.sh` does.
- **Spec with only `(new)` files**: Works correctly; the check extracts both new and modify markers.
- **Colourised tsc output**: Already handled by existing ANSI-stripping logic, no change needed.
- **Multiple diagnostics in one log**: Each is classified independently, same as current behavior.

## Failure modes

None. The change is additive (adding TS18046) and makes the spec available for future use. Existing classifications are unchanged.

## Risks

None. TS18046 is unambiguously a test bug — a correct failing-first test never accesses properties on `unknown`. Adding it to the reporting list cannot produce false positives.

## RUNNABLE

```bash
scripts/factory/check-acceptance-types.sh <spec.md> <tests-file> [tsc-log]
```

The acceptance tests must invoke this end-to-end with fixture specs and logs.

## Derived criteria

Based on the human's specification, this item asks for:

1. The check script now takes the spec path as its first argument, before the tests file path.
2. The check reads and parses the `## Files` section from the spec, extracting all listed files (both new and modify).
3. TS18046 diagnostics (property access on `unknown`/`never`) are always reported, never silenced.
4. The existing TS2554, TS2493, TS2339-on-never reporting continues unchanged.
5. All existing silence cases (TS2307, TS2339 on module namespace, property access on wrong-but-changing types) remain silent.
6. The regression test corpus validates both directions: known unfixable errors must be reported, known correct failing-first tests must stay silent.
7. The script documents the TS2322 limitation clearly in its header, so the gap is known rather than rediscovered.
8. The PM workflow is updated to pass the spec path when calling the check.

The criterion that matters: the nine-case corpus must pass in both directions — no false negatives (letting bad tests through) and no false positives (blocking correct tests).
