# Issue #184: Correct jobs stranded at accrued under collected collections

**REQUIRES DATABASE MIGRATION: NO**

## Problem

When `settleFeeCollection` crashed between its three writes (fee_collection → jobs → contractors), jobs were left at `fee_status='accrued'` while their collection moved to `status='collected'`. The monthly batch (`runFeeCollectionBatch`) queries `jobs WHERE fee_status='accrued'`, so these stranded jobs are re-rolled into subsequent batches with a new `period_start`. This creates a second charge against the same jobs — a double-billing bug. Some trades have already been charged twice; others will be at the next batch unless corrected.

Policy is to correct legacy money records retroactively. Here that means: stopping pending second charges by marking stranded jobs `fee_status='collected'`, and listing already-double-charged jobs for manual TrueLayer refund.

## Scope: what changes

- A new backfill function `correctStrandedFeeJobs` in `src/lib/correct-stranded-fee-jobs.ts` that:
  - Runs in dry-run mode by default (`dryRun: true`)
  - Queries every job at `fee_status='accrued'` whose collection is `status='collected'`
  - For each stranded job, checks whether a second collection containing that job has been created (by scanning `fee_collections` for a later `period_start` where `job_ids @> ARRAY[job.id]`)
  - Returns a structured report with two groups:
    - **Not yet double-charged**: stranded jobs where no second collection exists
    - **Already double-charged**: stranded jobs where a second collection (status='pending' or 'collected') was created, listing both collection IDs, period dates, and amounts
  - When `dryRun: false`, updates `jobs.fee_status = 'collected'` for all stranded jobs (both groups), in one transaction per collection
  - Re-running after completion returns zero affected rows and makes no changes

- The function returns a typed result:
  ```typescript
  {
    strandedJobsFound: number;
    notYetDoubleCharged: Array<{jobId, collectionId, contractorId, periodStart, feeAmountPennies}>;
    alreadyDoubleCharged: Array<{jobId, firstCollectionId, secondCollectionId, firstPeriodStart, secondPeriodStart, feeAmountPennies}>;
    corrected: number; // how many jobs were updated (0 in dry-run)
  }
  ```

- A one-shot script or manual invocation path (exact location up to Engineer) that calls `correctStrandedFeeJobs({dryRun: true})` to produce the report, commits the report as a file, and after approval re-runs with `dryRun: false` to apply corrections

## Explicitly out of scope

- **Do not** issue refunds automatically. The already-double-charged list is for manual TrueLayer processing.
- **Do not** modify `settleFeeCollection` or any other settlement logic.
- **Do not** create, cancel, or modify any `fee_collection` rows.
- **Do not** create, modify, or reverse any TrueLayer charges.
- **Do not** send contractor notifications from this code. Notification happens manually after reviewing the report.
- **Do not** correct any other `fee_status` inconsistency not caused by this specific crash pattern (job accrued, collection collected).

## Edge cases

1. **Job already double-charged**: list it with both collection IDs and amounts for manual refund. Correcting `fee_status` afterwards is still required to prevent a third charge.

2. **Collection is collected but the charge later failed or was reversed**: if a collection is `status='collected'` but the TrueLayer payment was later reversed, exclude that collection from correction and list it separately. Do not guess — this requires a human to reconcile.

3. **Contractor account deleted or anonymised**: skip and list separately. Do not attempt to correct jobs for non-existent contractors.

4. **Job deleted since settlement**: if a job in a collected collection's `job_ids` array no longer exists, skip it and note the orphan collection in the report.

5. **Stranded job whose contractor has since cancelled their mandate**: correct `fee_status` as normal. The correction prevents re-billing; no new charge is created either way.

6. **No stranded jobs found**: report states "0 stranded jobs found" and exits cleanly. This is success, not an error.

7. **Re-running after completion**: the query (`fee_status='accrued' AND collection.status='collected'`) matches zero rows, so the report shows zero affected and no updates happen. Idempotent.

8. **Job appears in multiple collections**: if a stranded job somehow appears in more than one collected collection (should be impossible but check), list it separately as an anomaly requiring manual investigation. Do not auto-correct.

## Risks

- **Money**: this backfill prevents future double-charges and identifies past ones. Errors could cause under-billing (if we incorrectly mark a genuinely accrued job as collected) or fail to prevent a second charge (if we miss a stranded job). The dry-run-first approach gates this.

- **User data**: updates `jobs.fee_status`, a money-critical field. Changes are permanent once committed. The dry-run report must be reviewed and approved before the write runs.

- **Idempotency**: the correction must be safe to re-run. The query itself is idempotent (once corrected, jobs leave the result set), but the double-charge detection must not double-count.

- **Concurrency**: this backfill should NOT run while the bug that creates stranded jobs is still live, or it will race new occurrences. The issue states "Do not run while the bug that creates these records is still live" — the Engineer must verify `settleFeeCollection` is fixed (or the fix is in the same PR) before running the backfill.

- **Foreign key constraints**: jobs reference fee_collections, but the correction only updates jobs — no cascade risk. Contractors reference is read-only for this backfill.

## Derived criteria

1. A function `correctStrandedFeeJobs` exists that identifies jobs at `fee_status='accrued'` under collections at `status='collected'`

2. The function runs in dry-run mode by default and writes nothing without an explicit `dryRun: false` flag

3. The dry-run report lists every stranded job with: job ID, collection ID, contractor ID, period_start, fee amount in pennies

4. The report separates jobs into two groups: not yet double-charged, and already double-charged (where a second collection containing that job has been created)

5. The already-double-charged group includes both collection IDs, both period dates, and the fee amount for each occurrence

6. When `dryRun: false`, the function updates `jobs.fee_status = 'collected'` for all stranded jobs, transactionally per collection

7. The update only touches jobs where `fee_status='accrued'` AND their collection is `status='collected'` — no other jobs are modified

8. Re-running after completion reports zero affected rows and makes no changes (idempotent)

9. The function does not create, modify, or reverse any charge or collection row

10. The function does not issue refunds — the already-double-charged list is for manual processing

11. The invariant holds after completion: no job under a collected collection remains at `fee_status='accrued'`

12. Edge cases (contractor deleted, job deleted, charge reversed, no jobs found) are handled explicitly as specified above
