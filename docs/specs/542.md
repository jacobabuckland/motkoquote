# PFIX-6: Retire the dead audio-capture path and three orphan tables

## Problem

Three artefacts of removed features are live on production with no code behind them. The audio path has a `jobs.source_audio_url` column with no writer, a `voice-notes` storage bucket with 21 objects (4.6 MB, 10–12 July 2026, all under one owner folder), per-user access policies, and an account-erasure sweep that references it. Only 5 job rows reference an object; 16 are orphaned. Three orphan tables — `client_errors`, `feedback`, and `rate_limits` — exist on production, are created by no migration, and are written by no code. The drift check that exists to catch precisely this cannot see them: all three were written into the public-surface manifest by the same commit that created the check, so they are permanently inside its allowlist.

**Decision 3 Sep 2026 — Jacob:** Delete the audio, keep the stored transcripts. The 21 recordings go, the `source_audio_url` column goes, the `voice-notes` bucket and its policies go, the erasure sweep stops referencing it, and the three orphan tables (`client_errors`, `feedback`, `rate_limits`) are dropped and removed from the public-surface manifest.

## Scope: what changes

1. **Storage deletion script** (`scripts/backfill/delete-voice-note-objects.ts`) — a deliberate two-step: bare invocation lists what it would delete (bucket, object count, total bytes, owner folder) and deletes nothing. `--confirm` performs the deletion. Idempotent: second run reports zero and exits 0.

2. **Migration 064** (`supabase/migrations/00000000000064_retire_audio_path_and_orphan_tables.sql`) — drops the three orphan tables (`client_errors`, `feedback`, `rate_limits`), drops `jobs.source_audio_url`, drops the `voice-notes` bucket policies. Must not silently succeed if the bucket is non-empty: if objects remain, stop and say so.

3. **Account erasure** (`src/lib/account-erasure.ts`) — remove `"voice-notes"` from the `OWNED_BUCKETS` array, and remove the `source_audio_url: null` line from the job-scrub update. The erasure tests must still pass.

4. **Manifest** (`src/checks/public-surface.json`) — remove the three orphan tables (`client_errors`, `feedback`, `rate_limits`).

5. **Object-inventory check** (`src/checks/object-inventory.check.test.ts`) — the check must pass with the three tables removed from the manifest, and fail if one of them is reintroduced.

## Explicitly out of scope

- The 3 stored transcripts on `jobs.transcript` are untouched. This item deletes audio, not text.
- The manifest-seeding blind spot (that a drift check whose baseline was seeded from production has a blind spot equal to whatever was already wrong that day) is not in this item — it is CHK-1.
- The `logos` and `receipts` storage buckets are unchanged.
- No changes to job rows that still point at a deleted object: the column is being dropped, so this resolves itself, but the script must not fail on it.

## Edge cases

- **Object already gone**: Idempotent — second run reports zero and exits 0, so a partial failure can be retried.
- **Job row still pointing at deleted object**: Five rows do. The column is being dropped, so this resolves itself, but the script must not fail on it.
- **Bucket not empty at migration time**: The migration must not silently succeed over a non-empty bucket. If objects remain, stop and say so.
- **No credentials provided**: Script refuses to run without SUPABASE credentials, reporting what is missing.

## Risks

**This is an irreversible deletion.** Once the storage objects are gone and the tables are dropped, they cannot be recovered. The order of operations is load-bearing:

1. Script runs first (bare, then with `--confirm`)
2. Migration applied by hand (after objects gone, before code merge)
3. Manifest change merges last (after tables actually dropped)

The deletion is deliberate and decided, but the sequence matters: schema must precede code (CLAUDE.md), and deletion must precede schema.

## Order of operations

This is part of the contract:

1. The script runs first, and it is a deliberate two-step. A bare invocation lists what it would delete — bucket, object count, total bytes, owner folder — and deletes nothing. `--confirm` performs the deletion. A one-shot destructive default is not acceptable here.
2. The migration is applied by hand by Jacob (`supabase db push`), after the objects are gone and before the code that stops referencing them merges. Schema precedes code; deletion precedes schema.
3. The manifest change merges last, because until the tables are actually dropped the check should still expect them.
