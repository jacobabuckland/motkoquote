# Issue #258: LED-5: Voice cost capture

**BLOCKING DEPENDENCY:** This item MUST NOT be implemented until LED-1 (#244), LED-2 (#252), and LED-3 (#254) are live on production and the ledger is populated with real data. Voice over an untrusted or empty ledger produces confident answers about nothing — the failure pattern this codebase has seen repeatedly.

**Database migration required:** No — writes to the `job_costs` and `counterparties` tables created by LED-1

## Problem

The capture moment that actually happens is the drive back from the merchant, hands not free. Voice already exists for job capture (scope of work); this extends it to cost capture. A contractor needs to log "Materials came to two eighty at Screwfix for the Henderson job" while driving, and have it draft a confirmed cost entry without touching the keyboard.

## Scope: what changes

### 1. Voice cost capture flow

A new voice interface accessible from two places:
- From the job page: a "Record a cost" button (or similar) that opens the voice cost capture flow scoped to that job
- From "Speak to motko": a general voice interface that accepts cost entries alongside other voice commands

The flow:
1. Contractor speaks a cost: "Materials came to two eighty at Screwfix for the Henderson job"
2. Model extracts: amount (£280), counterparty (Screwfix), category (materials), and attempts job matching by customer name ("Henderson")
3. System presents a confirmation screen showing:
   - Parsed amount in unambiguous form: "£280.00"
   - Counterparty: "Screwfix"
   - Category: "Materials"
   - Matched job: "Henderson bathroom" (or similar job title/customer name)
   - Date: defaults to today, editable
   - VAT treatment: defaults to standard (or contractor's usual), editable
4. Contractor confirms or corrects
5. On confirmation, code writes the cost row to `job_costs` with `source = 'voice'`

**Money-integrity rule (non-negotiable):** The model may propose structure. Code computes and validates every amount. A spoken amount is parsed to integer pence by deterministic code from the transcript, never taken from a model-authored number field. The parsed figure is repeated back for confirmation before any write occurs.

### 2. Deterministic amount parsing

A new module `src/lib/voice/parse-amount.ts` that converts spoken amounts to integer pence:

```typescript
/**
 * Parses a spoken amount to integer pence. Returns null for ambiguous/unparseable input.
 * Examples:
 * - "two eighty" → 28000 (£280)
 * - "two hundred and eighty" → 28000
 * - "280 pounds" → 28000
 * - "two eighty five ninety-nine" → AMBIGUOUS → null (ask for clarification)
 * - "fifty pence" → 50
 * - "two pounds fifty" → 250
 */
export function parseSpokenAmount(transcript: string): number | null
```

The parser must:
- Handle British currency conventions: "two eighty" means £280, not £2.80
- Distinguish "two hundred and eighty pounds" (£280) from "two eighty" (also £280)
- Detect ambiguous cases (e.g. "two eighty five ninety-nine" — is that £2859.90 or two separate amounts?) and return null rather than guessing
- Handle pence explicitly: "fifty pence" → 50 pence, "two pounds fifty" → £2.50
- Be deterministic: same input always produces same output
- Return null for unparseable input rather than throwing

When the parser returns null, the voice flow asks for clarification: "Sorry, I didn't catch that amount — how much was it?"

### 3. Job matching

Jobs are matched by:
- Customer name (primary): "for the Henderson job" matches jobs where `customers.name` contains "Henderson"
- Job reference (if implemented): "for job 23" matches `jobs.id` or a human-readable reference if one exists

Matching rules:
- Exact match (single result): auto-select and show for confirmation
- Multiple matches: present a disambiguation screen: "I found two Henderson jobs — which one?" with a list of job titles/addresses
- No match: present a list of recent jobs for manual selection, or offer to add the cost without a job link (if supported)
- Never invent a job or customer that doesn't exist

The match is performed server-side against the contractor's own jobs only (RLS-scoped).

### 4. Counterparty matching

Counterparty names are matched and created exactly as LED-1 specifies:
- Case and whitespace-insensitive matching: "Screwfix", "screwfix", "SCREWFIX " all match the same counterparty
- Match or create on miss: if "Screwfix" doesn't exist, it's created with `kind = 'supplier'` (default for merchant names)
- Stored in the `counterparties` table with `contractor_id` scoping

### 5. Category inference

The model may suggest a category (`materials`, `labour`, `subcontractor`, `plant_hire`, `other`) based on context ("materials came to..."), but the confirmation screen shows it and allows correction.

Default to `materials` when uncertain.

### 6. Multiple costs in one utterance

The spec says "Multiple costs in one utterance handled or explicitly refused — decide and state".

**Decision:** Explicitly refuse and ask for one at a time.

If the model detects multiple amounts in a single utterance (e.g. "I spent fifty at Screwfix and another thirty at Toolstation"), respond: "I can log one cost at a time — let's start with the first one. Was that £50 at Screwfix?"

This avoids the complexity of handling multiple confirmations and reduces error risk.

### 7. No vacuous answers

The voice-invention defect (captured in other tickets) must not recur here. If a field cannot be determined from what the contractor said:
- Job: ask "Which job is this for?" rather than inventing one
- Counterparty: ask "Where was this from?" rather than defaulting to "Unknown" without asking
- Amount: if unparseable, ask again rather than setting a placeholder

A cost row is never written with invented data.

### 8. Confirmation screen

Before any database write, the contractor sees and confirms:
- The parsed amount, shown as "£280.00" (unambiguous, with pence)
- The repeated-back amount in words: "That's two hundred and eighty pounds — is that right?"
- Counterparty, job, category, date, VAT treatment
- "Confirm" and "Cancel" buttons
- Ability to edit any field before confirming

Only "Confirm" writes to the database.

## Explicitly out of scope: what does not change

- **No querying** (LED-6): "How much have I spent at Screwfix?" is out of scope
- **No editing existing costs by voice**: voice is for capture only, not for modifying rows
- **No receipt photo in the same flow**: LED-3's photo capture remains separate
- **No batch entry**: one cost per voice interaction
- **No offline capture**: voice requires network connectivity for the realtime API
- **No P&L queries**: "Did the Henderson job make a profit?" is LED-6

## Edge cases

### Amount parsing edge cases

- **"two eighty"**: £280 (not £2.80 — British convention)
- **"two hundred and eighty"**: £280
- **"280 pounds"**: £280
- **"two pounds eighty"**: £2.80
- **"fifty pence"**: £0.50
- **"two eighty five ninety-nine"**: AMBIGUOUS → ask for clarification (could be £2859.90 or two separate amounts)
- **"twenty"**: AMBIGUOUS → "Twenty pounds or twenty pence?"
- **"negative amount" or "minus"**: Ask for clarification — refunds should be stated clearly: "I got a refund of fifty pounds"
- **"a hundred and something"**: Unparseable → ask again
- **"about fifty quid"**: Parse as £50, ignore the "about" qualifier

### Job matching edge cases

- **No job matched**: Offer a list of recent jobs for manual selection, or allow adding the cost without a job (if the schema permits `job_id` to be null — check LED-1)
- **Multiple jobs for the same customer**: Disambiguate by address or date: "I found two Henderson jobs — one on Cedar Road and one on Park Street. Which one?"
- **Job name vs customer name**: Match on customer name primarily, but allow "the bathroom job" or similar natural references
- **Deleted or archived job**: Should not appear in match results

### Counterparty edge cases

- **Merchant name with noise**: "I was at, uh, Screwfix" → extract "Screwfix"
- **Abbreviations**: "B&Q" vs "B&amp;Q" vs "B and Q" → normalize and match
- **Generic descriptions**: If the contractor says "the supplier" without a name, ask: "Which supplier was that?"
- **No counterparty mentioned**: Valid for some costs (fuel, parking) — `counterparty_id` can be null per LED-1 schema

### Confirmation and correction

- **Mis-heard amount**: Contractor corrects during confirmation: "No, it was three eighty, not two eighty" → re-parse and re-confirm
- **Wrong job matched**: Provide a way to select a different job during confirmation
- **VAT treatment wrong**: Editable on the confirmation screen

### Failure modes

- **Network failure during voice session**: Show error, offer to retry or enter manually
- **Realtime API unavailable**: Fall back to manual cost entry form
- **Database write fails after confirmation**: Show error, do not leave the contractor thinking it succeeded
- **Amount parser returns null**: Ask for clarification, do not default to zero or guess

## Risks

### Money handling

- **Amount parsing errors** would write wrong amounts to the ledger. Mitigated by:
  - Comprehensive unit tests on `parseSpokenAmount`
  - Repeat-back confirmation before write
  - Deterministic parsing (no model involvement in amount computation)

- **Silent write failures** would lose cost data. Mitigated by:
  - Explicit error handling
  - Confirmation screen only shown after successful parse, not after write
  - Database write errors surfaced to the user

### Data integrity

- **Cross-tenant access** to costs or counterparties would leak sensitive data. Mitigated by:
  - RLS enforced by LED-1 migrations
  - Explicit RLS tests in acceptance criteria

- **Inventing jobs or counterparties** would pollute the ledger. Mitigated by:
  - Explicit "never invent" rule
  - Match-or-ask pattern for ambiguous cases

### User trust

- **Wrong amounts written silently** would destroy trust in voice capture. Mitigated by:
  - Mandatory confirmation screen
  - Visual and verbal repeat-back of the amount

### Rollout

- **Untested on device**: The spec requires final verification in the WKWebView wrapper on cellular, which the factory pipeline cannot do. Jacob must verify before shipping.

## Derived criteria

What I understood the human to be asking for:

1. A voice interface for capturing costs (amount, counterparty, category, job) accessible from the job page and/or general voice entry
2. Deterministic amount parsing from spoken input (£280 from "two eighty"), unit-tested, with ambiguous cases asking for clarification rather than guessing
3. Job matching by customer name or reference, with disambiguation for multiple matches and no invention of non-existent jobs
4. Counterparty matching and creation following LED-1's normalization rules
5. A confirmation screen showing the parsed cost (amount, counterparty, job, category, date, VAT) with editable fields, before any database write
6. Amount repeat-back for confirmation (verbal: "That's two hundred and eighty pounds", visual: "£280.00")
7. Explicit refusal of multiple costs in one utterance (one at a time only)
8. No field ever set from a vacuous or invented answer — always ask when uncertain
9. Costs written to the `job_costs` table with `source = 'voice'` only after confirmation
10. Works in the iOS WKWebView wrapper on cellular (final verification by Jacob)
11. Does not ship until LED-1 through LED-3 are live and the ledger has real data
