# Issue #595: CONN-2 — Onboarding opens in SFSafariViewController, never the Capacitor webview

## Problem

The Stripe Connect onboarding flow currently navigates the entire iOS app's WKWebView away from motko.app and onto connect.stripe.com via `window.location.href = res.url`. This is correct on web but breaks in the iOS shell: Stripe's hosted onboarding requires camera and document upload and is not built to run inside an embedded webview, and the app has no back/close chrome once it leaves motko.app. Zero of six external accounts have a connected Stripe account (verified production, 5 Sep). A trade who opens onboarding in the native app cannot finish it.

## Scope: what changes

1. **Add @capacitor/browser plugin** (Capacitor 7 line) to package.json dependencies
2. **Branch the onboarding handler in stripe-connect-section.tsx** on `Capacitor.isNativePlatform()`:
   - Native: call `Browser.open()` with the account-link URL to present in SFSafariViewController
   - Web: continue using `window.location.href` assignment
3. **Handle browser closure on native**: listen for the `browserFinished` event from @capacitor/browser, then call the existing `refreshStripeStatus()` server action to re-read account status and re-render the section
4. **Preserve error surfacing**: both paths must continue to display the error message when `startStripeOnboarding()` returns `{ error: string }`
5. **Extend tests/helpers/capacitor.ts** to mock @capacitor/browser alongside the existing seven plugins

## Explicitly out of scope

- The onboarding funnel, copy, and payment-link gate (CONN-1)
- The payout leg (PAY-8)  
- Associated-domains or universal-link configuration
- Changes to the web path beyond guarding it behind the platform check
- Behavior when the plugin is missing at runtime (degrades to current behavior, which is acceptable until the TestFlight build ships)

## Files

- package.json (modify) — add @capacitor/browser to dependencies
- src/app/settings/stripe-connect-section.tsx (modify) — branch onboarding handler, add browserFinished listener
- tests/helpers/capacitor.ts (modify) — extend CapacitorPluginMocks to include Browser
- tests/acceptance/595.test.tsx (new) — acceptance tests

## Edge cases

- **Plugin not available at runtime**: code must not throw; degrades to current `window.location.href` behavior until the native rebuild ships. Not tested (cannot be expressed without a conditional import), documented as acceptable degradation.
- **Failed startStripeOnboarding**: error message must surface in both the native and web paths, exactly as it does today.
- **Browser closed without completing onboarding**: `refreshStripeStatus()` runs regardless; if the account remains incomplete, the section stays in its pre-onboarding state, which is correct.
- **refreshStripeStatus returns error**: treated as a failed refresh (status does not update); the section remains in whatever state it showed before the browser opened. The user can retry.
- **Multiple rapid clicks on the setup button**: `useTransition`'s `starting` flag already disables the button while `startStripeOnboarding` is in flight, so duplicate onboarding flows cannot race.

## Risks

- **Requires native rebuild**: adding a Capacitor plugin requires `npx cap sync` and cannot reach devices through Vercel deploy. Ships with the next TestFlight build, not on merge. Merge is safe because the web path is unchanged and the native path degrades to current behavior if the plugin is absent.
- **Touches payment onboarding**: though behavior-preserving on web and purely additive on native, this is customer-money-adjacent. Tested with mocks; human checklist below confirms on physical device before TestFlight submission.

## Human checklist — not an acceptance criterion

After the native rebuild and before TestFlight submission:
- [ ] Confirm on a physical iOS device that tapping "Connect to Stripe" presents the onboarding flow in SFSafariViewController (not in the app's own webview)
- [ ] Confirm that completing onboarding returns to the app with the section showing "Set up ✓"
- [ ] Confirm that abandoning onboarding (closing the Safari view mid-flow) returns to the app with the section unchanged

No test in this repo can observe SFSafariViewController vs. WKWebView, so this remains a manual check.

## Derived criteria

I understood the issue to be asking for:

1. On the native platform (iOS shell), the Stripe onboarding handler must call `Browser.open()` with the account-link URL and must never assign to `window.location.href`, so the flow presents in SFSafariViewController rather than navigating the app's own webview away.

2. On the web platform, the handler must continue to assign to `window.location.href` and must never call `Browser.open()`, preserving the current correct behavior.

3. When the in-app browser reports closure (via the `browserFinished` event), the app must call `refreshStripeStatus()` to re-read account status from Stripe and re-render the section, so a trade who completes onboarding sees "Set up ✓" rather than the section remaining in its pre-onboarding state.

4. Neither the native nor web path may swallow the error case: when `startStripeOnboarding()` returns `{ error: string }`, that message must surface in the UI exactly as it does today.

5. The Capacitor test helper at `tests/helpers/capacitor.ts` must be extended to mock `@capacitor/browser` alongside the existing plugins, following the same call-recording pattern and honoring the `mockNativePlatform(true|false)` flag.
