# CHK-1: Derive object-inventory manifest from migrations

## Problem

The public-surface manifest (`src/checks/public-surface.json`) that `object-inventory.check.test.ts` asserts against was seeded from a live production snapshot on 31 Aug 2026. Everything that was already wrong on production that day is now permanently inside the check's allowlist. The check can only ever catch drift that happened *after* it was installed, while reading as though it certifies the whole surface.

A drift check whose baseline is taken from the system it is checking has a blind spot equal to whatever was already wrong when it was taken. That blind spot hid `settle_fee_collection` — a `SECURITY DEFINER` function callable by `anon`, able to mark fees collected and clear a contractor's billing hold, present in no migration, called by no code, live for weeks with every gate green.

## Scope: what changes

Re-derive the manifest from the migrations rather than from production. The migrations become the source of truth for what production is allowed to contain. An object present on production with no migration behind it now fails the check by construction, whether it appeared before or after the check existed.

A generator script walks `supabase/migrations/*.sql` and produces the expected object set: tables and functions created by migrations, minus those dropped by later migrations, excluding extension-owned objects. The generator is invocable as a command, so verifying production against the migrations is a matter of running the script and comparing its output to what the live check sees.

## Explicitly out of scope

- The live check (`object-inventory.check.test.ts`) continues to compare production against the manifest file, as it does today. Its assertion logic does not change.
- The database query (`check_public_object_inventory`) does not change. Migration 58's extension exclusion already does what is needed.
- The manifest file remains at `src/checks/public-surface.json` and continues to be committed. The generator's job is to produce it, not to replace it with a runtime query.

## Files

- `scripts/checks/derive-object-manifest.ts` (new) — generator that walks migrations and outputs the expected manifest
- `src/checks/public-surface.json` (modify) — will be regenerated by the generator, committed, and continue to be read by the live check
- `src/checks/object-inventory.check.test.ts` (modify) — update comment to reflect that the manifest is now migration-derived

RUNNABLE: npx tsx scripts/checks/derive-object-manifest.ts --out <path>

## Edge cases

**Conditional creation** (e.g., `create table if not exists`, or creation inside a `do $$ … end $$;` block): Parse what can be parsed. DDL outside a procedural block is unambiguous and covers nearly every migration in this repository. A migration the generator cannot parse should fail loudly rather than being silently skipped — a silent skip reintroduces the blind spot in a new form.

**Objects dropped by later migrations**: The manifest is the result of replaying migrations in order, not the union of everything ever created. If migration N creates `foo` and migration N+50 drops it, the final manifest must not contain `foo`. The generator must track drops.

**Extension-owned objects**: Migration 58 already excludes these from `check_public_object_inventory()`. Keep that exclusion and its reasoning — an extension is reviewed as a unit when it is installed, and its members are covered there. The check exists to find objects that belong to no extension and no migration.

**Re-running produces identical output**: Running the generator twice on an unchanged migration tree must produce bitwise-identical output, so a diff means something changed. Sort deterministically (by kind, then name) and format consistently (JSON, 2-space indent, trailing newline).

## Risks

None. This is a tightening of a check, not a mutation of production state or a schema change. The worst-case outcome is the check surfacing pre-existing drift that was previously invisible — which is the point, not a risk.

## Derived criteria

1. A generator script at `scripts/checks/derive-object-manifest.ts` can be invoked as `npx tsx scripts/checks/derive-object-manifest.ts --out <path>`
2. The generator walks `supabase/migrations/*.sql` in order and builds the expected object set
3. It recognizes `create table`, `create function`, `create or replace function` and records the object
4. It recognizes `drop table`, `drop function` and removes the object from the set
5. Re-running the generator on an unchanged tree produces identical output
6. The manifest format matches `src/checks/public-surface.json`: an array of `{object_kind, object_name}` objects, sorted by kind then name
7. A table or function created by a migration appears in the generated manifest
8. A table or function dropped by a later migration does not appear in the final manifest
9. The generator is stricter than a baseline seeded from production: an object with no migration behind it is absent from the generated manifest, even if it exists on production
10. Extension-owned objects (determined by `pg_depend.deptype = 'e'`) are excluded, following migration 58's pattern
