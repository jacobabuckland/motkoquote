# CFIX-1: A contract whose delivery fails is marked sent, cannot be re-sent, and says nothing

## Problem

The `createContract` action in `src/app/dashboard/actions.ts` inserts the contract row with `status: "sent"` immediately, then attempts PDF rendering (guarded) and customer notification (unguarded). When `notifyCustomer` throws, the contract is already persisted as sent but the action never completes. This produces four compounding failures:

1. The contract row exists with `status: "sent"` and `sent_at` populated, but no `contract_sent` event was recorded, so nothing indicates delivery
2. `revalidatePath("/dashboard")` never runs—it sits after the throw—so the cached dashboard still shows the quote under "Accepted quotes awaiting contract"
3. Every retry attempt fails immediately on the `contracts_quote_id_key` UNIQUE constraint, showing a raw Postgres error message
4. The contractor sees React's production redaction notice instead of an authored error message, because the throws are bare `new Error(...)` rather than `actionableError(...)`

The customer may have received nothing, the database says they were sent it, the dashboard invites retry, and retry produces an unintelligible error. There is no way forward from inside the app.

## Scope: what changes

1. **Guard `notifyCustomer` the same way PDF rendering is guarded**: wrap it in `.catch()` so delivery failure does not throw. The action completes with `delivered: false`, allowing the existing `delivered=0` banner path to surface the copy-link fallback.

2. **Ensure `revalidatePath` runs regardless of delivery outcome**: the dashboard must reflect the contract's existence whether or not the email landed.

3. **Catch duplicate-contract attempts and return an authored message**: a second send for the same quote returns an `actionableError` explaining the contract was already sent, with the existing contract's URL for the contractor to share.

4. **Replace all bare `throw new Error(...)` calls with `actionableError(...)`**: authored messages survive the production build's redaction; raw Supabase errors and generic failures do not.

## Explicitly out of scope

- Removing or relaxing the `contracts_quote_id_key` unique constraint—one contract per quote is correct; the bug is the unguarded path into violating it
- Re-sending or repairing existing orphaned contracts like `95f1efc5`—that is a data question for the operator, not this item's job
- Changing anything about the successful-send path—delivered contracts navigate and display exactly as they do today

## Files

- `src/app/dashboard/actions.ts` (modify) — guard `notifyCustomer`, handle duplicate-key errors, use `actionableError` for all throws
- `src/app/dashboard/create-contract-form.tsx` (verify) — already handles `actionableError` via `actionableMessage`; no change expected, but verify error display works with the new error types

## Edge cases

- **PDF renders but both email and SMS fail**: still `delivered: false`, still navigates to the job page with `delivered=0` banner and copy-link fallback
- **Customer has phone-only, or email-only, or has opted out of SMS**: already handled correctly by `notifyCustomer`; do not regress the existing channel-selection logic
- **The contract insert itself fails** (e.g., foreign-key violation, database unavailable): that is a genuine failure with nothing sent—it must NOT mark the record as sent, and needs its own authored `actionableError` message
- **Two send attempts race on the same quote**: the unique constraint is the backstop; the loser receives the authored "contract already sent" message with the existing contract's URL

## Risks

None. The change is purely additive error handling around an existing flow. Successful sends are unchanged; failed sends gain a forward path they currently lack.

## Derived criteria

1. A contract whose delivery reaches no channel (email fails, SMS unavailable/failed) completes normally: the contract row is inserted with `status: "sent"`, the dashboard is revalidated, and the contractor lands on the job page with the `delivered=0` banner offering a copy-link fallback
2. `revalidatePath` runs after any outcome (delivered or not), so the dashboard never shows a stale "awaiting contract" card for a quote that has a contract
3. A second attempt to send a contract for a quote that already has one returns a user-facing error message (via `actionableError`) explaining the contract was already sent and offering its URL, rather than showing a raw `duplicate key value violates unique constraint "contracts_quote_id_key"` message
4. All exceptions a contractor can reach on this path use `actionableError` and produce messages the contractor can read and act on, not React's production redaction notice
5. A successful send (delivery succeeds) navigates to the job page with `sent=contract` (no `delivered=0`), exactly as it does today
6. A contract insert failure (before `notifyCustomer` is attempted) throws an `actionableError` explaining the failure, does not mark anything as sent, and allows safe retry
