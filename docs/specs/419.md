# Problem

There is no way for a contractor to say the work is done. The job goes from "contract signed" directly to "invoice" with no state in between and no control to set one. This gap is why a Final invoice for the full amount was offered on a job with the contract unsigned and no work started — the invoice gating item requires completion, and cannot be built because there is nothing to read.

# Scope: what changes

A completion state on the job, and a contractor-facing control that sets it.

- A new stage `work_complete` between `contract_signed` and `invoiced` in the pipeline.
- A new situation `work_complete` derived when `contract.signed_at` is set and `work_completed_at` is set, but no invoices exist yet.
- A `work_completed_at` column on the `jobs` table (timestamptz, nullable).
- A "Mark work complete" control on `/jobs/[id]`, offered once the contract is signed.
- Timeline event "Work marked complete" when the completion is recorded.
- Copy for the new state in the job page's next-step card.
- The control follows the settled end-state pattern: button lands on its terminal "Marked complete ✓" before navigation fires.
- Navigation destination is `/jobs/[id]` with `?sent=work_complete` and a confirming banner.

## The design decision this item makes

`job-stages.ts` opens with: "Pure derivation of a job's position in the quote → paid pipeline. All state is read from existing quote/contract/invoice rows — no new state storage."

Completion breaks that. Nothing in the existing rows implies that work finished, so this item adds the first piece of genuinely stored pipeline state: `jobs.work_completed_at`.

**Decision:** Keep the derivation pure — read the new column as an input to `deriveSituation`, exactly as `contracts.signed_at` is read. Do not move logic into the component. The stored state lives on the job; the derivation reads it and computes the situation from it.

This is recorded in `areas/motko.md` with `Precedent: yes` — later tickets will copy the pattern, and the reversal cost should be visible before four of them inherit it.

# Explicitly out of scope: what does not change

- **The invoice gating itself.** Separate item, and blocked additionally on decision D10. This item supplies the state the gating will read; it does not change what any invoice is allowed to do.
- **`deriveInvoiceAmount` in `src/lib/invoice-amount.ts`.** Untouched here.
- **The dashboard's section derivation.** `dashboardSection` in `src/lib/dashboard-sections.ts` maps the new `work_complete` situation to `null` — a completed job's next action is the invoice, which is the gating item's call, not this one's.
- **Any automatic completion.** Nothing infers completion from a date, a duration, or an invoice. A person marks it.
- **Full audit trail of completion changes.** A reversal path is required (a misfire must be reversible), but a log of every toggle is not.

# Edge cases

- **Marking complete before the contract is signed.** The control is not offered. Server-side, the action refuses the request — safer default, costs nothing.
- **Marking complete on a job with no contract at all.** Some contractors skip straight to invoicing today, and `deriveSituation` already handles `invoices.length > 0` with no contract. Do not break that path. A job with no contract keeps behaving as it does now — the completion state is only read when a contract exists.
- **Un-marking.** A misfire must be reversible: a contractor who taps it on the wrong job needs a way back. The control shows "Undo" once completion is set, and the action clears `work_completed_at`. No separate timeline event for the reversal — idempotent.
- **Already invoiced, then marked complete.** Out of order, but harmless and reachable today. Record the completion timestamp, do not refuse it, do not retro-change the invoice. The situation will be `invoice_unpaid` because invoices take precedence in the derivation.
- **Already marked complete, tapped again.** Idempotent. The timestamp is already set, the timeline event already exists, nothing changes. No second event fires.
- **A legacy job that finished long ago.** `work_completed_at` is null. It must not read as "in progress" in a way that blocks anything. Nothing gates on this column until the invoice-gating item ships, which is precisely why this lands first.

# Risks

- **First stored pipeline state.** The precedent is the risk, not the column itself — hence the recorded decision with `Precedent: yes`.
- **Migration must precede code.** Supabase migrations are applied by hand via `supabase db push` and do NOT run on Vercel deploy. Apply the migration to production BEFORE the code that reads the column merges, or the deploy breaks. After merge, confirm `supabase migration list` shows prod in sync, and probe that the column actually exists (not just that the ledger says it was applied).
- **No money moves.** Nothing is charged, invoiced or displayed differently to a customer. The gating that money depends on is a separate, separately-blocked item.

# Derived criteria

- A signed job with `work_completed_at` null derives a different situation from one with it set.
- `deriveStages` places the new `work_complete` stage between `contract_signed` and `invoiced`, and stays monotonic.
- The job page renders a control to mark the work complete once the contract is signed, and does not render it before.
- The control lands on its terminal state ("Marked complete ✓") before navigating.
- The control navigates to `/jobs/[id]` with `?sent=work_complete` and a confirming banner.
- Marking complete twice produces one timeline event, not two.
- Completion is reversible from the job page — the control shows "Undo" once set.
- A job with no contract and an existing invoice derives the same situation it does today.
- A job with `work_completed_at` null behaves exactly as it does today in every other respect.
- `dashboardSection` returns `null` for the `work_complete` situation.
- No job appears in two dashboard sections.
- The migration creating the column is present in `supabase/migrations/`, and no select names the column without the migration being present.
- `buildTimeline` includes "Work marked complete" at the `work_completed_at` timestamp when it is set.
- The decision is recorded in `areas/motko.md` with `Precedent: yes`.
