# Issue #152: Build the reassurance strip on the customer payment page

**Source:** [Notion roadmap item](https://app.notion.com/p/Build-the-reassurance-strip-on-the-customer-payment-page-3b81e4f908b481e59511db954b68a6aa)

**Requires database migration:** No

AMBIGUOUS: Approved copy strings for reassurance strip not provided in issue body (required input for regulatory/data-handling claims)

---

## Problem

The customer payment page (`src/app/i/[id]/page.tsx:120`) presents a single `text-xs text-muted` sentence as the entire reassurance to a customer about to transfer a large sum by bank. This is the highest-stakes moment on any Motko surface — the customer has no relationship with Motko, only with the trade, and is being asked to authenticate with their bank on a page they have never seen. The current design carries no visual weight and provides minimal reassurance.

## Scope: what changes

1. **Replace the single sentence** (lines 120-123) with a reassurance strip component
2. **Strip layout** includes:
   - A shield glyph (source/implementation TBD — no icon library currently installed)
   - The payee company name in bold weight
   - The approved security and regulatory copy strings (NOT PROVIDED — required before implementation can proceed)
3. **Pay button label** changes from "Pay by bank" to "Pay £{amount} by bank" — the amount matches `invoice.amount` exactly and uses identical formatting to the amount displayed elsewhere on the page (`formatGBP`)
4. **Copy strings module**: Create a single module (e.g. `src/lib/copy/payment-reassurance.ts` or similar) to hold the approved strings so they can be changed without touching layout code
5. **Contrast and sizing**: All text in the strip must meet WCAG AA contrast requirements. No element uses `text-muted` at `text-xs` size
6. **Viewport**: The strip renders above the fold on a 375px-wide viewport

## Explicitly out of scope

- Do **not** author, edit, paraphrase, or improve the copy. Use the supplied strings verbatim (when provided).
- Do **not** change payment initiation, the TrueLayer flow, or any payment logic.
- Do **not** change how the amount is calculated or retrieved.
- Do **not** add trust badges, third-party logos, or testimonials beyond the supplied copy.
- Do **not** change the page's data fetching (the `admin.from("invoices").select(...)` query at lines 50-56).
- Do **not** modify `buildPayPanel` logic or the `PayButton` component's payment creation flow.
- Do **not** add animations, transitions, or progressive disclosure to the strip.

## Files

Expected touches:

- `src/app/i/[id]/page.tsx` — replace the single sentence (lines 120-123) with the reassurance strip, update PayButton label to include amount
- `src/app/i/[id]/pay-button.tsx` — accept an `amount` prop and display "Pay £{amount} by bank" instead of "Pay by bank"
- **New file**: Copy strings module (e.g. `src/lib/copy/payment-reassurance.ts`) holding the approved regulatory copy
- **New file** (possibly): Reassurance strip component (e.g. `src/app/i/[id]/reassurance-strip.tsx` or `src/components/ui/payment-reassurance-strip.tsx`) — depends on implementation approach (inline vs extracted component)
- `tests/acceptance/152.test.tsx` — acceptance tests (blocked until copy strings are provided)

## Edge cases

1. **Payee company name is missing** (`contractor.company_name` is null or empty string):
   - Render the strip without the name rather than an empty bold element or placeholder text
   - The strip remains visible with the shield glyph and copy strings

2. **Amount is null or undefined**:
   - Render the button label as "Pay by bank" (original text) rather than "Pay £0 by bank" or "Pay £null by bank"
   - Report this case if observed — it should not occur given the page's existing data requirements (line 61 guards on invoice existence)

3. **Copy strings are not supplied**:
   - Stop and report. Do not proceed with placeholder text (per issue requirement).
   - This is the current blocking state.

4. **Very long company name**:
   - Truncate with an ellipsis (`text-overflow: ellipsis`, `overflow: hidden`, `white-space: nowrap`) at the strip's bounds
   - Do **not** wrap to a third line — the strip is a single-height bar with possible two-line copy, not a variable-height block

5. **Legacy persisted data**:
   - Invoices predating this change render the strip identically to new invoices
   - No stored field changes, no migration required

6. **Loading state**:
   - The strip is static (no data fetching or async state) and renders immediately on page load
   - The PayButton's existing loading state ("Connecting to your bank…") is unchanged

7. **Error state**:
   - If the PayButton's payment creation fails, the existing error display (lines 40 in pay-button.tsx) is unchanged
   - The strip remains visible and unchanged during/after errors

8. **Shield glyph missing/not implemented**:
   - If no icon library is available and the implementation path is unclear, the spec should document what icon library to install or what SVG asset to use
   - **Current state**: No icon library installed (no lucide-react, heroicons, react-icons in package.json), no SVG assets in `/public`

## Risks

- **User-facing on highest-stakes page**: This change is visible to every customer who attempts to pay an invoice. The page handles actual payment initiation for potentially large sums.
- **Regulatory copy claims**: The copy strings (when provided) will make claims about Motko's regulatory status and data handling practices. Incorrect or misleading copy could create legal/compliance risk. The strings must be reviewed and approved before implementation.
- **No stored data changes**: This is purely a UI change with no database writes, so rollback is a deploy revert only.
- **Sequencing with capability-token security work**: The issue notes that this item touches the same route (`src/app/i/[id]/page.tsx`) as the capability-token security work. If both are in flight, coordinate sequencing or batch them to avoid merge conflicts.
- **Amount formatting consistency**: The button must display the amount using `formatGBP(invoice.amount)` exactly as the page does at line 103, otherwise a mismatch (e.g. "Pay £8,132.00 by bank" on the button vs "£8,132" displayed as amount due) would erode trust rather than build it.
