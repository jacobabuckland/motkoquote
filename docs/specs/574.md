# SETUP-1: Saving business setup replaces the whole profile, destroying fields the other path collected

## Problem

`persistContractorSetup` (src/app/setup/actions.ts) upserts the contractors row with `business_profile: input.business_profile`, replacing the entire JSONB column rather than merging with what is already stored. There are two paths that write this field — the manual setup form and the voice setup interview — and they do not collect the same fields. Whichever path runs last silently deletes every key the other collected that it did not. Production evidence: one contractor's profile holds ten keys but no `business_structure` at all (not empty: absent), which is the signature of a profile written by the voice path that never asked. The visible symptom is a nagging "business details are missing" banner. The actual defect is silent data loss on a column that feeds every contract's opening paragraph.

## Scope: what changes

`persistContractorSetup` will be modified to merge the incoming `business_profile` with the existing stored profile rather than replacing it wholesale. Before the upsert, fetch the existing contractor row (if one exists for this `owner_user_id`). If the existing row holds a `business_profile`, merge the incoming profile over it using the existing `mergeBusinessProfile` helper from `src/lib/schemas/business-setup.ts` (which will need to be exported). A field present in the incoming profile overwrites the stored value; a field absent from the incoming profile (undefined) is left untouched. A field explicitly set to null or empty string in the incoming profile clears the stored value (this is how deliberate clearing works). A null or {} existing profile is treated as an empty base.

The merge is shallow: if `registered_address_components` (a nested object) is present in the incoming profile, it replaces the entire stored `registered_address_components` object. This is correct because `registered_address` and `registered_address_components` are tightly coupled — they represent the same address, set together when the form picks a Google Places suggestion. A deep merge that attempted to preserve sub-fields would leave stale components orphaned from their formatted string.

**Note on clearing fields:** All business_profile string fields use the `nullishString` schema, which transforms null to undefined. Therefore, setting a field to null is equivalent to omitting it (both preserve the existing value). To explicitly clear a field, set it to empty string. The merge function writes any defined value (including empty string) and preserves the existing value only when a field is undefined.

## Explicitly out of scope

- Backfilling the profiles already damaged. Existing accounts with missing fields are not repaired; the lost values are not recoverable from the row, only from re-asking the user.
- Changing which fields either path collects, or making `business_structure` required.
- The dashboard banner's copy or its validation logic. The banner already checks for missing fields correctly; it will simply stop firing once the merge prevents fields from being lost.
- Handling race conditions beyond Postgres's existing last-write-wins on the contractors table. Two concurrent saves racing is acceptable and already handled by the upsert conflict resolution; the fix here ensures that the loser's fields are not silently dropped from the winner's write.

## Files

- `src/lib/schemas/business-setup.ts` (modify) — export `mergeBusinessProfile` so it can be imported by actions.ts
- `src/app/setup/actions.ts` (modify) — modify `persistContractorSetup` to fetch the existing business_profile and merge the incoming profile over it before upserting

## Edge cases

- **business_profile is null or {} on the existing row.** Merge treats this as an empty base. The incoming profile is written verbatim, same behaviour as today.
- **A key holds a nested object (registered_address_components).** Shallow merge: if the incoming profile sets `registered_address_components`, the entire stored object is replaced. This is correct because the nested object is tightly coupled to its parent formatted string.
- **A field the user deliberately clears.** Because business_profile fields use `nullishString` (which transforms null to undefined), explicitly clearing a field requires setting it to empty string. Omitting a field or setting it to null both leave the existing value untouched. The `mergeBusinessProfile` function writes any defined value (including empty string) and preserves existing values only for undefined fields.
- **No existing contractor row (first-time setup).** The fetch returns null, merge treats it as an empty base, and the upsert inserts the row. Identical to today's behaviour.
- **A field collected by only one path.** `business_structure` is on the form but often omitted by voice. After this fix, if the form runs first and captures it, the voice setup completing later will leave it intact. Today it is deleted.

## Risks

None. This is purely additive: fields that would have been lost are now preserved. The merge semantics (undefined = not provided, null = explicitly cleared) already match how both paths build their input, so no caller behaviour changes. The only new failure mode is if the existing-row fetch fails, in which case the upsert proceeds with the incoming profile unmerged (same as today), and the error is already logged by the existing error handling.

## Derived criteria

I understood the human to be asking for:

1. When one setup path (form or voice) writes a business_profile, any fields the other path previously collected but this path did not provide must be preserved, not deleted.
2. A contractor completing setup via voice after filling the form (or vice versa) must end up with the union of what both collected, in any order.
3. A field explicitly set to empty by the user must end up cleared in the stored profile (merging must not trap stale values).
4. A contractor seeing the "business details are missing" banner must be seeing it because the field is genuinely absent after the merge, not because one path deleted what the other collected.
5. A first-time setup (no existing contractor row) must behave exactly as it does today: the incoming profile is written verbatim.
