# Issue #293: Route every customer-facing lifecycle send through one dispatcher

**Branch:** factory/293  
**Audited against:** main @ 64751b3

## Problem

There is no dispatcher for customer-facing lifecycle notifications. Each send is written inline at its call site, and only the quote send supports SMS delivery. Contract and invoice sends are email-only — the customer's phone number is present in the selected data but never consulted.

`src/lib/sms.ts` exports only `sendQuoteSms` and `sendChaseSms`. No contract or invoice SMS function exists. The quote send path contains ~60 lines of channel eligibility logic, timeout handling, per-channel error logging, and idempotent status marking — none of it reusable.

The contract send is, in full:
```typescript
if (job.customer?.contact?.email) {
  const result = await sendContractEmail({…});
  delivered = result.delivered;
}
```

The `sms_opt_out` field exists on the customer contact record, is written by `sendQuote` and the Twilio STOP handler, and is honoured by exactly two of five customer-facing sends. The other three cannot honour it because they have no SMS path.

**Customer-facing consequence:** A customer who provides a phone number and no email receives the quote by SMS, then silence. The contract that needs their signature and the invoice that needs their money are sent to an email address they don't have. The job stalls and the contractor chases something the product never sent.

**Revenue impact:** An invoice that reaches no channel does not get paid, and under fee-at-source motko earns nothing on it either.

This is the AGENTS.md anti-pattern: a signal that must change behaviour exists, is trusted, and is not consulted at every site that needs it.

## Scope: what changes

1. **New dispatcher:** `src/lib/notify-customer.ts` exporting `notifyCustomer()` — the single entrypoint for all customer-facing lifecycle sends (quote, contract, invoice).

2. **SMS senders expanded:** Add `sendContractSms` and `sendInvoiceSms` to `src/lib/sms.ts`, mirroring the graceful-degradation pattern from `sendQuoteSms` (missing Twilio credentials → `{delivered: false}`, never throw).

3. **Rewrite quote send:** `sendQuote` in `src/app/jobs/actions.ts` calls `notifyCustomer()` instead of inline email/SMS logic. The `markSent()` call remains at the call site (status transitions are the caller's business).

4. **Rewrite contract send:** `createContract` in `src/app/dashboard/actions.ts` calls `notifyCustomer()` with `event: "contract_sent"` and the PDF attachment. Must now select and pass `customer.contact.phone` from the database.

5. **Rewrite invoice send:** `createInvoiceRecord` in `src/lib/invoicing.ts` calls `notifyCustomer()` with `event: "invoice_sent"`. The `CreateInvoiceRecordInput` schema gains optional `customerPhone` and `customerSmsOptOut` fields; both call sites (dashboard action and `signContract` in `src/app/c/[id]/actions.ts`) must pass them.

6. **Delivery reporting:** The dispatcher returns the same shape `sendQuote` already returns:
   ```typescript
   {
     delivered: boolean;  // true if ANY channel succeeded
     email: { attempted: boolean; delivered: boolean };
     sms: { attempted: boolean; delivered: boolean };
   }
   ```
   This preserves the existing `?delivered=0` banner convention and all callers.

7. **Channel eligibility consolidated:** The dispatcher owns once:
   - Email eligibility: `channels.email && Boolean(customer.email)`
   - SMS eligibility: `channels.sms && Boolean(normalizedPhone) && !customer.smsOptOut`
   - Phone normalisation via `src/lib/phone.ts`
   - `withTimeout` per channel at existing `TIMEOUT_MS` budgets
   - `Promise.all` so neither channel blocks the other
   - Per-channel `logError`
   - Per-event copy table (subject/body text)

8. **LifecycleEvent type:** The dispatcher accepts `event: LifecycleEvent` where:
   ```typescript
   type LifecycleEvent =
     | "quote_sent" | "contract_sent" | "invoice_sent"
     | "contract_signed" | "payment_received";
   ```
   Only the first three are called by any code path in this ticket. The last two are declared for type completeness but have no send implementation yet.

## Explicitly out of scope

- **Chase cron** (`src/app/api/cron/chase/route.ts`) — its per-channel claim/release dedup against `chase_events` is a different concern from one-shot lifecycle delivery. It already honours `sms_opt_out`.

- **Contractor notifications** (`src/lib/notify-contractor.ts`) — different recipient, different channels (email + push).

- **New lifecycle events** — `contract_signed` and `payment_received` are declared in `LifecycleEvent` for type completeness, but no send site for either is implemented here.

- **Copy changes** — no change to `sendQuoteSms`/`sendQuoteEmail` message content, or to any existing email body or subject.

- **Data model changes** — no new customer preference fields. The existing negative `sms_opt_out` flag plus per-send `channels` input is the model.

- **Schema validation changes** — no change to `customerInputSchema` or its at-least-one-contact refine.

- **Retry/queue/dead-letter** — best-effort delivery only, as today.

- **Backfill or re-send** — nothing already sent is re-delivered.

## Edge cases

### Channel availability
- **Email only:** SMS not attempted, `sms.attempted === false`. Not an error.
- **Phone only:** Email not attempted, `email.attempted === false`. Not an error.
- **Neither:** `customerInputSchema`'s refine blocks this at quote send; contract/invoice inherit the customer row created there. If one somehow reaches the dispatcher, it attempts nothing and resolves `delivered: false`. Record still flips to `sent`, caller navigates to the `?delivered=0` banner. No throw.
- **Phone fails E.164 normalisation:** Treat as no phone. SMS not attempted, `sms.attempted === false`, `logError` once.

### Channel outcomes
- **SMS fails, email succeeds:** `delivered: true`. Independent channels, per existing quote-send comment.
- **Both fail:** `delivered: false`. Record still marked `sent`, caller navigates to `/jobs/[id]?sent=…&delivered=0`. No exception reaches the UI.
- **One channel exceeds timeout:** That channel resolves `{delivered: false}` and does not delay the other channel's result. `Promise.all` ensures independence.
- **Email rejects, SMS delivers:** `{delivered: true, email: {delivered: false}, sms: {delivered: true}}`. No throw.

### Missing credentials
- **Twilio credentials absent:** SMS senders return `{delivered: false}` without throwing, mirroring `src/lib/sms.ts:22-25`.
- **Resend credentials absent:** Email senders return `{delivered: false}` without throwing, mirroring `src/lib/email.ts`.

### Timing and opt-out
- **Customer changes preference mid-job:** Already-sent steps do NOT resend. `notifyCustomer` is called at the moment of a lifecycle transition and nowhere else. A customer who texts STOP after the quote went out will not get the contract by SMS. Nothing already delivered is re-delivered on any channel.
- **STOP arrives between eligibility check and Twilio dispatch:** The message may still go out. Accepted — the window is milliseconds, Twilio enforces STOP at carrier level independently, and closing it would require read-modify-write per send.

### PDF attachment
- **Contract PDF fails to render:** Unchanged — `renderContractPdf` is already `.catch(() => null)` in `src/app/dashboard/actions.ts:176`. Email sends without the attachment, SMS is unaffected (carries URL only).

### Idempotency
- **Duplicate invoice (idempotency hit):** `createInvoiceRecord` returns early on an existing matching invoice (`src/lib/invoicing.ts:57-64`) before any send. `notifyCustomer` is not called. Unchanged.
- **Deposit invoice on double-signature race:** `signContract` bails before `createInvoiceRecord` when the UPDATE matches no row (`src/app/c/[id]/actions.ts:57`). Unchanged.

### Status transitions
- **Both channels fail on contract send:** The contract row is still written with `status: "sent"` (`src/app/dashboard/actions.ts:165`) — unchanged, per CLAUDE.md's spent-form rule. The form is spent; the user navigates away.
- **Both channels fail on invoice send:** Invoice row is still written with `status: "sent"` (`src/lib/invoicing.ts:73`). Unchanged.

## Risks

**Money path:** Invoice sends now fan out to SMS. A defect in the SMS path that throws could block invoice creation entirely. Mitigation: the dispatcher never throws on channel failure — `withTimeout` and graceful degradation ensure every channel failure resolves `{delivered: false}`, never rejects.

**Opt-out compliance:** The new SMS senders MUST include "Reply STOP to opt out" (PECR requirement). Defect: omitting it from `sendContractSms` or `sendInvoiceSms` would send non-compliant texts. Mitigation: acceptance tests explicitly assert the STOP suffix on every SMS body.

**Data selection:** `createContract` must now select `customer.contact.phone`. Omitting it from the `.select()` call would silently treat every customer as phone-less. Mitigation: acceptance tests assert SMS delivery for a customer with phone + email.

**Schema extension:** `CreateInvoiceRecordInput` gains two optional fields. Both call sites must pass them or invoice sends will never attempt SMS (silent regression, not a crash). Mitigation: acceptance tests assert SMS delivery from the deposit-invoice path (`signContract` → `createInvoiceRecord`).

**No database migration required.**

## Derived criteria

1. A shared dispatcher exists at `src/lib/notify-customer.ts`, exporting `notifyCustomer()`.

2. The dispatcher is imported and called by `sendQuote`, `createContract`, and `createInvoiceRecord`.

3. Neither `createContract` nor `createInvoiceRecord` contains a direct call to `sendContractEmail` or `sendInvoiceEmail`.

4. `src/lib/sms.ts` exports `sendContractSms` and `sendInvoiceSms`, both including "Reply STOP to opt out" in their body.

5. Sending a contract to a customer with both email and phone (and `smsOptOut = false`) attempts both channels.

6. Sending a contract to a phone-only customer attempts SMS, not email, and returns `delivered: true` when SMS succeeds.

7. Sending an invoice to a phone-only customer attempts SMS, not email, and returns `delivered: true` when SMS succeeds.

8. When `contact.sms_opt_out = true`, contract and invoice sends attempt email only, and `report.sms.attempted === false`.

9. When email rejects and SMS resolves `{delivered: true}`, the dispatcher resolves `{delivered: true, email: {delivered: false}, sms: {delivered: true}}` and does not throw.

10. When both channels fail, the dispatcher resolves `delivered: false` and does not throw.

11. When both channels fail on a contract send, the contract row is still written with `status: "sent"` — unchanged, per CLAUDE.md's spent-form rule.

12. A channel exceeding its timeout budget resolves `{delivered: false}` and does not delay the other channel's result.

13. The deposit invoice raised automatically by `signContract` fans out on both channels for a customer with both email and phone.

14. `sendQuote`'s return shape is unchanged: `{delivered, email: {attempted, delivered}, sms: {attempted, delivered}, quoteUrl}`.

15. All acceptance tests pass lint (`npx eslint tests/acceptance/293.test.tsx`) and typecheck.
