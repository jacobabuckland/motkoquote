# Issue #212: PAY-6: Update payment trust copy and all TrueLayer references (supersedes #152 wording)

## Problem

Customer-facing copy and product claims still reference TrueLayer as the payment provider. Most critically, the #152 reassurance strip on the customer payment page (`src/lib/payment-reassurance-copy.ts`) states "Payments are processed by TrueLayer, authorised and regulated by the Financial Conduct Authority" — which must not ship now that the provider is Stripe. The privacy policy also names TrueLayer in the processors list. TrueLayer declined to onboard motko (12 Aug 2026), and all payment rails have moved to Stripe Pay by Bank.

## Scope: what changes

Update all customer-facing TrueLayer references to either:
- **Stripe** (when naming the specific provider adds trust value), or  
- **Provider-neutral wording** (preferred where possible, so the next rail change is a config edit rather than a copy sweep)

### Files to change

1. **`src/lib/payment-reassurance-copy.ts`** (critical — customer payment page)
   - Line 5: Update `PAYMENT_COPY_LINE_1` to the Stripe equivalent
   - The new copy must accurately state: payments are processed by Stripe, an FCA-authorised payment institution
   - The precision rule from #152 still applies: motko holds no authorisation; copy must not blur who is regulated
   - Line 8: `PAYMENT_COPY_LINE_2` likely needs no change (already provider-neutral)

2. **`src/app/privacy/page.tsx`** (critical — public privacy policy)
   - Line 64: Change "TrueLayer (open banking payments)" to provider-neutral wording or Stripe, maintaining accuracy about what the processor does

3. **`README.md`** (documentation)
   - Line 19: Update the Payments row from `TrueLayer (VRP for fee collection, Payment Initiation for customer payments)` to Stripe Pay by Bank, or a provider-neutral description

**Legal gate:** The exact reassurance strip strings (`PAYMENT_COPY_LINE_1`) are subject to legal sign-off before merge. The PR must carry an unticked checklist item for legal approval and must not merge to `main` until confirmed.

## Explicitly out of scope: what does not change

- **No layout or design changes** to the reassurance strip component (`src/components/ui/reassurance-strip.tsx`) — only the copy strings it imports
- **No code-path changes** — payment logic, API routes, TrueLayer implementation files stay as-is (those are for PAY-2/3/5 migration tickets)
- **Historical documents** (specs in `docs/specs/*.md`, migration files, past commit messages) — leave as generated; only live templates change
- **Test files** that mock TrueLayer for historical acceptance tests — those document what was built and tested at the time
- **Email templates** (`src/lib/email.ts`) — already provider-neutral, no TrueLayer references exist
- **TrueLayer implementation files** (`src/lib/truelayer*.ts`, `src/app/api/truelayer/*`) — those files remain until PAY-5 deprecation ticket removes them

## Edge cases

**Provider name changes again:** Prefer provider-neutral phrasing ("payments are processed by an FCA-authorised payment institution" or similar) where the specific provider name adds no trust value, so future rail changes require only a config update, not a copy sweep. Use "Stripe" only where naming the provider explicitly adds customer reassurance.

**Historical receipts and invoices:** Customers who paid via TrueLayer before this change will have generated receipts that say TrueLayer. Those are historical records — leave them as-is. Only live templates and forward-looking copy change.

**Legal sign-off delayed:** The PR can be built, previewed, and reviewed while legal sign-off is pending, but must not merge to `main` until legal confirms the exact wording in writing on the PR.

**Copy module fails to load:** If `PAYMENT_COPY_LINE_1` or `PAYMENT_COPY_LINE_2` are undefined at runtime, the reassurance strip component should fail at build time (it already imports from the module). This is not an edge case to handle gracefully — it's a deployment blocker.

## Risks

⚠️ **Legal approval required before merge.** The reassurance strip copy is regulatory-sensitive (FCA authorisation claims). The exact wording must be confirmed by legal before merging to `main`. The PR must carry a checklist item for this gate.

**Regulatory precision:** Same constraint as #152: Stripe (via its FCA authorisation) is the authorised payment institution. Motko is not. Copy must attribute authorisation accurately and never state or imply that motko is FCA regulated. If the new copy says "payments are processed by Stripe, an FCA-authorised payment institution", that satisfies the constraint; "motko is FCA authorised" does not.

**Provider-neutral vs provider-specific trade-off:** Where copy can be provider-neutral without reducing customer trust, prefer that. "Payments are processed by an FCA-authorised payment institution" is more future-proof than "payments are processed by Stripe" if Stripe's name adds no trust delta. Use judgment: on the reassurance strip (highest-stakes moment), naming Stripe may add value; in the privacy policy processors list, "payment processor" may suffice.

**High-stakes page:** The payment reassurance strip appears on the page where customers transfer thousands of pounds. Test the updated copy renders correctly, passes typecheck and lint, and matches the approved legal wording exactly character-for-character before merge.

**Missed references:** If a customer-facing TrueLayer reference exists outside the three files listed (payment copy, privacy policy, README), it is a spec miss. The acceptance tests check those three files; any others discovered during implementation must be added to the scope and tested.
