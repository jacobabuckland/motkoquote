# REF-5: A liability query Jacob can read without writing SQL

## Problem

Banked subscription months from referrals are uncapped by design (D26) — a trade referring thirty others is a cost line motko is happy to carry. That only holds while the liability is visible. An uncapped liability nobody can see is not a decision, it is an accident waiting to be discovered in a bank statement.

Currently there is no way to see the total unconsumed banked months across all accounts without writing SQL. This makes it impossible to monitor what motko owes.

## Scope: what changes

Create a SQL query file at `docs/queries/referral-liability.sql` that returns a single number: the total unconsumed banked months across all contractor accounts.

The calculation:
- Every 5 activated referrals credit 1 banked month (REF-3)
- Banked months = `FLOOR(activated_referral_count / 5)` for each contractor
- Total liability = `SUM(FLOOR(activated_referral_count / 5))` across all contractors
- Since the subscription consumption system (REF-3's "applied across two consecutive invoices") is not yet implemented, all banked months are currently unconsumed

The query can be run directly with `psql` or through the Supabase dashboard, returning a single integer.

## Explicitly out of scope

- Alerting or thresholds on the liability number
- Tracking which specific months have been consumed (will be needed when REF-3 ships the consumption logic)
- Breaking down the liability by contractor (this is total across all accounts)
- Historical tracking of how the liability has changed over time

## Files

- docs/queries/referral-liability.sql (new) — the query file
- tests/acceptance/655.test.ts (new) — tests that verify the query calculates correctly

## Edge cases

### Zero liability
- No contractors exist: returns 0
- Contractors exist but none have activated referrals: returns 0  
- Contractors have activated referrals but fewer than 5 each: returns 0
- Query result is never null, always a non-negative integer

### Calculation boundary cases
- 4 activations = 0 months (floor(4/5) = 0)
- 5 activations = 1 month (floor(5/5) = 1)
- 9 activations = 1 month (floor(9/5) = 1)
- 10 activations = 2 months (floor(10/5) = 2)

### Multiple contractors
- Liability is summed across all contractors
- Example: contractor A has 7 activations (1 month), contractor B has 12 activations (2 months) → total liability is 3 months

## Risks

- **Read-only query, no data changes:** This is a `SELECT` statement only, no writes
- **No PII exposure:** The query returns only an aggregate count, not contractor identities or personal information
- **No impact on existing systems:** This is a diagnostic query for human use, not integrated into application logic

## Derived criteria

I understood the requirement as:

1. A SQL query file exists at `docs/queries/referral-liability.sql`
2. The query can be executed directly (e.g., `psql -f docs/queries/referral-liability.sql`) and returns a single integer
3. The integer represents total unconsumed banked months across all contractor accounts
4. The calculation is `SUM(FLOOR(activated_referral_count / 5))` from the contractors table
5. The query returns 0 (not null) when there are no banked months
6. The query correctly handles the floor division (4 activations = 0 months, 5 activations = 1 month)
7. The query is readable by a human without SQL expertise — clear column names, comments explaining the calculation
