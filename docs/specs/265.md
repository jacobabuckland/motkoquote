# Issue #265: LED-4: Cross-job money position — owed to you, you owe, set aside

**Auditing branch:** `factory/265` @ `f268270`  
**Database migration required:** NO — builds on LED-1 and LED-2's existing tables

## Problem

Job-level profit (LED-2) is retrospective and per-job. What actually keeps a tradesperson awake is the aggregate: who am I owed by, who do I owe, and what is genuinely left. The quoting-tool space does not solve this well, and every input already exists once LED-1 and LED-2 are in place. This is the projection that makes the ledger worth having.

## Scope: what changes

### 1. Money position surface on the dashboard

Integrated into the existing dashboard at `/jobs` (NOT a separate Reports tab — must be visible without seeking it out), add a money position panel above or alongside the job history list showing:

#### Owed to you
- **Unpaid invoices** aggregated across all jobs, grouped by customer
- Each customer row shows: customer name, total owed (sum of unpaid invoice amounts), oldest unpaid invoice age (days since `invoices.created_at` for the oldest unpaid invoice)
- Tapping a customer row expands or navigates to show the constituent unpaid invoices
- Empty state (no unpaid invoices): "All caught up — no outstanding invoices"

#### You owe
- **Unpaid job_costs** aggregated across all jobs, grouped by counterparty
- Each counterparty row shows: counterparty name, total owed (sum of unpaid `job_costs.amount_net + vat_amount`), number of jobs these costs span
- Example: "Frank — £2,000 across 4 jobs"
- Tapping a counterparty row shows the constituent costs and allows marking them paid individually or together
- Costs with no counterparty (`counterparty_id IS NULL`) are grouped under "No counterparty specified" and shown separately
- Empty state (no unpaid costs): "All costs paid"

#### Set aside
- **VAT position** — shown ONLY if the contractor is VAT-registered (`contractors.vat_registered = true`)
- Displays:
  - "VAT collected: £X" — sum of VAT on paid invoices across all jobs (`invoices.amount * 0.2` for standard-rate invoices, where `invoices.status = 'paid'`)
  - "VAT on costs: £Y" — sum of `job_costs.vat_amount` where `job_costs.paid = true` and `vat_amount IS NOT NULL`
  - "VAT position: £Z" — collected minus costs VAT
- **Explicit disclaimer** (must be agreed with Jacob before merge):  
  "Estimate only, not tax advice. This assumes standard-rate VAT on a cash accounting basis and does not account for flat-rate scheme, CIS reverse charge, or partial exemption. Check with your accountant."
- If contractor is not VAT-registered: hide this entire section rather than showing zeros

#### What's left
- **Money in minus costs paid** — clearly defined in the UI as "money collected, minus costs you've paid"
- NOT labelled as profit, cash available, or take-home — must be explicitly non-advisory
- Computed as: sum of paid invoice amounts minus sum of paid job_costs amounts (both net and VAT)
- Shows the figure with plain-language definition: "What's left: £X (money collected, minus costs you've paid)"

### 2. Server-side computation

A new server action or data-fetching function (e.g. `getMoneyPosition` in `src/app/jobs/money-position-actions.ts`) returns:

```ts
type MoneyPosition = {
  owedToYou: Array<{
    customerId: string;
    customerName: string;
    totalOwed: number;  // in pence
    oldestInvoiceAgeDays: number;
    unpaidInvoiceIds: string[];
  }>;
  youOwe: Array<{
    counterpartyId: string | null;
    counterpartyName: string | null;  // null for "No counterparty specified"
    totalOwed: number;  // in pence
    jobCount: number;
    costIds: string[];
  }>;
  vat: {
    collected: number;  // in pence
    onCosts: number;    // in pence
    position: number;   // in pence
  } | null;  // null if not VAT-registered
  whatsLeft: number;  // in pence
};
```

All amounts computed on the server from integer pence. The client NEVER computes sums or VAT.

### 3. Marking costs paid from the aggregate view

When a contractor marks one or more costs as paid from the "You owe" counterparty drill-down:
- Calls the existing `updateJobCost` server action from LED-1 (`src/app/jobs/[id]/cost-actions.ts`)
- Sets `paid = true` and `paid_on = today` on the selected cost(s)
- Updates both:
  - The aggregate money position (reduced "you owe" for that counterparty)
  - Any job-level P&L view that includes those costs
- **One write path, no duplicate logic** — the money position re-fetches after the update, rather than maintaining separate update logic

### 4. Counterparty grouping correctness

The grouping aggregates correctly across jobs and is unit-tested with fixtures including:
- One counterparty appearing in costs across several jobs (must sum correctly)
- Costs with no counterparty (`counterparty_id IS NULL`) grouped separately
- A counterparty with all costs paid (must disappear from "you owe" list)
- A counterparty owed a negative net (e.g. supplier refund exceeds costs) — show plainly, do not hide

### 5. Mobile rendering

The money position panel must render correctly at **390px width** in the WKWebView wrapper. All figures render via the `<Money>` component (display face, tabular numerals per `docs/design-direction.md` §3).

### 6. Empty states

Each section has a correct empty state in the product voice:
- "All caught up — no outstanding invoices" (owed to you)
- "All costs paid" (you owe)
- No dashed boxes or placeholder UI

## Explicitly out of scope: what does not change

- **No forecasting, trend charts, or month-on-month comparison** — that is an accounting product and is explicitly not this
- **No voice query** — LED-5 adds voice querying over the ledger
- **No export or accounting-package integration** — out of scope for the LED programme
- **No partially paid costs** — a cost is paid or not; there is no partial payment tracking. State this limitation explicitly in the UI or help text if a contractor attempts to mark a cost partially paid
- **No changes to invoice or cost creation** — this is a read/aggregate surface only (except for the mark-as-paid action, which uses the existing update path)

## Edge cases

1. **Zero data across all sections**  
   The money position panel shows all four sections with their respective empty states. No dashed boxes, no "no data" error — just the empty-state copy.

2. **Contractor with many counterparties (e.g. 50+)**  
   The "you owe" list is ordered by amount owed descending. Show the top N (e.g. 10) with a "See all" expansion or link. The exact threshold is determined by testing at 390px width and stated in a code comment.

3. **A counterparty owed a negative net (refund exceeds costs)**  
   A supplier who refunded £100 but was only owed £60 shows as "-£40" in the list. Do not hide negative amounts — they are meaningful and must be visible.

4. **Costs with no counterparty**  
   Costs where `counterparty_id IS NULL` are grouped under "No counterparty specified" and shown as a separate row in the "you owe" list, with the sum of those costs.

5. **All costs for a counterparty are paid**  
   The counterparty disappears from the "you owe" list entirely. A counterparty with £500 total costs, all paid, does not appear.

6. **Partially paid costs (out of scope)**  
   A cost is paid or not; there is no partial payment tracking. If a contractor asks or attempts to mark a cost partially paid, show a message: "Costs can only be marked fully paid or unpaid. To track partial payments, split the cost into separate entries."

7. **VAT-registered contractor with no paid invoices or costs**  
   The VAT section shows "VAT collected: £0.00 / VAT on costs: £0.00 / VAT position: £0.00" with the disclaimer. Do not hide the section if it's enabled (contractor is VAT-registered).

8. **Non-VAT-registered contractor**  
   Hide the entire "Set aside" section. Do not show it with zeros.

9. **Very old unpaid invoice (e.g. 365+ days)**  
   The "oldest invoice age" shows the actual number (e.g. "372 days") without capping or euphemism. This is a signal the contractor needs to see.

10. **Multiple jobs with the same customer, mixed paid/unpaid invoices**  
    Only unpaid invoices contribute to "owed to you". A customer with three jobs, two invoices paid and one unpaid, shows only the unpaid invoice amount in the aggregate.

11. **Invoice amounts are in pounds, costs are in pence**  
    The computation layer must convert invoice amounts (pounds, `numeric(10, 2)`) to pence before aggregating. A £50.00 invoice is 5000 pence, not 50 pence. Unit tests cover this boundary.

12. **Marking multiple costs paid at once from counterparty drill-down**  
    The UI allows selecting multiple costs for one counterparty and marking them all paid in one action. This calls `updateJobCost` in a loop or batches the update. The money position re-fetches afterward to reflect the new state.

## Risks

- **LEGAL / ACCURACY GATE: VAT figure must be reviewed by Jacob before merge.** The VAT position is the highest-risk element. Flat-rate scheme, cash vs accrual accounting, and CIS reverse charge all change what this number means. The spec must state which assumption the figure encodes (currently: standard-rate VAT on cash accounting basis, no flat-rate, no CIS reverse charge, no partial exemption), and the UI must say so too. **If that cannot be stated precisely, ship without the VAT panel rather than with a wrong one.**

- **Money-adjacent feature.** Individual diff review required before merge, regardless of QA verdict. Every computation that touches GBP amounts must be reviewed by a human.

- **Aggregation across many jobs.** A contractor with 200+ jobs and 500+ costs must not time out or OOM. Test with a realistic data set (e.g. 100 jobs, 300 costs) before merge. If performance is poor, consider pagination or a `LIMIT` on the query with a "showing top N" message.

- **Unit conversion boundary (pounds ↔ pence).** Invoices are stored in pounds (`numeric`), costs in pence (`int`). Mixing the two without conversion silently produces nonsense. Mitigation: unit tests explicitly cover the conversion, and a code comment at the conversion site warns about the difference.

- **Client-side computation is forbidden but easy to slip in.** A `{owedToYou.reduce((sum, c) => sum + c.totalOwed, 0)}` template expression is client-side. All sums must come from the server. Mitigation: acceptance tests assert the server action returns pre-computed totals, and code review checks no arithmetic appears in the component.

- **Marking paid from the aggregate view must update job-level P&L consistently.** The write path is the existing `updateJobCost` from LED-1, so consistency is guaranteed, but the acceptance tests must verify that a cost marked paid from the aggregate view also updates the job-level P&L (LED-2) for that job.
