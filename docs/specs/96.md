# Issue #96: Add haptics utility and wire it to resolved actions

**Source:** [Notion roadmap item](https://app.notion.com/p/Add-haptics-utility-and-wire-it-to-resolved-actions-3b81e4f908b4811eb719d62f16db9228)

**Requires database migration:** No

---

## Problem

The app ships with `@capacitor/haptics` installed but never used. The one attempt at tactile feedback — `navigator.vibrate(35)` at jobs/new/page.tsx:247 — is a no-op inside iOS WKWebView, the platform the app targets. Touch feedback is the single largest contributor to whether a Capacitor app reads as native or as a website wrapper, and the API surface is small, so this is the highest ratio of perceived quality to implementation effort in the product.

## Scope: what changes

1. **New haptics utility** at `src/lib/haptics.ts` exporting five functions:
   - `tap()` — light impact, fires on every primary button press
   - `press()` — medium impact, reserved for long-press or significant touches (not wired in this item)
   - `success()` — success notification, fires when send/sign/payment actions resolve successfully
   - `error()` — error notification, fires when submit actions fail
   - `select()` — selection feedback, fires on checkbox/toggle/segmented control changes

2. **Platform gating**: Each function is a no-op returning `undefined` when `Capacitor.isNativePlatform()` returns false. No console warnings, no errors — web is silent.

3. **Dynamic import**: The `@capacitor/haptics` import is dynamic (lazy-loaded) so the plugin is not evaluated on web. Verified by asserting the source uses `import(` rather than a static import — NOT by grepping build output: a dynamic import necessarily leaves the module specifier in the bundle so the loader can resolve it at runtime. That string is expected and correct, and its presence proves nothing about whether the code is evaluated.

4. **Primary button integration**: `haptics.tap()` fires on press of every component rendering `variant="primary"` button. The call happens in the Button component's onClick handler, before calling the user-provided onClick prop.

5. **Action resolution integration**:
   - `haptics.success()` fires when a send, sign, or payment action resolves successfully — at the same point the button's terminal success state is set (e.g., "Sent ✓"), not on request dispatch.
   - `haptics.error()` fires when a submit action resolves in a failure state that shows an error message to the user.

6. **Form control integration**: `haptics.select()` fires on change of every toggle, checkbox, and segmented control. For checkbox, the call happens in the onChange handler before calling the user-provided onChange prop.

7. **Replace navigator.vibrate**: Remove `navigator.vibrate(35)` from jobs/new/page.tsx:247 and replace with `haptics.tap()`.

8. **Error handling**: Every call site wraps the haptics call so a failure (thrown error, rejected promise) cannot propagate into the calling action. A try-catch or `.catch(() => {})` suffices — no logging, no user-visible error.

## Explicitly out of scope

- Do **not** add haptics to scroll, hover, page navigation, component mount, or any lifecycle event.
- Do **not** add haptics to celebration moments or choreography — those compose this utility later.
- Do **not** change any action's success or failure logic, only add a haptics call alongside existing state updates.
- Do **not** add a user-facing setting to disable haptics — the OS-level setting is the only control.
- Do **not** modify Capacitor configuration, add Capacitor plugins, or change iOS project files.
- Do **not** wire the `press()` function — it's exported for future use but has no call sites in this item.

## Files

Expected touches:

- `src/lib/haptics.ts` — **new file** with the five exported functions
- `src/components/ui/button.tsx` — add `haptics.tap()` call in onClick handler for `variant="primary"`
- `src/components/ui/checkbox.tsx` — add `haptics.select()` call in onChange handler
- `src/app/jobs/new/page.tsx` — replace `navigator.vibrate(35)` with `haptics.tap()`
- Any files with send/sign/payment action handlers that set button success state — add `haptics.success()` call at the same point
- Any files with submit action handlers that show user-visible errors — add `haptics.error()` call at the same point
- `tests/acceptance/96.test.tsx` — **new file** with acceptance tests
- Build verification: none. See criterion 3 — the module specifier is expected in the bundle.

## Edge cases

1. **Web platform**: Every function is a no-op. No console warning, no error, no side effect. The platform check happens inside each function, not at the call site.

2. **Native platform with haptics disabled at OS level**: The Capacitor call fails silently (Capacitor's documented behaviour). Do not detect this, do not compensate, do not log.

3. **Action resolves successfully but component has unmounted**: The haptics call is guarded (try-catch or promise catch) and does not throw. The unmount scenario is caught by the error handler, not special-cased.

4. **Rapid repeated presses**: Each press fires a haptic. Do not debounce, do not throttle — the OS handles coalescing.

5. **Dynamic import fails** (e.g., network error in a bizarre edge case): The haptics functions catch the import failure and become no-ops for that session. No user-visible error.

6. **Build output verification**: withdrawn. `grep -r '@capacitor/haptics' .next/static/` returning a match is the normal, correct result of a dynamic import — the specifier must survive for the runtime loader. This criterion was unsatisfiable as written and is replaced by the source-level assertion in criterion 3.

7. **Checkbox with onChange handler that throws**: The haptics call happens before the user's onChange, so if the user's handler throws, haptics has already fired. This is correct — the user interaction (the check) succeeded, even if the subsequent logic failed.

8. **Button onClick handler that throws**: Same as checkbox — haptics fires before the user's onClick, so the feedback happens even if the user's logic throws. The try-catch around the haptics call only guards haptics failures, not user code.

## Risks

- **None touching money, migrations, or user data** — this is purely additive tactile feedback with no effect on business logic.
- **Tree-shaking failure risk**: a statically imported plugin would be evaluated on web. Mitigation: the source-level assertion in criterion 3. Bundle size is not the test — the specifier appearing in the bundle is expected.
- **Over-firing risk**: If haptics.tap() is called at the wrong level (e.g., on every button, not just primary), the app becomes annoyingly buzzy. Mitigation: acceptance tests assert tap() fires only on primary variant.
- **Regression risk**: The existing 538 tests must pass unchanged. The only behavioural change visible to existing tests is the removal of `navigator.vibrate(35)`, which was already a no-op in the test environment (node, no navigator).
