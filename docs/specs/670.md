# CONN-5: Connect readiness is keyed on the wrong capability

## Problem

Connect readiness gates on `capabilities.transfers`, but CONN-4 (shipped 5 Sep, efae97d) set `on_behalf_of` on every PaymentIntent, making the connected account the settlement merchant. From that commit on, the connected account's payment capabilities determine whether Stripe permits the charge — and `transfers` is not one of them. The capability Stripe documents for Pay by Bank payments on Express connected accounts is `pay_by_bank_payments`, which `createConnectedAccount` never requests and `refreshAccountStatus` never stores. So accounts can show "Set up ✓ — you can take payments" while holding only the capability to receive transfers, not the one to accept payments.

## Scope: what changes

1. **Request `pay_by_bank_payments` at account creation.** `createConnectedAccount` adds it alongside `transfers` in the `capabilities` object passed to `stripe.accounts.create`.

2. **Store the capability separately.** A new column `stripe_pay_by_bank_enabled` holds `capabilities.pay_by_bank_payments === "active"`. `refreshAccountStatus` populates it the same way it populates `stripe_payouts_enabled` from `transfers`.

3. **Gate on the payment capability, not on transfers.** `canAcceptStripePayment` reads `stripe_pay_by_bank_enabled` instead of `stripe_payouts_enabled`. The payment-link gate at `stripe-connect.ts:211` (the function-internal check) reads it too.

4. **Keep the two capabilities independent.** `stripe_payouts_enabled` stays populated from `transfers` and continues to carry its current meaning — the account may receive transfers into its Stripe balance. Tests must prove that when one capability is active and the other is not, the code reads them separately rather than deriving one from the other.

5. **Update the settings UI.** `StripeConnectSection` shows "Set up ✓ — you can take payments" only when `stripe_pay_by_bank_enabled` is true, regardless of `stripe_payouts_enabled`.

6. **Existing accounts.** Two contractors hold connected accounts on production as of 6 Sep, both with only `transfers` active. Requesting `pay_by_bank_payments` for them requires calling Stripe's API to update their account capabilities — a one-time deployment step, not a backfill script. After requesting the capability, `refreshAccountStatus` must be called for each account to populate the new column. The deployment runbook notes this as a manual step.

## Explicitly out of scope

- Setting `on_behalf_of` itself — CONN-4 shipped that on 5 Sep.
- Renaming `stripe_payouts_enabled` — it is documented as misnamed in the source, and a rename would break frozen acceptance contracts. This item adds a correctly-named column alongside it, not a replacement for it.
- The payout leg (whether money reaches the contractor's bank) — PAY-8.
- Any change to how `isOnboardingComplete` determines completion — it stays keyed on `stripe_payouts_enabled` (the `transfers` capability) because onboarding completion means "Stripe has verified them enough to receive money", not "they can accept payments".

## Edge cases

- **Account with `transfers` active but `pay_by_bank_enabled` false**: `canAcceptStripePayment` returns false. The pay button is hidden. The settings UI shows the in-progress or requirements-due state, not the affirmative.
- **Account with both active**: both gates pass, pay button shows, settings says "Set up ✓ — you can take payments".
- **Account with `pay_by_bank_enabled` true but `transfers` false**: `canAcceptStripePayment` returns false (requires the account ID to be non-null AND pay-by-bank enabled). But payout-related UI and logic (anything reading `stripe_payouts_enabled`) sees false and behaves accordingly — the two flags stay independent.
- **Newly-created account**: requests both capabilities. Both start inactive, and both go active when Stripe completes onboarding (assuming no requirements failures).
- **`refreshAccountStatus` with missing capability in Stripe response**: treats absence the same as any non-"active" value — stores false. This matches the existing behaviour for `transfers` and `card_payments`.

## Risks

- **Money.** This changes what gates payment acceptance. An account that was payable before this change (holding `transfers`) but lacks `pay_by_bank_payments` would become unpayable after merging. However, the two existing accounts are already in that state — CONN-4 made them unpayable on 5 Sep by setting `on_behalf_of`, because their capabilities were never sufficient under that model. This change aligns the gate with reality rather than creating a new restriction.
- **Migration timing.** If code merges before the migration applies, every read of `stripe_pay_by_bank_enabled` is a TS2339 or a runtime null-reference at the database layer (column does not exist). The usual schema-precedes-code rule applies. If the migration applies but the two existing accounts are not updated before code merges, they become unpayable until manually fixed — acceptable given they were already unpayable as of 5 Sep, and the fix is a known manual step.

## Derived criteria

- `createConnectedAccount` requests `pay_by_bank_payments` alongside `transfers` when creating the Stripe Express account.
- `refreshAccountStatus` reads `capabilities.pay_by_bank_payments` from the Stripe account object and stores it as `stripe_pay_by_bank_enabled` in the contractors table.
- `canAcceptStripePayment` returns true only when `stripe_account_id` is non-null AND `stripe_pay_by_bank_enabled` is true, regardless of `stripe_payouts_enabled`.
- The settings UI renders "Set up ✓ — you can take payments" only when `stripe_pay_by_bank_enabled` is true.
- Given a stubbed Stripe account where `transfers` is "active" and `pay_by_bank_payments` is "inactive", after calling `refreshAccountStatus`, the database row has `stripe_payouts_enabled = true` and `stripe_pay_by_bank_enabled = false`, proving the two are stored independently.
- Given a stubbed contractor with `stripe_pay_by_bank_enabled = false`, `canAcceptStripePayment` returns false even if `stripe_payouts_enabled = true`.
- Given a stubbed contractor with `stripe_pay_by_bank_enabled = true`, `canAcceptStripePayment` returns true (assuming stripe_account_id is non-null), even if `stripe_payouts_enabled = false`.
