# Issue #189: Add associated domains and appUrlOpen handling for bank redirect return

## Problem

When a customer pays via TrueLayer or a trade sets up their fee billing mandate, the flow redirects to their bank's app, then attempts to return to `https://motko.app/i/[id]/paid` or `https://motko.app/settings?mandate=done`. With no universal link configuration, iOS cannot guarantee the return lands in the Motko app — it may open in Safari instead, leaving the customer uncertain whether their payment worked and forcing the trade to field a phone call. This is the return leg of every payment the product exists to collect.

## Scope: what changes

**App.entitlements** (`ios/App/App/App.entitlements`)
- Add `com.apple.developer.associated-domains` entitlement with value `applinks:motko.app`

**AASA file**
- Serve a valid `apple-app-site-association` file at `/.well-known/apple-app-site-association`
- Content type: `application/json`
- No redirect (must be direct)
- HTTPS only (Vercel handles this)
- File contents committed to the repository (not generated at request time)
- App identifier: `PLFZC3LK8F.app.motko.ios` (team ID + app ID from capacitor.config.ts)
- Paths list:
  - `/i/*/paid` - customer payment returns
  - `/settings` - mandate setup returns (catches `?mandate=done` query param)
- Exclude marketing routes so they continue opening in Safari rather than forcing the user into the app for public content

**appUrlOpen handler** (`src/components/native-app-init.tsx`)
- Register an `App.addListener("appUrlOpen", ...)` handler
- Extract the incoming URL's path and navigate the WKWebView to it using `window.location.assign()` or `router.push()`
- Do NOT reload the app at its root — navigate to the specific incoming path
- Fall through gracefully if the URL is malformed or unexpected (log and do nothing, rather than crashing or showing an error)

## Explicitly out of scope

- Do not change the TrueLayer flow, redirect URLs, or payment logic
- Do not add Android app links in this item (universal links are iOS-specific; Android requires a separate app links implementation)
- Do not change push notification deep linking, which already works via the existing notification tap handler
- Do not add a browser-based fallback using SFSafariViewController — if universal links prove insufficient on device, raise that separately
- Do not change routing inside the web application (Next.js routes, server components, etc.)
- Do not change the WKWebView server URL configuration in capacitor.config.ts

## Files

Expected to touch:
- `ios/App/App/App.entitlements` - add associated domains
- `src/app/.well-known/apple-app-site-association/route.ts` - serve the AASA file as a Next.js route handler, reading a committed JSON file
- `public/.well-known/apple-app-site-association.json` - the AASA file contents (served by the route handler)
- `src/components/native-app-init.tsx` - register appUrlOpen listener

May also touch:
- `capacitor.config.ts` - if the app ID needs adjustment, though it should already be correct
- Type definitions if the URL shape needs documenting

## Edge cases

**iOS has cached an older AASA or none at all**
- Association does not take effect on existing installs until iOS refetches the AASA
- iOS refetches on app install and periodically (timing is opaque and cannot be forced)
- This cannot be verified immediately after deploy on an existing install
- State this limitation in the PR description
- Verify with a fresh install on a test device

**App not installed on the device**
- The universal link opens in Safari as normal
- Do not attempt to force an install prompt (Smart App Banners are out of scope)
- This is the expected fallback and requires no special handling

**Deep link to a route requiring authentication, arriving while logged out**
- The existing session check in the app will redirect to `/login?redirect=<path>`
- The destination path is preserved via query param
- After authentication, the user continues to the intended destination
- This is already handled by the existing app logic — no change needed

**Malformed or unexpected path in the incoming URL**
- Log the unexpected URL to the console (for debugging)
- Fall through to the app root rather than erroring or rendering a broken route
- Do not show an error message to the user — treat it as a navigation to `/`

**User returns via the bank app rather than the redirect**
- Some banks provide a "Return to [app]" button in their own UI after authorization
- This is unchanged by this item and relies on the bank's implementation
- Worth verifying separately on device, but not a blocker for this item

**Universal link opens in Safari despite correct configuration**
- This can happen if the user long-presses the link and chooses "Open in Safari"
- Or if the link is opened via a third-party app that bypasses universal link handling
- The web app is fully functional in Safari — no special handling needed
- Not a bug, just a user choice or platform limitation

**Path includes query parameters or fragments**
- Query params (e.g. `?mandate=done`) are part of the URL and should be preserved in the navigation
- Fragments (e.g. `#section`) should also be preserved if present
- Test that `https://motko.app/settings?mandate=done` navigates to `/settings?mandate=done` in the WKWebView

**AASA file serves with wrong content type or 404**
- iOS will not establish the association — universal links will not work
- The route handler must return `Content-Type: application/json` explicitly
- Return HTTP 200, not 301/302 redirect (Apple's requirement)
- Test this in the acceptance tests (cannot test HTTP headers directly, but can test that the route exists and returns the expected JSON structure)

## Risks

**Money/payment flow**
- This item does not change payment logic, only the return path after payment
- A misconfigured AASA or broken handler could strand users in Safari after paying, but the payment itself is unchanged
- The existing `/i/[id]/paid` page works in Safari — universal links are a better experience, not a functional requirement

**User data**
- No user data changes
- No database migrations

**Session/authentication**
- Deep linking while logged out is handled by the existing session guard (see edge cases)
- No new authentication logic introduced

**Deploy order**
- The AASA file must be deployed and accessible BEFORE the app binary with the new entitlements is released to users
- Otherwise, iOS may attempt to fetch the AASA for validation and fail, preventing universal link association
- Deployment order: (1) deploy AASA file to production, (2) rebuild and release iOS app with new entitlements
- The iOS app can be rebuilt immediately after deploy — Vercel serves the AASA file as soon as the PR merges

**iOS refetch timing**
- iOS refetches the AASA on install and periodically (Apple does not document the exact timing)
- Existing installs may not pick up the AASA immediately after deploy
- This is an Apple platform limitation, not a bug in our implementation
- State this in the PR and verify with a fresh install

## Derived criteria

What I understood the human to be asking for:

1. Universal links are configured for `motko.app` so payment and mandate flows can return directly into the app instead of Safari
2. The iOS app's entitlements include `applinks:motko.app`
3. A valid AASA file is served at `https://motko.app/.well-known/apple-app-site-association` with:
   - The correct app identifier (team ID + app ID)
   - Paths covering payment returns (`/i/*/paid`) and mandate setup (`/settings`)
   - Marketing routes excluded so they stay in Safari
   - Content type `application/json`
   - No redirect (direct serve)
   - Contents committed to the repository, not generated at request time
4. An `appUrlOpen` listener is registered in the native app init component
5. The listener navigates the WKWebView to the incoming URL's path (not the root)
6. Malformed URLs are handled gracefully (log and fall through, no crash or error UI)
7. Query parameters and fragments in the incoming URL are preserved during navigation
8. The handler does not interfere with existing push notification deep linking
9. iOS refetch timing is documented as a limitation (cannot force, requires fresh install to verify immediately)
10. Deployment order is documented (AASA file first, then app binary with new entitlements)
