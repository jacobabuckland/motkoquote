# NOTIF-3: Permission timing and the in-app pre-prompt

## Problem

On iOS the OS permission prompt is one-shot. A denial is effectively permanent (reversible only via Settings), and asking at the wrong moment spends the single chance on a user who has no reason yet to say yes. The current implementation shows the in-app prompt after every quote send, which is too frequent and doesn't respect the ideal trigger point.

## Scope: what changes

1. **Add server-side trigger tracking**: a `first_quote_sent_at` column on `contractors`, stamped when a contractor sends their first quote from any device (app or web).

2. **Client-side trigger evaluation**: the in-app prompt now checks whether (a) a first quote has been sent (`first_quote_sent_at` is set), and (b) the contractor has not yet been asked on this device. This evaluation happens on app open, not immediately after send.

3. **Already-denied state handling**: when the OS permission is already denied, show an honest message and a button that deep-links into iOS Settings > motko > Notifications, rather than a dead "Enable" button or silence.

4. **Remove the immediate post-send prompt from the job page**: the existing `PushPrompt` component in `src/app/jobs/[id]/push-prompt.tsx` is retired. The new prompt appears at app open, gated by the trigger condition.

5. **Migration**: `supabase/migrations/00000000000067_first_quote_sent_at.sql` adds the column and backfills it with `created_at` for contractors who already have sent quotes (status != 'draft').

## Explicitly out of scope

- Which events are sent (NOTIF-2)
- The web push registration flow (unchanged)
- The Settings notification control (unchanged)
- Testing on a physical device (manual verification)

## Files

- supabase/migrations/00000000000067_first_quote_sent_at.sql (new)
- src/lib/push/native.ts (modify) — add `canOpenSettings` check
- src/lib/push/client.ts (modify) — export utility for iOS Settings deep link
- src/app/jobs/[id]/push-prompt.tsx (modify) — retire or gate the old post-send prompt
- src/app/layout-shell.tsx or src/app/layout.tsx (modify) — mount the new app-open prompt
- src/components/push/first-quote-prompt.tsx (new) — the new in-app pre-prompt
- src/app/jobs/actions.ts (modify) — stamp `first_quote_sent_at` on first send

## Edge cases

- **Contractor deletes and reinstalls the app**: localStorage dismissals are reset, so they may be asked again even if they previously declined twice. The server-side `first_quote_sent_at` persists, so the trigger condition still evaluates correctly.
- **Contractor uses multiple devices**: each device tracks its own dismissal count and permission state independently. The server-side trigger fires once per account, but each device evaluates it separately.
- **First quote sent from web, app opened later**: the prompt appears on the next app open after `first_quote_sent_at` is stamped, regardless of where the quote was sent from.
- **OS permission already granted**: the prompt never shows. `nativePushPermission()` returns "granted" and the component short-circuits.
- **OS permission already denied before the first quote is sent**: the prompt shows honest copy ("Notifications are blocked — open Settings to enable them") and a button that deep-links to Settings, rather than a dead "Enable" button.
- **Contractor sends multiple quotes in quick succession**: `first_quote_sent_at` is stamped once, idempotently. The prompt is held until the next app open (not shown mid-session), so rapid sends do not trigger repeated prompts.

## Risks

- **Schema precedes code**: the migration must be applied to production before merging the code that reads `first_quote_sent_at`, or the query will fail with "column does not exist".
- **Deep link to Settings may not work on all iOS versions**: the `UIApplicationOpenSettingsURLString` deep link is documented as iOS 8+, so it should work on all supported versions, but a failure would leave the button inert rather than crashing.
- **localStorage may throw in some iOS configurations**: already handled in the existing `PushPrompt` code (private browsing, site data blocked). The new component must handle the same failure mode.

## Derived criteria

1. A fresh install that reaches signup and abandons has not consumed the OS prompt — the prompt never shows before a quote is sent.
2. Declining the in-app explainer leaves the OS permission still requestable — a soft "Not now" does not call `registerNativePush`, so the OS alert is never shown.
3. Accepting the explainer produces the OS prompt — "Yes, tell me" calls `registerNativePush`, which requests permission and shows the system alert.
4. An already-denied state is handled with honest copy and a route into iOS Settings — when `nativePushPermission()` returns "denied", the prompt shows different copy and a button that opens Settings.
5. The trigger fires for a trade whose first quote was sent from the web, on their next app open — `first_quote_sent_at` is stamped server-side in `sendQuote`, so it is set regardless of which client sent the quote.
6. The trigger is evaluated device-side, not at the moment of send — the prompt appears on app open when the trigger condition is met, not immediately after `sendQuote` returns.
7. The prompt appears at most twice per device — the existing `MAX_ASKS` logic is preserved, and dismissals are tracked per-device in localStorage.
8. A contractor who has already granted permission never sees the prompt again — `nativePushPermission()` returns "granted" and the component returns null.
