# Issue #123: [BACKFILL] Correct duplicate referral_unlock credits

**Auditing branch:** `factory/123` @ `7faaa5c`  
**No database migration required.**

**⚠️ MOVES USER-VISIBLE BALANCES.** Requires dry-run report approval before executing.

## Problem

Where a referee's first two jobs settled concurrently (both checked `isFirstPaidJob` and found a pending referral at the same instant), `paid-job-settlement.ts` created two `referral_unlock` credit_events rows (+5 each) for the same `related_referral_id`, granting the referrer 10 free jobs instead of 5. The duplicate rows are already persisted and already reflected in `free_jobs_remaining`. These duplicates violate policy (one referral = one reward) and block creation of the unique index planned for a later item.

The uniqueness constraint at `00000000000023_pricing_referral.sql:70-72` applies only to `reason='job_consumed'`. No equivalent guard exists for `referral_unlock`, so the concurrent settlement race inserted both rows. This is legacy data that must be corrected retroactively before the index can be created.

## Scope: what changes

A new pure library function and async correction runner in **`src/lib/correct-referral-duplicates.ts`** (new file):

1. **Pure analysis function:** `computeReferralDuplicateCorrections(events, contractors)` takes all `referral_unlock` credit_events and all contractors, identifies surplus rows (grouped by `related_referral_id`, keeping the earliest `created_at`), and returns a correction plan per contractor: which event IDs to delete and how much to decrement their `free_jobs_remaining` (floored at zero, recording shortfalls).

2. **Async runner:** `correctReferralDuplicates(admin, { dryRun, applyCorrections })` runs the analysis and either:
   - **Dry-run mode** (default when `applyCorrections=false`): Returns a report object listing affected contractors, surplus counts, current balances, resulting balances, and any shortfalls. Writes nothing to the database.
   - **Correcting write mode** (`applyCorrections=true`): For each affected contractor, deletes the surplus credit_events rows and then decrements `free_jobs_remaining` by the same amount (using `increment_free_jobs_remaining` with negative delta). The two writes are sequential, not transactional — see criterion 7. Returns the same report structure plus confirmation counts, and the ids of any contractor whose decrement did not land after its delete did.

3. **Reporting:** The dry-run report is committed to the PR as **`docs/backfill-reports/123-referral-duplicates.json`** (new file) before the correcting write flag is ever set. A human reviews this report and approves the corrections before the script is run with `applyCorrections=true`.

The script is **idempotent**: running the correction a second time finds zero duplicates and makes no changes.

## Explicitly out of scope

- **Do not create the unique index.** That is a separate item which runs after this correction completes and is verified.
- **Do not modify `paid-job-settlement.ts` or any settlement logic.** The race condition will be fixed separately; this item only corrects the legacy duplicates.
- **Do not send any notification.** Notification (if any) is a manual step taken after reviewing the report, not automated by this code.
- **Do not correct any other credit reason, including `job_consumed`.** Only `reason='referral_unlock'` duplicates are touched.
- **Do not modify the `referrals` table or referral status.** The referral record itself is unchanged; only the duplicate credit_events rows are deleted.
- **No database migration required.** This is application code that runs once, not a schema change.

## Edge cases

### 1. Referrer has already spent the surplus credits
**Input:** Referrer received +10 (duplicate), spent 8 jobs, `free_jobs_remaining=2`. Correction should remove 5.  
**Behaviour:** Balance goes to `max(0, 2 - 5) = 0`. The 3-job shortfall is recorded in the report under `shortfall: 3`. No negative balance is created. These are jobs already delivered free and cannot be recovered.

### 2. Three or more duplicates for one referral
**Input:** Three `referral_unlock` rows for `related_referral_id='ref-x'`, created at T1, T2, T3.  
**Behaviour:** Keep the row created at T1 (earliest `created_at`). Delete the rows created at T2 and T3. Decrement `free_jobs_remaining` by 10 (two surplus × 5 each).

### 3. Referrer account is deleted or anonymized
**Input:** A duplicate exists but the referrer's contractor row was deleted (`on delete cascade`) or anonymized.  
**Behaviour:** The credit_events rows cascade-delete automatically when the contractor is deleted, so the duplicate no longer exists. If the contractor was anonymized (still exists but identifying data cleared), treat it the same as any other contractor — apply the correction and list it in the report. A separate section of the report lists any orphaned credit_events found (events with no matching contractor), but these should be rare given the cascade.

### 4. Referral later cancelled or reversed
**Input:** The referral status is no longer `rewarded` (e.g. manually set to `pending` or `activated` by an admin action).  
**Behaviour:** Out of scope. The correction runs against credit_events rows, not referral status. If the referral itself was reversed, that is a separate correction and should be reported but not automatically handled here. The dry-run report can flag any duplicates where the referral status is unexpected, but the script does not fail — it lists the anomaly for human review.

### 5. No duplicates found
**Input:** Every `related_referral_id` appears exactly once (or zero times).  
**Behaviour:** The report shows `affectedContractors: []`, `totalSurplusCredits: 0`, and the correcting write makes zero changes. Idempotent success.

### 6. Dry-run called multiple times
**Input:** The dry-run function is called repeatedly before any correction is applied.  
**Behaviour:** Identical report every time. No database writes occur. Safe to run as many times as needed.

### 7. Correcting write called after partial manual correction
**Input:** A human manually deleted one duplicate row directly in the database, then the script runs with `applyCorrections=true`.  
**Behaviour:** The script detects the remaining duplicate(s), computes the correction for the remaining surplus only, and applies it. The report reflects the state as found (not the original duplicate count).

### 8. Write failure during correcting write
**Input:** One contractor's correction fails part-way (e.g. the database connection drops between the delete and the decrement).  
**Behaviour:** There is no rollback — the delete may already have committed. The script records that contractor as **partially corrected**, naming it and which step landed, and continues with the others; each contractor's correction is independent. Re-running is safe: the detection query finds no surplus rows for a contractor whose delete succeeded, so a retry decrements only what is still outstanding. Until then the nightly `reconcile-free-jobs` job will bring that contractor's cache back in line with the ledger on its own, so the drift closes even if nobody retries.

## Risks

### 1. Moves user-visible balances (HIGH)
**Risk:** Correcting `free_jobs_remaining` reduces the balance a referrer can see in the app. If they had 10 free jobs (from the duplicate) and already spent 7, correcting to 5 total would floor them at 0, preventing them from using any more. This is a user-visible change that requires communication.  
**Mitigation:** The dry-run report is reviewed and approved by a human before `applyCorrections=true` is set. The report lists every affected contractor, their current balance, and the resulting balance, so the impact is known before execution. Affected referrers are contacted before the correction runs (manual step, not automated).

### 2. Incomplete or incorrect duplicate detection (MEDIUM)
**Risk:** The query that detects duplicates misses some cases or flags false positives, leading to incorrect corrections.  
**Mitigation:** The pure analysis function is unit-tested with all edge cases (single duplicate, triple duplicate, no duplicates, mixed). The dry-run mode allows the correction plan to be reviewed before any writes occur. The query is simple: group by `related_referral_id` where `reason='referral_unlock'`, count > 1 → duplicates.

### 3. Race condition during correcting write (LOW)
**Risk:** A new referral unlocks between the dry-run and the correcting write, or during the correcting write itself, causing the balance to be decremented incorrectly.  
**Mitigation:** The decrement uses the database function `increment_free_jobs_remaining(id, -N)`, which is safe for concurrent writes (folded into a single statement, not read-modify-write), so a referral unlock landing during the correction composes correctly rather than being clobbered. The delete and the decrement are sequential rather than atomic — see criterion 7 — so a failure between them leaves the ledger corrected and the cache briefly stale. That direction is the safe one: the ledger is the source of truth, and the nightly reconcile recomputes the cache from it.

### 4. Shortfall not communicated (MEDIUM)
**Risk:** Referrers who already spent surplus credits are floored at zero, creating a debt the system doesn't track. The shortfall is recorded in the report but not surfaced anywhere else.  
**Mitigation:** The report explicitly lists shortfalls. The human reviewing the dry-run report sees which contractors owe jobs they already consumed. Follow-up communication (manual) addresses this case if needed. The correction itself is still correct: the ledger now matches policy (one referral = 5 credits), and the cache is floored at zero (no negative balances).

### 5. Idempotency is not tested (MEDIUM)
**Risk:** Running the correcting write twice applies the correction twice, creating negative balances or deleting the wrong rows.  
**Mitigation:** Acceptance tests explicitly verify idempotency: after the first correction, running it again finds zero duplicates and makes zero changes. The correction deletes specific event IDs determined by the duplicate analysis; re-running the analysis finds no duplicates, so no IDs are targeted for deletion.

## Derived criteria

What I understood the human to be asking for:

1. **Detect duplicates:** Multiple `referral_unlock` credit_events rows with the same `related_referral_id`.

2. **Keep the earliest, delete the rest:** For each duplicate set, keep the row with the earliest `created_at`, delete the others.

3. **Decrement balance by surplus:** For each affected contractor, decrement `free_jobs_remaining` by (number of surplus rows × 5).

4. **Floor at zero, record shortfalls:** If the decrement would produce a negative balance, set it to zero and record the shortfall in the report.

5. **Dry-run mode is the default:** When `applyCorrections=false` (or omitted), produce the report without writing to the database.

6. **Correcting write requires explicit flag:** Only when `applyCorrections=true` are the deletes and decrements applied.

7. **Sequential per contractor, with failure tracking:** Each contractor's correction performs the delete and then the decrement, and records whether each step succeeded. A contractor whose decrement fails after its delete committed is reported as partially corrected, by id, so it can be retried. The two writes are deliberately *not* required to be atomic: Supabase has no client-side transaction control, so atomicity here would mean a `SECURITY DEFINER` database function, and this item is chartered as a one-shot script with no schema change. The drift a half-applied correction leaves is bounded and self-repairing — `credit_events` is the source of truth, `free_jobs_remaining` is a cache, and the nightly `reconcile-free-jobs` job recomputes every cache from the ledger and writes back the ones that disagree (`src/lib/reconcile-free-jobs.ts`). The window is one night of a contractor holding free jobs they should not, which is the same exposure the ledger/cache split already carries by design.

8. **Idempotent:** Running the correction a second time finds zero duplicates and makes no changes.

9. **Report is committed to PR:** The dry-run report is committed as `docs/backfill-reports/123-referral-duplicates.json` before any correcting write occurs.

10. **No notification, no settlement changes, no unique index creation:** These are all explicitly out of scope.
