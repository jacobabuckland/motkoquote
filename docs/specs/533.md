# DATA-1: Mark internal accounts

## Problem

The contractors table has no way to distinguish internal or test accounts from real ones. Every metric derived from production data silently mixes testing behavior with actual contractor behavior, which has already invalidated two headline figures: a 55% invention rate (actually 18.9% when internal accounts are excluded) and a 41% abandonment rate (actually 11 test runs). No query anywhere in the product can currently exclude internal accounts because there is no flag to query against.

## Scope: what changes

Add `is_internal` boolean column to the contractors table:
- Not null, defaults to false
- Additive only — no existing rows are modified, no behavior changes
- Set manually for identified test accounts (Jacob's accounts and Aspire Plastering)
- Enables future metrics to exclude test/internal accounts

## Explicitly out of scope

- Building a metrics dashboard (this makes honest metrics possible; it doesn't build one)
- Deleting or anonymizing internal account data
- Any change to what contractors can see or do
- Automatically deriving the flag from domain, name, or signup source
- Retroactively recomputing or correcting historical published figures

## Files

- `supabase/migrations/00000000000063_contractor_is_internal.sql` (new) — numbered 063, one above current highest (062)

## Edge cases

**Migration idempotency:** Safe to run multiple times. Use `IF NOT EXISTS` or equivalent guards so re-running doesn't fail.

**Existing rows:** Every existing contractor gets `is_internal = false`. No accounts are reclassified by the migration itself — that happens through explicit manual updates after the column exists.

**Default for new rows:** Any contractor created after this migration defaults to `is_internal = false`. Setting it true requires an explicit update.

**Empty state:** If no accounts are ever marked internal, every query continues to work exactly as it does today.

## Risks

**Migration verification:** The migration ledger can show a migration as "applied" even if its DDL never actually landed (phantom apply from `migration repair`). The acceptance tests verify the migration file is correct, but confirming the column exists on production requires probing the actual schema after Jacob applies it via `supabase db push`.

**Irreversible if data is deleted:** Once internal accounts are marked and then data is deleted based on that flag, the deletion can't be reversed. This migration doesn't delete anything, but it enables future cleanup work. The flag itself is reversible (can be flipped back).

## Derived criteria

The human spec asks for:
1. A boolean column `is_internal` on contractors table
2. Not null, default false
3. No existing account behavior changes
4. Set manually, not automatically derived
5. Enables future metric queries to exclude internal accounts

The acceptance tests verify:
- Migration file exists at the correct path with correct number (063)
- Migration DDL adds the column with correct type and constraints
- Migration is idempotent (safe to run multiple times)
- Default value is false, column is not null
- No existing rows are modified by the migration
