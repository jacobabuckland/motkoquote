# Issue #221: Enable row level security on cron_locks

**This item requires a database migration.** Schema changes must be applied to production BEFORE the code is merged, per CLAUDE.md migrations guidance.

## Problem

The `cron_locks` table was created in migration 028 without row level security. Under Supabase's default grants, the anon role — whose key ships publicly as `NEXT_PUBLIC_SUPABASE_ANON_KEY` — retains insert and select privileges on the table. An insert into `cron_locks(name) values ('collect-fees')` issued with the public anon key causes the advisory lock acquire to conflict, blocking every cron sharing that mechanism (fee collection, dunning, account purge, free-jobs reconciliation) on every subsequent run until the row is manually deleted. Every other tenant table in the schema has RLS enabled with owner-scoped policies. This is the single table that assumes unreachability it does not have.

## Scope

1. **Migration file** at `supabase/migrations/00000000000XXX_cron_locks_enable_rls.sql` (next available number) that runs:
   ```sql
   alter table cron_locks enable row level security;
   ```
   with a corresponding down migration that runs:
   ```sql
   alter table cron_locks disable row level security;
   ```

2. **RLS check** at `src/checks/rls.check.test.ts` that queries the database schema (via Supabase admin client) to assert that every table in the `public` schema has `relrowsecurity = true` (the pg_catalog.pg_class column). If any table does not have RLS enabled, the check fails and reports the table name. The check runs as a vitest test in the CI suite.

## Explicitly out of scope

- **Do not add RLS policies** to `cron_locks`. No policy is the intended state: anon is denied, service role bypasses.
- **Do not modify** the lock acquire or release logic in `src/lib/cron-lock.ts`. The fencing token is a separate item.
- **Do not change RLS** on any other table. If the check discovers tables without RLS, report them and fail — do not enable RLS on them as part of this item, as each needs its own policy review.
- **Do not rotate or change** the anon key itself.
- **Do not modify** which role the cron jobs authenticate as (they use the service role and will continue to do so).

## Files

Expected touches:
- `supabase/migrations/00000000000XXX_cron_locks_enable_rls.sql` (new)
- `src/checks/rls.check.test.ts` (new)

No changes to:
- `src/lib/cron-lock.ts` (lock logic unchanged)
- `src/app/api/cron/*/route.ts` (cron routes unchanged)
- `.env` or secrets (no key rotation)

## Edge cases

1. **Rows already present in cron_locks when the migration runs**: untouched. Enabling RLS does not delete rows. If a stale lock exists it will still block. The Engineer should check for and clear stale rows before applying the migration, and report any found.

2. **A cron is mid-run during migration**: service-role access is unaffected by RLS (service role bypasses it), so an in-flight run completes normally. No impact.

3. **The src/checks addition finds other tables without RLS**: the check must report them and fail. Do not enable RLS on other tables as part of this item — each needs its own policy review. The item is scoped to `cron_locks` only.

4. **Anon client attempts insert after migration**: returns a permission error (exact Supabase/Postgres error code: `42501` or similar, message about RLS denying access). This is the intended state.

5. **Anon client attempts select after migration**: returns a permission error. This is the intended state.

6. **Service role client (cron jobs) attempts insert/select after migration**: succeeds. Service role bypasses RLS entirely. No change to existing behavior.

7. **Legacy data in cron_locks**: none. This table holds only transient lock rows, which are deleted after each cron run completes.

8. **User-visible impact**: none. End users never interact with `cron_locks`. This is internal infrastructure.

## Risks

1. **Migration must precede code deployment**: per CLAUDE.md, Supabase migrations are applied manually via `supabase db push` against the linked project and do not run automatically on Vercel deploy. The migration must be applied to production BEFORE merging the PR. If code depending on RLS-enabled state deploys before the migration lands, the check will fail in CI.

2. **Stale locks can block crons**: if a lock row is abandoned by a crashed run and never reclaimed (because the next run is >10 minutes later and the TTL logic in `acquireCronLock` has not expired it yet), that cron will no-op silently. This is existing behavior, not a regression introduced by this item, but the migration is an opportunity to verify no stale locks exist before applying.

3. **Check can fail CI on unrelated tables**: if other tables in the schema lack RLS, the new check will flag them and fail CI. This is a feature, not a bug — it surfaces a security gap. However, it means this item may uncover additional work that must be addressed separately.

## Derived criteria

What I understood the human to be asking for:

1. Enable row level security on the `cron_locks` table via a new migration, so the anon role can no longer insert or select rows.
2. Add a check to `src/checks` that asserts all tables in the `public` schema have RLS enabled, querying `pg_catalog.pg_class.relrowsecurity`.
3. Verify that anon key access is denied (insert and select both return permission errors) after the migration is applied.
4. Verify that service role access (used by crons) continues to work after the migration, as service role bypasses RLS.
5. Clear any stale lock rows before applying the migration, and report if any are found.
6. Do not add policies to `cron_locks` — deny-all (no policy) is the intended state.
7. Do not change the lock logic in `cron-lock.ts` or the authentication role used by crons.
8. If the check finds other tables without RLS, report them and fail — do not enable RLS on them as part of this item.
