# OBS-6: Stop the stepper ticking a stage that did not happen

## Problem
The job stepper derives six stages (quote sent, accepted, contract signed, work complete, invoiced, paid) from four different row families. When the sequence is non-monotonic — for example, an invoice raised before the contract is signed — the stepper finds the last complete stage and marks every earlier incomplete stage as complete to maintain visual monotonicity. This means a contractor who raises an invoice before signing a contract sees "contract signed" rendered with a green tick, when no contract was actually signed. The discrepancy is recorded to the events table but shown to nobody. Production: seven firings across two distinct jobs, always with "contract signed" being forced.

## Scope: what changes

1. **Introduce a "forced" stage state** alongside "complete", "current", "future", and "declined" to represent stages that were back-filled for monotonicity rather than genuinely reached.

2. **Render forced stages visibly distinct** from complete stages in the pipeline stepper. The distinction must be perceivable without hovering — a different icon, color, or label that makes clear this stage was skipped.

3. **Preserve forced-stage information in the dashboard listing** rather than discarding it. The dashboard's job-history module currently drops `inconsistentStages` entirely; it must preserve and expose this information so the listing can render forced stages distinctly.

4. **Deduplicate the telemetry event** so it counts jobs rather than page views. Currently `track("stepper_inconsistency")` fires on every render with no deduplication, so seven firings may represent two jobs viewed multiple times. Persist a dedupe key (job_id + forced_stages) so each unique inconsistency is logged exactly once.

## Explicitly out of scope

- Redesigning the six-stage linear model or supporting arbitrary job orderings
- Changing the invoice state machine or workflow rules
- Preventing non-monotonic sequences from occurring (they are legitimate)
- Making forced stages interactive or editable

## Files

- `src/lib/job-stages.ts` (modify) — add "forced" to `StageState` type, update `deriveStages` to return forced stages with state="forced" instead of state="complete"
- `src/components/ui/pipeline-stepper.tsx` (modify) — add rendering for forced state with distinct visual treatment
- `src/lib/job-history.ts` (modify) — preserve `inconsistentStages` in the normalized history row so the dashboard can render forced stages
- `src/app/jobs/[id]/page.tsx` (modify) — deduplicate the stepper_inconsistency telemetry event
- `src/app/jobs/page.tsx` (modify) — pass forced-stage information to the listing row renderer if needed
- `src/components/ui/pipeline-row.tsx` (modify) — may need to accept and display forced-stage information
- `tests/acceptance/546.test.tsx` (new) — acceptance tests

## Edge cases

- **A job with multiple forced stages**: all must render as forced, not just the first or last
- **A forced stage that later becomes genuinely complete**: once the underlying row (e.g., contract signed) is present, the stage should render as genuinely complete, not forced
- **Telemetry deduplication across time**: if the same job's forced stages change (e.g., contractor signs the contract, removing one forced stage), the new state should log as a distinct event
- **Empty or all-complete pipelines**: a pipeline with no forced stages renders exactly as today (no visual change for the happy path)

## Risks

None. This is a display-only change with no money, auth, or data-migration implications. The underlying monotonic enforcement logic is unchanged; only the presentation differs.

## Derived criteria

**What this ticket delivers:**

1. A new stage state "forced" that represents stages marked complete only because a later stage was complete
2. Visual distinction in the pipeline stepper between genuinely complete stages (green tick) and forced stages (different treatment, perceivable without hover)
3. The dashboard listing showing forced stages distinctly, not rendering them identically to genuinely complete stages
4. Telemetry that counts unique job-level inconsistencies rather than page-view count
5. No change to the happy path: a monotonic pipeline renders exactly as today
