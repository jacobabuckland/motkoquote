# SUB-2: Three free jobs, waiving the transaction fee only

**Source:** Notion roadmap item SUB-2  
**Module:** payments

## Problem

The code sets `FREE_JOB_ALLOWANCE = 5` (src/lib/motko-fee.ts:18). The decided figure is three, waiving both subscription and transaction fee. This was already enacted at the ledger level by #330 (FEE-1), which set the signup grant to 3 credits, but the named constant still reads 5. That constant is what `motkoFeePennies` checks to decide whether a job is free, so the mismatch means nothing enforces the three-job rule at settlement time.

The earlier #586 (RAIL-2) made the counter decrement on ANY completed job — rail, cash, cheque or bank transfer — so one counter already exists and already counts everything. This item corrects the allowance constant and the DB default to match the ledger grant that has been shipping since FEE-1.

## Scope: what changes

1. **Change `FREE_JOB_ALLOWANCE` from 5 to 3** in src/lib/motko-fee.ts
2. **Add a migration** to change the DB default for `contractors.free_jobs_remaining` from 5 to 3
3. **Update the comment** in src/lib/referral-signup.ts (line 89-90) from "defaults to 5" to "defaults to 3"

The nightly reconciliation job (`reconcileFreeJobs`) will correct any existing contractors whose cache drifted from the ledger, so no backfill is needed — the reconciliation is already the mechanism that makes the ledger the source of truth.

## Explicitly out of scope

- **The fee schedule itself** (SUB-3) — the ladder rates and floor stay unchanged
- **When billing starts** (SUB-1) — that item owns what the exhausted counter triggers
- **The signup grant amount** — already 3 since #330 (FEE-1), unchanged here
- **The counter decrementing logic** — already fixed in #586 (RAIL-2) to decrement for any settlement method

## Files

All files that must change:

- **src/lib/motko-fee.ts** (modify) — `FREE_JOB_ALLOWANCE` changes from 5 to 3
- **supabase/migrations/** (new) — new migration to alter the DB default for `contractors.free_jobs_remaining` from 5 to 3
- **src/lib/referral-signup.ts** (modify) — comment on line 89-90 updated to reflect the new default

## Edge cases

- **Three cash jobs, then a rail job.** The fourth carries a fee. The counter decremented three times (once per cash job), so the fourth job sees `freeJobsRemaining = 0` and accrues the full fee. Consistent with what the trade was told.
- **A job completed then archived.** Still counts. The work happened, the counter decremented at settlement, and archiving does not undo that.
- **A staged job** (deposit, then final payment). Consumes one free job, not one per stage. The per-job idempotency guard in `settlePaidJob` ensures the counter burns exactly once on the job's first settlement.
- **Existing contractors with free_jobs_remaining = 5 from the old default.** The nightly `reconcileFreeJobs` cron corrects the cache to match sum(delta) from the ledger. Since FEE-1 shipped, new signups get a signup_grant of 3, so their ledger sum is 3, and reconciliation will correct the cache from 5 to 3.

## Risks

None. The ledger grant has been 3 since #330 (FEE-1) shipped, and #586 (RAIL-2) made the counter decrement for all settlement methods. This item aligns the constant and DB default with what has already been shipping, so it removes a discrepancy rather than introducing one.

The migration changes only the DEFAULT for new rows; it does not update existing rows. Existing contractors are corrected by the nightly reconciliation, which is already the mechanism that keeps the cache in sync with the ledger.

## Derived criteria

A plain-language checklist of what must be true:

1. `FREE_JOB_ALLOWANCE` equals 3 (not 5)
2. The first three completed jobs (of any settlement method — rail, cash, cheque, transfer) are free of both subscription and transaction fee
3. The fourth completed job accrues a fee (or pays one at source if on-rail)
4. The remaining count is visible to the trade on the dashboard
5. A staged job (deposit, then final) consumes exactly one free job, not two
6. Cash and off-rail jobs decrement the counter exactly as on-rail jobs do (already true since #586)
7. The DB default for new contractors' `free_jobs_remaining` is 3, not 5
