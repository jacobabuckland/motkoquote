# Issue #252: LED-2: Cost entry and job-level P&L view

**Auditing branch:** `factory/252` (to be created)  
**Database migration required:** NO — builds on LED-1's tables from migration 00000000000041

## Problem

The LED-1 foundation (#244) created the tables and server actions for tracking job costs, but contractors have no way to enter costs or see whether a job was profitable. This ticket adds the first user-visible ledger surface: a cost entry form on the job page and a P&L panel showing what the job actually made.

## Scope: what changes

### 1. Cost entry UI on the job page

Below the existing job content (timeline, quote, contract, invoice sections), add a "Costs" section with:

- **Cost list** — one row per cost, showing: description, counterparty name (if present), amount (net), category icon/label, incurred date, paid/unpaid indicator
- **Add cost button** — opens a cost entry form (inline expansion or modal, Engineer's choice based on 390px width constraint)
- **Cost entry form** with fields:
  - Description (text, required)
  - Amount (number input, pounds and pence, required — converted to integer pence on submission)
  - Category (select: materials, labour, subcontractor, plant_hire, other)
  - Counterparty (text input with type-ahead over existing counterparties for this contractor, creates new counterparty on miss per LED-1's matching logic)
  - Date incurred (date picker, defaults to today, may predate job creation)
  - VAT treatment (select: standard, zero, exempt, reverse_charge, unknown — defaults to `standard` if contractor is VAT-registered, else `zero`)
  - Paid/unpaid toggle (defaults to unpaid)
- **Edit and delete** — each cost row has edit and delete actions
  - Delete shows a **native confirmation UI** (Action Sheet on iOS, Alert Dialog on Android/web), NOT `window.confirm()` which reveals the WebView origin
  - Confirmation copy: "Delete this cost? This cannot be undone."
- **Mark as paid** — quick action on each unpaid cost row, sets `paid = true` and `paid_on = today`, reversible by editing the cost back to unpaid

All mutations use the existing server actions from LED-1 (`src/app/jobs/[id]/cost-actions.ts`), which are already RLS-scoped and contractor-isolated.

### 2. Job P&L panel

Below the costs list, add a P&L summary card showing:

- **Invoiced (net)** — sum of all invoice amounts for this job's quote (converted to pence for computation), or "Not yet invoiced" if no invoice exists
- **Costs (net)** — sum of `job_costs.amount_net` in pence
- **Gross profit** — invoiced net minus costs net, in pence, rendered via `<Money>` component (pounds conversion happens in `formatGBP`)
  - If no invoice exists: show "Not yet invoiced" state, do NOT show a negative profit figure
  - If costs exceed invoiced value: show the loss plainly (e.g. "-£240 loss")
- **Margin** — gross profit as a percentage of invoiced net: `(profit / invoiced) * 100`, rounded to 1 decimal place, displayed alongside profit (e.g. "£1,200 (24.0%)")
  - If invoiced is zero: show "—" instead of attempting division
- **VAT position** — shown SEPARATELY, clearly labelled as an estimate:
  - "VAT collected: £X" (sum of VAT on invoices for this job)
  - "VAT on costs: £Y" (sum of `job_costs.vat_amount` where not null)
  - "VAT position: £Z" (collected minus costs VAT)
  - **Disclaimer** (agreed with Jacob before merge): "Estimate only, not tax advice. Check with your accountant."
  - If contractor is not VAT-registered (`contractors.vat_registered = false`): hide this entire VAT section rather than showing zeros
- **Unpaid costs callout** — if any costs have `paid = false`, show: "£X of costs still to pay" with the sum of unpaid amounts

All monetary figures render via the `<Money>` component (display face, tabular numerals per `docs/design-direction.md` §3).

### 3. Server-side computation

All amounts are computed on the server and returned to the client pre-calculated. The client NEVER computes sums, VAT, or percentages itself.

A new server action or data-fetching function (e.g. `getJobPnL`) returns:
```ts
{
  invoicedNet: number;      // in pence
  costsNet: number;         // in pence
  grossProfit: number;      // in pence
  marginPct: number | null; // null if no invoice
  vatCollected: number;     // in pence
  vatOnCosts: number;       // in pence
  vatPosition: number;      // in pence
  unpaidCosts: number;      // in pence
  hasInvoice: boolean;
}
```

The computation handles:
- **Invoice amounts are in pounds** (`invoices.amount` is `numeric(10, 2)`) — multiply by 100 and round to convert to pence for computation
- **Cost amounts are already in pence** (`job_costs.amount_net` is `int`)
- **Negative costs** (refunds) reduce total costs and increase profit
- **Null VAT amounts** on costs are treated as zero in the sum
- **Multiple invoices** for one job (deposit + balance) — sum all invoices for the job's quote

### 4. Mobile rendering

The entire costs section and P&L panel must render correctly at **390px width** in the WKWebView wrapper. Test at this width before merge.

### 5. VAT treatment defaulting

When creating a cost, the VAT treatment select defaults to:
- `standard` if `contractors.vat_registered = true`
- `zero` if `contractors.vat_registered = false`

The user can override this default in the form.

## Edge cases

1. **Job with costs but no invoice**  
   The P&L panel shows costs and a clear "Not yet invoiced" state in the invoiced row, rather than showing a negative profit. Gross profit and margin rows show "—" or are hidden entirely.

2. **Costs exceeding invoiced value (loss-making job)**  
   Show the loss plainly: "Gross profit: -£240 (-12.0%)" — no euphemism, no hiding. Tradespeople need to see this.

3. **Non-VAT-registered contractor**  
   Hide the entire VAT section rather than showing "VAT collected: £0.00 / VAT on costs: £0.00". If they're not VAT-registered, VAT is not relevant to them.

4. **Job with zero costs**  
   The costs list shows an empty state: "No costs added yet." The P&L panel shows £0.00 costs and profit = invoiced net.

5. **Negative cost (refund from a supplier)**  
   A cost with `amount_net < 0` reduces the total costs and increases profit. The cost list shows it with a minus sign (e.g. "-£50 refund from Screwfix").

6. **Very large cost count (~50+ costs on one job)**  
   The list stays usable without pagination up to ~50 costs. Above that threshold (exact number determined by testing at 390px), consider a "Show more" expansion or virtualization. State the chosen threshold in a code comment.

7. **Unpaid costs callout with mixed paid/unpaid**  
   Only unpaid costs contribute to the "£X still to pay" figure. A job with £500 total costs, £300 paid and £200 unpaid, shows "£200 of costs still to pay".

8. **Multiple invoices for one job (deposit + balance)**  
   Sum all invoices for the job's quote. A quote with a £500 deposit invoice and a £1,500 balance invoice shows "Invoiced (net): £2,000".

9. **Deleting a cost**  
   Use a native confirmation UI (Action Sheet / Alert Dialog), not `window.confirm()` which reveals "This page at file://" in the WKWebView. The confirmation must work correctly in both native app and browser contexts.

10. **Invoices are in pounds, costs are in pence**  
    The computation layer must convert invoice amounts (pounds, `numeric(10, 2)`) to pence before summing with cost amounts (already in pence). A £50.00 invoice is 5000 pence, not 50 pence. Unit tests cover this boundary.

## Risks

- **Money-adjacent feature.** Individual diff review required before merge, regardless of QA verdict. Every computation that touches GBP amounts must be reviewed by a human.

- **Unit conversion boundary (pounds ↔ pence).** Invoices are stored in pounds (`numeric`), costs in pence (`int`). Mixing the two without conversion silently produces nonsense (a £50 invoice reported as 50p). Mitigation: unit tests explicitly cover the conversion, and a code comment at the conversion site warns about the difference.

- **Client-side computation is forbidden but easy to slip in.** A `{costsNet + invoicedNet}` template expression is client-side. All sums must come from the server. Mitigation: acceptance tests assert the server action returns pre-computed totals, and code review checks no arithmetic appears in the component.

- **VAT disclaimer must be agreed with Jacob before merge.** The wording "Estimate only, not tax advice" is provisional. Jacob must sign off the exact copy to avoid any implication that motko is providing tax advice.

- **Native confirmation UI may not exist in the component library.** If the repo has no Capacitor-aware confirmation dialog, the Engineer must build one or use a third-party sheet component. `window.confirm()` is not acceptable because it reveals the WebView origin.

- **Deleting a job with costs still fails (LED-1's RESTRICT FK).** This ticket does not change that behavior, but the costs section makes it more likely a contractor will hit the error. A future ticket may add "archive" instead of hard delete.
