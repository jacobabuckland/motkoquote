# LED-2: Cost entry and job-level P&L view

**REQUIRES MIGRATION** — applies to production before code merge.

## Problem

A contractor needs to track what they spent on a job (materials, subcontractor costs, equipment hire) and see whether the job actually made money. Without this, they can price the next job but cannot tell if the last one was profitable. This is the first user-facing piece of the ledger — every later projection is judged against what the job page says it made.

## Scope

### Database migration

A new `job_costs` table:
- `id` (uuid, primary key)
- `job_id` (uuid, references jobs, on delete cascade)
- `description` (text, not null)
- `amount_pence` (integer, not null) — stored in pence for exact arithmetic
- `category` (text, nullable) — freeform, for later grouping
- `counterparty` (text, nullable) — who was paid
- `incurred_on` (date, not null)
- `vat_treatment` (text, not null, check constraint: 'standard' | 'zero' | 'exempt')
- `paid` (boolean, not null, default false)
- `paid_on` (date, nullable)
- `created_at` (timestamptz, not null, default now())
- RLS policy: contractor-scoped via job → contractor → owner_user_id

### Server actions (src/app/jobs/cost-actions.ts)

Four mutations, all RLS-scoped and server-derived:
- `addJobCost(jobId, { description, amountPence, category, counterparty, incurredOn, vatTreatment })` → { success: boolean, costId?: string, error?: string }
- `updateJobCost(costId, { description, amountPence, category, counterparty, incurredOn, vatTreatment })` → { success: boolean, error?: string }
- `deleteJobCost(costId)` → { success: boolean, error?: string }
- `markCostPaid(costId, paid: boolean)` → { success: boolean, error?: string }

When marking paid, `paid_on` is set to today (London timezone date); when marking unpaid, `paid_on` is cleared.

### UI on the job page (src/app/jobs/[id]/page.tsx)

**Cost entry section**, below the activity timeline:
- Card titled "Costs" (eyebrow style)
- "Add cost" button opens a form (inline, not a modal) with:
  - Description (text, required)
  - Amount (pounds, required) — input in pounds, stored as pence server-side
  - Category (text, optional)
  - Counterparty (text input with type-ahead over existing counterparties from this contractor's past costs, creating on miss, optional)
  - Date (date picker, defaults to today, required)
  - VAT treatment (radio group: Standard rate / Zero rate / Exempt, defaults based on contractor.vat_registered)
- "Save cost" / "Cancel" buttons
- Cost list: each cost shows description, amount (via `<Money>`), counterparty, date, paid status
- Actions per cost: Edit (opens inline form pre-filled), Delete (native confirmation, not window.confirm), "Mark paid" / "Mark unpaid" toggle

**P&L panel**, below costs:
- Card titled "Profit & loss" (eyebrow style)
- Rows (each with label and `<Money>` amount):
  - **Invoiced (net)** — sum of invoices.amount for this job, excluding VAT
  - **Costs (net)** — sum of job_costs.amount_pence / 100, excluding VAT
  - **Gross profit** — invoiced net minus costs net, in the display face
  - **Margin** — (gross profit / invoiced net) × 100, shown as "X%" alongside gross profit
- Separate VAT section (visually distinct, below a divider):
  - **VAT collected** — computed from invoices
  - **VAT on costs** — computed from job_costs where vat_treatment = 'standard'
  - **VAT position** — collected minus spent
  - Disclaimer (agreed with Jacob before merge): "This is an estimate for your information, not tax advice. Consult your accountant for VAT liability."
- If unpaid costs exist, callout above the panel: "£X of costs still to pay" (using `<Money>`)

## Edge cases

1. **Job with costs but no invoice**: P&L panel shows costs and a clear "Not yet invoiced" state for the invoiced row, with gross profit shown as "—" (not a negative number that implies the job lost money before it's even been invoiced).

2. **Costs exceeding invoiced value**: Show the loss plainly. The gross profit is negative, the margin is negative, and both are rendered in the error colour (red) without euphemism. Tradespeople need to see this.

3. **Non-VAT-registered contractor**: Hide the entire VAT section rather than showing zeros. The section does not exist for them.

4. **Very large cost counts**: The list stays usable up to ~50 costs without pagination. Beyond that is out of scope for LED-2 — state the threshold in a comment, but do not implement pagination yet.

5. **Refund (negative cost)**: Accepted and rendered correctly. A negative cost increases gross profit.

6. **Counterparty type-ahead with no past counterparties**: The input works as a plain text field; the type-ahead is an enhancement, not a requirement.

7. **Delete confirmation cancel**: When the delete confirmation is cancelled, nothing happens — the cost remains.

8. **Concurrent edits**: Two tabs editing the same cost is not guarded — last write wins. Out of scope for LED-2.

## Risks

- **Money-adjacent**: Every calculation must be tested against integer pence, not floating-point pounds. The P&L computation is the single source of truth for "did I make money" and must be correct.
- **Migration timing**: The migration must be applied to production **before** the code merge, or the deploy will break when the code tries to read/write job_costs.
- **VAT disclaimer**: The exact wording must be agreed with Jacob before merge. Presenting VAT figures without a clear "not advice" treatment could imply the product is giving tax guidance.
- **RLS**: Every mutation must be contractor-scoped via the jobs table. A missing RLS policy would let one contractor see or edit another's costs.
- **Native confirmation**: Using `window.confirm` would expose the WebView origin to users on the Capacitor build. The confirmation must be a native-styled dialog within the app canvas.

## Out of scope

- Receipt photos (LED-3)
- Cross-job aggregation or "who I owe" (LED-4)
- Voice capture or query (LED-5, LED-6)
- Changes to how quotes or invoices are priced
- Pagination for large cost lists (threshold: ~50)
- Concurrency guards for simultaneous edits
- Bulk cost import
- Cost categories as a fixed enum (they remain freeform for LED-2)

## Derived criteria

1. A cost can be added, edited, deleted, and marked paid from the job page
2. All cost mutations are server actions, RLS-scoped via job → contractor
3. The P&L panel computes gross profit and margin correctly from integer pence
4. The P&L computation is unit-tested against: no costs, unpaid costs only, negative cost (refund), job with no invoice, costs exceeding invoiced value, non-VAT-registered contractor
5. Every monetary figure in the cost list and P&L panel renders via `<Money>` with tabular numerals
6. The VAT section is hidden entirely for non-VAT-registered contractors
7. The VAT disclaimer is explicit and agreed with Jacob before merge
8. Delete confirmation uses a native-styled dialog, not `window.confirm`
9. The panel renders correctly at 390px in the WKWebView wrapper
10. No amount is ever computed client-side — all P&L figures come from the server
