# Spec: Collapse the remaining Settings sections

**Issue:** #359  
**Module:** ui

## Problem

The Settings page is half-converted to collapsible sections. Currently only the "Getting paid" section (Stripe Connect and payout details) is wrapped in a Disclosure component with `defaultOpen={false}`. Everything below it — fees statement, referral, notifications, support, and delete account — renders as a flat run of always-open sections. The page reads as inconsistent rather than as a deliberate hierarchy.

## Scope

Wrap four sections in Disclosure components:

1. **Fees statement** (`FeesStatementSection`)
   - id: `"fees"`
   - title: `"Motko fees"`
   - defaultOpen: `{true}`
   - Must preserve the one-liner guard: `contractor?.id && ...` (see Risks below)

2. **Referral** (`ReferralSection`)
   - id: `"referral"`
   - title: `"Refer a trade"`
   - defaultOpen: `{true}`

3. **Notifications** (`SettingsClient`)
   - id: `"notifications"`
   - title: `"Notifications"`
   - defaultOpen: `{true}`
   - Wraps both the h2 "Notifications" and the h3 "What to notify me about" — they are siblings in the current markup, not nested disclosures. One Disclosure wraps both.

4. **Support** (`SupportSection`)
   - id: `"support"`
   - title: `"Need a hand?"`
   - defaultOpen: `{true}`

All four sections use `defaultOpen={true}` to maintain test compatibility (see Risks below).

## Explicitly out of scope

- Changing the default state of the existing "Getting paid" Disclosure (stays `defaultOpen={false}`)
- Wrapping or collapsing the "Delete account" section — it remains uncollapsed below support, so someone who cannot make something work finds the way to ask before they find the way to delete their account
- Adding attention markers or dynamic titles (e.g. "— action required") to any of the four new sections — none have identifiable actionable states that can be computed at render time without significant refactoring
- Moving sections around or changing their order
- Changing section content, copy, or internal structure
- Modifying the Disclosure primitive itself

## Files

- `src/app/settings/page.tsx` — wrap fees, referral, and support sections
- `src/app/settings/settings-client.tsx` — wrap the entire SettingsClient export (both h2 and h3) in a Disclosure, or modify the component to render its own Disclosure wrapper

The choice between wrapping SettingsClient at the call site vs. inside the component definition is left to the Engineer, with the constraint that the h2 and h3 must both sit inside the single Disclosure body, not as separate nested disclosures.

## Edge cases

### Empty or partial states
- **Fees statement**: already conditionally rendered only when `contractor?.id` exists. The Disclosure wrapping preserves this guard.
- **Referral code null**: section renders a placeholder message. No special handling needed.
- **Notifications not registered**: section shows "Not switched on yet." No special handling needed.
- **Support**: static link, no state.

### Section interaction
- All sections collapse independently (no accordion behavior) — Disclosure primitive already ensures this.
- Deep-link auto-expand: handled by Disclosure primitive (a URL hash pointing inside a collapsed section opens it).
- State persistence: handled by Disclosure primitive (per-section, keyed on id, native + web).

### Reduced motion
- Handled by Disclosure primitive (motion tokens zero out under `prefers-reduced-motion`).

## Risks

### Test 334 will fail on a literal pattern match

`tests/acceptance/334.test.tsx` (frozen, from issue #334) includes this assertion:

```typescript
expect(
  source,
  "FeesStatementSection must only be guarded by contractor?.id, not a billing flag",
).toContain("contractor?.id && <FeesStatementSection");
```

Wrapping FeesStatementSection in a Disclosure breaks this literal match — the source will now read `contractor?.id && <Disclosure` instead of `contractor?.id && <FeesStatementSection`.

**Why this happens:** Test 334 verifies that the fees statement is not gated by billing feature flags (after FEE-3 deleted the flag). It uses a literal string match to prove the only guard is `contractor?.id`. That test is frozen and cannot be edited by the Engineer.

**Why it's not a blocker:** The *intent* of test 334 (ensure fees statement is not gated by billing flags) remains satisfied. Wrapping in Disclosure does not add a billing gate. The section is still present whenever `contractor?.id` is truthy, just collapsible. Test 334's literal pattern match is an implementation detail of how it verifies "no billing flag," not the decision itself.

**Resolution path:** Test 334's literal assertion must be updated to accept `contractor?.id && <Disclosure` as satisfying the "no billing flag" requirement, OR to verify the requirement in a different way (e.g., checking that `FEE_BILLING_ENABLED` does NOT appear, which already passes). This is a necessary update to a frozen test due to a new feature changing the code it depends on. The Engineer will discover this when test 334 fails and should escalate to unblock.

**Alternative:** If updating a frozen test is unacceptable, remove fees statement from the collapse list and leave it as a bare section. This contradicts the brief's "Suggested shape" but preserves test 334.

### Test 306 counts defaultOpen={false}

`tests/acceptance/306.test.tsx` (frozen, from issue #306) counts Disclosures declaring `defaultOpen={false}` and expects exactly 1 (the "Getting paid" section).

**Why this is NOT a risk:** All four new Disclosure sections use `defaultOpen={true}`, so the count of `defaultOpen={false}` stays at 1. Test 306 passes without changes.

### The prettier-ignore comment will need updating

`src/app/settings/page.tsx` line 161 carries a `prettier-ignore` comment specifically for test 334's one-liner requirement. Once fees statement is wrapped in Disclosure, that comment's rationale is obsolete (the one-liner no longer exists in the same form). The comment should be updated or removed.

## Derived criteria

When implementation is complete:

1. Four sections are wrapped in Disclosure: fees statement, referral, notifications, support
2. Each Disclosure has a stable `id` (fees, referral, notifications, support) for state persistence
3. All four use `defaultOpen={true}`
4. The "Getting paid" Disclosure remains unchanged (`defaultOpen={false}`)
5. The "Delete account" section remains unwrapped, below support
6. The `contractor?.id &&` guard on fees statement is preserved (even if the literal pattern changes)
7. No billing flag checks are added to any section
8. The Notifications Disclosure wraps both the h2 and the h3 (one disclosure, not two nested)
9. Page layout and section order remain unchanged except for the Disclosure wrappers
10. Deep-link auto-expand, state persistence, haptics, and motion tokens work for all four new sections (inherited from Disclosure primitive)
11. Tests in `tests/acceptance/359.test.tsx` pass
12. Test 306 still passes (count of `defaultOpen={false}` stays at 1)
13. Test 334 will fail on the literal pattern match and requires resolution per the Risks section above
