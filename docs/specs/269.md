# #269: Add a branded loading state on app launch

## Problem

On app launch the screen displays nothing but a solid green background until the app has loaded, with no indication that anything is happening. On a slow connection this reads as a frozen or broken app. This is the very first thing every user sees on every session, and tradespeople opening the app on site are often on poor cellular connections where the blank period is longest.

## Scope

Add a branded loading screen that displays during app launch, consisting of:
- The motko wordmark (lowercase, always)
- A loading spinner
- A rotating status message that cycles through phrases like "Loading your quotes", "Loading your contracts", "Loading your bills"

The loading screen replaces the blank green screen and disappears as soon as the app is ready to render. Message rotation is cosmetic only and not tied to actual load progress. The rotation interval should be roughly 1.5–2.5 seconds per message.

## Explicitly out of scope

- No changes to what is loaded, load order, or performance optimizations
- No skeleton states on individual pages (covered by separate roadmap items)
- No new animation framework dependencies (use existing motion/design tokens if available, plain CSS otherwise)
- No changes to client-side navigation loading states — this applies only to app launch

## Files

Expected files to be created or modified:
- New component: `src/components/app-loading-screen.tsx` or similar
- Styles: either co-located CSS module or additions to existing global styles
- Next.js loading UI: `src/app/loading.tsx` (Next.js loading convention)
- Potentially Capacitor integration if the loading screen needs to coordinate with the native splash screen
- Config: possibly Capacitor or Next.js config if integration requires it

## Edge cases

**Load failure or timeout:** The loading screen must not spin indefinitely. After a reasonable timeout (suggest 30 seconds), it should surface any existing error/retry mechanism rather than continuing to spin. If no such mechanism exists, note this in implementation and keep timeout behaviour minimal — do not invent a new error UX.

**Instant loads (warm cache):** A brief flash of the loading screen is acceptable. No flash is also acceptable. Do not engineer complex flash-prevention logic.

**Repeat visits mid-session (client-side navigation):** The loading screen applies only to app launch (cold start), not to route changes within the app. Client-side navigation continues to use whatever loading states already exist.

**Message rotation during very fast loads:** If the app loads before the first message interval completes (1.5–2.5s), the loading screen may disappear immediately. The loading screen must not enforce a minimum display time — faster is better.

**iOS WKWebView rendering:** The loading screen must render correctly in the iOS WKWebView wrapper, where the blank green launch state is most visible. This is the primary environment where the improvement will be noticed.

## Risks

- No money, migration, or user data risks identified
- Loading screen must not block or delay app readiness — it should be purely cosmetic and non-blocking
- Ensure the loading screen does not interfere with error states or prevent error messages from surfacing
- Do not add a minimum display time that would delay fast loads
