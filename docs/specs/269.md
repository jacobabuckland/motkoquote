# Issue #269: Add a branded loading state on app launch (replace the blank green screen)

## Problem

On cold launch, the app shows only a solid green background (#004225) with no branding or feedback until the app has fully loaded. On slow connections this blank period reads as a frozen or broken app, which is the very first impression of every session. Tradespeople opening the app on site are often on poor cellular connections where the blank period is longest and most jarring.

## Scope: what changes

A new `AppLoadingScreen` component renders on app launch showing:
- The motko wordmark (lowercase) centered
- A spinner beneath the wordmark
- A rotating status message beneath the spinner cycling through strings like "Loading your quotes", "Loading your contracts", "Loading your bills"
- Messages rotate at a readable interval (1.5–2.5s each) — this is cosmetic rotation, not tied to actual load progress

The loading screen:
- Renders as soon as the app DOM is available (early in the React tree)
- Replaces itself with the actual app content as soon as the app is interactive
- Must not enforce a minimum display time — if loading completes before the first message interval, the app may appear immediately
- Renders correctly in both the web app and the iOS WKWebView wrapper

The component mounts in the root layout and removes itself from the DOM once the app is ready, rather than relying on React conditional rendering that keeps the elements in memory.

## Explicitly out of scope

- No changes to what is loaded, load order, or performance optimization work
- No skeleton states on individual pages (those are separate roadmap items)
- No animation framework additions — use existing CSS/design tokens
- No changes to the native splash screen in `native/www/index.html` or Capacitor's SplashScreen plugin configuration
- No server-side rendering of the loading screen — this is a client component that mounts early

## Files

- `src/components/app-loading-screen.tsx` — new component
- `src/app/layout.tsx` — mount the component in RootLayout
- `src/app/globals.css` — add keyframe animation for message rotation if needed (or inline styles)

## Edge cases

**Instant loads (warm cache):** If the app loads fast enough that the loading screen never appears or only flashes briefly, that is acceptable. Do not engineer around it or add artificial delays.

**Load failure or timeout:** The loading screen must not spin forever. After a reasonable timeout (e.g. 10 seconds), it should surface the existing error/retry path rather than an infinite spinner. If no such path currently exists, state that in implementation and keep the timeout behavior minimal — log to console and remove the loading screen rather than inventing a full error UX.

**Repeat visits mid-session (client-side navigation):** The launch loading screen applies to app launch only, not route changes. Once the app is interactive and the user navigates between pages, the existing per-route loading.tsx files handle those transitions.

**Message rotation timing:** Messages cycle at regular intervals regardless of load state. If loading completes mid-message, the screen should disappear immediately — do not wait for the current message to finish its interval.

**Reduced motion:** The spinner animation should respect `prefers-reduced-motion: reduce` by rendering a static spinner or very subtle animation per the existing globals.css motion handling.

## Risks

- **Accessibility:** The spinner must have `role="status"` and appropriate `aria-live` or `aria-busy` attributes. The rotating messages should not be announced individually by screen readers (use `aria-hidden` on the message text itself), only the existence of a loading state.

- **Timing races:** The component must not interfere with the existing `NativeAppInit` component's SplashScreen.hide() call. The loading screen renders in parallel and removes itself independently based on app-ready state, not based on the native splash being hidden.

- **Flash of content:** If the loading screen mounts after the app is already interactive (e.g. on fast connections), it should not appear at all. Check for readiness before mounting, not just after.

## Derived criteria

1. A new `AppLoadingScreen` component exists and exports a default component
2. The component renders the motko wordmark (lowercase text "motko") centered on screen
3. A spinner renders below the wordmark
4. At least three distinct rotating status messages render below the spinner
5. Messages cycle at intervals between 1.5–2.5 seconds
6. The component mounts in the root layout
7. The component removes itself from the DOM once the app is interactive
8. The component does not enforce a minimum display time
9. The component works in both web and native iOS contexts
10. The spinner respects `prefers-reduced-motion`
11. The loading screen has appropriate ARIA attributes for accessibility
12. If loading takes longer than 10 seconds, the loading screen removes itself or surfaces an error
