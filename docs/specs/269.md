# Issue #269: Add a branded loading state on app launch (replace the blank green screen)

## Problem

On app launch, particularly in the iOS WKWebView wrapper, the screen displays only a solid green background with no indication that the app is loading. On slow connections — common for tradespeople on site — this blank state can persist for several seconds and is indistinguishable from a frozen or crashed app. There is no feedback to the user that work is happening. This is the very first thing users see every time they open the app.

## Scope: what changes

1. **Create `src/app/loading.tsx` as the root loading state.** This file exports a default component that renders while Next.js loads the root layout and initial route.

2. **The loading screen contains:**
   - The motko wordmark (lowercase text "motko" — rendered as text or as an inline SVG if a wordmark asset exists)
   - A spinner positioned below the wordmark
   - A rotating status message beneath the spinner, cycling through messages like "Loading your quotes", "Loading your contracts", "Loading your bills"

3. **Messages rotate at a human-readable interval.** Each message displays for approximately 1.5–2.5 seconds before cycling to the next. The messages are cosmetic — they are NOT tied to actual load progress or sequenced to real loading stages.

4. **At least three distinct messages.** The rotation includes at least three different status strings to avoid the appearance of being stuck.

5. **No artificial delay.** The loading screen is replaced by the app as soon as the app is ready. It must never add delay beyond actual load time. If the app loads before the first interval elapses, the loading screen may disappear immediately — no minimum display duration is enforced.

6. **Styling matches the brand.** The loading screen uses the solid green background that currently displays (`--green` or `#004225`), with the wordmark and text in a contrasting color (likely white or `--ground`) for legibility.

## Explicitly out of scope

- **No changes to what is loaded, load order, or performance.** This item only addresses the visual state shown while loading happens — it does not optimize or change the loading itself.
- **No skeleton states on individual pages.** Route-specific loading skeletons (like those in #145) are separate concerns and already exist for many routes.
- **No animation framework additions.** Use existing motion/design tokens from `globals.css` (e.g. `--ease-spring`, `--dur-base`) or plain CSS. Do not add new animation libraries.
- **No error boundary or retry UI in this component.** Load failure or timeout surfacing is out of scope. If a timeout or error mechanism is needed, state that clearly in the implementation notes rather than building one.

## Files

- `src/app/loading.tsx` — new file exporting the root loading component
- `src/app/globals.css` — may add keyframe animations for the spinner rotation if not already present (check existing styles first)
- `tests/acceptance/269.test.tsx` — acceptance tests covering all criteria and edge cases

## Edge cases

1. **Very fast loads (warm cache, localhost).** If the app loads before the first message interval completes, the loading screen disappears immediately. This is acceptable — no flash prevention is required, and a brief flash is also acceptable.

2. **The loading screen persists only as long as Next.js takes to load the root layout.** Once the layout and initial route are ready, Next.js replaces the loading state with the app content. This component has no control over load timeout or failure — if the app fails to load, the existing error boundaries or browser-level error handling apply.

3. **Repeat visits mid-session (client-side navigation).** This loading screen applies to **app launch only**, not to route changes. Client-side navigation between routes may show route-specific loading states (from each route's `loading.tsx` file), but not this root loading screen.

4. **Accessibility.** The loading screen should include appropriate ARIA attributes: `role="status"` or `aria-live="polite"` on the rotating message container, and the spinner should have `aria-label="Loading"` or similar to communicate loading state to screen readers.

5. **Reduced motion.** Under `prefers-reduced-motion: reduce`, the spinner should render static (no rotation animation) and message transitions should be instant (no fade or slide animations).

## Risks

- **No database migration required.**
- **No user data or money risk.** This is a purely visual change to the loading state.
- **Breaking change risk: none.** Next.js automatically uses `loading.tsx` when present — adding this file does not break existing functionality.
- **Visual regression risk: low.** The loading screen only appears during the initial app load, which currently shows a blank green screen. Any loading screen is an improvement over the blank state.
