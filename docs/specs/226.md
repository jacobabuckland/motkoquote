# Issue #226: Move settleFeeCollection post-claim effects into a single SECURITY DEFINER RPC

**REQUIRES DATABASE MIGRATION** — this spec includes a new Postgres function. The migration must be applied to production via `supabase db push` before merging the code that calls it.

## Problem

`settleFeeCollection` (collect-fees.ts:403-440) performs three separately awaited database writes: marking the collection as collected, flipping the jobs from accrued to collected, and returning the contractor to active billing status. If the process crashes after the first write but before the second or third, the collection is marked collected but the jobs remain stranded at fee_status='accrued'. On webhook redelivery, the `.neq("status", "collected")` guard in the first write matches zero rows and the function returns early, so the remaining writes never execute. The stranded jobs are then re-rolled into the next month's batch under a new period_start, bypassing the (contractor_id, period_start) unique index, and the trade is charged twice for the same work. A sole trader charged twice by their software cancels the mandate rather than filing a bug report.

## Scope: what changes

1. **New Postgres function** (migration): Create a SECURITY DEFINER RPC named `settle_fee_collection` that performs all three post-claim effects in a single transaction:
   - Mark the collection as collected (update fee_collections.status, collected_at, optionally provider_collection_ref)
   - Flip the collection's jobs from accrued to collected (update jobs.fee_status)
   - Set the contractor's billing status to active (update contractors.fee_collection_status)

2. **Update settleFeeCollection** (src/lib/collect-fees.ts): Replace the three separate awaited writes with a single call to the new RPC. The function signature and return behavior remain unchanged.

3. **Invariant check** (src/checks/fee-stranded-jobs.check.test.ts): Add a check that asserts no job at fee_status='accrued' belongs to a collection already in 'collected' status. This is a static code check (not a runtime query), verifying that the code structure prevents the scenario.

4. **Production audit query**: Before the PR is opened, run a query against production counting jobs at fee_status='accrued' whose collection is already collected, and include the count in the PR description. This documents the baseline before the fix.

## Explicitly out of scope: what does not change

- How collections are created, batched, or which jobs are included in each batch
- The fee amount calculation, VAT split, or banding logic
- The dunning flow, retry schedule, or the decision to pause billing
- The claim that precedes these writes (the `.neq("status", "collected")` guard on the collection update — the RPC only handles post-claim effects)
- The TrueLayer charge call, its idempotency key, or mandate authorization flow
- Correction of existing stranded records in production — that is a separate backfill item and must not be attempted as part of this implementation
- Any RLS policies, table structure, or indexes beyond adding the new RPC

## Edge cases

1. **Webhook redelivery on an already-settled collection**: The RPC is called again for a collection already in 'collected' status with all jobs already 'collected'. Result: The RPC completes successfully as a no-op. No row is re-updated (idempotent behavior).

2. **RPC fails partway through the transaction**: Postgres rolls back all three writes automatically. The collection remains in its pre-RPC state (likely 'pending'). The caller treats this as a failed settlement and the existing failure path applies unchanged.

3. **Contractor already at 'active' billing status**: The RPC still commits. Setting an already-set value is not an error.

4. **Collection has zero jobs** (job_ids is an empty array): The jobs update is skipped (no rows to update), but the collection and contractor updates still commit. This is a valid edge case (e.g., a collection created in error or a race condition that removed all jobs before settlement).

5. **Webhook arrives for a non-existent collection**: The RPC is never called because the collection SELECT returns null. Existing behavior unchanged.

6. **Legacy stranded records** (jobs at 'accrued' under a 'collected' collection, created before this fix): The RPC does not repair them. They remain stranded until a separate backfill item runs. The RPC only prevents NEW instances of the bug, not historical ones. Do not attempt inline repair.

7. **Partial application state** (collection collected but jobs still accrued, from a prior crash): This is the exact scenario the RPC prevents going forward. If the RPC is called on such a collection (e.g., manual reconciliation), it should flip the jobs and contractor as needed. However, the `.neq("status", "collected")` guard in the application code will prevent the RPC from being called on an already-collected collection via the normal webhook path, so this case only arises in manual/repair scenarios.

## Risks

- **Money**: Stranded jobs cause double-charging. This fix prevents future instances but does not repair existing ones. The backfill item (out of scope here) must be tracked separately.
- **Database migration**: The RPC must be applied to production before the code that calls it is deployed. If the deployment happens first, the code will attempt to call a non-existent function and fail.
- **Webhook idempotency**: The RPC must be truly idempotent — calling it twice on the same collection must have the same effect as calling it once. The tests verify this.
- **Transaction isolation**: The RPC runs with SECURITY DEFINER, bypassing RLS. Ensure it only performs the three intended writes and does not expose or modify other data.
- **Backward compatibility**: The RPC is additive (no schema changes to existing tables, only a new function). Rolling back is safe: drop the function, revert the code change.

## Derived criteria

From the Notion spec, the implementation must:

1. Create a single Postgres RPC that performs all three post-claim effects (collection to collected, jobs to collected, contractor to active) in one atomic transaction
2. Verify atomicity: a test that forces a failure after the first write asserts that NONE of the three writes took effect (all rolled back)
3. Handle webhook redelivery on an already-collected collection without error and without duplicating effects (idempotent)
4. Handle redelivery on a partially-applied state (collection collected, jobs still accrued) by completing the remaining effects rather than returning early — though the application-level guard prevents this from happening via the webhook path, the RPC itself should be robust to it
5. Add an invariant check (src/checks) that asserts no job at fee_status='accrued' belongs to a collection in 'collected' status
6. Preserve the existing (contractor_id, period_start) unique index unchanged
7. Report a production query count of accrued jobs under collected collections in the PR description
8. Not change how collections are created, batched, fee amounts calculated, VAT split, dunning flow, or the TrueLayer charge call
9. Not attempt to correct existing stranded records as part of this implementation
