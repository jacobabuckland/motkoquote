# FEE-1: Free-job grants — trial 3, referral 3, champion tier of 5 after five activated referrals

**Auditing branch `factory/330` @ `ddaa068`**

## Problem

The free-job allowance is granted in two places and both values are now wrong. New accounts receive 5 free jobs (should be 3), and referrers receive a flat +5 when a referee completes their first paid job (should be +3, rising to +5 once the referrer has five or more activated referrals). There is also no durable record of how many referrals a user has activated — the system tracks only the spendable balance `free_jobs_remaining`, which goes down as credits are spent. A tier cannot be computed from a balance. A separate monotonic counter is required.

The trial length sets the monetisation lag. At ~6 jobs/month, 5 free jobs burns in ~3.5 weeks; 3 burns in ~2 weeks. Compounding growth plus a lag means the billed cohort is always smaller than the active cohort, so shortening the lag moves December revenue more than repricing does. The champion tier converts the referral reward from early-adopter pricing into a PLG reward motion: the reward grows for users who actually drive acquisition.

## Scope: what changes

1. **Add `activated_referral_count` column to `contractors` table** — integer, default 0, never decremented. This is a monotonic counter distinct from the spendable balance.

2. **Change trial grant from 5 to 3** — in `src/lib/referral-signup.ts:119`, change the `delta: 5` signup grant to `delta: 3`.

3. **Implement tiered referral reward** — in `src/lib/paid-job-settlement.ts:130`, replace the flat `delta: 5` with a tier function that reads `activated_referral_count` immediately after incrementing it:
   - Activations 1–4: grant +3
   - Activations 5+: grant +5

4. **Increment `activated_referral_count` before computing the grant** — in `src/lib/settle-paid-job.ts`, when a referral activates (referee's first paid job), increment the referrer's `activated_referral_count` BEFORE calling `planPaidJobSettlement`, so the fifth activation itself pays 5.

5. **Migration** — a new migration that:
   - Adds the `activated_referral_count` column (integer, default 0, not null)
   - Backfills `activated_referral_count` for existing contractors from historical `referrals` where `status = 'activated'`, counting the number of activated referrals where `referrer_contractor_id` matches
   - Does NOT adjust any existing `free_jobs_remaining` balances

## Explicitly out of scope

- Any cap on the banked free-job balance. Unlimited stacking is deliberate — do not add a balance ceiling.
- The per-credit waiver cap (that is FEE-2).
- Any user-facing copy describing the new numbers (that is FEE-3, invisible while `FEE_BILLING_ENABLED` is off).
- Any change to what triggers an activation (still the referee's first settled paid job).
- Any change to fee amounts or bands.
- Retroactive top-up for contractors who cross the threshold — the new tier applies only to future activations.

## Edge cases

- **Fifth activation grants 5, not 3** — increment the counter first, then read the tier. The fifth activation sees count=5 and grants +5.
- **No retroactive top-up** — crossing the threshold does not award additional credits for the first four activations. Forward-only.
- **Self-referral / circular referral** — behaviour unchanged by this ticket. If existing guards prevent it, they continue to apply; if none exist, do not add them here.
- **Legacy accounts granted 5 trial jobs** — grandfathered. No claw-back, no adjustment. The new trial value (3) applies to accounts created after deploy only.
- **Migration cannot determine historical activations** — for contractors where historical data is unavailable, set `activated_referral_count` to 0 rather than guessing. This under-counts a small number of early users; that is acceptable and preferable to inflating the tier.
- **Reversed or refunded referee payment** — if a settlement is reversed after an activation was recorded, the counter does not decrement and the granted credits are not clawed back. The counter is monotonic by design.
- **Concurrent activations for the same referrer** — each must increment the counter exactly once; the tier is evaluated per activation against the post-increment value.
- **Spending free credits down to 0** — does not change `activated_referral_count`. A subsequent activation for a user at count >= 5 still grants 5.
- **Referral grants stack without limit** — a user with 8 activations and no jobs run holds a balance of 3 (trial) + 3+3+3+3+5+5+5+5 = 35.
- **Referral created but never activated** — a referee who never completes a paid job grants nothing and does not increment the counter.

## Risks

**This ticket touches money.** It changes:
- The trial grant amount (5 → 3)
- The referral reward amount (flat 5 → tiered 3/5)
- Adds a new persistent counter that gates the tier

All three are on the escalation list. Review carefully:
- The tier function must read the counter AFTER the increment, or the fifth activation will pay 3 instead of 5
- The counter must increment exactly once per activation, even under concurrent settlements
- The migration backfill must count only `status = 'activated'` referrals, not pending ones
- Existing balances must not be adjusted — only the counter is backfilled

**Migration order matters.** The migration must run before code deploy, or the application will attempt to read a column that does not exist and throw.

**No user-facing surface yet.** `FEE_BILLING_ENABLED` is off and no fee UI has shipped, so changing these constants costs nothing in trust. Once the dashboard chip is live, this becomes a promise to users.

## Derived criteria

I understood the human to be asking for:

1. A new `activated_referral_count` column on `contractors`, integer, default 0, monotonically increasing
2. Trial grant reduced from 5 free jobs to 3
3. Referral reward tiered: +3 for activations 1–4, +5 for activations 5 and beyond
4. The counter increments BEFORE the tier is evaluated, so the fifth activation itself grants 5
5. Migration backfills the counter from historical `referrals` where `status = 'activated'`
6. Existing `free_jobs_remaining` balances are untouched by the migration
7. No retroactive top-up when crossing the threshold
8. The counter never decrements, even if a payment is reversed
9. Spending credits down to 0 does not affect the counter
10. Referral grants stack without limit (a user can bank 35+ free jobs)
