# Issue #244: LED-1: Job costs and counterparties data model (ledger foundation)

**Auditing branch:** `factory/244` @ `dc490a4`  
**Database migration required:** YES — two new tables (`counterparties`, `job_costs`) with RLS. Apply to production BEFORE merging the code.

## Problem

motko knows what was quoted, invoiced and collected, but has no idea what a job COST. This means contractors cannot see whether the work was profitable, and motko cannot tell them what they owe suppliers or subcontractors. The revenue side of the ledger exists; the cost side is missing entirely. This card establishes the data foundation for job costs — the tables and access rules that every later ticket in the LED programme will build on.

## Scope: what changes

### 1. Migration creates two new tables

**`counterparties`** — suppliers, subcontractors, and other payees  
Making these first-class entities (rather than free text on a cost line) enables "you owe Frank £2,000 across four jobs" projections later.

- `id` uuid primary key
- `contractor_id` uuid not null references contractors (id) on delete cascade
- `name` text not null
- `kind` text not null check (kind in ('supplier', 'subcontractor', 'other'))
- `created_at` timestamptz not null default now()

**`job_costs`** — one row per cost incurred against a job

- `id` uuid primary key
- `job_id` uuid not null references jobs (id) on delete restrict
- `contractor_id` uuid not null references contractors (id) on delete cascade
- `counterparty_id` uuid nullable references counterparties (id) on delete set null
- `description` text not null
- `amount_net` int not null (integer pence, never floats)
- `vat_amount` int nullable (integer pence)
- `vat_treatment` text not null default 'unknown' check (vat_treatment in ('standard', 'zero', 'exempt', 'reverse_charge', 'unknown'))
- `category` text not null check (category in ('materials', 'labour', 'subcontractor', 'plant_hire', 'other'))
- `incurred_on` date not null (when the cost happened, may predate job creation)
- `paid` boolean not null default false
- `paid_on` date nullable
- `evidence_url` text nullable (receipt photo, added in LED-3)
- `source` text not null check (source in ('voice', 'photo', 'manual'))
- `created_at` timestamptz not null default now()
- `updated_at` timestamptz not null default now()

Both tables enable RLS from the migration itself, with contractor-scoped read policies. A contractor sees only their own rows; cross-tenant access is impossible.

The `job_costs.job_id` foreign key is **ON DELETE RESTRICT** — deleting a job with cost rows fails rather than orphaning or silently purging the costs. This matches the existing retention/purge design (see migration 00000000000030_retention_fk_restrict.sql).

### 2. Server actions for cost CRUD

Four new server actions in `src/app/jobs/[id]/cost-actions.ts` (or similar):
- **`createJobCost`** — create a cost row, scoped to the owning contractor
- **`updateJobCost`** — update description, amounts, payment status, etc.
- **`markCostPaid`** — convenience action to set `paid = true` and `paid_on = <date>`
- **`getJobCosts`** — read all costs for a job (RLS-scoped)

All operations use the user-scoped Supabase client for reads (RLS enforcement) and the admin client for writes (to touch counterparty rows if needed).

### 3. Counterparty matching logic

When creating a cost, the client supplies a counterparty name (free text). The server:
1. Normalises the name (lowercase, trim whitespace)
2. Searches for an existing counterparty with that normalised name (case/whitespace-insensitive match)
3. If found, uses that `counterparty_id`; if not, creates a new counterparty row
4. Returns the cost row with the resolved `counterparty_id`

This is unit-tested with near-miss cases ("Frank", "frank ", "FRANK" all resolve to the same counterparty).

### 4. Money integrity

All amounts are stored as **integer pence**, never floats — matching the convention established in migration 00000000000023_pricing_referral.sql. A unit test asserts no float arithmetic exists in the cost creation/update path (reject calculations like `amount * 0.20`, require `Math.round(amount * 20 / 100)`).

The server derives every total; no client-supplied totals are trusted (same pattern as `deriveInvoiceAmount`).

### 5. Sign convention for amounts

**Positive amounts = money OUT (costs)**. A refund from a merchant is entered as a negative `amount_net` (e.g., `-500` for a £5 refund). All projections (job P&L, counterparty balances) must handle negative amounts correctly — a negative cost reduces what you owe or increases job profit.

## Explicitly out of scope: what does not change

- **No UI** — this ticket is data-only. LED-2 adds the cost entry form, LED-3 adds receipt capture, LED-4/5/6 add projections (job P&L, counterparty balances, period reports).
- **No voice integration** — the `source = 'voice'` enum value is reserved for LED-2, not implemented here.
- **No receipt capture or OCR** — `evidence_url` is nullable and unused in this ticket. LED-3 adds photo upload.
- **No counterparty management UI** — no screen to browse, edit, or merge counterparties. Matching is implicit (create-on-miss) only.
- **No accounting package integration** — LED-7 or later.
- **No changes to quote/invoice/fee logic** — the revenue side is untouched.

## Edge cases

1. **A cost with no counterparty** (fuel, parking, consumables bought anonymously)  
   `counterparty_id` is nullable. All read/update paths handle `null` gracefully — a cost without a counterparty still appears in the job's cost list and contributes to job P&L, just not to any "you owe X" counterparty projection.

2. **A cost incurred before the job existed** (materials bought speculatively, then assigned to a job later)  
   `incurred_on` may predate `jobs.created_at`. There is NO validation that rejects this — speculative purchases are real.

3. **Negative amounts** (a refund from a merchant, a credit note from a supplier)  
   Negative `amount_net` is allowed. The sign convention: positive = money OUT (cost), negative = money IN (refund/credit). Projections must handle this correctly:
   - Job P&L: `profit = revenue - sum(amount_net)`. A negative cost increases profit.
   - Counterparty balance: `owed = sum(amount_net WHERE paid = false)`. A negative unpaid cost reduces what you owe.

4. **Existing jobs have zero cost rows**  
   Every projection (job P&L, counterparty lists, period reports) must render correctly with an empty cost set. A job with no costs shows £0 total cost and profit = revenue.

5. **Deleting a job with cost rows**  
   The foreign key is `ON DELETE RESTRICT`, so `DELETE FROM jobs WHERE id = <job-with-costs>` FAILS. The application must either:
   - Prevent job deletion if costs exist (error: "Remove all costs before archiving this job"), OR
   - Cascade-delete costs when a job is deleted (requires changing the FK to `ON DELETE CASCADE`)
   
   **Recommendation:** RESTRICT (as specified), with a future archive/soft-delete path that moves the job to a "closed" state without hard deletion. This matches the retention design (invoices, contracts also use RESTRICT). The Engineer must test that a job with costs cannot be deleted, and that the error is surfaced.

6. **Deleting a counterparty with cost rows**  
   The foreign key is `ON DELETE SET NULL`, so deleting a counterparty orphans its costs (they stay in the job, `counterparty_id` becomes null). This is intentional — you may want to remove a counterparty (merge duplicates, clean up typos) without losing the cost history.

7. **Cross-tenant access**  
   A contractor MUST NOT be able to read, create, or update costs on another contractor's jobs. RLS policies enforce this. The acceptance tests explicitly assert that a cost created by contractor A is invisible to contractor B, even if contractor B knows the cost's ID.

8. **VAT treatment edge cases**  
   - `vat_treatment = 'unknown'` is the default — a cost can be entered without knowing the VAT status.
   - `vat_treatment = 'reverse_charge'` exists because CIS reverse charge is real for subcontractor costs in UK construction. The migration creates the enum, but no logic enforces it yet — that's a future ticket.
   - `vat_amount` may be null even if `vat_treatment = 'standard'` (user didn't capture it). Projections must handle nulls.

## Risks

- **Migration must be applied to production BEFORE code merges.** If the code deploys first, every cost action will fail with "table does not exist". Mitigation: CLAUDE.md documents this pattern; verify `supabase migration list` shows prod in sync, AND manually insert/delete a row to confirm the DDL actually landed (the ledger can lie — see the events-table drift incident).

- **Money stored as integer pence must be consistent.** Mixing pence (int) and pounds (numeric) causes silent errors (a £5 cost stored as `5` pence instead of `500` pence). Mitigation: unit tests assert all amounts are in pence, and a comment in the migration warns about the convention. The existing codebase uses both conventions in different tables (old tables: pounds, new tables: pence) — be explicit at every boundary.

- **RLS policy must scope to contractor, not to user.** The pattern is `contractor_id IN (SELECT id FROM contractors WHERE owner_user_id = auth.uid())`, not `contractor_id = auth.uid()`. The latter is a type error (uuid vs uuid) and fails silently in some clients. Mitigation: copy the RLS pattern from migration 00000000000023_pricing_referral.sql verbatim.

- **Counterparty matching can create duplicates if normalisation is inconsistent.** "Frank Smith" vs "Frank  Smith" (double space) vs "frank smith" must all resolve to ONE counterparty. Mitigation: the matching logic trims and lowercases; a unit test covers this. Future: a merge tool (LED-8 or later) can clean up any duplicates that slip through.

- **Deleting a job with costs is a footgun.** If the Engineer forgets to test the RESTRICT behavior, the first contractor who tries to archive a job with costs hits a raw Postgres error instead of a friendly message. Mitigation: the acceptance test explicitly asserts the deletion fails, and the Engineer must surface a user-facing error.
