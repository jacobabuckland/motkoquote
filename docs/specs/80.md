# Issue 80: Gate the pricing slot on pricing.mode being explicitly set

## Problem

The pricing/duration slot (line 725 in `src/lib/schemas/sow.ts`) is currently satisfied if either `pricing != null` OR `duration_days != null`. An incidental duration mention — "it'll be about four days" — fills `duration_days` and drops the slot from both natural follow-up questions and the `concludeOrAskRequired` safety net. `resolvePricingMode` then silently defaults to `"calculated"` when `pricing === null`, meaning the user never chose a pricing mode and is never told one was chosen for them.

This violates CLAUDE.md's invariant: "Voice sessions must ask, not infer, required pricing slots."

## Scope: what changes

1. **Slot-filling logic** (`getUnansweredChecklistQuestions` in `src/lib/schemas/sow.ts:725`):
   - Gate the duration slot on `pricing.mode` being explicitly set
   - A duration mention alone (`duration_days` set but `pricing === null`) must NOT satisfy the slot

2. **resolvePricingMode signature** (`src/lib/schemas/sow.ts:91-93`):
   - Change return type from `PricingMode` to `PricingMode | null`
   - Return `sow.pricing?.mode ?? null` instead of defaulting to `"calculated"`
   - When `pricing === null`, this function now returns `null` (unset state), not a fallback

3. **applyPricingMode** (`src/lib/pricing-mode.ts:57-68`):
   - Handle the case where `resolvePricingMode` returns `null` for legacy jobs
   - When `mode === null` (pricing was never set), produce the calculated breakdown with a comment explaining this is a legacy fallback
   - This ensures existing jobs with `pricing: null` continue to render exactly as they do today

## Explicitly out of scope

- No change to how `pricing.mode` gets set (voice intake, manual editor, etc.)
- No UI changes
- No database migration
- No change to the pricing schema itself
- No change to how duration_days is captured

## Files

Expected to be modified:

1. `src/lib/schemas/sow.ts` (slot-filling logic at line 725, resolvePricingMode signature at lines 91-93)
2. `src/lib/pricing-mode.ts` (applyPricingMode handling null mode)
3. `src/app/jobs/actions.ts` (two call sites at lines 625 and 997 that need to handle nullable return)
4. `src/lib/schemas/sow.test.ts` (update existing test at line 538 that expects "calculated" default)
5. `src/lib/pricing-mode.test.ts` (update existing test at line 146 that expects "calculated" default, add new test for null mode)

## Edge cases

1. **Incidental duration mention without pricing statement**: Duration is captured in `duration_days`, but the slot remains unsatisfied because `pricing.mode` is unset. The assistant asks for pricing mode.

2. **Explicit pricing mode without duration**: If the user says "I want a fixed price" (setting `pricing.mode = "fixed"`), the slot is satisfied even without `duration_days`.

3. **Legacy jobs with `pricing: null`**: When `applyPricingMode` is called on an old job where pricing was never set, it receives `null` from `resolvePricingMode` and produces the calculated breakdown (exactly as today), with a comment in the code explaining this is the legacy path.

4. **Deflection ("you work it out")**: Must explicitly set `pricing.mode = "calculated"`, not leave `pricing` as `null`. This is a voice intake behavior; the spec assumes this already works correctly.

## Risks

### Money

- **Legacy job pricing**: Existing jobs with `pricing: null` must render at the same price after this change. The mitigation is explicit: `applyPricingMode` treats `null` mode the same as `"calculated"` — it produces the calculated breakdown, which is what `resolvePricingMode` was already returning for these jobs (via the `?? "calculated"` default).
  
- **Type safety**: Changing `resolvePricingMode` return type to nullable requires auditing all call sites. Any code that assumed `resolvePricingMode` always returns a valid mode must now handle `null`.

### User data

- No migration required: this change only affects how new conversations flow and how existing data is interpreted, not the data itself.

### Other

- **Call flow**: New calls with incidental duration mentions will now re-ask for pricing mode. This is the intended behavior (per CLAUDE.md), not a regression.

## Derived criteria

I understand the human to be asking for:

1. A duration mention alone (setting `duration_days`) must not satisfy the pricing/duration slot
2. The slot is only satisfied when `pricing.mode` is explicitly set to one of `"days"`, `"fixed"`, or `"calculated"`
3. `resolvePricingMode` should return `null` when `pricing === null`, not default to `"calculated"`
4. Existing jobs with `pricing: null` must continue to render the calculated breakdown (no price changes)
5. The change applies only to the slot-filling gate — it doesn't change how `pricing.mode` gets set in the first place
6. Test coverage for: incidental duration mention with no pricing statement (slot stays unsatisfied), and `applyPricingMode` handling `null` mode for legacy jobs
