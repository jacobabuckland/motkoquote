# REFUND-1: Full and partial refund on a settled job

## Problem

Currently there is no refund path in the product. With Pay by Bank becoming the default payment method and having no dispute mechanism, once a payment is settled it's irreversible inside motko — no chargeback, no refund. Stripe supports Pay by Bank refunds (full and partial) for up to 730 days, so this is a build limitation, not a platform constraint.

## Scope: what changes

Add refund capability for settled jobs that processes refunds through Stripe:
- Check eligibility: job must be settled via Stripe, not manually marked paid
- Process full or partial refunds through the Stripe API
- Show balance consequences before confirmation (money leaves trade's account, may go negative)
- Mark jobs with distinct refund state (settled → refunded or partially_refunded)
- Track refund history to enforce total-refunded-never-exceeds-settlement
- Idempotent: repeated refund of same amount does not move money twice

## Explicitly out of scope

- Staged jobs (deposit + final invoice) — handled by REFUND-2
- Policy limits on who may refund or time windows
- settlement-reversal.ts cleanup — CLEAN-5
- tests/setup.ts — not to be touched by this item

## Files

- src/lib/refund-settlement.ts (new) — core refund logic: eligibility check, Stripe API call, state update
- src/app/jobs/[id]/refund-actions.ts (new) — server actions for refund operations
- src/app/jobs/[id]/refund-button.tsx (new) — UI component with confirmation dialog
- src/app/jobs/[id]/page.tsx (modify) — integrate refund UI into job detail page

## Edge cases

**Connected account is empty** — Common case: trade has been paid out. Refund proceeds and account goes negative. The pre-confirmation warning makes this acceptable rather than a surprise.

**Multiple partial refunds** — Total refunded is tracked and never exceeds the original settlement. Each partial refund reduces the remaining refundable amount.

**Customer's bank rejects return** — Reported to the trade via error message, not swallowed. The job state reflects the attempt; manual resolution required.

**Manually-marked-paid job** — Has no Stripe payment_provider_ref to refund against. Eligibility check returns ineligible with clear reason: "No settlement to reverse (manual payment)".

**Already fully refunded** — Eligibility check returns ineligible: "Job already fully refunded".

**Idempotency** — Same refund request (job + amount) within a short window uses Stripe's idempotency keys. Repeated submission does not double-charge.

**Job never settled** — Eligibility check returns ineligible: "Job not settled".

## Risks

- **Money movement** — refunds debit the trade's Stripe connected account, potentially leaving it negative. The pre-confirmation warning is critical.
- **Stripe API failure** — must be surfaced to the trade, not buried. Partial state (fee reversed but Stripe call failed) must be impossible.
- **Audit trail** — refund history must be queryable for support and accounting.

## Derived criteria

What the acceptance tests verify:

1. **Eligibility for settled Stripe job** — a job with settlement_state='settled' and payment_provider_ref set returns eligible with correct maxRefundablePennies
2. **Not eligible for manual payment** — a job marked paid manually (no payment_provider_ref) returns ineligible
3. **Not eligible for unsettled job** — a job with no settlement returns ineligible
4. **Full refund processes** — refunding the full settlement amount calls Stripe refunds.create with correct payment_intent, updates job settlement_state to 'refunded'
5. **Partial refund processes** — refunding part of the settlement updates state to 'partially_refunded', reduces maxRefundablePennies
6. **Multiple partials up to total** — two partial refunds together equaling the settlement succeed; a third attempting to exceed it fails
7. **Idempotent** — calling refund twice with the same parameters does not double-process (uses Stripe idempotency)
8. **Integration flow** — end-to-end: check eligibility → confirm → process refund → verify state updated

All mocks (Supabase, Stripe) are built inside the test file, not in tests/setup.ts.
