# Issue #188: [BACKFILL] Recover fees lost to concurrent over-waiving of free jobs

**Migration required:** No

**IMPORTANT:** This item creates real charges. It requires a dry-run report approved per contractor before any collection is created.

## Problem

When two jobs settled concurrently against a single remaining free credit, both were waived and both consumed the credit. The second job should have accrued a fee but did not. This occurred because both settlement operations read the same `free_jobs_remaining` value (1) before either wrote their decrement, so both saw themselves as eligible for the free allowance. Both jobs landed with `fee_status = 'not_applicable'` and `fee_waived_reason = 'free_allowance'`, and both wrote a `job_consumed` credit event with `delta = -1`. The contractor's balance correctly shows -1 (both decrements applied atomically via `increment_free_jobs_remaining`), but one of the waivers was invalid.

Unlike other reconciliation problems, the ledger and cache are internally consistent here — the over-waive is only detectable by reconstructing the settlement sequence from event timestamps and identifying jobs that were waived when the running balance was already zero or negative.

## Scope: what changes

1. **Detection logic** (pure function, I/O-free): accepts a contractor's `credit_events` ordered by `created_at`, replays the timeline to compute the running balance at each event, and identifies `job_consumed` events that fired when the balance was already ≤0. Returns a list of over-waived jobs with their settlement timestamp and the fee that should have applied.

2. **Dry-run mode** (default): runs detection for all contractors (or a filtered subset) and writes a report to stdout listing each affected contractor, each over-waived job, its settlement timestamp, the reconstructed balance at that moment, and the fee amount to recover. Does not write to the database.

3. **Correction mode** (requires explicit flag): accepts a single contractor ID as input, re-runs detection for that contractor only, and for each over-waived job:
   - Changes `jobs.fee_status` from `not_applicable` to `accrued`
   - Sets `jobs.fee_amount_pennies`, `fee_net_pennies`, `fee_vat_pennies` to the fee that should have applied (band decided on the job's `job_value_pennies`)
   - Clears `jobs.fee_waived_reason` to `null`
   - Creates a new `fee_collection` row with `period_start = period_end = <date of correction>`, status `pending`, containing only the recovered jobs for this contractor
   - Deletes the invalid `job_consumed` credit event (the one that fired when balance was ≤0)
   - Calls `increment_free_jobs_remaining` with `delta = +1` to return the credit to the contractor's balance

4. **Dry-run report**: the report generated by dry-run mode is committed to the PR (e.g. `docs/backfill-188-report.txt`) before any correction executes. The report includes:
   - Earliest reliable event timestamp (events before this date are excluded from detection)
   - Per contractor: contractor ID, current balance, list of over-waived jobs (job ID, settlement timestamp, reconstructed balance at that moment, fee to recover)
   - Total contractors affected, total jobs affected, total fees to recover

5. **Idempotency**: re-running correction for a contractor whose over-waived jobs have already been corrected reports zero affected rows. A corrected job has `fee_status = 'accrued'` and no corresponding `job_consumed` event in the invalid window, so detection skips it.

## Explicitly out of scope: what does not change

- **Do not modify the settlement logic** (`settle-paid-job.ts`, `paid-job-settlement.ts`). The race that created these records should already be fixed by the atomic `increment_free_jobs_remaining` RPC. This item only corrects legacy data.
- **Do not charge the created collections**. The correction writes `fee_collection` rows with status `pending`; the existing monthly collection cron will attempt to charge them on its next run. Do not add charge logic to this backfill.
- **Do not notify contractors**. The correction is silent. The contractor will see the charge when the collection is attempted (via the existing dunning/statement flow).
- **Do not correct cache/ledger drift**. Drift between `free_jobs_remaining` and the ledger sum is `reconcile-free-jobs`'s job. This item only corrects fee accrual for over-waived jobs.
- **Do not process multiple contractors in one invocation**. Correction mode accepts exactly one contractor ID and errors if none or multiple are passed. Bulk correction is a loop over single-contractor runs.

## Files

- `src/lib/detect-over-waived-jobs.ts` — pure detection logic (exported function, no I/O)
- `src/lib/detect-over-waived-jobs.test.ts` — unit tests for the detection logic
- `scripts/backfill/recover-over-waived-fees.ts` — Node script that runs detection (dry-run or correction mode) against the Supabase database
- `tests/acceptance/188.test.ts` — acceptance tests covering detection, dry-run, correction, idempotency, and edge cases
- `docs/backfill-188-report.txt` — the dry-run report (committed before any correction executes)

## Edge cases

1. **Two settlements with identical `created_at` timestamps**: the sequence cannot be reconstructed reliably. The detection logic flags the pair in the report with a warning ("ambiguous order: timestamps identical") and excludes both jobs from automatic correction. A human must investigate and correct manually if needed.

2. **Event history is incomplete** (events table predates the first `credit_events` rows, or early rows are missing): detection computes the earliest reliable timestamp as the minimum `created_at` across all `credit_events` rows, and only considers events after that point. The report states this earliest date prominently and notes that periods before it cannot be checked.

3. **Detection finds no candidates**: the report shows zero contractors affected, zero jobs affected, total recovery £0.00. This is a valid outcome (the race may never have fired in production).

4. **Contractor has since cancelled their fee mandate** (`fee_mandate_status = 'revoked'` or `fee_collection_status = 'paused'`): the job is still corrected (fee accrued, credit returned), and the collection is created with status `pending`. The next collection run will attempt to charge it, fail (no valid mandate), and move the contractor to `past_due` → dunning → `paused` as usual. The correction does not skip these contractors; it includes them and flags their mandate status in the report.

5. **Correcting the credit takes the contractor's current `free_jobs_remaining` above what they should hold** (because they've since consumed credits that were only available due to the over-waive): the credit is returned (`+1`) and the balance stands at the higher value. Do not attempt to net this across later activity — the ledger is append-only and the later consumption was legitimate given the state at that moment.

6. **The job's `job_value_pennies` is `null`** (settlement predates the pricing rollout): skip the job (cannot compute the fee band without a value). Flag it in the report as "skipped: no job value recorded".

7. **Re-running correction for the same contractor**: detection finds zero over-waived jobs (they've all been corrected: `fee_status = 'accrued'`, no invalid `job_consumed` event). The script reports zero rows affected and exits cleanly.

8. **Multiple over-waives for the same contractor** (balance went to -1, then -2, then -3 before any credits were granted): each invalid waive is detected and corrected independently. The contractor receives `+1` credit per corrected job, and their balance may end up positive if they've since consumed credits.

## Failure modes and empty states

- **No `credit_events` exist for a contractor**: their running balance is 0 throughout (no events = no deltas). Any `job_consumed` event would be invalid (balance was 0, not > 0). This is correct behaviour: a contractor with no signup grant and a waived job is an over-waive.

- **Detection query times out** (too many contractors or events): the script processes contractors in batches (configurable batch size, default 100). Progress is logged per batch so a timeout can be diagnosed and the batch size reduced.

- **Correction partially fails** (one update succeeds, another throws): each contractor's correction runs in a Supabase transaction (via `.rpc('begin')` / `commit` or the service client's implicit transaction if available). If any step fails, the whole contractor's correction rolls back and the script logs the error and continues to the next contractor.

- **Dry-run report is too large to commit** (hundreds of affected contractors): the report is written in a compact tabular format (one line per affected job, grouped by contractor). If it exceeds a reasonable size (e.g. 10,000 lines), the script truncates it and notes "report truncated at 10,000 jobs; full report available at <path>". The full report is still written to disk for manual review.

## Risks

- **Creates real charges**: each corrected job moves from `not_applicable` to `accrued`, and a `fee_collection` is created. The next monthly collection cron will attempt to charge these. Approval of the dry-run report per contractor is mandatory before running correction mode.

- **Retroactive money correction**: trades will see a charge for a job previously marked free. This is policy (retroactively correct money records), but it's user-visible and may generate support queries. The correction is silent; the contractor only learns of it when the collection is attempted.

- **Idempotency depends on fee_status**: if a corrected job's `fee_status` is manually changed back to `not_applicable`, re-running correction will detect it again (it will still have no valid `job_consumed` event in the reconstructed timeline). This is unlikely but would cause a duplicate collection. Mitigation: the correction writes `fee_status = 'accrued'` and never `'not_applicable'`, so a manual revert is obvious in the audit log.

- **Deletes credit_events rows**: the invalid `job_consumed` event is deleted (not nullified or marked invalid). This is safe because the ledger is reconstructed from `created_at` order in detection, and the corrected state (no event, credit returned via a new inverse event or RPC) is the truth. But it means the original over-waive is not visible in the ledger history after correction — it's as if it never happened. This is acceptable (the correction IS the fix), but worth noting.

- **No dependency gate**: the issue body states "depends on the free-job band decision RPC item" and "do not run while the race that creates these records is still live". These are deployment constraints, not enforced by the code. The script must be run only after the settlement race is fixed and the band decision RPC is deployed, or it will immediately re-introduce the same over-waives.

## Derived criteria

What I understood the human to be asking for:

1. A pure detection function that accepts a contractor's `credit_events` (ordered by `created_at`), reconstructs the running balance over time, and identifies `job_consumed` events that fired when the balance was ≤0 (invalid waives).

2. The detection method and its assumptions are documented in the PR, including what happens when timestamps are identical (flag as ambiguous, exclude from auto-correction).

3. A dry-run mode (default) that runs detection for all contractors, computes the fee to recover for each over-waived job (band decision on `job_value_pennies`), and writes a report listing: contractor ID, over-waived job IDs, settlement timestamps, reconstructed balance at each event, fee amounts.

4. The dry-run report is committed to the PR as a file, and no write executes without an explicit flag naming a single contractor.

5. Correction mode accepts one contractor ID, re-runs detection, and for each over-waived job: changes `fee_status` from `not_applicable` to `accrued`, sets the fee amount fields, clears `fee_waived_reason`, deletes the invalid `job_consumed` event, returns the credit to the contractor's balance, and creates a one-off `fee_collection` with `period_start = period_end = <correction date>`.

6. The one-off collection has its own distinct period (not added to a monthly batch), contains only the recovered jobs for this contractor, and has status `pending` (the existing collection cron will charge it).

7. Re-running correction for a contractor reports zero affected rows (idempotent: corrected jobs have `fee_status = 'accrued'` and no invalid event, so detection skips them).

8. Edge case (identical timestamps): flag the pair, exclude from auto-correction, state this limitation in the report.

9. Edge case (incomplete event history): compute the earliest reliable timestamp (min `created_at` of all events), exclude anything before it, state this date in the report.

10. Edge case (no candidates): report zero contractors, zero jobs, £0.00 total recovery. Valid outcome.

11. Edge case (cancelled mandate): include in the report, flag the mandate status, create the collection anyway (it will enter dunning when charged).

12. Edge case (credit return creates over-balance): return the credit, let the balance stand higher than it "should" be. Do not net across later activity.

13. The detection logic handles contractors with no `credit_events` (balance is 0 throughout), contractors with multiple over-waives (each corrected independently), and jobs with no `job_value_pennies` (skipped, flagged in report).
