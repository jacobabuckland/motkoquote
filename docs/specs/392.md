# Issue #392: Run the acceptance test before freezing it, and check it fails for the right reason

## Problem

**The card's premise is wrong, and the correction is the whole of this item.** It is titled "the PM freezes acceptance tests it has never run". The PM does run them. `.github/workflows/factory-pm.yml` has carried a step called "Acceptance tests must fail before implementation" since before any of the recorded incidents, and it runs `npx vitest run "$TESTS"` on the exact file it is about to freeze.

What that step does with the result is the defect:

```bash
if npx vitest run "$TESTS" > /tmp/acceptance.log 2>&1; then
  # ... tests passed against an unmodified tree: block
fi
echo "Acceptance tests fail before implementation, as required."
```

It branches on the **exit code alone**. Zero means "passed, so the contract is worthless" and is correctly blocked (this is the #315 guard). Every non-zero outcome falls through to *"as required"* — including a file that could not be loaded at all.

That is exactly what #352's re-derive was. `await import("@/../../tests/regression/signup-referral-field.test")` does not resolve, vitest exits non-zero, and this step said the tests fail before implementation as required and waved it through. The gate did not miss the run; it misread it.

Measured on this tree, the two outcomes are mechanically distinguishable and the summary says so plainly. A test that fails:

```
 Test Files  1 failed (1)
      Tests  1 failed (1)
```

A file that could not be loaded:

```
 Test Files  1 failed (1)
      Tests  no tests
```

At suite scale that second shape is what the card recorded on #352: `1 failed | 202 passed` test **files** with **zero** failing tests, 2,632 assertions passing and not one of them in the file just frozen.

### Why it is the most expensive defect the pipeline has

A frozen acceptance test cannot be repaired downstream — that is the point of freezing it. So a test that cannot run does not cost a retry. It costs the item, plus an Engineer run, plus a QA run, plus a human round-trip to diagnose, then a full re-derive. #352 burned two complete cycles and went to a third.

## Scope: what changes

A new script, `scripts/factory/check-acceptance-run.sh`, taking the spec and a vitest log and emitting a verdict. Pure — two file paths in, a verdict out, no network, no vitest invocation of its own — so the classification rules are exercised by fixture logs in tests rather than only in anger. This mirrors `check-deliverable.sh` deliberately: it is the same kind of check at the same moment, and it should be readable by the same person.

The existing step keeps running vitest and keeps its pass-means-block branch. It gains one thing: on a non-zero exit it pipes the log through the new script instead of declaring success.

### The classification

**Block — `::no-tests-executed::`.** The log's `Tests` summary reads `no tests`, or reports zero tests for a run that named one file. The file could not be loaded, so nothing in it was ever checked.

Except where the unresolved specifier is a file this spec declares it is creating. This is the distinction the card flagged as needing care rather than guessing, and it is real: an acceptance test for a brand-new component top-level-imports that component, so before implementation it produces the identical `no tests` shape. The two are told apart by **what** failed to resolve, never by the shape of the failure:

- Read the unresolved specifier out of the log's `Cannot find package` / `Cannot find module` / `Failed to load` line.
- Read the spec's `## Files` section and collect every entry marked `(new)`.
- If the specifier maps to one of those paths, this is the expected pre-implementation state. Pass.
- Otherwise, block. A specifier under `tests/` can never be a spec-declared new source file, so #352's case is caught unconditionally.

**Block — `::tests-all-passed::`.** Retained behaviour, moved into the script so all three verdicts live in one readable place and are covered by the same fixtures. The existing step's message and decision block are preserved verbatim; this item does not reword a working guard.

**Pass — assertion failures.** A test that ran and failed an assertion is the expected state for an item that modifies existing behaviour, and there is no mechanical way to tell a correct one from #352's first derive (referral codes the normaliser rejects) or #356 (asserting copy that a sibling item removes). Both of those are semantic errors in a runnable test. **This gate does not catch them and must not pretend to** — a check that claims more than it does is worse than a narrow one, because the next reader trusts it.

## Explicitly out of scope: what does not change

- **The three specific contracts from the card.** #352 has been re-derived, #356 needs its assertion dropped; both are their own items.
- **Catching semantically wrong tests that run.** Stated above and stated again because it is the tempting scope creep here. #352's first derive and #356 would both pass this gate. They are QA's and the human's to catch.
- **The pass-means-block branch's wording, message, or decision options.** It works. It is relocated, not rewritten.
- **Any other step in `factory-pm.yml`.**
- **`tests/regression/` and `tests/integration/`.** Neither is frozen, so neither carries the cost this exists for.
- **Running the whole suite.** The existing step already refuses an empty `TESTS` path with a comment explaining that an empty value once ran everything, saw it pass, and blocked the item for "acceptance tests pass before implementation". That guard stays exactly as it is.

## Edge cases

- **A spec with no `## Files` section, or none marked `(new)`.** Then no unresolved specifier can be expected, and any `no tests` outcome blocks. Correct: an item creating no new files has nothing whose absence is expected.
- **An item that is `AMBIGUOUS:` and froze no acceptance tests.** The step does not run, guarded by the same resolved-path output its neighbours use.
- **A vitest log the script cannot parse.** Block, naming what it could not read. A classifier that cannot classify must not return "fine" — that is the failure being fixed here, one level up.
- **Multiple unresolved specifiers.** All are extracted; the run passes only if **every** one maps to a spec-declared new file. One stray `tests/` import among three legitimate ones still blocks.
- **A specifier written with the `@/` alias.** Resolved against the alias in `vitest.config.ts` (`@` → `./src`) before comparison, so `@/app/foo/page` matches a Files entry of `src/app/foo/page.tsx`. Extension differences are tolerated; a path outside `src/` after resolution never matches.
- **A file that loads but registers zero tests** — an empty `describe`, or every test `.skip`ped. Blocks under `::no-tests-executed::`, and correctly: a frozen file that checks nothing is the same defect with a different cause.
- **The log contains a `Cannot find module` from application code under test, not from the test file.** Both block. Before implementation, an acceptance test whose subject is missing is the expected state only for a spec-declared new file; anything else means the test reaches for something nobody is building.

## Risks

- **A correct pre-implementation run is misclassified and blocks the item.** The mitigation is the `(new)` Files check, and the failure mode is one PM re-run with a message naming the specifier — not a lost cycle. The reverse error, which is current behaviour, costs the item.
- **The spec's `## Files` section becomes load-bearing.** It is, now, and that is a real coupling: a spec that omits a new file from its Files list will see its acceptance test blocked. This is defensible — the Files section is already the contract for what gets built, and `#365` records the cost of omitting something from it — but it should be stated in `AGENTS.md` so a PM knows the list is read by a gate rather than only by a human.
- **No money, auth, migration or customer-facing surface is touched.** Factory tooling only.

## Derived criteria

- `scripts/factory/check-acceptance-run.sh` exists and is executable
- Given a log whose `Tests` summary reads `no tests` and whose unresolved specifier is under `tests/`, it exits non-zero and its output contains `::no-tests-executed::`
- Given the exact #352 specifier `@/../../tests/regression/signup-referral-field.test`, it exits non-zero
- Given a log whose `Tests` summary reads `no tests` and whose unresolved specifier resolves to a path the spec's `## Files` section marks `(new)`, it exits zero
- Given a log reporting one or more failed tests and no load failure, it exits zero
- Given a log reporting that all tests passed, it exits non-zero and its output contains `::tests-all-passed::`
- Given a log with two unresolved specifiers, one spec-declared and one under `tests/`, it exits non-zero
- Given a spec with no `## Files` section and a `no tests` log, it exits non-zero
- Given an unparseable log, it exits non-zero with a message naming what could not be read
- A specifier using the `@/` alias is resolved against `src/` before being compared to the Files list
- `.github/workflows/factory-pm.yml` pipes the vitest log through the script on the non-zero branch, and no longer prints "as required" unconditionally
- The existing pass-means-block behaviour still blocks, with its message and decision options unchanged
- The existing empty-`TESTS` guard is still present and still exits non-zero
- `scripts/factory/check-deliverable.sh` is unmodified
