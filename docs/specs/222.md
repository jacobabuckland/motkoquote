# Issue #222: Add partial unique index on credit_events for referral_unlock

**THIS ITEM REQUIRES A DATABASE MIGRATION.** Schema must precede code: apply the migration to production BEFORE merging the code that relies on the constraint, or concurrent settlements will continue to duplicate credits until the index lands.

## Problem

When a referee's first two jobs settle concurrently — a TrueLayer webhook and a manual mark-paid arriving together, or two webhooks for different jobs racing — each execution reads `isFirstPaidJob` as true, because the count at settle-paid-job.ts:108-113 excludes only the job performing the count. Each then inserts a +5 credit event with reason='referral_unlock' at paid-job-settlement.ts:112-124, and each increments the referrer's `free_jobs_remaining` cache by 5. The referrer receives 10 free jobs instead of 5. The `status='pending'` guard on referral activation executes after the ledger writes and cannot undo them, so the application-level check provides no protection. Direct revenue loss that recurs on every concurrent settlement.

The existing partial unique index `credit_events_job_consumed_key` (migration 023:70-72) already guards `reason='job_consumed'` to make webhook redelivery idempotent. The `referral_unlock` reason is unguarded.

## Scope: what changes

1. **Migration** — create a partial unique index on `credit_events(related_referral_id) where reason = 'referral_unlock'`, matching the pattern of the existing job_consumed guard. Include a matching `DROP INDEX` in the down migration.

2. **Error handling** — catch the unique violation error (SQLSTATE 23505) when inserting a `referral_unlock` credit event and treat it as an already-applied no-op. Log it distinctly from other errors so the race is visible in telemetry, but do not propagate it to the caller as a failure (the settlement succeeded; the other path just won the race).

3. **Cache increment gating** — the `increment_free_jobs_remaining` RPC call for a referral_unlock entry must execute only when the insert returns a row. If the insert fails with a unique violation, skip the cache increment entirely (the other path already incremented it). This keeps the cache correct without a compensating decrement.

4. **Duplicate detection** — a helper function or inline query exists that counts existing duplicate referral_unlock rows (grouped by `related_referral_id`, showing only groups with count > 1). This query returns zero rows when the backfill has completed and the migration can proceed safely.

## Explicitly out of scope: what does not change

- Do NOT modify `isFirstPaidJob` or the counting logic at settle-paid-job.ts:108-113. The index makes the race harmless without changing the read.
- Do NOT add uniqueness for any other `reason` value. Only `referral_unlock` is affected.
- Do NOT change the credit amount, the referral activation flow, or referrals table state transitions.
- Do NOT delete or correct existing duplicates in the migration. That is the backfill item, which runs first and is a dependency.
- Do NOT change how `free_jobs_remaining` is decremented on spend.
- Do NOT add `ON CONFLICT DO NOTHING` to the insert SQL. The unique violation must be caught in application code so it can be logged distinctly and skip the cache increment.

## Edge cases

### Duplicates still present when the migration runs
The `CREATE UNIQUE INDEX` statement fails if any duplicate rows exist. Do NOT add `ON CONFLICT DO NOTHING` or delete rows to force it through. Stop and report that the backfill has not completed. The index cannot be applied until the ledger is clean.

### `related_referral_id` is null on some rows
Partial unique indexes in Postgres do NOT constrain null values, so multiple rows with `reason='referral_unlock'` and `related_referral_id IS NULL` remain permitted after the index is created. Before applying the migration, confirm whether any referral_unlock rows have a null `related_referral_id` and report the count. If any exist, stop — the index will not protect them, and the null rows represent a data integrity issue that must be resolved separately.

### Legacy referral_unlock rows predating this change
Existing single referral_unlock rows are untouched and remain readable. Only new inserts are constrained. The backfill item removes any existing duplicates before this migration runs.

### Concurrent insert loses the race
The losing insert throws a unique violation error (SQLSTATE 23505, Postgres error code `23505`). The application catches this error, logs it as a distinct event type (e.g., "referral_unlock_duplicate_detected"), and returns successfully without incrementing the cache. The referrer's balance is correct because the cache increment is gated on the insert returning a row. No compensating action is needed.

### User-visible impact
None for existing users. New referrals credit correctly (no double-crediting). Referrers who already received duplicate credits from past concurrent settlements keep them — the backfill item decides whether to correct those, not this one.

## Risks

- **Revenue impact**: This fix prevents future revenue loss from duplicate referral credits, but it does not recover past losses. The backfill item (a dependency) quantifies and optionally corrects historical duplicates.
- **Migration dependency**: The migration MUST run before the code that relies on the constraint is deployed, or concurrent settlements will continue to duplicate credits until the index lands.
- **Backfill dependency**: The migration WILL FAIL if duplicate rows still exist. The backfill item must complete successfully before this migration can be applied.
- **Null handling**: If any `referral_unlock` rows have `related_referral_id IS NULL`, the index will not protect them. The duplicate detection query must check for this case and report it as a blocker.
- **Logging verbosity**: If concurrent settlements are common (high-volume trades settling multiple jobs near-simultaneously), the "duplicate detected" logs could be noisy. Consider rate-limiting or sampling the log emission if this becomes a problem in practice.
