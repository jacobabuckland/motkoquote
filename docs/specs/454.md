# DATA-3: The voice ledger can never find a job by name

## Problem

`src/app/ledger/query-actions.ts:198-201` attempts to select `jobs.description`, which does not exist in the database schema. PostgREST rejects the entire query, returning `{ data: null, error: {...} }`, but the code destructures only `data`, never checks the error, and treats the null result identically to "no matching job found". This breaks job lookup for every voice ledger query that names a job by its customer ("how's the Henderson job doing?").

The query also attempts to filter on the non-existent `description` field at lines 214-217. Both must be removed.

## Scope: what changes

1. **Remove `description` from the select** (line 199). The field does not exist on `jobs`; attempting to select it causes PostgREST to reject the query.

2. **Remove `description` from the filter logic** (lines 214, 216). Match on customer name alone, which the query can actually supply via the `customer:customers(name)` join.

3. **Destructure and check the error**. The surrounding `catch` at lines 224-236 already distinguishes test-environment errors (cookies called outside request scope) from real database errors and rethrows the latter so the voice session can say "try again". A rejected query must not read as "no match" — that distinction is what #438 fixed for contractor lookup and #409 catalogues for six other queries.

The select becomes:
```ts
const { data: jobs, error } = await supabase
  .from("jobs")
  .select("id, customer:customers(name), created_at")
  .eq("contractor_id", contractorId)
  .order("created_at", { ascending: false });
```

And the error must be checked before proceeding. If `error` is non-null, let it propagate — the surrounding catch will handle it correctly.

## Explicitly out of scope: what does not change

- **Adding a searchable job description or title.** `jobs` has no such field and nothing computes one. Whether a contractor should be able to name a job by its work ("the rewire") rather than its customer is a product question, and giving it a source would be a migration. Both belong to their own item.
- **Searching `sow_json`, `extracted_json` or `transcript`** for the term. Plausible, materially different behaviour, not decision-free.
- **The other #409 drifts**, in particular `src/app/jobs/[id]/pnl-actions.ts:45,55` and `src/lib/recover-lost-fees.ts:165` (a money path).
- **Ranking.** "Most recent match wins" is unchanged — the query already sorts by `created_at` descending, and the first match is taken.
- **LED-6 voice queries themselves.** This fixes the job lookup they depend on; the queries remain unchanged.
- **Matching semantics.** `includes` for partial matching is unchanged. This ticket removes a field, it does not retune matching.

## Edge cases, including failure modes and empty states

- **Two jobs for the same customer** → unchanged behaviour: already sorted by `created_at` descending, most recent wins.
- **A job with no customer row** (`customer_id` is null, or the joined customer does not exist) → contributes an empty name and does not match. Must not throw.
- **A genuine miss** (no job for any customer whose name contains the term) → the existing not-found path stands. `jobId` remains null, and the function throws "Job not found" at line 255. The distinction being restored is *rejected query* versus *no match*, not the wording of a miss.
- **A term matching a customer's name in part** → `includes` semantics are unchanged. "Henderson" matches "Henderson Ltd" and "Henderson & Co".
- **A query error** (network failure, timeout, permission denied, column does not exist) → must propagate rather than being treated as "no match". The surrounding `catch` at 224-236 already distinguishes test-environment errors from real ones and rethrows the latter.

## Risks: anything touching money, migrations, or user data

- **No migration required.** This removes a reference to a column that never existed.
- **No money paths.** Job lookup feeds into `getJobPnL`, which reads invoice and cost data, but the lookup itself does not compute or store money.
- **Reads customer name from production.** The query joins `customers(name)` to match against the spoken term. This is existing behaviour — the only change is removing the non-existent `description` field.

## Derived criteria

A unit test with a recording stub client (node environment, following the pattern in `tests/regression/owed-to-you-status-filter.test.ts`) that asserts:

1. **The select names no column `jobs` does not have.** Inspect the recorded `select()` call and assert the string does not contain `description`.
2. **A job is found by its customer's name.** Stub two job rows with joined customer names; a spoken term matching one resolves to that job's id.
3. **The most recent of two matches wins.** Stub two jobs for the same customer (or two customers whose names both contain the term), ordered by `created_at` descending; the first match is returned.
4. **A query error does not read as "no match".** Stub `{ data: null, error: { message: "..." } }` and assert the error propagates (is thrown) rather than the function returning a not-found result or null `jobId`.
5. **A genuine empty result still yields not-found**, distinct from criterion 4. Stub `{ data: [], error: null }` and assert "Job not found" is thrown.
6. **A row whose joined customer is null does not throw** and does not match. Stub a job with `customer: null` alongside one with a valid customer name; only the valid one is considered.

Mock parameters must be **optional** (`_param?: Type`). The stub client must be cast once where it is returned: `return { from } as unknown as SupabaseClient`. See `tests/acceptance/240.test.ts:241-260` for the pattern.
