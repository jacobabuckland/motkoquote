# Issue #97: Add rate limiting to create-payment, Companies House proxy, PDF routes and public actions

**Auditing branch:** `factory/97` @ `bea238f`  
**Database migration required:** A new `rate_limits` table with RLS for persistent, multi-instance limit state.

## Problem

The application has no rate limiting on any routes. Four surfaces are particularly exposed:

1. **`POST /api/truelayer/create-payment`** — initiates real payment flows, unauthenticated
2. **`GET /api/companies-house/search`** — consumes a finite third-party quota shared across all users
3. **`GET /api/quotes/[id]/pdf` and `GET /api/contracts/[id]/pdf`** — expensive PDF rendering competes with the request path
4. **Public customer actions** (`acceptQuote`, `declineQuote`, `signContract`, `declineContract`) — unauthenticated state-changing endpoints

A missing limit means the Companies House quota can be exhausted (taking company lookup down for everyone), PDF rendering can saturate resources under load, and state-changing endpoints can be hammered without cost. All are reachable without authentication.

## Scope: what changes

### 1. New rate limiter module
**File:** `src/lib/rate-limit.ts` (new)

A general-purpose rate limiting utility that:
- Accepts a key (IP address, resource ID, etc.) and a limit config (max requests, window duration)
- Returns `{ allowed: true }` or `{ allowed: false, retryAfter: number }`
- Stores limit state in a backing store that survives instance restarts (likely Supabase or similar)
- Fails open (allows the request) if the backing store is unavailable, with loud logging
- Supports combining multiple limits (per-IP AND per-resource) via logical AND

### 2. Environment configuration
**File:** `.env.example` (update)

Add environment variables for each protected surface:

```bash
# Rate limits — requests per window (seconds). Unset = no limit (not recommended for production).
# create-payment: per-IP and per-invoice. Invoice limit prevents one link being hammered from many IPs.
RATE_LIMIT_CREATE_PAYMENT_PER_IP=10
RATE_LIMIT_CREATE_PAYMENT_WINDOW_IP=60
RATE_LIMIT_CREATE_PAYMENT_PER_INVOICE=5
RATE_LIMIT_CREATE_PAYMENT_WINDOW_INVOICE=60

# Companies House proxy: per-IP. Generous to accommodate shared corporate NATs.
RATE_LIMIT_COMPANIES_HOUSE_PER_IP=30
RATE_LIMIT_COMPANIES_HOUSE_WINDOW=60

# PDF routes: per-IP and per-resource (quote/contract). Resource limit prevents one PDF being fetched in a tight loop.
RATE_LIMIT_PDF_PER_IP=20
RATE_LIMIT_PDF_WINDOW_IP=60
RATE_LIMIT_PDF_PER_RESOURCE=10
RATE_LIMIT_PDF_WINDOW_RESOURCE=60

# Public customer actions (accept/decline/sign): per-IP and per-resource (quote/contract). Resource limit prevents one quote being accept/decline toggled.
RATE_LIMIT_CUSTOMER_ACTION_PER_IP=30
RATE_LIMIT_CUSTOMER_ACTION_WINDOW_IP=60
RATE_LIMIT_CUSTOMER_ACTION_PER_RESOURCE=5
RATE_LIMIT_CUSTOMER_ACTION_WINDOW_RESOURCE=60
```

### 3. Apply rate limiting to create-payment route
**File:** `src/app/api/truelayer/create-payment/route.ts`

Add both per-IP and per-invoice limits at the top of the POST handler, after config checks but before the invoice lookup. If either limit is exceeded:
- Return 429 status
- Include `Retry-After` header with the longest wait time
- Return customer-readable error message: `"Too many payment requests. Please try again in {retryAfter} seconds."`

### 4. Apply rate limiting to Companies House proxy
**File:** `src/app/api/companies-house/search/route.ts`

Add per-IP limit at the top of the GET handler. If exceeded, return 429 with `Retry-After` header and error message.

### 5. Apply rate limiting to PDF routes
**Files:** `src/app/api/quotes/[id]/pdf/route.ts`, `src/app/api/contracts/[id]/pdf/route.ts`

Add both per-IP and per-resource (quote/contract ID) limits at the top of each GET handler. If either limit is exceeded, return 429 with `Retry-After` header.

### 6. Apply rate limiting to public customer actions
**Files:** `src/app/q/[id]/actions.ts`, `src/app/c/[id]/actions.ts`

Add both per-IP and per-resource (quote/contract ID) limits at the top of each server action (`acceptQuote`, `declineQuote`, `signContract`, `declineContract`). Server actions don't have direct access to the request object, so IP extraction will need a helper that reads from Next.js headers via `headers()` from `next/headers`.

If either limit is exceeded, throw an error with a user-friendly message that the calling page can surface.

### 7. IP address extraction utility
**File:** `src/lib/get-client-ip.ts` (new)

A utility to extract the client IP from:
- Next.js `NextRequest` object (API routes) — check `x-forwarded-for`, `x-real-ip`, fallback to `request.ip`
- Next.js `headers()` (server actions) — same header checks

Returns `null` if no IP can be determined (allows the request to proceed, logged as a warning).

### 8. Exclude authenticated service callers
**File:** `src/lib/rate-limit.ts`

The limiter should accept an optional `skipAuth` parameter. When a route is called with a valid service credential (e.g., `CRON_SECRET` for crons), bypass rate limiting entirely. For the public routes in this issue, `skipAuth` will always be `false` — this is defensive future-proofing in case a service ever needs to call one of these routes.

## Explicitly out of scope

- **No rate limiting on authenticated internal routes** — the dashboard, job pages, settings, etc. are already gated by login
- **No CAPTCHA, bot detection, or challenge flow** — limits are hard gates, not interactive challenges
- **No route behaviour changes below the limit** — the routes work exactly as they do today when under the threshold
- **No IP blocking, banning, or allowlist** — limits are time-windowed, not permanent
- **No changes to Companies House integration** — only the proxy route gains a limit; the underlying `searchCompanies` function is unchanged
- **No middleware allowlist changes** — the public route guards in `src/lib/supabase/middleware.ts` are untouched

## Edge cases

### 1. Multiple customers behind one corporate/mobile carrier NAT
**Input:** 20 different customers, all from IP `203.0.113.1`, opening their own quote PDFs.  
**Behaviour:** Per-IP limit is generous (20 requests/min for PDFs). Each customer is also gated by the per-resource limit (10 requests/min per quote), so 20 customers opening 20 different quotes = 20 requests, all allowed. If the per-IP limit is hit, the per-resource limit must still allow legitimate use — choice: bias toward higher per-IP limits for shared-NAT scenarios, or accept that some corporate NAT users may occasionally hit limits.  
**Mitigation:** Set per-IP limits high enough that normal corporate NAT use doesn't trigger them. Per-resource limits are the primary protection against hammering a single resource.

### 2. Limit exceeded on create-payment mid-journey
**Input:** Customer clicks "Pay now" on an invoice for the 11th time in 60 seconds (per-IP limit is 10).  
**Behaviour:** Return 429 with customer-readable message: "Too many payment requests. Please try again in 23 seconds." The UI can surface this as an alert, not a raw error. Customer knows to wait, not retry immediately.  
**Implementation:** The error message must include the `retryAfter` value so it's actionable.

### 3. Cron or internal caller hitting a limited route
**Input:** A future cron job needs to fetch a PDF or trigger an action.  
**Behaviour:** Exclude authenticated service callers from limits. Check for `Authorization: Bearer ${CRON_SECRET}` (or similar service credential) before applying limits. If present and valid, bypass entirely.  
**Implementation:** The `rate-limit` utility accepts a `skipAuth` flag. Routes check for service credentials before calling the limiter.

### 4. Rate limit backing store unavailable
**Input:** Supabase (or whatever stores limit state) is down or unreachable.  
**Behaviour:** **Fail open** — allow the request to proceed and log loudly. A limiter outage must not take payments or PDFs down. Log at ERROR level with context (route, IP, resource) so it's visible in monitoring.  
**Implementation:** The rate limiter catches backing store errors, logs them, and returns `{ allowed: true }`.

### 5. Legitimate burst when a trade sends one quote to many recipients
**Input:** Contractor sends quote `q-123` to 10 customers via a group chat. All 10 click the link within 30 seconds.  
**Behaviour:** Per-resource limit must accommodate this. If the per-resource limit is 10 req/min, 10 customers opening the quote = 10 requests, all allowed. The PDF route is GET (read-only), so 10 fetches in 30 seconds is plausible. The per-resource limit should be high enough to allow this.  
**Mitigation:** Set per-resource limits for PDFs to 10-15 req/min (tested against realistic send fan-out). Adjust upward if real usage shows legitimate bursts exceeding this.

### 6. Customer opening their own quote 5 times in a minute
**Input:** Customer refreshes their quote page 5 times (testing PDF rendering, checking details, etc.).  
**Behaviour:** **Allowed.** Per-resource limit is 10 req/min for PDFs, so 5 fetches is well under. This is explicitly tested in the acceptance tests — the chosen threshold must not block this.

### 7. IP cannot be determined (missing headers, localhost, proxy misconfiguration)
**Input:** Request arrives with no `x-forwarded-for`, no `x-real-ip`, and `request.ip` is `null`.  
**Behaviour:** Log a warning and allow the request (fail open). The per-resource limit still applies. Absence of an IP is a misconfiguration or unusual environment, not a reason to block legitimate traffic.  
**Implementation:** `getClientIp` returns `null`, rate limiter skips the per-IP check if IP is `null`, logs the skip.

### 8. Environment variables unset
**Input:** `RATE_LIMIT_CREATE_PAYMENT_PER_IP` is unset in production.  
**Behaviour:** No limit is applied (interpreted as "no limit configured"). Log at WARN level on first call so it's surfaced in monitoring. This is not recommended but doesn't break the route.  
**Implementation:** If the env var is unset, the limiter returns `{ allowed: true }` and logs the skip.

## Risks

### 1. Choosing limits too low (MITIGATED via acceptance tests + explicit justification)
**Risk:** Overly aggressive limits block legitimate use (e.g., customer refreshing their quote 5 times gets rate-limited).  
**Mitigation:** Acceptance tests verify that realistic legitimate use is not blocked. The PR description must state and justify each chosen limit against expected usage patterns (not copied from a library default). Limits are environment-configurable, so they can be tuned post-deploy without a redeploy.

### 2. Backing store adds latency to every request (MITIGATED via caching + fail-open)
**Risk:** Checking limits on every request adds a DB round-trip, slowing down the request path.  
**Mitigation:** The rate limiter should use an in-memory cache for recent limit checks (e.g., 5-second cache of "IP X is under the limit"). Cache invalidation is not critical — worst case, a request sneaks through 5 seconds after hitting the limit. If the backing store is slow or unavailable, fail open (allow the request).

### 3. State survives restart but not across distributed instances (ACKNOWLEDGED)
**Risk:** If the backing store is in-memory only, limits reset on each instance restart. If the app runs on multiple instances (Vercel serverless), limits are per-instance, not global.  
**Mitigation:** Use a shared backing store (Supabase table, Redis, etc.) so limits are enforced globally across all instances and survive restarts. This is a requirement, not a nice-to-have.

### 4. IP spoofing or header manipulation (ACKNOWLEDGED, not mitigated in this issue)
**Risk:** A sophisticated attacker could rotate IPs or manipulate headers to bypass per-IP limits.  
**Mitigation:** Out of scope for this issue. Per-resource limits provide a backstop — even if per-IP is bypassed, hammering one resource is still limited. True bot mitigation (CAPTCHA, fingerprinting) is a separate item.

### 5. Customer-readable error message on create-payment might be ignored (MITIGATED via UI handling)
**Risk:** The 429 response is returned as JSON; if the UI doesn't handle it, the customer sees a generic error.  
**Mitigation:** The acceptance tests verify that a 429 includes `Retry-After` and a readable `error` message. The calling UI must handle 429 status and surface the message. This is a requirement for the Engineer to test.

### 6. Server actions lack access to request headers (MITIGATED via `headers()`)
**Risk:** Server actions don't receive a `NextRequest` object, so IP extraction is harder.  
**Mitigation:** Use `headers()` from `next/headers` to read `x-forwarded-for` / `x-real-ip` in server actions. This is the standard pattern in Next.js 15+ for accessing request context in server actions.

## Derived criteria

What I understood the human to be asking for:

1. **Limits apply to four surfaces:** `create-payment`, Companies House proxy, both PDF routes (`/quotes/[id]/pdf` and `/contracts/[id]/pdf`), and the four public customer actions (`acceptQuote`, `declineQuote`, `signContract`, `declineContract`).

2. **Exceeding a limit returns 429 with `Retry-After` header.** The header value is the number of seconds until the window resets. For API routes, this is a standard HTTP header; for server actions, it's surfaced via the error message.

3. **Limits are configurable per route via environment variables.** Each surface has its own env vars (e.g., `RATE_LIMIT_CREATE_PAYMENT_PER_IP`). No hardcoded limits — everything comes from env. Unset env = no limit (logged as a warning).

4. **Both per-IP and per-resource limits apply.** A request is allowed only if BOTH limits pass (logical AND). One IP cannot exhaust a resource (per-resource limit stops that), and one resource cannot be hammered from many IPs (still costs quota/compute, but per-resource limit caps the blast radius).

5. **A customer opening their own quote 5 times in a minute is not blocked.** This is explicitly tested. The chosen per-resource limit for PDFs must be at least 5-10 req/min to accommodate this.

6. **Chosen limits are stated and justified in the PR description.** Not copied from defaults. Each limit is set based on expected legitimate usage: "PDF routes: 10 req/min per resource because a trade might send one quote to 10 customers who all open it at once. 20 req/min per IP because corporate NATs can have 20+ users."

7. **Limit state survives a single instance restart.** Limits are stored in a shared backing store (Supabase table, Redis, etc.), not in-memory only. This ensures limits are enforced globally and survive restarts.

8. **Authenticated service callers are excluded.** Crons, internal tools, or anything with a valid service credential (e.g., `CRON_SECRET`) bypass limits entirely. This is defensive — none of the routes in scope are called by services today, but the exclusion is built in.

9. **Backing store unavailable = fail open and log loudly.** If the rate limiter can't reach its backing store, allow the request and log at ERROR level. A limiter outage must not take payments or PDFs down.

10. **For create-payment, return a customer-readable message with retry path.** Not "Rate limit exceeded" — "Too many payment requests. Please try again in 23 seconds." This is a paying customer mid-transaction; the message must be actionable.

11. **Limits are time-windowed, not permanent.** Hitting a limit blocks requests for the window duration (e.g., 60 seconds), not forever. No banning, blocking, or allowlists.

12. **User-visible only when a limit is hit, which should be rare for legitimate use.** Below the limit, routes work exactly as today. Above the limit, the user sees a 429 response. For server actions, this surfaces as an error the UI can display.
