# PNL-1 — Money position: no VAT deduction, no fee term, and VAT extracted at the wrong rate

## Problem

The money position card computes `whatsLeft` as a bare scalar (collected − paid costs). Three defects:

1. **No VAT term.** For a VAT-registered trade, `collected` is gross, so it includes money that belongs to HMRC. The card over-states their spendable cash by the VAT amount.

2. **No motko fee term.** Fees where `fee_status = 'collected'` have actually left the trade's money. The computation ignores them entirely — verified by grep: `fee_amount_pennies` appears nowhere in `money-position-actions.ts`, `money-position-client.tsx` or `money-position-math.ts`. This is correct today only because free jobs set `fee_amount_pennies = 0`. The day fees go live it is silently wrong.

3. **VAT extracted at the wrong rate.** `money-position-actions.ts:177` computes `vatAmount: (inv.amount as number) * 0.2`. But `invoices.amount` carries `quotes.total`, which is already gross (subtotal + VAT). Extracting VAT from a gross figure is `gross − gross/1.2`, not `gross * 0.2`. On a gross £1,200 (£1,000 net + £200 VAT), the card reports £240 — a 20% over-statement of the VAT set-aside.

Because `whatsLeft` is a scalar, no consumer can show its working. The card cannot render a breakdown it was never given.

This is a trade's cash position. Over-stating it by the VAT they owe HMRC plus the fees they owe motko means a trade can spend money that is not theirs, stated with the authority of a computed figure.

## Scope

In `src/app/jobs/money-position-actions.ts`:

1. **Return a breakdown, not a scalar.** Add two new types and populate them in `getMoneyPosition`:

   ```typescript
   export type SafeToSpend = {
     collected: number;      // pence, gross — what actually landed
     costsPaid: number;      // pence, positive; the consumer renders the sign
     motkoFees: number;      // pence, positive
     vatToSetAside: number | null;  // pence; null when not VAT-registered
     total: number;          // pence — collected − costsPaid − motkoFees − (vatToSetAside ?? 0)
   };

   export type Projection = {
     owedNet: number;        // pence — owed invoices, net of VAT when registered
     unpaidCostsNet: number; // pence, positive — unpaid costs, net of reclaimable VAT
     feesOnOwed: number;     // pence, positive — estimated
     total: number;          // pence — safeToSpend.total + owedNet − unpaidCostsNet − feesOnOwed
   };
   ```

   Add `safeToSpend: SafeToSpend` and `projection: Projection` to the `MoneyPosition` type. Keep `whatsLeft` unchanged — PNL-4 (voice) will migrate it.

2. **Add the fee term.** Query `jobs.fee_amount_pennies` and `jobs.fee_status` for the contractor's jobs. Sum `fee_amount_pennies` where `fee_status = 'collected'` — the fee has actually left the trade's money. Treat null as 0. `'accrued'` is owed but not yet taken; do not deduct it from cash in hand. `'waived_refund'` contributes 0.

3. **Fix the VAT extraction.** Replace `money-position-actions.ts:177` with the existing `splitFeeVat` helper from `@/lib/motko-fee`:

   ```typescript
   import { splitFeeVat } from "@/lib/motko-fee";
   // invoices.amount is numeric(10,2) POUNDS; splitFeeVat works in pence.
   const { vatPennies } = splitFeeVat(Math.round((inv.amount as number) * 100));
   ```

   Use the same helper for the VAT section and the safe-to-spend term, so the two can never drift. Do not hand-roll `/1.2` anywhere.

4. **Gate VAT on registration explicitly.** Already the case (contractors.vat_registered boolean not null default false, read at :50, gates the VAT block at :156). Carry `vatToSetAside: null` (not 0) when not registered, so the UI can tell "not applicable" from "nothing owed".

5. **Compute the projection.** Under the cash-accounting basis the VAT section already uses, the arithmetic collapses cleanly:

   - An owed invoice landing brings in gross, of which VAT is set aside → net effect +net.
   - An unpaid cost being paid sends out net + VAT, and that VAT is reclaimable, reducing what is owed to HMRC → net effect −net.

   So:

   ```
   projection.total = safeToSpend.total + owedNet − unpaidCostsNet − feesOnOwed
   ```

   where `owedNet` and `unpaidCostsNet` are gross when not VAT-registered and net (via `splitFeeVat`) when registered.

   `feesOnOwed` is an estimate: allocate the contractor's current `free_jobs_remaining` across the owed invoices oldest first (the order they are most likely to land), then band the remainder with `motkoFeePennies`. Deterministic and testable. It renders £0.00 today for any trade still inside their free allowance.

- The voice answer — PNL-4 will migrate `getWhatsLeft` and the spoken sentence

- `FEE_BILLING_ENABLED` gating — the fee line is never gated on it
- Flat-rate scheme, CIS reverse charge, partial exemption — the existing estimate disclaimer stands
- Fee bands themselves — `motkoFeePennies` is used as-is
- Any backfill of already-shown figures — this is a display computation; nothing is stored

## Edge cases

- **Not VAT-registered**: `vatToSetAside: null`, not 0. `contractors.vat_registered` is boolean not null default false.
- **fee_amount_pennies null** (job never paid): contributes 0.
- **fee_status = 'waived_refund'**: contributes 0. The fee came back.
- **fee_status = 'accrued'**: contributes 0 to `motkoFees`. The fee is owed but not yet taken from cash in hand.
- **Negative total** (costs and fees exceed collected): return it negative. Do not clamp at zero; a trade in the red needs to see it. PNL-2 renders the sign.
- **Negative projection**: same. Possible when unpaid costs exceed everything owed.
- **Nothing owed at all**: `owedNet = 0`, `feesOnOwed = 0`, `projection.total = safeToSpend.total`. Still return the object; PNL-2 decides whether to render the line.
- **Rounding**: `invoices.amount` is numeric(10,2) in pounds; `job_costs.amount_net / vat_amount` and all fee columns are int pence. Convert pounds→pence with `Math.round(x * 100)` at the boundary, exactly as the existing code does, and never mix the two before that point. `splitFeeVat` takes pence.

## Risks

**This is a trade's cash position.** Over-stating it means a trade can spend money that is not theirs. The fee term is latent but will go live; adding it now while it evaluates to zero means the arithmetic is verifiable before any money moves through it.

The VAT extraction bug (20% of gross instead of proper extraction) only affects VAT-registered trades, and is a 20% over-statement of the VAT set-aside on every paid invoice. On typical job sizes this is tens of pounds per invoice.

The correct helper (`splitFeeVat`) already exists and is already tested. Use it rather than inventing new arithmetic.

## Derived criteria

1. `SafeToSpend` and `Projection` types added, with all fields documented
2. `MoneyPosition` gains `safeToSpend` and `projection` fields; `whatsLeft` unchanged
3. `motkoFees` sums `fee_amount_pennies` where `fee_status = 'collected'`
4. `motkoFees` treats null as 0; 'accrued' and 'waived_refund' contribute 0
5. VAT extraction uses `splitFeeVat` helper, not hand-rolled `* 0.2`
6. `vatToSetAside` is null when not VAT-registered, not 0
7. `safeToSpend.total = collected − costsPaid − motkoFees − (vatToSetAside ?? 0)`
8. `projection.total = safeToSpend.total + owedNet − unpaidCostsNet − feesOnOwed`
9. `owedNet` and `unpaidCostsNet` are gross when not VAT-registered, net when registered
10. `feesOnOwed` allocates `free_jobs_remaining` oldest-first across owed invoices
11. Negative totals are returned negative, not clamped to zero
12. The breakdown sums to the total — verifiable by recomputation in tests
13. The fee term is present at zero when no fees exist
