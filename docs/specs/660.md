# REF-3: Five activations credit one banked month

**Migration required:** Migration 75 (`referral_credits` table) must be applied to production via `supabase db push` before this PR merges. Schema precedes code.

## Problem

"Free until further notice" is an uncountable liability. Motko needs to track referral rewards as discrete, countable months that can be banked, consumed, and accounted for.

## Scope: what changes

### Banking credits
- Five activated referrals earn one banked month (discrete database record)
- Activations 1-4: no credit
- Activation 5: 1 credit
- Activation 10: 2 credits total (not 2 at once)
- No cap on accumulation (unlike free jobs, which cap at 10)
- Credits stored as rows in new `referral_credits` table with `consumed` boolean state
- Banking does NOT replace the existing `referral_unlock` free-job grant — both fire on the fifth activation

### Consumption
- `claimReferralCredit(contractorId, client)` function claims one unconsumed credit atomically
- Claim must be conditional: updates to `consumed = true` WHERE `consumed = false` AND `contractor_id` matches
- Returns the claimed credit row, or null if none available
- Two concurrent claims against the same contractor's credits must claim different rows (enforced by the conditional update)

### Cancellation play-out
- **Moved here from SUB-6** (decision 7 Sep, areas/motko.md): the item that invents banked months defines their value when a trade cancels
- `computeExtendedAccess(creditCount, paidUntil)` returns the access end date
- Trade cancels with 3 unconsumed credits → keeps access for 3 months beyond paid period
- Trade cancels with 0 credits → keeps access to end of paid period only (existing SUB-6 behavior, unchanged)
- Credits consumed sequentially as months elapse — trade returns after 1 month with 2 left
- The Stripe mechanics of how to extend a cancellation are left to the implementer

### Migration
- New table: `referral_credits` with columns for contractor_id, consumed boolean, created_at timestamp
- RLS enabled with standard contractor ownership policy: `contractor_id in (select id from contractors where owner_user_id = auth.uid())`
- NO grants for insert/update/delete to `anon` or `authenticated` roles (credits are system-managed)

## Explicitly out of scope

- Rest of cancellation: Settings UI control, what stays accessible after cancellation, customer's contract/invoice links — all SUB-6
- Stripe webhook integration or subscription invoice modification — implementer chooses where to call `claimReferralCredit`
- The £9.99 price itself or broader fee schedule changes
- Any change to `referral_unlock` behavior (the existing free-job grant on fifth activation)

## Edge cases

- **No unconsumed credits available**: `claimReferralCredit` returns `null`, does not throw
- **Cancellation with zero credits**: `computeExtendedAccess(0, paidUntil)` returns `paidUntil` unchanged
- **Concurrent consumption**: Two simultaneous claims against one contractor's credits must claim different rows, enforced by conditional `consumed = false` in the WHERE clause
- **Banking doesn't cap**: Unlike free jobs (max 10), credit accumulation is unlimited by design (D26)
- **Banking alongside free-job unlock**: Fifth activation grants both a credit AND the existing `referral_unlock` ledger entry — both fire, not either/or

## Risks

- **Migration timing**: Migration 75 MUST be applied to production before code merges. If code deploys first, any activation will attempt to write to a non-existent table.
- **Atomicity of claims**: If the `consumed = false` condition is missing, two concurrent claims can double-spend the same credit. Test explicitly asserts this condition appears in the query.
- **Money-equivalence**: Each credit is worth £9.99/month of subscription access. Bugs in banking or consumption directly affect contractor billing.

## Derived criteria

What the PM understood from the spec:

1. **Banking is every-5th**: Activations 4, 5, 9, 10, 14, 15 should grant 0, 1, 1, 2, 2, 3 credits respectively
2. **Credits are discrete rows**: Not a counter, but individual `referral_credits` table rows with `consumed` state
3. **Consumption is conditional**: The UPDATE query must include `consumed = false` in WHERE clause, verified by inspecting the built query on a stubbed client
4. **Cancellation extends by N months**: Where N is the count of unconsumed credits, added to the paid period end date
5. **Fifth activation grants both**: A `referral_unlock` ledger entry (existing) AND a credit (new)
6. **Migration has no dangerous grants**: No `anon` or `authenticated` can insert/update/delete credits
7. **Arithmetic is pure and testable**: `computeCreditsEarned(activationCount)` and `computeExtendedAccess(creditCount, date)` are pure functions, callable with no database

## Testing approach

- **Banking arithmetic**: Call `computeCreditsEarned(4)`, `computeCreditsEarned(5)`, etc. and assert the count
- **Preservation of existing behavior**: Call `planPaidJobSettlement` with `activatedReferralCount: 5` and assert both a `referral_unlock` ledger entry exists (unchanged) and something indicates a credit was granted

  **Where the credit half is verified, and why not in the acceptance file.** The
  acceptance test froze with only the first half of that sentence — it asserts
  the `referral_unlock` entry survives, and asserts nothing about the credit. It
  would therefore pass with the banking logic in `paid-job-settlement.ts`

  both.

  answered by this paragraph and is not a defect.** The acceptance test cannot be
  repaired downstream, and the behaviour is covered.
