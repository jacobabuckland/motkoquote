# Issue #257: LED-6: Voice query over the ledger (bounded question set)

**Auditing branch:** `factory/257` (to be created)  
**Database migration required:** NO — queries existing ledger data from LED-1/LED-2/LED-4

## Problem

A tradesperson will not open a P&L screen while working, but will ask a question with the engine running. This is voice as interrogation rather than input — the direction that makes the ledger a daily habit rather than a report. A spoken answer to "what am I owed" or "what's left" is the difference between a ledger that gets consulted and one that gets ignored.

## Scope: what changes

### 1. Voice ledger query interface

Add a voice query interface accessible from the dashboard (e.g. a dedicated "Ask about money" button or voice icon in the money position panel), which:

- Opens a voice session using the existing OpenAI Realtime infrastructure (same pattern as job intake)
- Listens for a single question, classifies it, speaks the answer, and closes
- Supports EXACTLY five query types (bounded set, no extrapolation):
  1. **"What am I owed?"** — outstanding invoices total and top few by age
  2. **"What do I owe?"** — unpaid costs by counterparty
  3. **"What do I owe [counterparty name]?"** — unpaid costs for a specific counterparty
  4. **"What did [job name/customer name] make?"** — job P&L (profit and margin)
  5. **"What's left?"** — collected minus paid costs (same definition as LED-4 screen)
- Out-of-set questions (trends, comparisons, actions, anything not in the five) respond: "I can't answer that yet. I can tell you: what you're owed, what you owe, what a job made, or what's left. Try one of those."
- Uses natural British phrasing for amounts: £1,240 as "twelve hundred and forty pounds" or "one thousand two hundred and forty pounds" (choose one convention and apply consistently)

### 2. API route for voice ledger session

New route at `src/app/api/ledger/query-session/route.ts`:

- Authenticated (contractor must be signed in)
- Mints an OpenAI Realtime client secret with ledger query instructions
- Rate limited per contractor (e.g. 10 queries per hour) to prevent abuse
- Returns `{ clientSecret: string }` on success, or error response on rate limit / auth failure

### 3. Voice prompt and classification

New prompt builder at `src/lib/voice/ledger-query-prompt.ts`:

- Instructs the model to classify the contractor's question into one of the five types, or "out_of_set"
- **The model interprets and speaks. Code computes.** The LLM receives pre-computed figures from server actions and assembles them into a natural spoken response — it NEVER performs arithmetic, aggregation, or filtering over ledger data
- Query classification returns structured output indicating which query type was recognized and any parameters (e.g. counterparty name, job identifier)
- Out-of-set questions are detected and rejected with a helpful prompt about what IS supported

### 4. Server actions for ledger query computations

New server action file at `src/app/ledger/query-actions.ts`:

- **Reuses existing computation functions** from LED-2 and LED-4 — no duplicate logic
- Provides five query handlers, each calling the corresponding existing function:
  - `getOwedToYou()` — calls `getMoneyPosition()` from LED-4 and returns `owedToYou` aggregate
  - `getYouOwe()` — calls `getMoneyPosition()` from LED-4 and returns `youOwe` aggregate  
  - `getYouOweCounterparty(counterpartyName: string)` — calls `getMoneyPosition()` and filters to matching counterparty
  - `getJobProfit(jobIdentifier: string)` — finds job by customer name or job description match, calls `getJobPnL()` from LED-2
  - `getWhatsLeft()` — calls `getMoneyPosition()` from LED-4 and returns `whatsLeft` figure
- Returns structured data (amounts in pence, names, ages) for the voice prompt to format into speech
- All monetary computation happens server-side in these functions — the voice prompt receives ready-to-speak figures

### 5. Response formatting conventions

Establish consistent British English spoken-money conventions:

- Amounts under £100: "forty-five pounds" (no "and")
- Amounts £100–£9,999: "twelve hundred and forty pounds" (hundreds form preferred for brevity)
- Amounts £10,000+: "fifteen thousand pounds" or "fifteen thousand two hundred pounds" (no hundreds form)
- Pence omitted unless non-zero: "forty-five pounds twenty" for £45.20
- Negative amounts: "You're down two hundred and forty pounds" or "minus two hundred and forty pounds" (context-dependent)

Documented in a code comment at the top of `ledger-query-prompt.ts` so the convention is discoverable.

### 6. Privacy: what gets spoken aloud

**Decision (stated in spec, enforced by prompt):**
- **Amounts:** always spoken (this is the point of the feature)
- **Counterparty names** (suppliers): always spoken when relevant ("You owe Frank two thousand pounds")
- **Customer names:** spoken ONLY when the contractor named the customer in their question
  - "What did the Smith job make?" → "The Smith job made twelve hundred pounds profit"
  - "What am I owed?" → "You're owed three thousand pounds. Your biggest invoice is four hundred days old." (NO customer name spoken unprompted)
- **Job descriptions:** treated same as customer names (only echoed if contractor mentioned it)

Rationale: amounts and supplier names are essential to the answer and likely known only to the contractor; customer names might be overheard by the customer themselves (on a driveway, through car speakers), so only speak them when the contractor has already said them aloud.

### 7. Mobile and native app rendering

- The voice query UI must work in the WKWebView (390px width)
- Uses the existing microphone permission and Capacitor audio infrastructure from job intake
- Haptic feedback on query start/end (same pattern as job intake)

### 8. Testing requirement: voice path and screen path call the same computation

Acceptance tests MUST assert that:
- `getOwedToYou()` in the voice query action calls the same `getMoneyPosition()` as the dashboard screen
- `getJobProfit()` calls the same `getJobPnL()` as the job page
- There are NO separate computation paths for voice vs screen — both must route to the same underlying functions

This prevents the voice answer diverging from the on-screen figure due to duplicate logic.

## Explicitly out of scope: what does not change

- **No trend or comparison questions** ("How does this month compare?" "Am I up or down?") — that is accounting software, explicitly not this
- **No actions by voice** (marking paid, editing costs, sending invoices) — query only in this card
- **No open-ended natural language reporting** — only the five specified queries are supported; anything else is rejected
- **No conversation or multi-turn dialogue** — ask one question, get one answer, session ends
- **No quieter mode or privacy toggle** — the privacy rule (don't speak customer names unprompted) is the mitigation; no UI setting for it

## Edge cases

1. **No data for a query**  
   - "What am I owed?" when no unpaid invoices: "You're all caught up — no outstanding invoices."
   - "What do I owe?" when all costs paid: "All costs are paid."
   - "What's left?" when zero collected or zero paid: "Nothing collected yet" or state the figure plainly if negative

2. **Ambiguous counterparty name**  
   "What do I owe Frank?" when there are counterparties "Frank Smith" and "Frank's Supplies": the model asks for clarification ("I see two Franks — Frank Smith and Frank's Supplies. Which one?") OR returns both with amounts. Engineer's choice based on what's clearer.

3. **Ambiguous job identifier**  
   "What did the Smith job make?" when multiple jobs have a customer named Smith: model asks for clarification or returns the most recent Smith job with a qualifier ("The most recent Smith job made..."). Must not guess silently.

4. **Job with no invoice yet**  
   "What did [job] make?" for a job with costs but no invoice: "That job's not invoiced yet, so I can't tell you the profit. It's got [amount] in costs so far."

5. **Query in wrong phrasing but semantically in-set**  
   "How much does Frank owe me?" is backwards (Frank is a supplier, not a customer) but the intent is clear — treat as "What do I owe Frank?" and answer it. The model should handle minor phrasing variations within the five query types.

6. **Out-of-set query that sounds plausible**  
   "What did I make last month?" or "Who's my biggest customer?" — clearly reject with the stock "I can't answer that yet" response and list the five supported queries.

7. **Very large amounts**  
   £47,320 as "forty-seven thousand three hundred and twenty pounds" — verify it sounds natural at realistic scale (most jobs under £50k).

8. **Multiple old invoices**  
   "What am I owed?" with 5 unpaid invoices: speak the total, then list the top 3 by age ("biggest invoice is 120 days old, then 90, then 30"). Exact count to list is Engineer's discretion, documented in code.

9. **Counterparty with no name**  
   Costs with `counterparty_id = null` are grouped under "No counterparty specified" in LED-4 — voice should say "You owe four hundred pounds to costs with no supplier specified" or similar phrasing.

10. **Network failure mid-query**  
    Realtime session drops before answer is spoken: same error handling as job intake (retry prompt or "Try again" message). No silent failure.

11. **Rate limit hit**  
    Contractor hits query rate limit (e.g. 10 queries in an hour): return clear error message from API route, surface it in the voice UI as "You've asked a lot just now — give it a few minutes and try again."

## Risks

- **Money-adjacent feature.** All monetary figures are computed by existing LED-2/LED-4 functions, which have already been reviewed and tested, but the new query routing layer and voice response formatting are new surfaces that touch money. Code review must verify no arithmetic happens in the prompt or voice layer.

- **Privacy: speaking money aloud.** The customer-name rule (only when contractor mentioned it) mitigates the "customer overhears their invoice amount" risk, but cannot eliminate it entirely (contractor might be on speakerphone, in earshot, etc.). The spec explicitly chooses this privacy boundary; if it's not acceptable, the feature needs a design change (e.g. text-only fallback, opt-in privacy mode).

- **LLM arithmetic is forbidden.** The prompt MUST instruct the model to use pre-computed server values, not compute sums/totals/percentages itself. Acceptance tests assert the voice layer calls the same server functions as the screen, which proves no duplicate computation exists.

- **Ambiguous query handling.** If the model silently guesses which Frank or which Smith job the contractor meant, and gets it wrong, the spoken answer is confidently incorrect. Mitigation: prompt instructs model to ask for clarification when ambiguous, never guess. Test with fixtures containing duplicate names.

- **Out-of-set query detection.** A plausible-sounding question the model mistakes for in-set (e.g. "What's my biggest invoice?" heard as "What am I owed?") produces a wrong answer. Mitigation: structured output schema with explicit `query_type` field and validation; if classification confidence is low (not directly expressible in structured output), fall back to out-of-set rejection.

- **British English amount phrasing.** The chosen convention must sound natural to a British tradesperson, not an American one. "Twelve hundred" for £1,200 is standard UK usage; "one thousand two hundred" is formal but acceptable. Pick one and test with a British English speaker if available.

## Derived criteria

- A contractor can access a voice ledger query interface from the dashboard
- The interface supports exactly five query types: what am I owed, what do I owe, what do I owe [counterparty], what did [job] make, what's left
- Out-of-set queries (trends, comparisons, actions, anything not in the five) are rejected with a clear list of what IS supported
- All monetary figures are computed by existing LED-2/LED-4 server functions — the voice path and screen path call the same computation, tested by assertion
- The LLM receives pre-computed figures and formats them into natural speech — it never performs arithmetic, aggregation, or filtering over ledger data
- Amounts are spoken in consistent natural British forms (documented convention in code)
- Counterparty names are always spoken when relevant; customer names only when the contractor named the customer in their question
- Job descriptions are treated same as customer names (only echoed if contractor mentioned them)
- The voice query UI works at 390px width in the WKWebView
- Empty states for each query type are handled with natural language ("all caught up", "all costs paid", etc.)
- Ambiguous queries (multiple Franks, multiple Smith jobs) ask for clarification or return multiple results with qualifiers, never guess silently
- A job with no invoice responds with a clear "not invoiced yet" message, optionally including costs incurred so far
- Very large amounts (£50k+) sound natural when spoken
- The API route is authenticated, rate limited (e.g. 10 queries per hour), and uses existing Realtime infrastructure
- Network failure or rate limit hit produces clear error messages, no silent failure
- Unit tests cover query classification, amount formatting, privacy rules, and edge cases (no data, ambiguous names, out-of-set queries)
- Acceptance tests assert the voice query actions call the same computation functions as the dashboard/job screens (same code path, not duplicate logic)
