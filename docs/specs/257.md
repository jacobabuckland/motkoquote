# Issue #257: LED-6: Voice query over the ledger (bounded question set)

**Auditing branch:** `factory/257` (to be created)  
**Database migration required:** NO — builds on LED-1 through LED-5's existing tables and computations

## Problem

A tradesperson will not open a P&L screen, but will ask a question with the engine running. This is voice as INTERROGATION rather than input — the direction that makes the ledger a daily habit rather than a report. Without queryable voice, the ledger remains a screen you have to remember to check, not a thing you can ask while your hands are on the wheel.

## Scope: what changes

### 1. Voice query flow reachable from dashboard

A new "Ask about money" entry point appears on the dashboard (`/jobs/page.tsx`) alongside the existing money position panel, and also in the "Speak to motko" hub (`/app/motko/page.tsx`) as a new option card.

Both entry points navigate to a new page (`/app/ledger/voice/page.tsx`) that:
- Uses the existing voice infrastructure (WebRTC to OpenAI Realtime API)
- Prompts: "What would you like to know?"
- Captures a short spoken question (typically 5–15 seconds, hard-capped at 1 minute)
- Shows a live transcript as the contractor speaks
- Interprets the question, fetches the computed data server-side, and speaks the answer back

### 2. Bounded query set: exactly five questions

The system recognizes and answers ONLY these five queries:

1. **What am I owed?** — Outstanding invoices aggregated by customer (total and top few by age)
2. **What do I owe?** — Unpaid costs aggregated by counterparty
3. **What do I owe [counterparty]?** — Unpaid costs for a specific counterparty by name
4. **What did [job] make?** — Job P&L for a specific job (matched by customer name or job reference)
5. **What's left?** — Money collected minus costs paid (the "what's left" figure from the money position panel)

Anything outside this set produces a clear response: "I can't answer that yet. I can tell you: what you're owed, what you owe, what a specific job made, or what's left after costs. What would you like to know?"

The system MUST NOT attempt general natural-language reporting or arithmetic over the ledger beyond these five queries.

### 3. Query interpretation via Claude API

A new server action `interpretLedgerQuery(transcript: string, contractor: ContractorContext)` in `src/app/ledger/query-actions.ts` calls the Claude API to classify the question and extract parameters:

```ts
const response = await anthropic.messages.create({
  model: "claude-sonnet-4-6",
  max_tokens: 256,
  system: LEDGER_QUERY_SYSTEM_PROMPT,
  messages: [{
    role: "user",
    content: transcript,
  }],
});
```

The system prompt instructs Claude to return a JSON object matching one of five query types:
- `{ type: "owed_to_you" }`
- `{ type: "you_owe", counterparty?: string }` (counterparty is optional — if omitted, return all)
- `{ type: "job_profit", job_reference: string }` (job_reference is customer name or job code)
- `{ type: "whats_left" }`
- `{ type: "out_of_scope" }`

The LLM interprets the question and extracts parameters (e.g. counterparty name, job reference) but NEVER computes numbers. All amounts come from server-side computation functions.

### 4. Server-side computation: code computes every number

Once the query type is classified, a new function `computeLedgerAnswer(query: ParsedQuery, contractorId: string)` in `src/lib/ledger-answer.ts` calls the existing computation functions from LED-2 and LED-4:

- **"What am I owed?"** → calls `getMoneyPosition()` and returns `owedToYou` (already computed, no new arithmetic)
- **"What do I owe?"** → calls `getMoneyPosition()` and returns `youOwe`
- **"What do I owe [counterparty]?"** → calls `getMoneyPosition()`, filters `youOwe` array by counterparty name (case-insensitive match)
- **"What did [job] make?"** → calls the existing `getJobPnL(jobId)` from LED-2 (already computed)
- **"What's left?"** → calls `getMoneyPosition()` and returns `whatsLeft`

**The computation layer performs ZERO arithmetic itself.** It delegates to the existing LED-2/LED-4 functions, which already compute everything from integer pence. This function is pure composition, not calculation.

### 5. Answer rendering via LLM (prose only, no arithmetic)

Once the computed data is fetched, a second Claude API call in `renderLedgerAnswer(query: ParsedQuery, data: ComputedData)` in `src/lib/ledger-answer.ts` converts the structured figures into spoken British English:

```ts
const response = await anthropic.messages.create({
  model: "claude-sonnet-4-6",
  max_tokens: 512,
  system: LEDGER_ANSWER_SYSTEM_PROMPT,
  messages: [{
    role: "user",
    content: JSON.stringify({ query, data }),
  }],
});
```

The system prompt instructs Claude to:
- Speak amounts in natural British forms: £1,240 as "twelve hundred and forty pounds" or "one thousand two hundred and forty pounds" (pick one convention and be consistent)
- NEVER perform arithmetic — only describe the figures provided
- Keep answers concise (2-3 sentences typical, 5 sentences max)
- Use natural, trade-friendly phrasing (not robotic "You are owed...")

Example spoken answers:
- **"What am I owed?"** → "You're owed fifteen hundred and twenty pounds across three customers. Henderson owes you the most — eight hundred pounds, and that invoice is twelve days old."
- **"What do I owe?"** → "You owe Screwfix two hundred and forty pounds, and Frank the plasterer three hundred."
- **"What did the Henderson job make?"** → "That one made you four hundred and eighty pounds — invoiced twelve hundred, costs were seven twenty."
- **"What's left?"** → "You've got two thousand one hundred pounds left after paying your costs."

The LLM receives pre-computed pence amounts and converts them to spoken pounds. It does NOT sum, subtract, or calculate percentages.

### 6. Privacy mode: customer names spoken only when named in the question

**Privacy decision (to be confirmed with Jacob before merge):**

- **Counterparty names** (suppliers, subcontractors) are ALWAYS spoken in answers — they are business entities, not homeowners
- **Customer names** are spoken ONLY when the contractor named them in the question (e.g. "What did the Henderson job make?" speaks "Henderson"; "What am I owed?" does NOT speak customer names, only amounts)
- **Amounts** are always spoken — this is the query's purpose

Rationale: A contractor on a driveway with the customer nearby should not have another customer's name spoken aloud. The workaround is to ask about a specific job by name, which makes the privacy choice explicit.

If Jacob requests a quieter mode (amounts whispered, no names spoken), that is a future ticket (LED-7 or later). This ticket ships the privacy-by-default described above.

### 7. Ambiguous job matching

When the contractor asks "What did the Smith job make?" and three jobs have customer name "Smith", the response is: "I found three jobs for Smith — which one did you mean?" and lists them briefly (customer name, job reference, most recent first).

The contractor clarifies ("the last one" or "M-K-1234") and the system re-queries with the specific job ID.

Job matching uses the existing `matchJobBySpokenReference` function from LED-5, with the same normalization and ambiguity handling.

### 8. Counterparty matching

When the contractor asks "What do I owe Frank?", the system normalizes "Frank" and searches the `counterparties` table (case-insensitive). If multiple counterparties match (e.g. "Frank Smith" and "Frank Jones"), the response asks for clarification.

If no counterparty matches, the response is: "I don't have any costs for Frank. Who did you mean?" and offers the top few counterparties by amount owed.

### 9. Out-of-scope questions

Anything outside the bounded set receives a plain-language refusal:

- "How much did I make last month?" → "I can't answer that yet. I can tell you: what you're owed, what you owe, what a specific job made, or what's left after costs. What would you like to know?"
- "Compare the Henderson job to the Smith job" → Same refusal
- "How much have I spent at Screwfix this year?" → Same refusal

The refusal is trade-friendly, not robotic, and offers the available options without repeating the full list on every query. The first refusal gives the options; subsequent refusals are shorter: "I can't answer that one — try asking what you're owed or what's left."

### 10. Works in WKWebView on cellular

The final verification is on-device (iPhone, real cellular connection, not simulator) and is Jacob's, not the pipeline's. The Engineer tests on web and states this in the PR; Jacob confirms on-device before merge.

## Explicitly out of scope: what does not change

- **No trend or comparison questions** — "how does this month compare to last month" is out of scope. This is deliberately not an accounting product.
- **No actions by voice** — marking invoices paid, editing costs, or creating new records by voice is out of scope. Query only.
- **No receipt or cost photo queries** — "show me the receipt for Screwfix" or "what did that receipt say" is out of scope. Voice queries answer from structured data only, not attachments.
- **No multi-turn conversations** — each query is independent. The system does not remember "Henderson" from "What did the Henderson job make?" when the next question is "What about costs?". Every query must be self-contained.
- **No drill-down by voice** — "Tell me more" or "Which invoices?" after an answer is out of scope. The contractor can ask a more specific question as a new query.
- **No currency conversion or VAT breakdowns** — the answer speaks the total figure from the money position computation, not a VAT-inclusive vs VAT-exclusive split.

## Edge cases

1. **No invoices exist (contractor has never invoiced)**  
   "What am I owed?" → "You're not owed anything yet — you haven't raised any invoices."

2. **No costs exist**  
   "What do I owe?" → "All costs are paid — you don't owe anyone."

3. **Contractor asks about a counterparty they've never paid**  
   "What do I owe Wickes?" → "I don't have any costs for Wickes. Did you mean Screwfix?" (offers nearest match if available)

4. **Job has no invoice yet (costs but no revenue)**  
   "What did the Henderson job make?" → "That job's not invoiced yet — you've spent two hundred and forty pounds on it so far, but no invoice has been raised."

5. **Job has costs exceeding revenue (loss-making)**  
   "What did the Henderson job make?" → "That one lost you sixty pounds — invoiced two hundred, costs were two sixty."

6. **Contractor asks about a job that doesn't exist**  
   "What did the Johnson job make?" → "I can't find a job for Johnson. Did you mean Henderson?" (offers nearest match by customer name)

7. **Ambiguous customer name (multiple jobs for "Smith")**  
   "What did the Smith job make?" → "I found three jobs for Smith — which one did you mean? M-K-1234 from last week, M-K-1189 from three weeks ago, or M-K-1067 from two months ago."

8. **Contractor asks the same question twice in a row**  
   The answer is recomputed each time (data may have changed). No caching or "I just told you that" response.

9. **Query interpretation is confident but wrong**  
   If the LLM misclassifies a query (e.g. interprets "What's owed to me?" as out-of-scope instead of `owed_to_you`), that is a defect. The acceptance tests cover the five canonical phrasings and five common rephrasings per query type, so misclassification is caught at test time, not in production.

10. **Contractor speaks a question but says nothing intelligible**  
    The transcript is empty or garbled. The system responds: "Sorry, I didn't catch that — what would you like to know?" and re-prompts.

11. **Voice session times out or drops mid-query**  
    The session hard-caps at 1 minute. If the contractor is still speaking at 1 minute (unlikely for a query), the session ends and processes whatever was captured. If the WebRTC connection drops (network loss), the flow shows: "Lost connection — try again when you have signal."

12. **Contractor says "nevermind" or "cancel" during the query**  
    The session ends cleanly with: "No problem — ask me anything when you're ready."

## Risks

- **Money-adjacent feature.** Individual diff review required before merge, regardless of QA verdict. Every computation path that touches GBP amounts must be reviewed by a human, even though this ticket computes nothing itself (it delegates to LED-2/LED-4). The delegation itself must be verified: the answer renderer receives pre-computed pence amounts and NEVER performs arithmetic.

- **LLM must never compute.** The cardinal rule is: code computes every number, the LLM only interprets questions and speaks answers. A model-authored sum, difference, or percentage is a defect. The acceptance tests explicitly assert that `renderLedgerAnswer()` receives structured data (pence amounts, customer names, counterparty names) and returns only prose, with NO arithmetic operations in the rendering function.

- **Privacy decision must be confirmed with Jacob.** The spec recommends speaking counterparty names always and customer names only when named in the question. If Jacob's decision differs (e.g. always speak all names, or never speak customer names even when asked), that changes the answer rendering logic. The decision must be documented in the code as a comment at the top of `ledger-answer.ts` so future readers know it was intentional.

- **Bounded set must not creep.** Adding "just one more" query type undermines the bounded design. If a sixth query is requested post-launch (e.g. "What did I spend at Screwfix?"), that is LED-7 or later, not a quick follow-up PR. The out-of-scope refusal is the load-bearing behaviour — it keeps the system honest.

- **On-device verification is required.** The WKWebView wrapper on iOS has broken voice before. The Engineer's web-based testing is necessary but not sufficient. Jacob's on-device sign-off (iPhone, real cellular, not simulator) is the gate.

## Derived criteria

- A contractor can ask a spoken question from the dashboard or "Speak to motko" hub, and receive a spoken answer in British English
- The system recognizes and answers ONLY the five bounded queries: what am I owed, what do I owe, what do I owe [counterparty], what did [job] make, what's left
- Anything outside the bounded set receives a plain-language refusal listing the available queries
- Query interpretation uses Claude API to classify the question and extract parameters (counterparty name, job reference), but NEVER computes amounts
- All amounts are computed server-side by calling the existing `getMoneyPosition()` and `getJobPnL()` functions from LED-2/LED-4
- Answer rendering uses Claude API to convert structured pence amounts into spoken British English prose, with NO arithmetic in the rendering function
- Amounts are spoken in natural British forms: £1,240 as "twelve hundred and forty pounds" (one convention chosen and applied consistently)
- Counterparty names are always spoken; customer names are spoken ONLY when the contractor named them in the question (privacy-by-default)
- Ambiguous job matches ask for clarification rather than guessing
- Empty states (no invoices, no costs, job not invoiced) are handled with plain-language answers, not errors
- Unit tests cover all five query types, out-of-scope refusal, ambiguous matches, and empty states
- Works in the WKWebView wrapper on cellular — final verification is on-device and is Jacob's, not the pipeline's
