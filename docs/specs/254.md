# Issue #254: LED-3: Receipt photo capture with confirmed extraction

**Auditing branch:** `factory/254` (to be created)  
**Database migration required:** YES — new storage bucket `receipts` with RLS policies

## Problem

Typing costs into a phone at the merchant counter will not happen. The two capture moments that will: photographing a receipt at the till, and speaking on the drive back. This card does the photo half. Without receipt capture, costs remain unrecorded or are entered from memory days later with no evidence, leading to incomplete job P&Ls and no audit trail for disputed costs.

## Scope: what changes

### 1. Receipt storage bucket and RLS

A new Supabase storage bucket `receipts` (private, not public) with RLS policies scoped to `auth.uid()` following the same pattern as the existing `voice-notes` bucket:

```sql
insert into storage.buckets (id, name, public)
values ('receipts', 'receipts', false)
on conflict (id) do nothing;

create policy "Users upload own receipts"
  on storage.objects for insert
  with check (
    bucket_id = 'receipts'
    and (storage.foldername(name))[1] = auth.uid()::text
  );

create policy "Users read own receipts"
  on storage.objects for select
  using (
    bucket_id = 'receipts'
    and (storage.foldername(name))[1] = auth.uid()::text
  );

create policy "Users delete own receipts"
  on storage.objects for delete
  using (
    bucket_id = 'receipts'
    and (storage.foldername(name))[1] = auth.uid()::text
  );
```

Storage paths follow the pattern `{auth.uid()}/{cost-id or temp-id}.jpg` so that RLS can enforce read isolation — a contractor cannot read another contractor's receipt photos.

### 2. Capacitor Camera plugin dependency

Add `@capacitor/camera` to `package.json` dependencies:

```json
"@capacitor/camera": "^7"
```

This plugin provides both camera capture and photo library access with unified permission handling on iOS and Android. The Engineer must run `npm install` and `npx cap sync` after adding the dependency.

### 3. Photo capture UI on the cost entry flow

The cost entry flow gains a photo capture entry point:

- **"Add receipt photo" button** appears above the existing manual cost form
- Tapping it presents a **native Action Sheet** (iOS) or **Alert Dialog** (Android/web) with two options:
  - "Take photo" → opens camera via `Camera.getPhoto({ source: CameraSource.Camera })`
  - "Choose from library" → opens photo picker via `Camera.getPhoto({ source: CameraSource.Photos })`
- **Permission handling:**
  - Camera permission requested on first camera use
  - Photo library permission requested on first library use
  - Permission denied → fall back to the other option (camera denied → offer library; library denied → offer camera)
  - Both denied → fall back to manual entry form with no photo
  - No "permission denied" error language that implies the user did something wrong — just present the available path

### 4. Photo compression before upload

Photos captured or selected are compressed client-side before upload to avoid multi-megabyte files that would slow down mobile uploads and waste storage:

- **Target size:** 500 KB maximum
- **Quality:** JPEG quality 80% via `Camera.getPhoto({ quality: 80 })`
- **Max dimensions:** 1920×1920 (scales down if source is larger, preserves aspect ratio)
- The Capacitor Camera plugin's `quality` option handles this automatically — no manual canvas resizing needed

After compression, upload to Supabase storage via `supabase.storage.from('receipts').upload(path, blob)`.

### 5. Extraction: Claude vision API reading the receipt

Once uploaded, the photo URL is sent to a new server action `extractReceiptData(photoUrl: string)` which:

1. Fetches the photo from Supabase storage (authenticated URL via `storage.from('receipts').createSignedUrl()`)
2. Calls the Claude API Messages endpoint with vision support (same pattern as the existing `src/lib/claude.ts`):
   ```ts
   const response = await anthropic.messages.create({
     model: "claude-3-5-sonnet-20241022",
     max_tokens: 1024,
     messages: [{
       role: "user",
       content: [
         {
           type: "image",
           source: {
             type: "url",
             url: signedUrl,
           },
         },
         {
           type: "text",
           text: "Extract from this receipt: total amount (number only), supplier name (text), date (YYYY-MM-DD), VAT amount if legible (number only). Return JSON: {total: number | null, supplier: string | null, date: string | null, vat: number | null}. If any field is illegible or not present, return null for that field."
         }
       ]
     }]
   });
   ```
3. Parses the JSON response and applies sanity bounds:
   - `total` must be between £0.01 and £50,000.00 (1 pence to 5,000,000 pence)
   - `total` outside this range is treated as illegible (set to `null`)
   - Implausible amounts (e.g. phone numbers read as totals like £7,700,900,123) are rejected
   - `date` must parse as a valid date via `Date.parse()`; invalid dates become `null`
   - `vat` must be ≤ `total`; if greater, set to `null`
4. Returns the extracted data as a draft cost object — **DOES NOT write to the database**

**Extraction failure is a normal outcome**, not an error. Blurry photos, non-English receipts, handwritten receipts, or photos of something other than a receipt all return `{ total: null, supplier: null, date: null, vat: null }`. The UI handles this gracefully (see next section).

### 6. Confirmation UI: editable draft cost

The extracted data is presented in the cost entry form as **pre-filled values that the user can edit**:

- Description field: pre-filled with `supplier ?? "Receipt"` (editable)
- Amount field: pre-filled with `total / 100` (pounds) if extracted, else empty (editable, required)
- Counterparty field: pre-filled with `supplier` if extracted, else empty (editable, optional)
- Date incurred field: pre-filled with `date` if extracted, else today (editable, required)
- VAT treatment: auto-selected based on `vat`:
  - If `vat` is present and ≈ 20% of `total` (within 1p tolerance for rounding): select "Standard (20%)"
  - Otherwise: default to contractor's VAT treatment per LED-2
- Category: defaults to "materials" (editable)
- Photo thumbnail visible at top of form (not editable — photo is already uploaded and linked)

**The form submit button reads "Confirm and save"** (not "Add cost") to emphasize that confirmation is required. Pressing it creates the cost row via the existing `createJobCost` action, passing `evidenceUrl: photoUrl` and `source: "photo"`.

**Extraction produces no database write until the user confirms.** This is tested explicitly: asserting `extractReceiptData()` calls the Claude API but produces zero rows in `job_costs`.

### 7. Extraction failure fallback: manual form with photo

If extraction returns all `null` fields (blurry photo, non-receipt, illegible), the UI presents the **same cost entry form** with:

- All fields empty except date (defaults to today) and category (defaults to materials)
- Photo thumbnail visible at top
- No error message saying "extraction failed" or implying the user did something wrong
- Just a clean form ready for manual entry, with the photo already attached as evidence

The user fills the form manually and submits. The photo is already uploaded, so `evidenceUrl` is populated even though extraction produced nothing.

### 8. Viewing the receipt photo on a cost row

After a cost is saved with `evidence_url` populated:

- The cost row in the cost list shows a **small thumbnail or camera icon** indicating a photo is attached
- Tapping the row or icon opens a **full-screen photo viewer** showing the receipt
- The photo URL is fetched via `supabase.storage.from('receipts').getPublicUrl()` (returns a signed URL for private buckets when the user is authenticated)
- The viewer has a close button (X in top corner) and no other controls

This works for costs created via photo capture (`source = 'photo'`) and also supports future voice capture (`source = 'voice'`) that might generate a receipt image from voice.

### 9. Offline handling

**Photo capture works offline** (Capacitor caches the photo locally), but **upload and extraction require network**. The behavior when offline:

- Photo captured successfully → stored locally by Capacitor
- Upload fails with a clear error: "No internet connection. Try again when online."
- The photo is NOT lost — the user can retry the upload when back online
- **No silent loss of the captured photo**

The Engineer must test this with airplane mode enabled.

### 10. Rotation and large images

- **EXIF orientation is respected** — a photo taken in portrait mode appears portrait, not rotated 90°
- The Capacitor Camera plugin handles this automatically via `correctOrientation: true` option
- Very large images (>1920px width or height) are downscaled by the plugin before upload (via `width: 1920` option)

## Explicitly out of scope: what does not change

- **No multi-receipt batch capture** — one photo at a time, one cost row per photo
- **No line-item extraction** — only total, supplier name, date, and VAT. Individual line items ("Timber: £40, Screws: £12") are ignored
- **No accounting export** — this is LED-7 or later
- **No receipt categorisation** — the extraction does not infer `category` (materials vs labour etc). The user selects category manually
- **No receipt editing or cropping** — the photo uploaded is the photo stored, no client-side editing tools
- **No receipt deletion** — once uploaded, a receipt photo stays linked to the cost row. Deleting the cost row does NOT delete the storage object (orphaned receipts are cleaned up by a future cron, not this ticket)
- **No counterparty merging UI** — if the extracted supplier name is "Screwfix" but the contractor previously entered "Screwfix Trade", those remain two separate counterparties. LED-8 or later adds merging

## Edge cases

1. **Permission denied for camera**  
   Present the "Choose from library" option instead. If the user declines, fall back to manual cost entry with no photo. No error language implying they did something wrong.

2. **Permission denied for photo library**  
   Present the "Take photo" option instead. If the user declines, fall back to manual cost entry with no photo.

3. **Both camera and library permissions denied**  
   Fall back to the manual cost entry form with no photo attached. The "Add receipt photo" button becomes disabled or hidden.

4. **Offline photo capture**  
   Photo is captured and cached locally by Capacitor. Upload attempt fails with: "No internet connection. Try again when online." The captured photo is NOT lost — reopening the form allows retry.

5. **Photo upload fails (network error, storage bucket full, RLS rejection)**  
   Show a clear error: "Failed to upload photo. Try again." The user can retry or proceed to manual entry without a photo.

6. **Extraction returns implausible total** (e.g. £77,009,012.34, likely a phone number read as an amount)  
   Sanity bounds reject this (outside £0.01–£50,000.00 range). The extraction returns `total: null` and the user sees the manual form with photo attached.

7. **Extraction returns a date in the future**  
   The sanity bounds do NOT reject future dates (a contractor might capture a receipt for a deposit paid today for delivery next week). The date is accepted as-is; the user can edit if wrong.

8. **Extraction returns VAT > total**  
   Sanity bounds reject this (VAT cannot exceed the total). The extraction returns `vat: null` and the VAT treatment defaults to the contractor's setting.

9. **Photo is rotated 90° (EXIF orientation not respected)**  
   The Capacitor Camera plugin's `correctOrientation: true` option fixes this. The photo displays correctly in the viewer.

10. **Very large photo (8 MB, 4000×3000 pixels) from a high-end phone camera**  
    Compressed to ~500 KB via `quality: 80` and downscaled to 1920×1920 via `width: 1920`. Upload completes in <5 seconds on 4G.

11. **Blurry photo or photo of a non-receipt**  
    Extraction returns `{ total: null, supplier: null, date: null, vat: null }`. The user sees the manual form with the photo thumbnail at the top. No "extraction failed" error shown.

12. **User edits the extracted amount from £45.00 to £40.00 (receipt was misread)**  
    The edited value is saved. The photo remains attached as evidence of what was actually paid, even though it contradicts the entered amount. The photo is evidence, not gospel.

13. **Contractor creates a cost from a photo, then deletes the cost row**  
    The photo remains in storage (orphaned). A future cron (not this ticket) deletes orphaned receipts older than 90 days. This matches the voice-notes retention pattern.

14. **Cross-tenant access: contractor A tries to read contractor B's receipt URL**  
    RLS on `storage.objects` rejects the read. The signed URL returns 403 Forbidden. This is tested explicitly in the acceptance tests.

15. **User captures a photo but closes the form without submitting**  
    The photo is uploaded but not linked to any cost row (orphaned). Same as edge case #13 — cleaned up by future cron.

16. **Extraction API is slow (>5 seconds)**  
    Show a loading spinner on the form with copy: "Reading receipt..." and allow the user to cancel and switch to manual entry. If extraction takes >10 seconds, timeout and fall back to manual form with photo.

17. **Claude API rate limit or quota exceeded**  
    Treat as extraction failure: return `null` for all fields, show manual form with photo. Log the error server-side for monitoring, but do not surface "API quota exceeded" to the user.

18. **Non-English receipt** (Spanish, Polish, etc.)  
    Claude can read many languages, but accuracy may vary. Extraction may return `null` for supplier name if the text is illegible to the model. The user fills manually if needed.

19. **Handwritten receipt**  
    Extraction likely returns `null` for most fields. The manual form handles this (same as blurry photo).

20. **Receipt photo is upside-down**  
    EXIF orientation does not cover manual rotation. The photo displays upside-down in the viewer. The user can re-capture or ignore (the extracted text is orientation-invariant in Claude's vision model, so extraction may still work).

## Risks

- **Migration must be applied to production BEFORE code merges.** If the code deploys first, every receipt upload will fail with "bucket does not exist". Mitigation: CLAUDE.md documents this pattern; verify `supabase migration list` shows prod in sync, AND manually upload/delete a test file to confirm the bucket and RLS policies actually work.

- **Camera permissions on iOS require Info.plist entries.** If `NSCameraUsageDescription` and `NSPhotoLibraryUsageDescription` are missing from `ios/App/App/Info.plist`, permission requests fail silently. Mitigation: the Engineer must add these entries (the spec does not list this in "Files" because it is a platform-specific config, not a source file):
  ```xml
  <key>NSCameraUsageDescription</key>
  <string>Take photos of receipts to track job costs</string>
  <key>NSPhotoLibraryUsageDescription</key>
  <string>Choose receipt photos from your library</string>
  ```

- **Claude vision API cost.** Each extraction costs ~1–3 cents in API usage (vision-enabled messages are more expensive than text). A contractor capturing 50 receipts/month costs motko ~$1.50/month in API fees. This is acceptable at current scale, but if receipt capture becomes high-volume (hundreds per contractor per month), consider batching or switching to a cheaper OCR provider. Mitigation: monitor usage via Anthropic dashboard; set a budget alert at $100/month.

- **Photo URLs are signed with TTL.** Supabase `createSignedUrl()` returns URLs that expire (default 1 hour). If a user opens a cost row >1 hour after the page loaded, the photo viewer shows a broken image. Mitigation: generate signed URLs on-demand when the viewer opens (server action `getReceiptSignedUrl(evidenceUrl)`) rather than pre-fetching all URLs on page load.

- **Storage bucket RLS must scope to auth.uid(), not contractor_id.** The existing voice-notes and logos buckets use `(storage.foldername(name))[1] = auth.uid()::text` as the RLS predicate. The receipts bucket must match this pattern exactly. Using `contractor_id` in the path or policy is wrong (a user can own multiple contractors, or a contractor can have multiple users via team access in future). Mitigation: copy the RLS policies from migration 00000000000004_voice_notes_storage.sql verbatim.

- **Extraction confirmation bypass.** If the client calls `createJobCost` directly without going through the confirmation UI, a cost row can be written without human confirmation. This is not a security issue (the user is authenticated, the data is theirs), but it violates the "never write without confirmation" design principle. Mitigation: the acceptance tests explicitly assert that `extractReceiptData()` produces zero DB writes, and the UI flow (photo capture → extraction → pre-filled form → user edits/confirms → submit) is the only path to cost creation from a photo.

- **EXIF orientation bugs on Android.** Some Android devices embed incorrect EXIF orientation tags, causing photos to display rotated even with `correctOrientation: true`. Mitigation: the Capacitor Camera plugin handles most cases; if bugs surface in production, consider a server-side re-orientation step using an image library (e.g. `sharp`) before storing.

## Derived criteria

- A contractor can capture a receipt photo from the job page using camera or photo library
- Photos are stored in a Supabase storage bucket `receipts` with RLS policies scoped to `auth.uid()`
- A contractor cannot read another contractor's receipt photo (RLS enforced, tested explicitly)
- Photos are compressed to ~500 KB before upload via Capacitor Camera plugin quality and size options
- Extraction calls Claude vision API and returns total, supplier name, date, VAT (or `null` for any illegible field)
- Extraction does NOT write to the database — it returns a draft object only (tested: zero DB writes from `extractReceiptData()`)
- The extracted draft is presented in an editable cost entry form; user must confirm before the cost row is written
- Extraction failure (all fields `null`) is handled gracefully with a manual entry form and the photo attached
- The photo remains viewable on the cost row after creation via a full-screen viewer
- Camera and library permissions are requested on first use; permission denial falls back to the other option or manual entry
- Offline photo capture works (photo cached locally); upload fails with a clear error and retry path
- EXIF orientation is respected so portrait photos display portrait
- Works in the iOS WKWebView wrapper with correct Info.plist permission entries
- Sanity bounds reject implausible totals (outside £0.01–£50,000.00) and invalid dates
- VAT > total is rejected; VAT ≈ 20% of total auto-selects "Standard (20%)" VAT treatment
