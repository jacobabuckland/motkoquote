# PFIX-13: Extract "a grand and a half" (fraction after scale word)

## Problem

PFIX-11 fixed spoken money extraction for phrases where the fraction comes **before** the scale word ("seven and a half thousand" → £7,500). The form where the fraction comes **after** the scale word still extracts nothing: "a grand and a half" → currently returns nothing, should return £1,500.

Both orderings are ordinary trade speech. "A grand and a half" is if anything the more natural way to say £1,500 in British English.

This is an improvement, not an urgent repair. Before PFIX-11, the system returned **£1,000** for "a grand and a half" — a wrong price that could silently attach to a quote. Now it returns nothing, which is the safe failure mode: the contractor sees "no spoken prices were picked up" and enters it manually. Fixing extraction is valuable but not urgent.

## Scope: what changes

Extend `parseNumberWords` in `src/lib/parse-spoken-money.ts` to recognize the pattern `<number> <scale> and a <fraction>` where the scale word (hundred/thousand/grand) comes before the fractional phrase.

Examples of the new pattern:
- "a grand and a half" → £1,500
- "two grand and a half" → £2,500  
- "a thousand and a half" → £1,500
- "three thousand and a quarter" → £3,250

The implementation must handle this at the parser level, recognizing when a scale word (hundred/thousand/grand) is followed by "and a half", "and a quarter", or "and three quarters", and applying the fractional multiplier: `(base + fraction) × scale`.

## Explicitly out of scope

- **"half a grand"** — this is a third distinct construction (fraction-first with indefinite article). Handle it separately if needed, but not in this ticket.
- **PFIX-12's `transcript_span` behavior** — already merged at `e30de10`. The span now captures verbatim text (after redaction, before normalization), so no further work needed here.
- **Changing the regression test file name or location** — `tests/regression/spoken-money-leading-fraction.test.ts` stays as is. The acceptance tests for this ticket will cover both orderings to prevent future divergence.

## Files

- `src/lib/parse-spoken-money.ts` (modify) — extend `parseNumberWords` to handle scale-before-fraction pattern
- `tests/acceptance/569.test.ts` (new) — acceptance tests covering both orderings

## Edge cases

- **No scale word at all**: "seven and a half" (no "thousand"/"hundred"/"grand") must stay unextracted, as it's ambiguous (7.5 what?). PFIX-11 already asserts this; keep it that way.
- **Rate units present**: "a grand and a half a day" carries a rate unit and must return with `refused: true`, exactly like every other rate phrase.
- **Multiple fractional forms**: Support "and a half", "and a quarter", and "and three quarters" in the new ordering, matching what PFIX-11 added for the fraction-before-scale ordering.
- **Implicit "one"**: "a grand and a half" normalizes to "one thousand and a half" before parsing, so the base number is 1, not 0.

## Risks

None. This is pure extraction logic with no side effects. The change extends a deterministic parser to recognize an additional spoken form. It cannot affect pricing, invoicing, or stored data — only what gets extracted from voice transcripts during intake.

The risk of extracting a **wrong** amount was already eliminated by PFIX-11 returning nothing instead of £1,000. This change moves from safe-failure to correct-extraction.

## Derived criteria

1. "a grand and a half" extracts as £1,500 (150000 pence) end-to-end through `extractStatedPrices`.
2. "two grand and a half" extracts as £2,500 (250000 pence).
3. "a thousand and a half" extracts as £1,500 (150000 pence).
4. All PFIX-11 cases (fraction before scale) continue to work: "seven and a half thousand" → £7,500, "two and a half grand" → £2,500, "one and a quarter thousand" → £1,250, "three and three quarters grand" → £3,750.
5. Both orderings are tested in the same file, named clearly to distinguish them, so they can never diverge again.
6. "seven and a half" (no scale word) continues to return nothing (stays unextracted).
7. "a grand and a half a day" returns with `refused: true` because rate units make extraction unsafe.
8. The tests name the ordering they cover explicitly ("fraction before scale" vs "fraction after scale") so the distinction is visible.
