# FACT-2: Poll on merge, not only on a clock

## Problem

The factory's admission trigger is schedule-only ("17 * * * *"). GitHub's scheduled workflows are best-effort and dropped under load. Evidence from this repository shows four consecutive gaps of 5-13 hours where one hour was asked for, and on 6 September the poller did not run between 09:30 and 13:37, requiring manual intervention twice. Nine items merged that day, and each merge freed a slot that nothing asked about for up to four hours. This is a single point of failure: every other stage is triggered by a label write and is immediate; only admission waits on a clock that is allowed to skip.

## Scope: what changes

Add a second, independent trigger: push to main. A merge is exactly when capacity frees up, so admitting on merge makes the admission rate track the completion rate rather than a clock. The hourly schedule stays as the floor for periods when nothing is merging.

The duplicate guard is the core change: today, only the Status: In factory write-back prevents duplicates, and that happens AFTER issue creation (poll-notion.mjs steps 1 and 2). Any failure between the two leaves the item in the ready filter. Polling more often enters that window more often. The guard must check whether a ready item already carries a GitHub issue before creating a new one.

The check reuses loadKnownItems(), which is already lazy and already fetches the issue list when a programme-ordering check needs it. Adding an unconditional request to main() would break tests/acceptance/115.test.ts, which is frozen and drives poll-notion.mjs through a mocked fetch whose call sequence is part of the contract.

## Explicitly out of scope

- Changing FACTORY_MAX_PER_RUN, the stopped-queue ceiling of 5, or the policy of any admission gate
- The triggers of any other factory workflow
- Paying for a hosted scheduler

## Files

- `.github/workflows/factory-poll-notion.yml` (modify) — add push trigger
- `scripts/factory/poll-notion.mjs` (modify) — add duplicate guard using loadKnownItems
- `tests/acceptance/643.test.ts` (new) — test duplicate guard, per-run cap, ceiling, existing behavior

## Edge cases

**Duplicate detection:** A Notion item marked "Ready for factory" that already has a GitHub issue URL recorded in its "GitHub Issue" property is never admitted a second time. The guard checks the issue list before creating, not only the Status after creating.

**Empty page body:** Still skips without consuming a cap slot. The duplicate guard does not fire for an item whose body is empty — empty items are parked in "Needs spec" without ever creating an issue, so there is nothing to be duplicate of.

**Programme ordering:** The ordering gate still holds a stacked programme's later item until its predecessor is started. The duplicate guard and the ordering gate are independent: an item can be held for ordering and never checked for duplicates, or checked for duplicates and never examined for ordering, depending on whether it belongs to a sequenced programme and whether it has already been admitted.

**Per-run cap:** Given more ready items than FACTORY_MAX_PER_RUN, at most that many pipelines start. A duplicate-detected item does not consume a cap slot, exactly as with an empty page body or a held item.

**Stopped-queue ceiling:** The workflow's shell gate still refuses admission at or above 5 stopped items, on either trigger. The duplicate guard lives in the script and never runs when the shell gate has already refused.

**Concurrency group:** The workflow's concurrency: factory-poll with cancel-in-progress: false already collapses a burst. N merges in quick succession do not produce N polls — GitHub keeps at most one pending run per group.

**Failure modes:**
- If the issue list cannot be read (API error, token failure), the duplicate guard opens rather than stopping the queue, and logs a warning. Better to risk a duplicate on one poll than to halt the queue for a transient error.
- A Notion item whose "GitHub Issue" property is a URL that is not a valid GitHub issue (wrong repository, deleted issue, malformed URL) is treated as having no issue and is admitted. The guard compares issue numbers, not URL strings.

## Risks

**Duplicate issues on concurrent polls:** The push trigger can fire while a scheduled poll is already running, or two pushes can arrive faster than one poll completes. The concurrency group serializes them, but it does not prevent both from seeing the same Notion state. If poll A creates an issue and poll B queries Notion before A's write-back lands, poll B sees the item as ready with no issue and creates a duplicate.

**Mitigation:** The window is narrow (one second of sleep, one issue-creation request, one write-back request) and the worst outcome is one duplicate issue, which a human closes. The schedule trigger has always had this risk — two hourly polls cannot overlap by more than the workflow timeout, but a long-running poll (admission gates, many items) can still be running when the next schedule fires. This item does not introduce the race; it makes it more likely.

**Write-back failure leaves item in ready filter:** If the Notion write-back fails after issue creation, the item stays "Ready for factory" with an issue URL recorded. The next poll sees it as ready and the duplicate guard now prevents a second issue. But the item never gets a stage label, so no agent runs on it. Today this is a stuck item; with the duplicate guard it stays stuck but is now silent.

**Mitigation:** The duplicate guard logs "Already has issue #N, skipping" when it fires, so a duplicate-skipped item appears in the workflow log. The stuck state is unchanged from today — a write-back failure already produces it — but the symptom is now quieter. If this becomes a problem, the guard can check whether the issue has a stage label and re-apply it if missing, but that is not in scope here.

## Derived criteria

When I drive the poller twice against a Notion board whose ready item already carries a factory issue URL, exactly one issue is created, not two. The second poll logs that it skipped the item because it already has an issue.

The per-run cap still bounds: given five ready items with MAX_PER_RUN=2, exactly two issues are created. The duplicate guard does not change what counts against the cap.

A held item (programme-ordering hold, or empty page body) still does not consume a cap slot. The duplicate guard does not fire for held items because they are never admitted in the first place.

The stopped-queue ceiling still refuses admission at or above 5 stopped items, on both the schedule and the push trigger. The shell gate runs before the script, so the duplicate guard never sees a poll that was refused at the ceiling.

The Notion query, its Status filter, and its Priority/created_time sort order are unchanged. The duplicate guard does not alter the ready filter or the order in which items are considered.

The push trigger is added to the workflow's `on:` section alongside the schedule. Neither trigger is removed.
