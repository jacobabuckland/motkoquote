# Issue #179: Block Deploy agent merge on red CI with no override path

**Source:** [Notion roadmap item](https://app.notion.com/p/Block-Deploy-agent-merge-on-red-CI-with-no-override-path-3b71e4f908b4808b82eacd5f8764cd6e)

**Requires database migration:** No

---

## Problem

The Deploy agent currently merges factory PRs to main after batch preview confirmation without verifying CI check status. Although branch protection exists to constrain merges through the standard path, the Deploy agent holds FACTORY_TOKEN and its merge path has not been audited against that constraint. Branch protection that an automation can circumvent is not a gate — the entire safety argument for autonomous merging rests on CI being unbypassable specifically on the agent's path, which is the only path that merges without a human present.

## Scope: what changes

### 1. Deploy agent queries check-run status before merge
**Location:** The Deploy agent workflow or script that performs the merge after batch confirmation.

Before executing any merge, the Deploy agent must:
1. Fetch all check runs for the PR's head SHA via GitHub's API
2. Identify which checks are required (consult branch protection rules or a known list)
3. Verify that every required check has `conclusion: "success"`
4. Only proceed with the merge if all required checks pass

The check is performed against the PR's current head SHA. If the SHA changes between the check and merge attempt, the verification must be re-run against the new SHA.

### 2. Block and report on check failures
**Location:** Same Deploy agent workflow/script.

When required checks are not all successful:
- **Do not merge** the PR
- Set the Notion Status field to "Blocked" (via the existing Notion API integration)
- Comment on the GitHub PR with:
  - Clear statement that the merge was refused due to failing checks
  - List of check names that failed, are pending, or are missing
  - Instructions for how to proceed (fix the issue, push again)

The agent treats these states as failures:
- `conclusion: "failure"`, `"cancelled"`, `"timed_out"`, `"action_required"`
- `conclusion: "neutral"` or `"skipped"` (not success)
- `status: "queued"`, `"in_progress"`, `"waiting"` (not concluded)
- Zero check runs reported for the head SHA (absence = failure)

### 3. Audit and remove admin-merge capabilities
**Location:** All workflows in `.github/workflows/`

Search every workflow file for merge API calls that use admin or bypass parameters:
- `gh pr merge --admin`
- `gh pr merge --bypass`
- GitHub API calls to `/repos/{owner}/{repo}/pulls/{number}/merge` with `bypass_branch_protections: true` or similar

Remove any such parameters. Document in the PR description that the audit was performed and what (if anything) was found and removed.

### 4. Document the refusal behavior
**Location:** New or existing `FACTORY.md` file (or `docs/factory.md` if that's the convention)

Add a section explaining:
- The Deploy agent checks CI status before every merge
- What states cause a merge refusal
- Where to look when an item lands on "Blocked" due to CI
- That absence of check runs is treated as failure (fail-closed)

## Explicitly out of scope

- **Do not change which checks are required.** That is branch protection configuration, not something this code determines.
- **Do not modify the batch preview confirmation step** or add additional human gates.
- **Do not change the factory label state machine** (previewed, shipped, blocked, etc.) beyond setting Status to Blocked on refusal.
- **Do not alter FACTORY_TOKEN permissions.** The fix is in the code's behavior, not the token's scope.
- **Do not implement retry-on-failure or auto-fix behavior.** When checks fail, the agent stops and reports — it does not attempt to repair the issue or re-run checks.
- **Do not add new CI checks or change what the CI workflow tests.** The CI gate content is a separate concern.

## Files

Expected touches:

   - Add step to fetch check runs via GitHub API (`gh api` or direct REST call)

## Edge cases

### 1. Check run reported as neutral or skipped
**Input:** A required check concludes with `conclusion: "neutral"` or `"skipped"`.  
**Behavior:** Treat as not-success. Refuse the merge. Include in the list of failing checks in the PR comment.

### 2. GitHub API call fails or times out
**Input:** The request to fetch check runs returns an error or times out.  
**Behavior:** Refuse the merge and set Status to Blocked. Never merge on an unverified state — fail closed. Log the error and include it in the PR comment so a human can investigate.

### 3. PR already merged when the agent runs
**Input:** The Deploy agent is triggered but the PR has already been merged by a human or another process.  
**Behavior:** Exit cleanly without error. This is idempotent, not a failure. Log that the PR is already merged and take no further action.

### 4. Head SHA changes between check and merge
**Input:** The head SHA of the PR changes (new commit pushed) after the agent fetches check runs but before it executes the merge.  
**Behavior:** Re-fetch check runs for the new SHA and re-verify. Do not merge a SHA that was not verified. The GitHub API will reject a merge attempt with a stale SHA anyway, but the agent should catch this proactively.

### 5. Existing PRs already in flight when this ships
**Input:** PRs that were already in the "previewed" state before this change was deployed.  
**Behavior:** They go through the same check on their next Deploy agent run. No grandfathering or exemption — every merge goes through CI verification from the moment this deploys.

### 6. Zero check runs reported
**Input:** The GitHub API returns an empty list of check runs for the PR head SHA.  
**Behavior:** Refuse the merge and set Status to Blocked. Absence of checks is treated as failure, not success (fail-closed). Comment on the PR that no check runs were found and manual investigation is needed.

### 7. Some checks are not required
**Input:** The PR has 5 check runs, but only 3 are marked as required by branch protection.  
**Behavior:** Only the 3 required checks must have `conclusion: "success"`. The other 2 can have any status without blocking the merge. The agent should fetch the list of required checks from branch protection rules to know which to enforce.

### 8. Check run is in progress
**Input:** A required check has `status: "in_progress"` with no conclusion yet.  
**Behavior:** Do not merge. The agent should wait (or exit and be re-triggered) rather than treating pending as pass. Optionally: log that checks are still running and re-check after a delay, or simply exit and rely on being re-triggered when checks complete.

## Risks

- **No risk to money, migrations, or user data** — this affects the factory's internal merge automation only, not production application behavior.

- **Regression risk: PRs may be blocked that would have merged before** — This is the intended behavior. If CI is red, the PR should not merge. However, if the CI check itself is flaky or misconfigured, legitimate PRs may be blocked. Mitigation: ensure the CI workflow is stable and required checks are correctly configured before this ships. The dependency on "the CI gate item" in the issue acknowledges this.

- **Operational risk: Deploy agent could stop working entirely** — If the GitHub API call fails due to authentication, permissions, or API changes, the agent will refuse all merges. Mitigation: fail visibly with clear error messages and monitoring, and have a manual merge fallback (humans can still merge PRs through the GitHub UI).

- **Audit risk: missing an admin-merge call** — If the grep audit misses a workflow that uses admin/bypass parameters, that workflow could still circumvent branch protection. Mitigation: the audit is explicit and documented in the PR; the grep command is stated in the acceptance criteria and can be verified.

## Derived criteria

What I understood the human to be asking for:

1. **The Deploy agent must query GitHub check-run status before merging** — specifically, it must fetch check runs for the PR head SHA via the GitHub API and verify that all required checks have `conclusion: "success"`.

2. **Only merge when every required check is successful** — any other state (failure, pending, neutral, skipped, cancelled, timed_out, action_required) blocks the merge.

3. **Refuse merge and set Status to Blocked when checks fail** — the agent does not merge, sets the Notion Status to "Blocked", and comments on the PR with the names of failing checks.

4. **Refuse merge when checks are still running** — pending checks are not treated as passing. The agent waits or exits, expecting to be re-triggered when checks complete.

5. **Refuse merge when zero check runs are reported** — absence of checks is a failure state, not a pass (fail-closed).

6. **No workflow may use admin or bypass merge parameters** — audit all `.github/workflows/*.yml` files and remove any such parameters.

7. **Document the behavior in FACTORY.md** — explain the CI gate, what causes a merge refusal, and how to resolve a "Blocked" status.

8. **Existing PRs go through the same gate** — no exemption for PRs already in flight when this deploys. Every merge after this ships must pass CI.

9. **GitHub API errors cause merge refusal** — if the agent cannot fetch check runs, it does not merge. Fail closed, not open.

10. **Re-verify if the head SHA changes** — if a new commit is pushed between the check and the merge, re-fetch and re-verify before attempting the merge.
