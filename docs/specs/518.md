# Issue #518: HARN-2 — A replay harness that runs the quote pipeline offline

## Problem

A content defect in the quote pipeline — an invented material line, a stated price that became a different number, a superseded price that survived to the final quote — can only be found today by manual testing: speaking into a phone, waiting for the model to run, and reading the resulting PDF. That is a thirty-minute cycle per change, it does not parallelise, and it is the only thing standing between the factory and a pricing regression reaching a customer. Most of these defect classes are fully deterministic given a fixture transcript and SoW state, yet none of them can be checked without a live API key and network access. The fixture corpus from HARN-1 (#519) provides three substantial scenarios with expected outputs at each stage, but there is no harness to run them through the pipeline and verify the outputs match.

## Scope: what changes

Add a separate vitest project and an `npm run test:pipeline` script that runs the quote pipeline offline against the HARN-1 fixture corpus:

1. **A separate vitest project** (`vitest.pipeline.config.ts`) so the pipeline suite can gate independently of the main suite and be run on demand without running 2700+ other tests.

2. **An Anthropic record/replay wrapper** at the Anthropic client construction boundary. `src/lib/claude.ts` constructs the client lazily per call (`const client = () => new Anthropic(...)`), which makes that the clean seam to intercept. The wrapper:
   - In **replay mode** (the default), reads recorded responses from `fixtures/pipeline/recordings/[scenario]-[stage].json` and returns them without touching the network or needing an API key.
   - In **record mode** (opt-in via `RECORD_PIPELINE=1`), makes real API calls, writes the responses to disk, and fails loudly if a recording already exists for that (scenario, stage) pair — re-recording is an explicit overwrite, not a refresh.
   - **Fails loudly** when a recorded response's request hash does not match the current prompt — a prompt change invalidates the recording, and silently falling through to a live call would hide the determinism break.

3. **Explicit stubs for the three database-backed context lookups**:
   - Past-job retrieval (`similar_past_jobs`)
   - Known material prices (`known_material_prices`)
   - Learned contractor tendencies (`contractor_tendencies`)
   
   Each is passed as an empty array to `draftQuoteLineItems` and `compileDraftToLineItems`, matching the guest quote path. Left unstubbed, these would swallow their failures silently and return empty, making the harness replay a different pipeline than production — green, deterministic, and wrong. The tests assert that removing any stub causes a visible failure.

4. **Snapshot assertions at each stage** for each fixture scenario:
   - **Extraction**: `extractStatedPrices(transcript)` produces the committed `expectedStatedPrices` exactly
   - **Draft**: `draftQuoteLineItems(...)` produces a draft with the expected line count and categories (not byte-identical, since temperature is 1.0)
   - **Compiled line items**: `compileDraftToLineItems(...)` produces the committed `expectedLineItems` exactly (description, category, quantity, unit, unit_price on every line)
   - **Totals**: `computeQuoteTotals(lineItems, false)` produces the expected subtotal and total

5. **An npm script** `test:pipeline` in `package.json` that runs the pipeline suite alone.

The guest quote path (`src/lib/guest/quote.ts`) already runs this entire chain as a pure function with no database, no request context, and no server-only imports, so no refactoring is needed first. The harness drives `draftGuestQuote` with each fixture's `sowState` and verifies each stage's output against the committed expectations.

## Explicitly out of scope

- Wiring this into CI — that is a later item in the HARN programme (HARN-3)
- The Statement of Work golden render — also later (HARN-4)
- Changing pricing behaviour to make a fixture pass. A failing fixture is a finding, not something to adjust the code to accommodate
- Recording responses for all three scenarios in the first commit — the first scenario's recordings are sufficient to prove the harness works; the other two can be recorded in a follow-up or left for the Engineer

## Edge cases

- **A recorded response no longer matches the current prompt**: the harness must fail loudly naming the fixture and the mismatch, never silently falling through to a live call. A prompt change invalidates the determinism guarantee.
- **The drafting temperature is 1.0**, so a re-record is not reproducible. The recorded response is the contract; a re-record is a reviewed change to the expected output, not a refresh.
- **A fixture with no stated prices**: the pipeline behaves differently when `stated_prices` is empty (no reconciliation to perform). The corpus already covers this (one of the three scenarios has an empty stated-prices list), and the harness must run it without special-casing it.
- **An unstubbed context lookup fails silently**: the test explicitly asserts that removing any of the three stubs (`similar_past_jobs`, `known_material_prices`, `contractor_tendencies`) causes a visible failure rather than a silent empty result. This proves the harness is actually driving the stubs and would catch a regression where the production path stopped using them.

## Risks

This item touches no money logic that is not already covered by existing tests. It touches no migrations and no customer-facing surfaces. The risks are:

1. **The recorded responses become stale** if the prompt changes without re-recording. Mitigation: the harness fails loudly on a prompt/recording mismatch, and the re-recording flag is explicit.
2. **A stub that looks right but does not actually block the code path**, making the test pass while the production path breaks. Mitigation: explicit negative assertions that removing each stub causes failure.

## RUNNABLE

```
npm run test:pipeline
```

The acceptance tests must invoke this command end-to-end and verify it completes with exit code 0, runs offline (no network access), and completes in under 60 seconds.

## Derived criteria

A checklist of what must be true when this item ships:

1. ✅ A `vitest.pipeline.config.ts` file exists defining a separate vitest project
2. ✅ `package.json` contains a `test:pipeline` script that runs `vitest run --config vitest.pipeline.config.ts`
3. ✅ Running `npm run test:pipeline` completes successfully (exit code 0)
4. ✅ The pipeline suite runs with no network access (can be verified by running with `ANTHROPIC_API_KEY` unset)
5. ✅ The pipeline suite completes in under 60 seconds (measured wall-clock time, not test timeout)
6. ✅ At least one scenario's full pipeline is covered: extraction → narrative → draft → compile → totals
7. ✅ Changing any expected line item's `unit_price` by one penny causes a named test failure that identifies the fixture and the stage
8. ✅ Re-recording model responses requires an explicit opt-in flag (`RECORD_PIPELINE=1`); a normal run never reaches the network
9. ✅ Removing the `similar_past_jobs` stub from the test context causes a visible failure (not a silent empty array)
10. ✅ Removing the `known_material_prices` stub causes a visible failure
11. ✅ Removing the `contractor_tendencies` stub causes a visible failure
12. ✅ A fixture whose stated price does not survive to the final line items fails with a message naming both the stated figure and the final figure
13. ✅ Running the pipeline suite does NOT execute any test in the main suite (no cross-contamination)
14. ✅ The recording files are committed JSON, not binary blobs, so a diff in a re-record is human-reviewable
15. ✅ When a recorded response's prompt hash does not match the current prompt, the test fails loudly naming the scenario and stage, never falling through to a live call
