# Issue #418: PRICE-1 — Extract every spoken amount into a structured stated_prices record

## Problem

Stated prices reach the pricing stage as free text inside a transcript that the drafting model re-reads. Nothing carries an amount as an amount, so the figure survives into prose and dies before it becomes money. On the reviewed run, the tradesperson said £520 for consumer-unit labour (a spoken correction from £480, stated once, unambiguously, with no competing value). It reached the SoW narrative as "£520 for consumer unit labour agreed" but never reached a priced line — the quote carried £600 instead, bundled into a two-day line. This is the same class as the July £20 → £114 override: a repeat, not an incident.

This item introduces the foundation of the price-fidelity chain (PRICE-2 through PRICE-5 all consume the record it creates). It changes no customer-facing output on its own.

## Scope: what changes

A new extraction module processes transcripts and outputs every monetary amount stated during the conversation into a structured record. For each amount extracted:

- **amount** — integer pence. Parsed via `parseSpokenMoney` (already exists at `src/lib/parse-spoken-money.ts`, deterministic, returns `null` for ambiguous input). Reuse it; do not write a second parser.
- **item** — what the amount attaches to, as stated. Free text, nullable (null when no clear attachment).
- **transcript_span** — where in the transcript it came from. PRICE-3 turns this into a provenance reference on the rendered line; here it only has to be recorded.
- **qualifiers** — semantic flags: `each` (unit price), `fitted` (labour included), `already_paid` (already settled with customer), `excluded` (explicitly out of scope). These are binding per decision D3: "£85 each fitted" means unit price × quantity with labour included.
- **superseded_by** — set on a value the contractor later replaced. Decision D2: last-stated value wins; superseded values are retained for audit and never rendered.

The record is written alongside the existing SoW state so PRICE-2 can read it.

## Explicitly out of scope: what does not change

- **The drafting model's behaviour.** It still receives what it receives today. Locking line items to these amounts is PRICE-2's job. This item only produces the record.
- **Any rendered document.** Quote, SoW, and contract output is byte-identical after this item. `tests/regression/quote-pdf-golden.json` must not move.
- **`parse-spoken-money.ts`.** Reuse it as it stands. It is pure and deterministic by design ("Money integrity depends on this being deterministic") and has its own test suite at `src/lib/parse-spoken-money.test.ts`.
- **The voice conversation.** No new questions, no read-back, no change to what Motko asks. Conversational elicitation is explicitly a separate, larger piece of work.
- **`sow.pricing` / `agreed_costs`.** The existing fixed-price and agreed-day-rate mechanisms stay exactly as they are. This record sits beside them; reconciling the two is PRICE-4's job.
- **Deciding what to do with an extracted amount.** Suppression, flagging, and the £0/TBC treatment are PRICE-3's concerns.

### On storage

Prefer carrying the record inside the existing `sow_json` blob if it fits the shape cleanly — that needs no migration and no schema-before-code sequencing. If a separate column is genuinely required, then schema must precede code: Supabase migrations are applied by hand via `supabase db push` and do not run on Vercel deploy, so the migration must be applied to production BEFORE the code that reads the new column merges. `tests/acceptance/schema-in-tree` (shipped as #410) already rejects a `select` naming a column no migration creates.

## Edge cases

- **A correction that restates the same figure.** "£520... sorry, £520" is not a supersession. Only a genuinely different value sets `superseded_by`.
- **Three values for one item.** The last wins; the middle one is superseded too. Retain the whole chain, render none of it (rendering is PRICE-3's job).
- **An amount with no clear item.** Record it with a null `item` rather than guessing an attachment. PRICE-3 decides what an unattached amount does to a document; inventing an attachment here would be the same class of failure as inventing a price.
- **"Eighty-five each" with no quantity stated anywhere.** Record the `each` qualifier and the unit amount. Resolving quantity is not this item's job and must not be guessed.
- **An amount the contractor states as already paid.** "The EICR was £120, they've already paid that" → record it with `already_paid: true`. It is a real stated amount and must be extractable; whether it becomes a line is PRICE-2's decision. On the reviewed transcript, the correct answer was to exclude it.
- **A transcript with no amounts at all.** An empty record (empty array), not null or undefined. Downstream code should not have to distinguish "none stated" from "not extracted".
- **A range ("somewhere between four and five hundred").** `parseSpokenMoney` returns `null` for ambiguous input. Do not pick an end of the range. Record nothing and let PRICE-3 flag the item.

## Risks

- **Extraction quality is the whole chain's ceiling.** If this under-extracts, PRICE-4's gate flags correct quotes and contractors stop sending. Decision D11 covers this: the gate ships blocking and instrumented, and a failure rate above roughly one in five means the extraction gets fixed rather than the gate downgraded. That measurement is only possible if this item records what it found.
- **No money moves in this item.** Nothing is charged, invoiced, or displayed differently. The escalation-list concern that normally attaches to pricing work does not bite until PRICE-2.

## Derived criteria

- Against the fixture transcript, all seven stated amounts extract with their correct qualifiers.
- £480 is present in the record and marked superseded by £520; £520 is not marked superseded.
- The `each` qualifier is set on the £85 amount, and `fitted` alongside it.
- The EICR £120 carries `already_paid: true`.
- Amounts are integer pence, obtained via `parseSpokenMoney`, not floats.
- Each extracted amount carries a non-empty `transcript_span` locating it in the source.
- An amount whose spoken form is ambiguous produces no record entry rather than a guessed value.
- A transcript stating no amounts produces an empty record (empty array), not null or undefined.
- Rendered quote, SoW, and contract output is unchanged by this item — the quote PDF golden hashes do not move.
- The extraction function is pure: same input always produces same output, no API calls, no randomness.
- The schema validates all required fields and rejects invalid shapes.
- `src/lib/schemas/sow.ts` carries a `stated_prices` field that accepts the extracted record.
