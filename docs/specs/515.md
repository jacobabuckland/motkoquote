# OBS-2: Report client-side crashes instead of writing them to a console nobody reads

## Problem

Every render-phase crash in the app is written to the browser console and nowhere else. The app has three error boundaries (global, route, and voice-intake route) that all log to console and stop. A console line in a WKWebView on a contractor's phone in Norfolk reaches nobody, ever. The Realtime connect failure already reports via a server action to the events table — this item generalizes that pattern to all three error boundaries.

## Scope

1. Create a server action `reportRenderError` that calls `logError("client", ...)` with error details
2. Update all three error boundaries to call this server action in their `useEffect` hooks
3. Pass the current route path, error message, error digest (when present), and optionally run_id (when available)
4. Keep the existing console logging for local development
5. Make the reporting call fire-and-forget (no `await`) so a failed report never blocks rendering

## Explicitly out of scope

- Third-party crash reporting (OBS-5)
- Server-side error handling (already routes through analytics helper)
- The in-app report button (OBS-4)
- Any database migration (writes to existing events table)
- Removing or changing the existing error boundary UI
- Capturing run_id in contexts where it doesn't already exist

## Files

- `src/app/actions.ts` (modify) — add `reportRenderError` server action
- `src/app/global-error.tsx` (modify) — call reporting action
- `src/app/error.tsx` (modify) — call reporting action
- `src/app/jobs/new/error.tsx` (modify) — call reporting action

## Edge cases

- **Crash in global boundary itself:** The report must not recurse. A failure to report is swallowed (already handled by `logError` which never throws).
- **No session (signed out):** An anonymous crash still needs recording via the existing anonymous-write path in `track()` (already supported by `logError`).
- **Offline or network gone:** The error screen renders regardless; the report is fire-and-forget, so rendering is never blocked.
- **Error with no digest:** The digest field is optional in Next.js error props; report it when present, omit when absent.
- **No route available (global boundary):** Global boundary cannot use Next.js router hooks. Pass a fallback route identifier like `"[global]"`.

## Risks

- **Recording PII:** Error messages could contain user input. The existing `logError` already writes to the events table, so this is not a new exposure.
- **Infinite reporting loops:** If the reporting action itself throws during render, it must not trigger the error boundary again. The fire-and-forget pattern (`void reportRenderError(...)`) and `logError`'s never-throw guarantee prevent this.

## Derived criteria

1. When a component throws during render, the error is recorded to the events table with `source: "client"`
2. The recorded error includes: the route where it happened, the error message, and the digest (when present)
3. The recorded error is distinguishable from server-side errors (by the `source: "client"` field)
4. The existing Realtime connect-failure reporting continues to work (no changes to that code path)
5. A failure to record an error never prevents the error screen from rendering
6. All three error boundaries (global, route, voice-intake) report errors, not just write to console
7. The console logging remains unchanged (kept for local development)
