# PAY-8: Pay connected-account balances out to contractors' banks

## Problem

Stripe payouts are set to "manual" at connected account creation, but no code exists to trigger payouts. Money arrives in contractors' Stripe balances via destination charges but never reaches their banks. The complete set of Stripe API calls in `src/` contains no `stripe.payouts.create`, and the schedule set at account creation is never changed afterward.

**Corrected after this spec was written (2026-08-25).** The line here originally
read "this affects every contractor who has ever been paid through the Stripe
rail". That is wrong, and the dates say so: `src/lib/stripe-connect.ts` — the
file carrying `createConnectedAccount` and its `interval: "manual"` — did not
exist until 18 Aug 2026 (`2f8f3d7` adds it whole). Accounts created before that
date never went through this code path and took Stripe's own default schedule;
one such account was inspected on 25 Aug and shows `Payouts Daily` with an
upcoming payout.

So the defect is **prospective, not historical**: every account created by
`createConnectedAccount` from 18 Aug onwards carries `manual` and will never pay
out, and every account predating it is fine. Balances accumulate for the former
while the product's central promise — quote, contract, invoice, get paid —
remains unfulfilled at the last step for them.

This narrows the sweep in §2 rather than removing it: the sweep is still correct
and still idempotent, it simply has fewer accounts to fix than the original
framing implied. It also means the out-of-scope balance-clearing ticket may have
nothing to clear — check the Connect account list's creation dates before
treating that as work.

## Scope: what changes

1. **Account creation** — `createConnectedAccount` in `src/lib/stripe-connect.ts` sets `settings.payouts.schedule.interval: "daily"` instead of `"manual"`. This applies to all newly created accounts going forward.

2. **Sweep script** — A new runnable script updates every existing connected account's payout schedule to daily. The script is idempotent, skips accounts without a `stripe_account_id`, and reports how many accounts it updated.

3. **Regression guard** — A test asserts that no code path in the repository sets `interval: "manual"`, preventing this defect from being reintroduced.

## Explicitly out of scope: what does not change

- **Clearing existing balances** — Deliberately excluded per `areas/motko.md` (2026-08-25). Separate Bugs ticket: "Clear the Stripe balances accumulated under the manual payout schedule". Nothing in this ticket may move an accrued balance as a side effect.

- **`stripe_payouts_enabled` column naming** — Separate Bugs ticket, and the
  characterisation here has since been reversed. This originally said the column
  "is misnamed (reads `capabilities.transfers` instead of
  `account.payouts_enabled`)", implying the fix is to repopulate it. The owner
  decided on 25 Aug to rename the column instead, because repopulating it would
  silently change what the pay button gates on: `canAcceptStripePayment` reads
  this column, and `account.payouts_enabled` is false for a trade with no
  external account attached who can still legitimately receive transfers.
  Either way it is out of scope here and moves no money while this ticket is
  open.

- **`canAcceptStripePayment` logic** — Correct as written and must not be touched. These are destination charges; `card_payments` is never requested, so `charges_enabled` is false for every contractor. Gating on it would shut the pay button for everyone — a mistake this codebase has already made and already fixed.

- **When a job is marked paid** — Settled by owner on 2026-08-25: "paid" means the customer paid. This ticket delivers the "landed" half (separate state).

- **The motko fee** — Reaches the platform account via `application_fee_amount` and is unaffected by this change.

- **Charge creation, fee collection, or settlement timing** — Nothing about how payments are created or how fees are applied changes. Only the payout schedule changes.

## Files

- `src/lib/stripe-connect.ts` — change `interval: "manual"` to `"daily"` in `createConnectedAccount`
- `scripts/update-payout-schedules.ts` — new sweep script to update existing accounts
- `tests/acceptance/344.test.ts` — new acceptance tests

## Edge cases

- **Payouts fail** — Under an automatic schedule, Stripe retries and surfaces failures on the account. Whether a failed payout needs to reach the contractor in-product is out of scope for this ticket; it is exactly the class of signal that must not terminate in a log.

- **Incomplete onboarding** — A contractor who never completed Stripe onboarding has no external account attached, so payouts cannot run regardless of schedule. This is correct.

- **Existing accounts unchanged until swept** — Shipping the account-creation change alone fixes only new signups. The sweep is what helps anyone who already has money stuck.

- **Ledger rows unchanged** — Nothing recorded in the ledger changes. Jobs marked paid stay paid; fee rows stay as they are. The money exists and is correctly attributed — it is in the wrong account, not missing.

- **Idempotent sweep** — Running the script twice changes nothing on the second pass. It queries all contractors, attempts to update the schedule for each one with a `stripe_account_id`, and Stripe accepts the request even if the schedule is already set to daily.

- **No `stripe_account_id`** — The script skips contractors with `null` `stripe_account_id` rather than erroring. There is no Stripe account to update.

## Risks

**Money.** This changes when contractors receive their money. While the change moves it from "never" to "daily" — which is strictly an improvement — it is still a money-timing decision and belongs on the escalation list.

**Not provable from the repo.** None of this confirms a payout actually reaches a bank. That needs one real payout observed in the Stripe dashboard after the change lands in production — a five-minute check that could still invalidate this ticket if payouts turn out to be happening by a route not visible in the codebase.

## DELIVERABILITY

This item describes a runnable sweep script:

```
RUNNABLE: npx tsx scripts/update-payout-schedules.ts
```

The acceptance tests MUST invoke this command end to end, not just import a function behind it.

## Derived criteria

1. New connected accounts are created with automatic daily payouts, not manual.
2. A sweep script updates every existing connected account to the same schedule.
3. The sweep is idempotent — running it twice is safe.
4. The sweep skips contractors with no Stripe account rather than erroring.
5. No code anywhere sets `interval: "manual"`, so the defect cannot recur.
6. Existing payment regression tests pass without modification — charge creation, fee collection, and settlement timing are unchanged.
7. The script is executable via the exact command in the RUNNABLE line.
8. The script reports how many accounts it updated.
