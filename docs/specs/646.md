# CONN-6: Completing Stripe onboarding makes trade payable

## Problem

A contractor completes Stripe Connect onboarding and is told "set up" in settings, but their customer invoice page renders no way to pay. The pay panel gates on `payout_details_complete`, which is only set by the manual bank details form in Settings. Connect onboarding sets `stripe_payouts_enabled` but never touches `payout_details_complete`, so the two readiness signals are disconnected. A trade finishes onboarding, sees "set up", sends an invoice, and the customer hits a dead page with no payment button and no bank details.

## Scope: what changes

- Make `buildPayPanel` recognize Connect completion (`stripe_payouts_enabled: true`) as sufficient for payability, without requiring the manual payout form fields
- Prevent settings from showing the "set up" affirmative when the contractor is not actually payable on the customer-facing pay page
- Ensure the settings affirmative and the pay page agree in all four combinations of (`stripe_payouts_enabled`, `payout_details_complete`)
- Eliminate double entry: a contractor who completed Connect either has their bank details auto-populated from Connect's external account, or is recognized as payable without needing the manual fields at all

## Explicitly out of scope

- Which Stripe capability to key readiness on (CONN-5 addresses this separately)
- Setting `on_behalf_of` parameter (CONN-4)
- Renaming the `stripe_payouts_enabled` column (deferred)
- Correcting the two production accounts that already hit this — manual decision for Jacob, not an automated backfill
- Preserving the return destination through the sign-in bounce during Connect onboarding (separate UX issue)

## Files

- src/app/i/[id]/pay-panel.ts (modify) — change `buildPayPanel` or `hasPayoutDetails` to recognize Connect readiness
- src/lib/stripe-connect.ts (modify) — either populate payout fields from Connect external account on completion, or provide a readiness check that `buildPayPanel` can use
- src/app/settings/stripe-connect-section.tsx (modify) — gate the "set up" affirmative on actual payability
- src/app/settings/payout-details-actions.ts (modify) — coordinate with Connect state so manual form isn't required after Connect completes

## Edge cases

- **Connect complete but Stripe API fails when fetching external account**: should still show as payable if `stripe_payouts_enabled` is true in the database
- **Contractor manually entered details before Connect existed**: both signals set — contractor remains payable, no conflict
- **Connect onboarding incomplete** (`stripe_requirements_due` is true): must not be payable
- **Connect account later restricted by Stripe**: pay panel should degrade gracefully, not throw
- **No external account attached to Connect account**: rare but possible — contractor should still be recognized via `stripe_payouts_enabled` flag
- **Customer views `/i/[id]` before and after Connect completion**: page must reflect current state on each load

## Risks

- **Payment flow is critical**: any regression prevents contractors from receiving payment — the entire revenue path
- **Must not create false payability**: contractor appears payable but payment actually fails — destroys trust
- **Consistency between surfaces**: settings says "ready" but customer cannot pay, or vice versa — direct contradiction
- **Existing contractor state**: must not break contractors who are already payable via the manual form
- **Database reads**: ensure queries for contractor readiness are efficient and don't introduce N+1 problems

## Derived criteria

1. A contractor whose Connect onboarding is complete (verified by `stripe_payouts_enabled: true` and `stripe_requirements_due: false`) and who has filled in no manual payout form must see a payable mode from `buildPayPanel` — not `setup_incomplete`
2. The settings surface must not render the "set up ✓" affirmative when the contractor is not actually payable on the customer invoice page
3. The settings affirmative and the pay page result must agree in all four combinations of the two readiness signals:
   - (false, false) → both say not ready
   - (false, true) → both say not ready (Connect is required)
   - (true, false) → both say ready (the key fix)
   - (true, true) → both say ready
4. A contractor who completed Connect must not be asked to manually type sort code and account number a second time — either the form is hidden, pre-filled from Connect, or simply not required
5. The behaviour must be asserted by calling the real functions with the inputs production gives them, rather than by reading source files. For `buildPayPanel` that means a `PayPanelInput` object, exactly as `src/app/i/[id]/page.tsx` and `src/app/i/[id]/pay-panel.test.ts` call it — not a stubbed client. (The `tests/acceptance/240.test.ts:241-260` stub pattern applies to functions whose production signature *takes* a `SupabaseClient`, such as `reportOffRailsInvoices`. `buildPayPanel` does not, and requiring a client here produces a test-only overload in production code.) Where a function under test does take a client, stub it per 240.
