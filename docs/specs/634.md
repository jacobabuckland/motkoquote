# SEC-1: Remove bearer-token auth from middleware

## Problem

`src/lib/supabase/middleware.ts` accepts `Authorization: Bearer <token>` on all routes in addition to cookie sessions. This was added for a deploy health check that no longer exists (#571 deleted it). While not a security bypass—every token is validated through `supabase.auth.getUser(token)`—it is unjustified auth surface. Auth is on the escalation list, and a decision was required rather than folding this into the health check deletion.

**Decision taken 5 Sep 2026** (recorded in `areas/motko.md`): Option A, remove it. Cookie sessions only.

## Scope

Remove bearer token authentication from the middleware layer. The middleware will only accept cookie-based authentication going forward.

### Changes:
1. Remove bearer token extraction from `src/lib/supabase/middleware.ts` (lines 82-84)
2. Remove the conditional token-based auth call (line 88)
3. Update the comment on line 82 to remove "for health checks" reference
4. Always call `supabase.auth.getUser()` without a token parameter (cookie-based only)

### Consequence:
Any caller using a bearer token for authentication will receive signed-out behavior (redirect to /login for authenticated routes, or the public page for public routes). No known callers exist—the grep on 5 Sep found only:
- Voice/realtime surfaces sending Bearer tokens to OpenAI (not to this middleware)
- `src/lib/cron-auth.ts` checking `Bearer CRON_SECRET` inside route handlers (not in middleware)

## Explicitly out of scope

- Any changes to route handlers that check bearer tokens (like cron routes checking CRON_SECRET)
- Any changes to API clients that send bearer tokens to external services (OpenAI)
- Changes to authentication for specific API routes beyond what middleware provides
- The middleware's cookie-based authentication mechanism (unchanged)
- The PUBLIC_API_ROUTES list (unchanged)

## Files

- `src/lib/supabase/middleware.ts` (modify) — remove bearer token auth
- `tests/acceptance/634.test.ts` (new) — regression test asserting bearer tokens no longer work

## Edge cases

- **Unknown bearer token users**: Any unknown caller using bearer tokens starts getting signed-out behavior rather than an error that names the cause. This is acceptable—no known callers exist.
- **Expired/invalid bearer tokens**: Previously would be rejected by `supabase.auth.getUser(token)`. Now won't even be extracted, so behavior is the same (unauthenticated).
- **Valid session cookie + bearer token**: Previously the bearer token would take precedence. Now only the cookie is used.
- **Public routes**: Behavior unchanged—public routes remain accessible without authentication whether or not a bearer token is present.

## Risks

- **Unknown consumers**: The main risk is an unknown system sending bearer tokens that would start failing. Mitigation: the 5 Sep grep of the iOS shell and scripts found no consumers, and the only bearer token use in the tree is to external services or in route-handler-level checks, not middleware.
- **Test breakage**: Tests that mock bearer token authentication through middleware will fail, which is correct and expected. The frozen test in `tests/acceptance/257.test.ts` (LED-6) uses bearer tokens in a future API route context, not middleware, so it may need updating when that feature is built.

## Derived criteria

What this ticket delivers:

1. The middleware no longer extracts the Authorization header
2. The middleware no longer parses "Bearer " tokens
3. The middleware always calls `supabase.auth.getUser()` without a token parameter (cookie-based only)
4. A regression test proves that a request with a valid bearer token to an authenticated route is redirected to /login (treated as unauthenticated)
5. A regression test proves that a request with a valid bearer token to a public route succeeds (public routes remain public, but the token is ignored)
6. Cookie-based authentication continues to work unchanged
7. The comment referring to health checks is removed from the middleware
