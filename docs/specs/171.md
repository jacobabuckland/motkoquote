# Issue #171: Make QA stateful across cycles so it cannot re-flag what it passed

**No database migration required.**

## Problem

QA reviews from scratch on every cycle with no memory of what it approved previously. It can re-raise findings against code that has not changed since it was explicitly marked satisfied in an earlier cycle. This wastes cycles and can exhaust the three-cycle cap without converging, blocking the item for human intervention. #93 demonstrates the failure mode: cycle 2 objected to the consequence of cycle 1's demand, cycle 3 moved to a third position, and the Engineer complied each time yet still hit the cap.

## Scope: what changes

1. **Persist verdicts in issue comments.** When QA posts its findings comment (which already happens), the comment includes a machine-readable verdict record at the end: a `<!-- qa-verdict-N -->` HTML comment block containing a JSON object with the cycle number, commit SHA reviewed, and a list of criteria marked satisfied (or findings raised). Each criterion identifies the file and line range it covers.

2. **Load prior verdicts before review.** The QA workflow reads all prior verdict blocks from the issue's comments (using `gh api` to fetch comment bodies, then parsing the HTML comment blocks) before invoking the QA agent. Prior verdicts are passed to the agent in its prompt.

3. **Present settled criteria to QA.** The QA agent prompt includes a section listing criteria marked satisfied in previous cycles, each with the commit it was judged against. The agent is instructed that re-raising a settled criterion is only permitted if the code region it covers has changed since that commit.

4. **Validate re-raised findings.** After the QA agent writes its verdict, a validation step runs before posting the comment. For each finding that re-raises a criterion marked satisfied in a prior cycle, the validator runs `git diff <prior-commit>..HEAD -- <file>` to check whether the region changed. A finding that re-raises without a change in the region is rejected with a failure message, and the verdict is rewritten as `PASS` (since the only findings were invalid re-raises).

5. **Re-raised findings must name what changed.** When the agent re-raises a settled criterion, its finding must explicitly state what code change triggered the re-review. The validator checks for this by pattern-matching the finding text — if it doesn't reference a specific change, the finding is rejected.

6. **Iteration cap unchanged.** The three-cycle cap remains in place as the final backstop. Verdicts do not alter the cap logic.

## Explicitly out of scope: what does not change

- The iteration cap (3 cycles), the labels (`verify`, `qa-changes`, `previewed`, `blocked`), or the dispute route
- Verdict storage outside the issue: no database, no filesystem artefacts, no external state
- The QA review criteria themselves (migration safety, RLS, spec fidelity, etc.)
- How the Engineer receives or addresses findings
- The spec-derived or previewed stages
- First-cycle behaviour: when no prior verdicts exist, QA behaves exactly as it does today

## Edge cases

1. **Engineer's rework changes the region a settled criterion covers**: The criterion is no longer settled (because the diff for that region is non-empty), so QA reviews it again. This is correct behaviour — the code changed, so re-review is warranted.

2. **Settled criterion was settled wrongly**: The dispute route already exists. A human can adjudicate via the `blocked` state and the resume mechanism. Statefulness must not make a bad verdict permanent — a disputed finding can still be escalated.

3. **First cycle, no prior state**: The verdict extraction returns an empty array, the agent prompt omits the "settled criteria" section, and QA behaves exactly as it does today (stateless review).

4. **Prior verdicts unreadable or missing**: If comment parsing fails or produces invalid JSON, fail open to stateless behaviour rather than blocking the cycle. A bookkeeping failure must not stop the pipeline. Log the parse error to the workflow output.

5. **Cycle count resets on a fresh attempt** (after `spec-derived` is re-applied): Prior-attempt verdicts do not carry over, since the branch may have diverged or been rebased. Only verdicts from the current attempt (since the most recent `spec-derived` label event) are loaded.

6. **User-visible**: No. This is factory review process only — customers and contractors see no change.

7. **Verdict blocks accumulate in issue comments**: They are small (JSON, compressed) and scoped to a single attempt, so bloat is minimal. If an issue has many attempts, it will have many verdict blocks, but this is acceptable — the issue is the source of truth for audit trail.

8. **QA passes without raising any findings**: The verdict block lists satisfied criteria but has an empty findings array. The cycle advances to `previewed` as today.

9. **Merge conflicts or branch rebased**: If the commit SHAs in prior verdicts no longer exist in the branch history, treat those verdicts as stale and ignore them (fall back to stateless review). Log a warning but do not fail.

10. **Two findings target the same file and line range**: Treated as distinct findings unless their criterion names match exactly. Criterion identity is determined by a stable key (e.g. "spec-fidelity:src/app/page.tsx:12-34"), not just the file.

## Risks

- **Verdict parsing failure could silence valid findings.** Mitigation: fail open (stateless review) on parse errors, and log the failure. A broken verdict block does not stop the pipeline.

- **Diff comparison false negatives.** If `git diff` reports no change in a region but the code semantically differs (e.g. whitespace-only changes, or changes outside the line range that affect the region's behaviour), a finding may be incorrectly rejected. Mitigation: line range matching is conservative — a diff anywhere in the file counts as a change for the entire file's criteria. We do not attempt sub-line or semantic diff analysis.

- **False positives in re-raise validation.** If the validation is too strict (e.g. pattern-matching the finding text for "changed" or "modified"), legitimate findings may be rejected because the agent phrased them differently. Mitigation: the pattern match is loose (checks for any reference to code change, not a specific template), and the dispute route exists for edge cases.

- **Verdict blocks make issue comments longer.** The blocks are HTML comments (invisible in the rendered UI) and small (hundreds of bytes each), so the UX impact is minimal. The issue body already contains the spec and decision sections, so comment length is not a new concern.

- **Cycle count logic unchanged.** Stateful verdicts do not alter the three-cycle cap, so a pathological case (QA wrongly passes something, then wrongly re-raises it in cycle 2, then wrongly re-raises again in cycle 3) can still exhaust the cap. This is acceptable — the cap is the backstop for exactly this scenario, and the dispute route handles it.

## Derived criteria

What I understood the human to be asking for:

1. QA's per-cycle verdicts are persisted in the issue itself, as machine-readable HTML comment blocks appended to the QA findings comments. No external storage.

2. Each verdict block contains: cycle number, commit SHA reviewed, list of satisfied criteria (each with file, line range, and criterion name), and list of findings raised.

3. Before QA runs, all prior verdict blocks from the current attempt (since the most recent `spec-derived` label event) are extracted and passed to the QA agent.

4. The QA agent prompt includes a section listing criteria marked satisfied in previous cycles, each with the commit SHA it was judged against. The agent is instructed to only re-raise a settled criterion if the code region has changed.

5. After the agent writes its verdict, a validation step runs. For each finding that re-raises a settled criterion, `git diff <prior-commit>..HEAD -- <file>` checks if the region changed. If not, the finding is rejected.

6. A re-raised finding must explicitly name what changed (e.g. "the idempotency key logic at line 124 changed from per-attempt to per-collection"). The validator pattern-matches for this — a generic "still wrong" is insufficient.

7. If all findings in a CHANGES verdict are rejected (invalid re-raises), the verdict is rewritten to PASS, since there are no valid findings left.

8. The three-cycle iteration cap remains unchanged and still counts every `qa-changes` label event since `spec-derived`.

9. On the first cycle (no prior verdicts), QA behaves exactly as it does today — stateless review.

10. If verdict parsing fails (malformed JSON, missing blocks, unreadable comments), fail open to stateless review and log the error. The pipeline continues.

11. If a prior verdict's commit SHA no longer exists in the branch history (rebase, force-push), ignore that verdict and fall back to stateless review for its criteria.

12. The acceptance tests must cover:
    - Criterion passed cycle 1, code unchanged, re-flagged cycle 2 → finding rejected
    - Criterion passed cycle 1, code changed, re-flagged cycle 2 → finding accepted
    - First cycle with no prior verdicts → behaves as today
    - Re-raised finding without naming what changed → rejected
    - Verdict blocks written to issue comments in correct format
    - Verdict extraction from comments works correctly (parse HTML comment blocks, extract JSON)
